# 6.1 — `dj new <name>`: real project scaffolding (Phase 6, first slice)

## Scope

Phase 5 (THE ADMIN) is now fully done (DoD met at 5.9, 5.8 arc closed at 5.8.12 — see
`docs/design/phase-5-roadmap.md`). This begins Phase 6 (CLI & developer experience). Per
`PLAN.md`'s Phase 6 bullet: `djangors new <project>` (generates workspace, settings, git, tuned
dev profile). This slice builds `dj new <name>` for real — currently `commands::new()` is a
one-line stub (`println!("would create project... not yet implemented")`) — the CLI already
parses the subcommand (`crates/djangors-cli/src/cli.rs`, `Commands::New { name }`), only the
implementation is missing.

**Deliberately deferred, not in this slice** (ledger these in the roadmap when this lands):
`dj new-app` (generates an app crate wired into a multi-crate workspace — this slice's output is a
single standalone crate, matching `examples/polls`'/`examples/school`'s existing shape, not a
workspace; making `new-app` meaningful requires deciding the multi-crate project shape first, a
separate design question), `dj run`'s watch/rebuild/livereload (still a stub — this slice only
makes the generated project's own `cargo run` work, which `dj run` needs before it can wrap it),
`dj check` (system check framework), and swapping the generated `Cargo.toml`'s path dependencies
for crates.io version dependencies once `cargo login`/publishing is unblocked (ledgered, not
implementable now).

## Why path dependencies, not crates.io versions

Every djangors crate is publish-shaped but **not actually published** (blocked on the user running
`cargo login` — confirmed still true, see `docs/design/phase-5-roadmap.md`'s ledger). A generated
project with `djangors-core = "0.0.1"` would not build for anyone right now. Instead, `dj new`
must generate path dependencies pointing at the **same djangors checkout `dj` itself was built
from** — this is a legitimate v1 for a framework used entirely from a local checkout today (the
only way it's used at all), and is exactly how `examples/polls`/`examples/school` already
reference `../../crates/*`.

**Mechanism:** `crates/djangors-cli`'s own `env!("CARGO_MANIFEST_DIR")` resolves at *djangors-cli's
own compile time* to the absolute path of `crates/djangors-cli` in whatever checkout built the
`dj` binary. Its parent directory is the workspace's `crates/` directory. Compute this once as a
`const`/helper in `commands.rs`:

```rust
fn djangors_crates_dir() -> std::path::PathBuf {
    std::path::Path::new(env!("CARGO_MANIFEST_DIR"))
        .parent() // crates/djangors-cli -> crates/
        .expect("djangors-cli has a parent directory")
        .to_path_buf()
}
```

Generated `Cargo.toml` then uses **absolute** path dependencies:
`djangors-core = { path = "/abs/path/to/crates/djangors-core" }`. This works correctly with real
Cargo semantics: a path-dependency crate's own workspace membership is resolved by walking up
*from that crate's own manifest location* (finds `/root/dev/Rango/Cargo.toml`'s `[workspace]`,
resolving `version.workspace = true` etc. correctly) — completely independent of where the
*depending* project lives or whether it's part of any workspace itself. A brand-new standalone
project outside the djangors repo, depending via absolute path on crates living inside it, is
ordinary, well-supported Cargo usage — verified by reasoning through Cargo's actual workspace-
resolution rules, not assumed; the required test below (§ Required tests) proves it for real by
actually running `cargo build` against the generated project.

## What `dj new <name>` generates

Signature: `dj new <name>` (already parsed — `Commands::New { name: String }`). Creates a new
directory `./<name>` relative to the current working directory (mirrors `cargo new <name>`'s own
UX exactly). **Errors, does not overwrite,** if `./<name>` already exists — check
`std::path::Path::new(name).exists()` before writing anything, print `error: destination
'<name>' already exists` to stderr and `std::process::exit(1)`, matching every other
`commands::*` function's existing `eprintln!` + `exit(1)` error-reporting convention in this file
(see `migrate()`/`createsuperuser()` for the pattern to match exactly). Also validate `name` is a
non-empty, valid Rust crate identifier before doing anything (ASCII alphanumeric + `_`/`-`, must
not start with a digit) — reuse or mirror the identifier-validation Cargo itself would apply,
since an invalid crate name would otherwise fail confusingly deep inside a later `cargo build`
instead of failing immediately with a clear message. Rust identifier requires underscores not
hyphens for the actual `[package] name` inside `Cargo.toml`'s `[[bin]] name` — Cargo package names
allow hyphens (converted to underscores for the actual Rust crate name automatically), so keep
`name` as-given for the directory and `[package]`/`[[bin]]` `name` fields (Cargo handles the
hyphen-to-underscore conversion itself, same as `cargo new my-project` does today) — do not
manually convert hyphens to underscores anywhere in generated Rust source, only Cargo needs to
know about the raw name.

Files to write (all directories created with `std::fs::create_dir_all`, all files with
`std::fs::write`, checking each `Result` and erroring out via the same `eprintln!`+`exit(1)`
convention on any I/O failure — do not `.unwrap()` any filesystem call):

**`<name>/Cargo.toml`**:
```toml
[package]
name = "{name}"
version = "0.1.0"
edition = "2021"
publish = false

[[bin]]
name = "{name}"
path = "src/main.rs"

[dependencies]
djangors-core = { path = "{crates_dir}/djangors-core" }
tokio = { version = "1", features = ["full"] }
tower = { version = "0.5", features = ["util"] }
```

(`{crates_dir}` is the absolute path computed above, forward-slash-separated even on any
non-Unix build of `dj` — use `.display()`/`to_string_lossy()` and don't worry about Windows path
separators inside a TOML string value, forward slashes work fine in Cargo path deps on every
platform Cargo itself supports.)

**`<name>/src/main.rs`** — deliberately minimal: no database connection, no sessions/CSRF/auth
middleware, nothing requiring any environment setup beyond `cargo run`, so the DoD's "welcome page
in under 90 seconds on a clean machine" is achievable with zero configuration:

```rust
use djangors_core::{Djangors, DjangorsError, DjangorsSettings, Router};

mod views;

#[tokio::main]
async fn main() -> Result<(), DjangorsError> {
    djangors_core::logging::init_dev_logging();

    let (settings, warnings) = DjangorsSettings::load()?;
    for w in warnings {
        eprintln!("settings warning: {w}");
    }

    let router = Router::new().get("/", views::welcome);
    let router_service = djangors_core::router::RouterService::new(router, settings.debug);

    let service = tower::ServiceBuilder::new()
        .layer(djangors_core::middleware::security_headers_layer())
        .service(router_service);

    Djangors::new(settings, Router::new()).run_service(service).await
}
```

(Verify `Djangors::new(settings, Router::new()).run_service(service)` is the exact real call shape
by reading `crates/djangors-core/src/app.rs` before writing this file — `examples/polls/src/main.rs`
uses this exact pattern today, confirmed by direct read, but re-confirm signatures haven't drifted
before generating code that must compile.)

**`<name>/src/views.rs`**:
```rust
use djangors_core::{DjangorsError, PathParams, Request, Response, StatusCode};

pub async fn welcome(_req: Request, _params: PathParams) -> Result<Response, DjangorsError> {
    Ok(Response::html(
        StatusCode::OK,
        "<!DOCTYPE html><html><head><title>Djangors</title></head><body>\
<h1>It worked!</h1><p>Congratulations on your first Djangors project.</p>\
</body></html>"
            .to_string(),
    ))
}
```

**`<name>/.gitignore`**:
```
/target
*.env
```

**`<name>/djangors.toml`** (matches `DjangorsSettings::from_toml_str`'s real field set — read
`crates/djangors-core/src/settings.rs` directly to confirm field names before generating, don't
guess):
```toml
debug = true
```

**`<name>/README.md`** — short, real, not aspirational-marketing copy:
```markdown
# {name}

A Djangors project.

## Run it

    cargo run

Then visit http://127.0.0.1:8000/.

## Next steps

- Add models: see `examples/school` in the djangors repo for a real worked example
  (`#[derive(Model)]`, `AdminSite`, migrations-free `CREATE TABLE` in tests).
- Add the admin: `djangors-admin`'s `AdminSite` needs a `djangors_db::Database` in router state —
  see `examples/polls/src/main.rs` for the full wiring (DB connection, sessions, CSRF).
```

**`git init`**: after all files are written, run `git init` in `<name>/` via
`std::process::Command::new("git").arg("init").current_dir(&name).output()`. If `git` isn't on
`PATH` or the command fails, print a warning (`eprintln!("warning: 'git init' failed (is git
installed?), skipping — the project files were still created successfully")`) and continue —
**do not** treat a missing/failing `git init` as a fatal error for the whole command, since the
generated Rust project is fully usable without git. Do **not** run `git add`/`git commit` — match
`cargo new`'s own behavior of initializing but not committing, leaving the first commit to the
user.

On full success, print a Django-`startproject`-style summary (mirror the existing
`println!("[dj new] ...")`-with-brackets convention used by every other stub in this file, e.g.
`collectstatic`'s success message):
```
[dj new] created '{name}'
[dj new] next: cd {name} && cargo run
```

## Required tests

`crates/djangors-cli/src/commands.rs`'s existing `#[cfg(test)] mod tests` — add real, not just
argument-parsing, coverage:

1. **`test_new_generates_expected_files`**: call the real generation function (extract the
   file-writing logic into a testable function, e.g. `pub fn new(name: &str) -> Result<(), String>`
   returning `Result` instead of the current bare `println!`-and-return-nothing signature — update
   `main.rs`'s call site accordingly, printing the error via `eprintln!`+`exit(1)` there instead of
   inside `commands::new` itself, matching how `createsuperuser`/`migrate` already separate "do the
   work, return Result" from "report the error and exit" at the call site... check whether that
   split already exists for the `async` commands and mirror it for consistency, or note in the
   commit message if `new`/`new_app` end up using a different but equally reasonable convention),
   in a `tempfile`-style scratch directory (use `std::env::temp_dir()` + a unique per-test suffix,
   e.g. `std::process::id()` combined with the test name, cleaned up at the end of the test via
   `std::fs::remove_dir_all` even on assertion failure — wrap the body in a way that cleanup still
   runs, or accept the minor test-pollution risk and just clean up at both the start (defensive
   `remove_dir_all` ignoring errors) and end, matching how existing DB tests in this codebase
   `DROP TABLE IF EXISTS` both before and after). Assert every expected file exists
   (`Cargo.toml`, `src/main.rs`, `src/views.rs`, `.gitignore`, `djangors.toml`, `README.md`) and
   that `Cargo.toml`'s content contains the literal generated project name and an absolute
   `djangors-core` path pointing at a real, existing `crates/djangors-core` directory (assert
   `std::path::Path::new(<extracted path>).join("Cargo.toml").exists()` — proving the computed
   `crates_dir` is correct, not just present).
2. **`test_new_rejects_existing_directory`**: create the target directory first (empty is fine),
   call `new()`, assert it returns an `Err` and — critically — that no files were written/no
   existing content was touched (this is the exact "don't destroy pre-existing state" discipline
   this whole project already applies to git operations, applied here to filesystem writes).
3. **`test_new_generated_project_builds_and_serves`** (the real end-to-end proof, mirroring 5.9's
   "prove it against the real thing, not just assert file existence" precedent) — **marked
   `#[ignore]`** with a doc comment explaining why (spawns a real `cargo build` subprocess, slow —
   on the order of tens of seconds even for a two-dependency crate the first time its dependency
   tree needs building, though warm-cache reruns are fast; not suitable for the default fast
   `cargo test --workspace` loop every other slice's tests run in) and a comment telling a future
   session to run it explicitly via `cargo test -p djangors-cli -- --ignored` before trusting this
   slice, and to run it once for real during this slice's own verification pass (required — see
   below) even though it's `#[ignore]`d for routine runs. Generates a project into a scratch temp
   dir, runs `std::process::Command::new("cargo").args(["build"]).current_dir(&scratch_dir)`,
   asserts a zero exit status, then actually starts the built binary
   (`std::process::Command::new(scratch_dir.join("target/debug/{name}"))...spawn()`) on a
   non-default port via `DJANGORS_PORT=<free port>` env, waits briefly for it to bind (poll-retry a
   raw TCP connect for up to a few seconds rather than a fixed `sleep`, matching this project's
   existing "poll, don't guess a sleep duration" discipline used in socket-level tests elsewhere,
   e.g. `examples/school`'s integration test's own server-startup wait if it uses one — check and
   mirror whatever pattern that test already uses), makes one real HTTP GET to `/`, asserts `200`
   and the response body contains `"It worked!"`, then kills the child process
   (`Child::kill()`) and cleans up the scratch directory. This is the test that actually proves the
   absolute-path-dependency mechanism works, not just that files got written with plausible-looking
   content.

  scratch directory — a real, human-legible end-to-end smoke test alongside the automated one.
