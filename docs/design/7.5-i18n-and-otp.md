# 7.5 — `djangors-i18n` and `djangors-contrib-otp` (closes out Phase 7)

## Scope

The last two Phase 7 items after 7.1-7.4 (commits `c87a76d`, `168dd5c`, `845b770`, `f44cfa3`).
Bundled together since both are the last remaining PLAN.md Phase 7 bullets and each is otherwise
independent of the other.

## Two real scope decisions, read before writing code

**1. `djangors-i18n` cannot ship a real message-extraction tool in this dispatch.** PLAN.md's
literal text asks for "message extraction from templates+code" — a real implementation of that is
a source/template scanner (parsing Rust source for translation-marker calls, and minijinja
templates for a `{% trans %}` tag) that emits `.ftl` catalog stubs, which is a genuine parser-
writing project on its own, comparable in scope to a small compiler pass. **Deliberate v1 scope**:
ship the actual runtime i18n machinery (catalogs, lookup, locale detection, template integration) —
the extraction *tool* is explicitly out of scope, ledgered as a separate future `dj makemessages`-
style CLI command once the runtime side it would generate output for actually exists. Catalogs are
hand-written `.ftl` files for v1 (exactly how a Django/Fluent project starts before tooling exists
to help maintain them).

**2. `djangors-contrib-otp` ships TOTP only, not WebAuthn.** PLAN.md's own text already calls
WebAuthn a "stretch" goal for this item — this dispatch does TOTP (the primary ask) and explicitly
does not attempt WebAuthn (a materially different, larger crypto/browser-API surface).

## Part A — `djangors-i18n` (new crate)

Use the `fluent`/`fluent-bundle` crates (Mozilla's Fluent localization system — the actively
maintained, standard choice for Rust; confirm current stable versions before adding them as
dependencies, don't guess).

```rust
pub struct Catalog {
    // one FluentBundle per locale, loaded from .ftl source strings
}
impl Catalog {
    pub fn from_ftl(locale: &str, ftl_source: &str) -> Result<Self, I18nError>;
    pub fn get(&self, message_id: &str, args: Option<&FluentArgs>) -> Option<String>;
}

pub struct Locales {
    // locale code -> Catalog, plus a configured default/fallback locale
}
impl Locales {
    pub fn new(default_locale: &str) -> Self;
    pub fn add_locale(&mut self, locale: &str, ftl_source: &str) -> Result<(), I18nError>;
    pub fn translate(&self, locale: &str, message_id: &str, args: Option<&FluentArgs>) -> String;
    // falls back to `default_locale`'s catalog, then to `message_id` itself, if a translation
    // is missing — never a hard error or blank string in a rendered page
}
```

**Locale detection**: a `tower::Layer` (mirroring `SecurityHeadersLayer`'s shape in
`crates/djangors-core/src/middleware.rs`) that reads the `Accept-Language` header (simple
first-tag parsing is fine for v1 — full RFC 4647 quality-value negotiation is not required),
falling back to a session-stored locale override if present (reuse `djangors_sessions::Session`'s
existing get/set, a small session key like `"_locale"`), and inserts the resolved locale as a
request extension other handlers/template contexts can read.

**Template integration**: a minijinja filter (mirroring the exact `env.add_filter("name",
function)` pattern already used repeatedly in `crates/djangors-template/src/engine.rs` —
registered in **both** `new()` and `from_embedded()`, the same easy-to-miss duplication point
flagged in 7.2's design doc) — e.g. `{{ "hello-message" | trans }}` looks up the message id in the
current request's resolved `Locales`/locale. Since minijinja filters don't have direct access to
"the current request," the practical integration is: a filter that takes the message id *and* an
already-resolved `Locales`+locale pair passed into the template context by the caller (document
this clearly with a real example in the crate's module doc, the same "document the integration
point" pattern used for `djangors-contrib-messages` and `djangors-contrib-guardian` — this crate
cannot auto-wire into arbitrary template rendering call sites any more than those could).

**Localized formatting**: reuse `chrono` (already a workspace dependency everywhere) for date
formatting per-locale conventions — a small, real v1 (e.g. a locale → date format string mapping
for a handful of common locales: `en-US` → `%m/%d/%Y`, `en-GB`/most of Europe → `%d/%m/%Y`, ISO
`%Y-%m-%d` as the universal fallback) rather than a full CLDR-data-driven system, which is a much
larger dependency/scope decision explicitly not worth taking on here — document this as the v1
scope.

**Required tests**: `Locales::translate` falling back correctly (missing locale → default locale →
raw message id, in that order); the Accept-Language-parsing layer resolving a locale from a real
header value and falling back to the default when absent/unparseable; the `trans` filter producing
the correct localized string for a real `Locales` instance with at least two loaded locales; at
least one localized-date-format test across two different locale conventions.

## Part B — `djangors-contrib-otp` (new crate)

Use the `totp-rs` crate (an actively-maintained, standard Rust TOTP implementation — confirm its
current real API shape before writing code, don't guess method names from memory) for RFC 6238
TOTP generation/verification.

A real model for per-user TOTP enrollment:
```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_contrib_otp", table_name = "djangors_otp_device")]
pub struct OtpDevice {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user: ForeignKey<djangors_auth::User>,
    #[djangors(max_length = 255)]
    pub secret: String, // base32-encoded TOTP secret — store encrypted at rest if this
                         // framework has an existing encryption-at-rest convention for secrets;
                         // if not, document this as a known v1 gap (plaintext secret storage) —
                         // check whether djangors-auth's own password hashing module or any
                         // existing secret-handling code establishes a convention to follow
                         // before deciding, don't silently pick plaintext without checking
    pub confirmed: bool, // false until the user verifies their first code post-enrollment
}
```

```rust
pub fn generate_secret() -> String; // a new random base32 TOTP secret
pub fn provisioning_uri(secret: &str, account_name: &str, issuer: &str) -> String;
    // the otpauth:// URI a QR-code generator would encode — this crate does not need to
    // generate the QR image itself, just the URI (a real, useful, scoped v1)
pub fn verify_code(secret: &str, code: &str) -> bool;
```

**Admin 2FA enforcement setting**: a simple, real mechanism — check whether
`djangors_admin::AdminSite` has any existing extension point suitable for a pre-login-success hook
(re-read `crates/djangors-admin/src/lib.rs`'s login handler for the exact real flow before
assuming); if there's a clean way to gate successful admin login on "does this user have a
`confirmed` `OtpDevice`, and if so was a valid code just presented," wire it in as an opt-in
(a config flag on `AdminSite`, defaulting to off, so this doesn't change existing admin-login test
behavior unless a test explicitly opts in) — document the exact flow (login form → if OTP
required, a second code-entry step) in the crate's module doc. If wiring into the actual admin
login flow turns out to require changing a core, heavily-tested admin code path in a way that
risks the same blast-radius concern flagged for `djangors-contrib-guardian`'s non-integration with
`require_perm`, it's acceptable to ship the enrollment/verification primitives as a real, tested,
usable API without deep admin wiring, and document the manual integration point instead — say
explicitly which choice was made and why.

**Required tests**: `verify_code` accepting a freshly-generated valid code for a known secret and
rejecting an invalid one (use `totp-rs`'s own time-step semantics directly, don't hardcode a
specific code string that would only be valid at one instant — generate the code with the same
library function being tested against, at test-run time); `provisioning_uri`'s output containing
the expected `otpauth://` scheme, account name, and issuer; an `OtpDevice` enrollment round-trip
(create unconfirmed, verify a code, mark confirmed) against a real test database, mirroring the
`djangors_test::TestDatabase` pattern already used by `djangors-contrib-flatpages`/`-redirects`.
