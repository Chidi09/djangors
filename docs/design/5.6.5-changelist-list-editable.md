# 5.6 part 5 — Changelist `list_editable` (v1)

**Status:** design, not yet dispatched. Follows 5.6.4 (`date_hierarchy`, commit `a744250`). See
`docs/design/phase-5-roadmap.md` for full Phase 5 context — this is the slice that roadmap entry
flagged as needing its own design because it interacts with 5.6.3's bulk-delete `<form>`.

## Scope: text/numeric fields only, no Boolean, `formaction` instead of a second form

Django's `list_editable` lets specific `list_display` columns render as inline inputs on the
changelist, with a "Save" button that writes all edited cells in one POST. Two real constraints
carry over unchanged from Django, because they aren't stylistic choices — they're structural:

1. **A `list_editable` field must already be in the effective `list_display` columns, and can
   never be the first column.** The first column is always the row's edit link (`admin_changelist`,
   the `if i == 0 { <a href="{pk}/change/"> }` branch) — making it editable too would collide
   with the link, exactly the reason Django itself forbids it.
2. **No Boolean fields in `list_editable` v1.** An HTML checkbox only appears in the submitted
   form body when checked — an *absent* key is ambiguous between "this checkbox was rendered and
   left unchecked" and "this field isn't part of this edit at all." Django resolves this with its
   full form/formset machinery (management-form hidden fields, initial-value comparison), which
   this admin deliberately doesn't have (see 5.6.3's "no JS anywhere in this admin yet" note).
   Every other supported kind (text-like, numeric) doesn't have this problem: a `<input
   type="text">` always submits `name=value` even when the value is empty, so "key present in
   the submitted form" reliably means "this field was part of the edit." This is the same shape
   of decision 5.6.2 made for `list_filter` (Boolean-only there, for the opposite structural
   reason) — v1 here is Boolean-*excluded*, and just as deliberate.

**Only one `<form>` wraps the changelist table — same as today (5.6.3), not a second nested
form.** Nested `<form>` elements are invalid HTML, and a `<table>` can't sit inside two
independent forms at once. The existing bulk-delete `<form method="post" action="bulk-delete/">`
stays exactly as-is (**this task does not touch `bulk-delete/`'s route or handler at all** — zero
regression risk to already-shipped 5.6.3 code). The new "Save" button uses the plain HTML5
`formaction` attribute to submit to a *different* URL than the form's own default `action`,
without JavaScript:

```html
<form method="post" action="bulk-delete/">
  ...same table, now with some cells rendered as <input> instead of plain text...
  <button type="submit" formaction="bulk-delete/">Delete selected</button>
  <button type="submit" formaction="save-changelist/">Save</button>
</form>
```

`formaction` on a `<button>` overrides the form's `action` for that specific submit — this is
plain HTML5, universally supported, and needs zero JS, matching this admin's standing "no
client-side JS until 5.8 theming" constraint. The existing `<input type="submit" value="Delete
selected">` becomes `<button type="submit" formaction="bulk-delete/">Delete selected</button>` —
functionally identical (still submits to `bulk-delete/`), just switched to `<button>` so both
submit controls are the same element type. **The "Save" button (and the `formaction` attribute
on both buttons) only render when `admin.list_editable_fields()` is non-empty** — a model with no
`list_editable` configured sees byte-for-byte the same changelist HTML as before this task,
same "only render UI for configured features" pattern as `search_html`/`filter_html`.

## No transactional atomicity across the batch — same as every other save path in this codebase

`ModelAdmin::update_from_form` (the single change-form save, 5.4) validates and writes in one
non-transactional step already — there is no "validate all, then write all" primitive anywhere
in this codebase yet, for a single object or otherwise. `list_editable`'s multi-row save matches
that existing shape rather than inventing new transactional machinery as a side effect of this
task: **each edited row is validated and written independently; a row that fails validation is
skipped (not written) and reported, rows before/after it in the same submission are unaffected.**
This mirrors 5.6.3's own explicit "best-effort per pk" reasoning for bulk delete. Note real
cross-row atomicity as a future improvement in the roadmap ledger when this lands — it's a
genuine gap (shared with every other save path), not something to quietly half-fix here.

## `ModelAdmin` trait: two new methods

```rust
fn list_editable_fields(&self) -> &[&'static str];

async fn update_fields_from_form(
    &self,
    db: &djangors_db::Database,
    pk: i64,
    form: &std::collections::HashMap<String, String>,
) -> Result<Result<(), std::collections::HashMap<String, String>>, DjangorsError>;
```

`DefaultModelAdmin::list_editable_fields` returns `self.config.list_editable.unwrap_or(&[])` —
same one-line shape as `search_fields()`/`list_filter_fields()`.

`DefaultModelAdmin::update_fields_from_form` is `update_from_form` (~line 271-...) with exactly
one change: **only process a field if it's present as a key in `form`**, instead of treating an
absent key as an empty/required-field error. This is why it's a new method, not a change to
`update_from_form` itself — `update_from_form` (the single-object change-form save) legitimately
*wants* "absent key → required-field error" for non-nullable fields, since the change form always
submits every field. `list_editable` submits only the edited columns by design, so "absent" has
to mean "not part of this edit," not "cleared."

```rust
async fn update_fields_from_form(
    &self,
    db: &djangors_db::Database,
    pk: i64,
    form: &std::collections::HashMap<String, String>,
) -> Result<Result<(), std::collections::HashMap<String, String>>, DjangorsError> {
    let meta = M::meta();
    let mut errors = std::collections::HashMap::new();
    let mut sets = Vec::new();

    for field in meta.fields {
        if field.auto {
            continue;
        }
        let Some(raw) = form.get(field.name) else {
            continue; // not part of this edit - leave the column untouched
        };
        match parse_field_value(field, Some(raw.as_str())) {
            Ok(val) => sets.push((field.name, djangors_orm::expr::SetExpr::Literal(val))),
            Err(err_msg) => {
                errors.insert(field.name.to_string(), err_msg);
            }
        }
    }

    if !errors.is_empty() {
        return Ok(Err(errors));
    }
    if sets.is_empty() {
        return Ok(Ok(())); // nothing in `form` matched a real field - a no-op, not an error
    }

    let pk_field = meta
        .fields
        .iter()
        .find(|f| f.primary_key)
        .ok_or_else(|| DjangorsError::Internal("Primary key field not found".to_string()))?;
    let unresolved_cmp =
        djangors_orm::expr::UnresolvedExpr::And(vec![djangors_orm::expr::UnresolvedCompare {
            field: pk_field.name,
            value: djangors_orm::expr::Value::I64(pk),
        }]);
    let qs = M::objects()
        .filter(unresolved_cmp)
        .map_err(|e| DjangorsError::Internal(e.to_string()))?;
    qs.update(db, sets)
        .await
        .map_err(|e| DjangorsError::Internal(e.to_string()))?;

    Ok(Ok(()))
}
```

**Note the real call shape** (`update()` is an instance method on an already-pk-filtered
`QuerySet`, not an associated function taking `pk` directly — `crates/djangors-orm/src/queryset.rs`
~line 512, `pub async fn update(&self, db, sets: Vec<(&'static str, SetExpr)>) -> Result<u64,
OrmError>`): this snippet is the same pk-filter-then-`.update(db, sets)` sequence
`update_from_form` already does a few lines below where the `sets`-building loop above ends
(`crates/djangors-admin/src/lib.rs` ~line 310-330) — copy that block verbatim rather than
reinventing it, the only actual difference in this new method is the `sets`-building loop above
it (skip-if-absent vs. absent-is-an-error). No relation (`meta.relations`) handling needed —
`list_editable`'s registration validation above only allows `FieldKind` variants that can never
be a relation field.

`escaped` is safe to place inside a `value="..."` HTML attribute (it's already run through
`djangors_core::html_escape`, which escapes `"` — same as every other `value="..."` site in this
file, e.g. the search box). The `name="edit-{pk}-{col_name}"` format is the read-side contract
for the new route below — `col_name` is always a real, registration-validated field name (never
user input), so no ambiguity or injection risk in the key itself.

## New route + handler: `POST /{app}/{model}/save-changelist/`

```rust
.post(
    "/{app:slug}/{model:slug}/save-changelist/",
    move |req: Request, params: PathParams| {
        admin_save_changelist_post(req, params, save_changelist_admins.clone())
    },
)
```

Same closure-capture-a-cloned-vec pattern as every other admin route.

```rust
async fn admin_save_changelist_post(
    req: Request,
    params: PathParams,
    admins: Vec<Arc<dyn ModelAdmin>>,
) -> Result<Response, DjangorsError> {
    require_staff(&req).await?;

    let app = params.get("app").unwrap_or("");
    let model = params.get("model").unwrap_or("");
    let admin = admins
        .iter()
        .find(|a| {
            let meta = a.model_meta();
            meta.app_label == app && meta.struct_name.to_lowercase() == model
        })
        .ok_or(DjangorsError::NotFound)?;

    let db = req
        .state::<djangors_db::Database>()
        .ok_or_else(|| DjangorsError::Internal("Database connection not found".to_string()))?;

    let editable_fields = admin.list_editable_fields();
    let Form(pairs) = Form::<Vec<(String, String)>>::from_request(&req).await?;

    // Group by pk, allowlisting field names against list_editable_fields() -
    // a key naming a field that isn't configured as editable is silently
    // dropped, not applied and not an error (defense in depth: mirrors
    // list_filter's route-level allowlist check, in case a crafted request
    // names a real-but-not-editable field).
    let mut by_pk: std::collections::HashMap<i64, std::collections::HashMap<String, String>> =
        std::collections::HashMap::new();
    for (key, value) in &pairs {
        let Some(rest) = key.strip_prefix("edit-") else {
            continue;
        };
        let Some((pk_str, field_name)) = rest.split_once('-') else {
            continue;
        };
        let pk = pk_str
            .parse::<i64>()
            .map_err(|_| DjangorsError::BadRequest("invalid pk in edit field".to_string()))?;
        if !editable_fields.contains(&field_name) {
            continue;
        }
        by_pk
            .entry(pk)
            .or_default()
            .insert(field_name.to_string(), value.clone());
    }

    let mut row_errors: Vec<(i64, std::collections::HashMap<String, String>)> = Vec::new();
    for (pk, fields) in &by_pk {
        match admin.update_fields_from_form(db, *pk, fields).await? {
            Ok(()) => {}
            Err(errors) => row_errors.push((*pk, errors)),
        }
    }

    if row_errors.is_empty() {
        return Ok(Response::redirect(&format!("/{}/{}/", app, model)));
    }

    let mut items_html = String::new();
    for (pk, errors) in &row_errors {
        for (field, msg) in errors {
            items_html.push_str(&format!(
                "<li>Row {}: {}: {}</li>",
                pk,
                djangors_core::html_escape(field),
                djangors_core::html_escape(msg)
            ));
        }
    }
    let html = format!(
        "<p>Some rows could not be saved (rows without errors were saved):</p><ul>{}</ul>\
         <a href=\"/{}/{}/\">Back to changelist</a>",
        items_html, app, model
    );
    Ok(Response::html(StatusCode::OK, html))
}
```

Field-name parsing: `pk_str` is always digits (`i64::parse` enforces this — a malformed pk is a
`400`, matching the strict-pk-parsing convention `bulk-delete/`'s handler already established for
its own `selected` values), and `field_name` is whatever remains after the first `-` — safe
because real field names are Rust identifiers (`snake_case`, no `-` character possible), so
`split_once('-')` unambiguously separates `{pk}` from `{field_name}` with no edge case to worry
about.

## What NOT to touch in this task

- No changes to the `bulk-delete/` route, its handler, or its tests (5.6.3) — the two features
  share one `<form>` via `formaction`, nothing else.
- No Boolean (or any other non-text/numeric) `list_editable` fields — see scope section.
- No cross-row transactional atomicity — see scope section, this matches every other save path.
- No rich per-cell inline error rendering on the changelist itself — validation failures render
  as a separate small page (mirrors the bulk-delete confirm page's minimal style), not
  highlighted inline inputs. A future improvement, not required for v1.
- No changes to `list_display`/`search_fields`/`list_filter`/`date_hierarchy` logic beyond
  reading `list_editable_fields()` where specified above.
- No changes to `djangors-macros`.

## Required tests

Add to the existing `#[cfg(test)] mod tests` block in `crates/djangors-admin/src/lib.rs`, same
Postgres-backed socket-level style as every other test in this file. Reuse the `ModelD` fixture
(`name: String`, `content: String`, `test_model_d`) — it already has two non-pk text fields,
enough to exercise "editable" vs "not editable" without a new fixture.

1. Register `ModelD` with `list_display: Some(&["name", "content"])`, `list_editable:
   Some(&["content"])`. GET the changelist → 200, response body contains
   `name="edit-{pk}-content"` for an inserted row's `content` cell, does NOT contain an editable
   input for the `name` column (index 0, always the link), and contains
   `formaction="save-changelist/"`.
2. Registration-validation panics (bundle as `catch_unwind` blocks in the same test function,
   matching 5.6.1/5.6.4's style): (a) `list_editable` naming a field not in `list_display` →
   panics; (b) `list_editable` naming `list_display`'s first column → panics; (c)
   `list_editable` naming a Boolean field (use `ModelE`'s `is_active`) → panics; (d)
   `list_editable` naming a nonexistent field → panics.
3. POST `save-changelist/` with `edit-<pk1>-content=Updated1` for one row → 302 redirect, DB
   row's `content` actually updated to `"Updated1"`.
4. POST with edits for TWO different pks in the same request (`edit-<pk1>-content=A` and
   `edit-<pk2>-content=B`) → 302 redirect, BOTH rows updated correctly (proves the by-pk grouping
   handles multiple rows in one submission — the regression class this design doc's grouping
   logic exists to get right, same spirit as 5.6.3's own multi-row test).
5. POST with `edit-<pk>-content=` (empty string) where `content` is non-nullable → 200 (not a
   redirect), response body mentions `content` in an error message, and the DB row's `content` is
   UNCHANGED afterward (proves validation-before-write).
6. POST with an `edit-<pk>-name=Malicious` key, where `name` is a real field on the model but NOT
   in this admin's `list_editable` config → 302 redirect (as if nothing invalid was submitted),
   and the DB row's `name` is UNCHANGED (proves the allowlist check silently drops non-editable
   field keys rather than applying them).
7. POST with a non-numeric pk in an `edit-` key (e.g. `edit-abc-content=X`) → 400 Bad Request.
8. Unauthenticated / non-staff POST to `save-changelist/` → 401 / 403 (mirror the existing
   pattern from every other admin route's auth tests).
