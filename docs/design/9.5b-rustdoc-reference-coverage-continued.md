## Approach — work crate-by-crate, smallest to largest, verify and lock in as you go

For each crate (start with the smallest: `djangors-forms` at 3, work up to `djangors-orm` at 93
last):
1. Run `cargo doc -p <crate> --no-deps 2>&1 | grep "missing documentation"` to get that crate's

2. Write real, accurate `///` doc comments for every flagged item (see "what 'real' means" below —

3. Once that crate's own `cargo doc -p <crate> --no-deps` shows zero missing-docs warnings, upgrade

   reviewing your diff) a clear per-crate "done" signal as you go, so if you run out of budget again

## What "real" doc comments means (same standard as before, restated)

Every doc comment must accurately describe what the item actually does — not filler text written
just to satisfy the lint (e.g. `/// The name field.` on a field called `name` is useless). Match
the quality of this project's own best existing doc comments (e.g. `djangors_orm::meta`'s public
structs, `djangors-admin`'s public config structs) as the bar. For non-obvious items — anything
whose behavior has a real subtlety this project's own history has already surfaced (`ForeignKey`'s
lazy-loading, `Model` derive's explicit-primary-key requirement, `CsrfLayer`'s
header-first-with-form-fallback mechanism, `QuerySet::filter()`'s `q!` macro syntax, `AdminAction`'s
handler function-pointer signature, `#[task]`'s `inventory`-based registration, `Groups`/SSE's
v1 "plain `serve`/`run` path only, not `run_service()`" limitation) — capture that subtlety in the
doc comment, not just restate the type signature in prose. Crate-level (`//!`) docs for crates that
overlap with an existing `docs/src/guides/*.md` topic guide (ORM, templates, forms, auth, admin,
testing) should be consistent with what that guide already correctly documents — don't contradict
it.
