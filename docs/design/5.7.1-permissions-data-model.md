# 5.7 part 1 — Groups, Permissions, and `has_perm` (no admin wiring yet)

**Status:** design, not yet dispatched. Follows Phase 5's 5.6.x changelist arc (last: 5.6.6, CSV
export, commit `6f49e30`). See `docs/design/phase-5-roadmap.md` — this begins 5.7, flagged there
as needing its own auth-side design doc before any admin permission enforcement is possible.

## Scope: the data model and the `has_perm` check only — the admin still only checks `is_staff`

This slice does **not** touch `djangors-admin` at all. It builds, in `djangors-auth`, exactly
what Django calls `Group`/`Permission`/the M2M tables between `User`↔`Group`↔`Permission`, plus
the query that answers "does this user have this permission" — and stops there. Wiring
`require_staff()` (and friends) in the admin to actually call `has_perm()` per view is 5.7.2, a
separate follow-up slice, once this data model exists and is independently tested. Splitting this
way mirrors how 5.6.x was broken into 5.6.1 through 5.6.6 rather than one giant changelist slice.

## Why this doesn't need real many-to-many support in the ORM (and isn't blocked on it)

`RelationMeta`/`FieldKind` already has a `RelationKind::ManyToMany` variant, but it is a pure
stub — `grep -rn "RelationKind::ManyToMany"` across the whole repo turns up nothing but its own
declaration in `meta.rs`. There is no derive-macro attribute, no query-side join logic, nothing
real behind it. Building actual Django-style M2M support in the ORM (a general-purpose "through"
table with query sugar) would be its own multi-slice project, and this task doesn't need it:
Django's own `User.groups`/`Group.permissions`/`User.user_permissions` M2M fields are, under the
hood, just ordinary join tables (`auth_user_groups`, `auth_group_permissions`,
`auth_user_user_permissions`) — this task models those join tables directly as regular structs
with two `ForeignKey` fields each, which the ORM already fully supports today. No new ORM
capability needed anywhere in this slice.

## New models, all in `crates/djangors-auth/src/lib.rs`

```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_auth", table_name = "auth_permission")]
pub struct Permission {
    #[djangors(primary_key, auto)]
    pub id: i64,
    /// "{app_label}.{action}_{model_name_lowercase}", e.g. "polls.add_question".
    #[djangors(max_length = 255, unique)]
    pub codename: String,
    /// Human-readable label, e.g. "Can add question".
    #[djangors(max_length = 255)]
    pub name: String,
}

#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_auth", table_name = "auth_group")]
pub struct Group {
    #[djangors(primary_key, auto)]
    pub id: i64,
    #[djangors(max_length = 150, unique)]
    pub name: String,
}

/// Join table: which groups a user belongs to.
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_auth", table_name = "auth_user_groups")]
pub struct UserGroup {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user: ForeignKey<User>,
    pub group: ForeignKey<Group>,
}

/// Join table: which permissions a group grants.
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_auth", table_name = "auth_group_permissions")]
pub struct GroupPermission {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub group: ForeignKey<Group>,
    pub permission: ForeignKey<Permission>,
}

/// Join table: permissions granted directly to a user (bypassing any group).
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_auth", table_name = "auth_user_permissions")]
pub struct UserPermission {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user: ForeignKey<User>,
    pub permission: ForeignKey<Permission>,
}
```

`use djangors_orm::ForeignKey;` (already imported in files using it, e.g.
`examples/polls/src/models.rs` — mirror that field syntax exactly, e.g. `pub user:
ForeignKey<User>`, matching `pub question: ForeignKey<Question>` there).

**`ForeignKey<User>` hardcodes the concrete `djangors_auth::User` struct, not the generic
`AuthUser` trait.** This is not a new gap introduced by this task — it's the same, already-
documented scope decision from 5.1 ("Generic `AuthUser` support in the admin... the staff gate is
hardcoded to concrete `djangors_auth::User`; extending `AuthUser` with `is_staff()` is the
documented path when a real custom-user use case appears" — see the Phase 5 roadmap ledger). This
task extends that exact same, already-accepted limitation to cover groups/permissions too; it
does not need to be solved here.

## FK column-name convention — read this before writing any SQL in this task

**A `ForeignKey<T>` field's column name is the Rust field name itself, with no `_id` suffix.**
This is an established, previously-documented convention in this codebase (confirmed via
`examples/polls`'s `pub question: ForeignKey<Question>` having a column literally named
`question`, and used by every generic runtime code site: `update()`, `filter()`, `insert_raw()`,
`collect_related_objects()`). Concretely for this task: `UserGroup.user` → column `user`,
`UserGroup.group` → column `group`, `GroupPermission.group` → column `group`,
`GroupPermission.permission` → column `permission`, `UserPermission.user` → column `user`,
`UserPermission.permission` → column `permission`. **Not** `user_id`/`group_id`/`permission_id`.
This is the single easiest thing to get wrong in this task's raw SQL (below) — a query using the
wrong column name will fail at the `sqlx` level with a real Postgres error (column does not
exist), not silently return wrong results, so it will be caught by any test that actually runs —
but get it right on the first pass rather than relying on a test failure to catch it.

## `has_perm`: the core permission check

A free function in `djangors-auth`, not a trait method (it needs a `db` connection, and
`AuthUser`'s existing async methods like `update_user` already take `db` as a parameter this same
way, so this matches that shape rather than the trait itself):

```rust
/// Checks whether `user_id` has been granted `codename`, either directly
/// (`UserPermission`) or via any group they belong to (`UserGroup` ->
/// `GroupPermission`). Does NOT special-case superusers - callers that want
/// "superusers can do anything" should check `user.is_superuser()` first and
/// skip calling this entirely, avoiding a DB round-trip for the common case.
pub async fn has_perm(
    db: &djangors_db::Database,
    user_id: i64,
    codename: &str,
) -> Result<bool, AuthError> {
    let direct: i64 = sqlx::query_scalar(sqlx::AssertSqlSafe(
        "SELECT COUNT(*) FROM auth_user_permissions up \
         JOIN auth_permission p ON p.id = up.permission \
         WHERE up.\"user\" = $1 AND p.codename = $2"
            .to_string(),
    ))
    .bind(user_id)
    .bind(codename)
    .fetch_one(db.pool())
    .await
    .map_err(|e| AuthError::Database(djangors_orm::OrmError::Query(e)))?;
    if direct > 0 {
        return Ok(true);
    }

    let via_group: i64 = sqlx::query_scalar(sqlx::AssertSqlSafe(
        "SELECT COUNT(*) FROM auth_user_groups ug \
         JOIN auth_group_permissions gp ON gp.\"group\" = ug.\"group\" \
         JOIN auth_permission p ON p.id = gp.permission \
         WHERE ug.\"user\" = $1 AND p.codename = $2"
            .to_string(),
    ))
    .bind(user_id)
    .bind(codename)
    .fetch_one(db.pool())
    .await
    .map_err(|e| AuthError::Database(djangors_orm::OrmError::Query(e)))?;
    Ok(via_group > 0)
}
```

Note `"user"` and `"group"` are quoted in the SQL above — both are reserved/contextually-reserved
words in Postgres (`USER`, and `GROUP` as in `GROUP BY`), so the bare column names need
double-quoting to be used as identifiers rather than parsed as keywords. `permission` and
`codename` need no quoting. Confirm this compiles and the queries actually run against a real
Postgres test DB during review — don't assume the quoting is right without seeing a passing test
that exercises the group-membership path specifically (test 5 below).

`AuthError::Database(#[from] djangors_orm::OrmError)` already exists (`crates/djangors-auth/src/lib.rs`
~line 26-27); `djangors_orm::OrmError::Query(#[from] sqlx::Error)` also already exists — the
`.map_err(|e| AuthError::Database(djangors_orm::OrmError::Query(e)))?` shown above is the correct
two-step conversion since Rust's `?` only performs one `From` conversion per call, not a chain.

## Standard permission codenames + a seeding helper (`sync_permissions`)

Django auto-creates 4 standard permissions per model (`add`/`change`/`delete`/`view`) via a
migration signal. This project has no real migration system yet (a standing, already-tracked
deferral — see the roadmap ledger), so this task adds an explicit, idempotent seeding function
instead — the same shape of decision `createsuperuser` already made (non-interactive, explicit,
run-once-by-a-human-or-script, rather than automatic):

```rust
/// Ensures the 4 standard permissions (view/add/change/delete) exist for
/// every model currently registered via `djangors_orm::meta::all_registered_models()`
/// - every `#[derive(Model)]` struct in the binary, the same pre-existing
/// global registry 5.5's `collect_related_objects` already established as
/// the source of truth for "every model in the project." Idempotent: safe
/// to call on every app startup or as a repeatable CLI step. Returns the
/// number of (model, action) pairs considered (not the number newly
/// inserted - `ON CONFLICT DO NOTHING` makes re-runs cheap no-ops without
/// needing to track that distinction).
pub async fn sync_permissions(db: &djangors_db::Database) -> Result<usize, AuthError> {
    let mut count = 0;
    for meta in djangors_orm::meta::all_registered_models() {
        for action in ["view", "add", "change", "delete"] {
            let codename = format!(
                "{}.{}_{}",
                meta.app_label,
                action,
                meta.struct_name.to_lowercase()
            );
            let name = format!("Can {} {}", action, meta.struct_name.to_lowercase());
            sqlx::query(sqlx::AssertSqlSafe(
                "INSERT INTO auth_permission (codename, name) VALUES ($1, $2) \
                 ON CONFLICT (codename) DO NOTHING"
                    .to_string(),
            ))
            .bind(&codename)
            .bind(&name)
            .execute(db.pool())
            .await
            .map_err(|e| AuthError::Database(djangors_orm::OrmError::Query(e)))?;
            count += 1;
        }
    }
    Ok(count)
}
```

`ON CONFLICT (codename)` requires a real `UNIQUE` constraint on `auth_permission.codename` in the
actual table — since there's no real migration system, this is only as real as whatever `CREATE
TABLE` a deployment actually runs (same situation every other table in this project is already
in). Test fixtures must declare `codename TEXT NOT NULL UNIQUE` explicitly in their raw `CREATE
TABLE`, matching the exact same pattern `auth_user`'s own test fixture already uses for
`username TEXT NOT NULL UNIQUE` (`crates/djangors-auth/src/tests.rs` ~line 224-230).

```rust
pub async fn createpermissions() {
    let db_url = match std::env::var("DATABASE_URL") {
        Ok(url) => url,
        Err(_) => {
            eprintln!("[dj createpermissions] DATABASE_URL environment variable is not set");
            std::process::exit(1);
        }
    };
    let config = djangors_db::config::DatabaseConfig::new(db_url);
    let db = match djangors_db::Database::connect(&config).await {
        Ok(db) => db,
        Err(e) => {
            eprintln!("[dj createpermissions] failed to connect to database: {e}");
            std::process::exit(1);
        }
    };
    match djangors_auth::sync_permissions(&db).await {
        Ok(count) => println!("[dj createpermissions] synced {} permission(s)", count),
        Err(e) => {
            eprintln!("[dj createpermissions] failed: {e}");
            std::process::exit(1);
        }
    }
}
```

(`djangors-cli` already depends on `djangors-auth` — confirm this in `Cargo.toml` before assuming
it, since `createsuperuser` already uses `djangors_auth::User` directly, so the dependency should
already be present.)

## What NOT to touch in this task

- No changes to `djangors-admin` at all — no `require_staff` changes, no per-view permission
  gating. That's 5.7.2, a separate follow-up slice once this lands.
- No real many-to-many query sugar in the ORM (`RelationKind::ManyToMany` stays an unused stub) —
  see the scope section above for why this task doesn't need it.
- No admin UI for managing groups/permissions/user-group assignments (Django's own admin has
  built-in `Group`/`Permission` admin pages — that's a reasonable future addition once 5.7.2
  lands and there's a working permission *check* to actually protect those pages with, not
  before).
- No automatic permission seeding at model-registration time (`AdminSite::register_with` stays
  synchronous, untouched) — `sync_permissions`/`dj createpermissions` is an explicit step, same
  shape as `createsuperuser`.
- No changes to `djangors-macros`.

## Required tests

Add to `crates/djangors-auth/src/tests.rs`, same `DB_MUTEX`-guarded, real-`CREATE TABLE`/`DROP
TABLE IF EXISTS` Postgres-socket-level style as every existing test in that file.

1. Call `sync_permissions` against a DB with a couple of real registered test models → the
   `auth_permission` table ends up with exactly 4 rows per model (view/add/change/delete), each
   `codename` following the `{app_label}.{action}_{model_name_lowercase}` convention.
2. Call `sync_permissions` twice in a row → no error, no duplicate rows (row count after the
   second call equals the row count after the first) — proves the `ON CONFLICT DO NOTHING`
   idempotency.
3. `has_perm` for a user with no `UserPermission` row and no group membership at all → `Ok(false)`.
4. `has_perm` for a user with a direct `UserPermission` row for the exact codename being checked
   → `Ok(true)`.
5. `has_perm` for a user with *no* direct `UserPermission` row, but who belongs (via `UserGroup`)
   to a group that has a `GroupPermission` row for the codename → `Ok(true)` — this is the test
   that exercises the join chain and would catch a wrong FK column name (`user_id` vs `user`,
   `group_id` vs `group`) if the SQL got it wrong, since a wrong column name fails at the SQL
   level with a real error, not a silently-wrong boolean.
6. `has_perm` for a user who has *some* permission, but not the one being checked (a different
   codename) → `Ok(false)` — proves the check isn't accidentally matching on user/group alone
   without actually filtering by codename.
