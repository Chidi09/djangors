# Design 5.4 — Admin change form v1: add + edit (Phase 5 part 4)

**Status:** draft, pre-implementation. Fourth Phase 5 slice, per `docs/design/phase-5-roadmap.md`
("5.4 — Change form v1, the next big rock"). Builds add/edit pages for a registered model: a
plain HTML form of every field, POST to create or update, redirecting back to the changelist on
success. Fieldsets, readonly_fields, raw_id/autocomplete FK widgets, M2M widgets, and inlines are
all later slices (PLAN.md's full change-form bullet) — this is deliberately the smallest working
slice: one field per row, text/checkbox/number inputs only, server-side validation errors
re-render the form.

## The core problem this task solves, and why it does NOT touch the derive macro

5.2 solved "model instance → displayable strings" via derive-emitted `field_values()`. This task
needs the *reverse* — "form strings → a saved/updated row" — but it does **not** need a new
derive-emitted method, because two already-generic mechanisms cover both directions without
per-model codegen:

- **Edit** (`UPDATE`): `QuerySet::update(db, sets: Vec<(&'static str, SetExpr)>)`
  (`crates/djangors-orm/src/queryset.rs` ~line 412) already validates field names against
  `ModelMeta` and builds the SQL generically. Fetching the row to edit is also generic:
  `UnresolvedCompare { field: &'static str, value: Value }` (`expr.rs` line 141) only needs a
  `&'static str` field name — and every `FieldMeta::name` **is** `&'static str` already (it comes
  from the derive's compile-time string literals). So `meta.fields.iter().find(|f| f.primary_key)`
  gives a real `&'static str` pk field name usable in `UnresolvedExpr::And(vec![UnresolvedCompare
  { field: pk.name, value: Value::I64(id) }])` at runtime — **no `q!{}` macro needed**, that
  macro is just sugar over the same struct for the compile-time-known-field-name case.
- **Add** (`INSERT`): nothing generic exists yet for this direction — the derive's `save()` needs
  a fully-constructed typed `Self`, which the admin can't produce without reflection. Add one new
  generic method instead of touching the macro:

  ```rust
  // crates/djangors-orm/src/queryset.rs, on QuerySet<T> (associated fn, no `self` needed —
  // there's nothing to filter for an INSERT)
  impl<T: Model> QuerySet<T> {
      /// Generic INSERT built purely from `ModelMeta`, bypassing the derived typed `save()`.
      /// For callers (the admin) that only have `(field_name, Value)` pairs, not a real `Self`.
      /// Validates every field name against `meta.fields`/`meta.relations` (same validation
      /// `filter`/`order_by` already do) — unknown names are `OrmError::FieldNotFound`, not a
      /// panic. Skips `auto` fields even if supplied. Returns the new row's primary key.
      pub async fn insert_raw(
          db: &djangors_db::Database,
          values: Vec<(&'static str, crate::expr::Value)>,
      ) -> Result<i64, OrmError> { ... }
  }
  ```

  Mirror `compile_select_custom`'s pattern (build SQL from `meta.table_name` +
  `meta.fields`/`meta.relations` column-name lookups, `sqlx::AssertSqlSafe`, positional binds) —
  `"INSERT INTO {table} ({cols}) VALUES ({placeholders}) RETURNING {pk_column}"`. Assume `i64`
  pk (every real model in this workspace already does — `User.id`, `Question.id`, etc. — this
  isn't a new constraint). Add a focused unit test in `djangors-orm`'s own test file (real
  Postgres) proving `insert_raw` round-trips against an existing test model and rejects an
  unknown field name.

## Part 1 — `djangors-admin`: string → `Value` parsing

New function, not model-specific (works from `FieldMeta` alone):

```rust
/// Parses one raw form-field string into a Value for the given field's kind.
/// `raw: None` or `Some("")` means "field absent/empty" — `Ok(Value::Null)` if
/// `field.nullable`, else a validation error. Only the `FieldKind` variants the
/// derive macro actually allows through save/update codegen need real parsing
/// (see `crates/djangors-macros/src/model.rs`'s "unsupported types for
/// save/update operations" check ~line 324 — Date/Time/Duration/Uuid/Decimal
/// fields never reach a working `save()`/`update()`, so no real model in this
/// workspace can have one; treat hitting one here as `unreachable!` with an
/// explanatory message, not a case to silently support badly).
fn parse_field_value(field: &FieldMeta, raw: Option<&str>) -> Result<Value, String> {
    // Char/Text -> Value::Text(s.to_string())
    // Integer/BigInt -> raw.parse::<i64>() with a field-name-including error message
    // Float -> raw.parse::<f64>()
    // Boolean -> checkbox semantics: present (any non-empty value, including "on") = true,
    //            absent = false (HTML form convention: unchecked checkboxes send nothing)
    // DateTime -> chrono::NaiveDateTime::parse_from_str(raw, "%Y-%m-%d %H:%M:%S") -> Utc
    //             (matches the Display format Value::Display already emits, so the edit
    //             form's pre-filled value round-trips through the same format)
}
```

Relation (FK) fields aren't in `meta.fields` — they're in `meta.relations`
(`RelationMeta::field_name`) — parse the same way but always as an i64 id (`Value::I64`), no
`FieldKind` needed since a FK is always its target's pk type.

## Part 2 — `djangors-admin`: `ModelAdmin` grows change-form methods

```rust
#[async_trait]
pub trait ModelAdmin: Send + Sync {
    // existing model_meta, changelist ...

    /// Fetch one row by pk for the edit form, rendered via the existing
    /// `field_values()` mechanism (reuse, don't reinvent).
    async fn get_by_pk(&self, db: &Database, pk: i64) -> Result<Option<Vec<(&'static str, Value)>>, DjangorsError>;

    /// Validate + apply `form` (raw field_name -> submitted string) as an
    /// UPDATE against `pk`. Returns field-level errors keyed by field name
    /// on validation failure (re-render with those), or Ok(()) on success.
    async fn update_from_form(&self, db: &Database, pk: i64, form: &HashMap<String, String>) -> Result<Result<(), HashMap<String, String>>, DjangorsError>;

    /// Same, but INSERT — returns the new pk on success.
    async fn create_from_form(&self, db: &Database, form: &HashMap<String, String>) -> Result<Result<i64, HashMap<String, String>>, DjangorsError>;
}
```

`DefaultModelAdmin<M>` implements all three by iterating `M::meta().fields` (skipping
`auto`/`primary_key` for create; skipping `auto` alone for update, matching the derive's own
`save_fields`/`update_fields` split) plus `M::meta().relations`, calling `parse_field_value` per
field, collecting per-field errors instead of short-circuiting on the first one (so the
re-rendered form can show every error at once, matching Django's own change-form UX), then
either `QuerySet::<M>::insert_raw` or the pk-lookup-then-`update()` pattern from Part "core
problem" above.

## Part 3 — routes and rendering

Four new routes in `AdminSite::urls()`, alongside the existing index/changelist, following the
same `Arc<dyn ModelAdmin>`-closure-capture pattern 5.1/5.2 established:

- `GET /{app:slug}/{model:slug}/add/` — empty form.
- `POST /{app:slug}/{model:slug}/add/` — `create_from_form`; success → `Response::redirect` to
  the changelist (`../` relative, or absolute `/{app}/{model}/` — check which the router's
  `Response::redirect` helper expects and match existing usage in `examples/polls`'s
  `login_view`/`vote` redirects); validation errors → re-render the add form with errors + the
  submitted (unparsed) values so the user doesn't lose their input.
- `GET /{app:slug}/{model:slug}/{pk:i64}/change/` — `get_by_pk`, 404 if `None`, render prefilled.
- `POST /{app:slug}/{model:slug}/{pk:i64}/change/` — `update_from_form`; same success/error
  handling as add.

Staff gate (`require_staff`, already factored out in 5.2) on all four. CSRF already works
end-to-end for POST forms — reuse the exact pattern `examples/polls`'s `login_view` uses
(`X-CSRFToken` header + `csrftoken` cookie double-submit; there is **no** hidden-input
`csrfmiddlewaretoken` field support — this project's CSRF middleware deliberately validates the
header only, documented in `middleware.rs` — so the rendered form's HTML needs client-side JS to
read the cookie and set the header, OR (simpler v1, no JS) skip the browser-form-submission path
entirely for now and note in the doc that this makes the add/change *pages* fully real but
requires an API client (or a future JS enhancement) to actually submit them — **do not silently
add a body-field CSRF exemption or a hidden `csrfmiddlewaretoken` input that the middleware
doesn't check**, that would be a false sense of protection. State this limitation plainly in
both the code's doc comment and the commit message; it's a legitimate, previously-documented gap
(see the roadmap doc's CSRF ledger entry), not new scope creep to fix here.)

All rendering: plain `format!` HTML matching 5.1/5.2's style (no `djangors-template` yet, still
deferred to the theming slice) — `<form method="post">`, one `<label>`+`<input>` (or `<input
type="checkbox">` for Boolean, `<input type="number">` for Integer/BigInt/Float) row per field
in declaration order, values escaped via `djangors_core::html_escape`, per-field error text (also
escaped) shown under its input when present, `auto`/primary-key fields omitted entirely from the
add form and rendered read-only (no `<input>`, just the value) on the edit form.

**Changelist integration** (closes the deferred item from 5.2): the first column's cell in each
changelist row becomes `<a href="{pk}/change/">{value}</a>` instead of plain text — needs the
row's pk value, which `field_values()` already provides (find the pk column by name via
`M::meta()`, same lookup pattern used elsewhere).

## What this task does NOT include

- Fieldsets, `readonly_fields` customization (beyond the always-readonly pk), raw_id/autocomplete
  FK widgets + async search endpoint, M2M widgets, inlines/formsets — all later slices.
- Delete (separate 5.5 slice, `phase-5-roadmap.md`).
- Fixing the CSRF header-only limitation — explicitly out of scope, see Part 3.
- `list_editable` (inline editing from the changelist) — different feature, later slice.

## Required tests

- `djangors-orm`: `insert_raw` round-trip (insert via raw values, verify via typed `get()`) and
  unknown-field-name rejection.
- `djangors-admin` (extend the existing real-Postgres + mounted-router test module):
  - `GET .../add/` as staff → 200, contains an input per non-auto field.
  - `POST .../add/` with valid data → redirect (or 200 depending on `Response::redirect`'s real
    status — check it), row exists in DB afterward with correct values.
  - `POST .../add/` with an unparseable field (e.g. non-numeric into an Integer field) → 200
    (re-rendered, not an error status — matches Django's own change-form UX) containing the
    field-level error text and NOT losing the other submitted values.
  - `GET .../{pk}/change/` for a seeded row → 200, inputs pre-filled with that row's values
    (assert the rendered `value="..."` attributes).
  - `POST .../{pk}/change/` with valid data → row updated in DB.
  - `GET .../{pk}/change/` for a nonexistent pk → 404.
  - Changelist row's first cell now links to `{pk}/change/` (regression coverage for the new
    link, extending the existing changelist test rather than duplicating its whole setup).
  - unauthenticated/non-staff still 401/403 on all four new routes (reuse `require_staff`, so a
    single representative case per new route is enough — the gate itself is already covered).
- Full workspace green: `cargo fmt --all`, `build --workspace --all-targets`, `clippy --workspace
  --all-targets -- -D warnings`, `test --workspace`.
