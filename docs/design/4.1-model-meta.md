# Design 4.1 — Model metadata without reflection

**Status:** draft, pre-implementation. Read `PLAN.md` Part 4.1 first — this expands it into an actual data shape and macro contract.

## The problem

Django's admin, migrations, forms, and serializers all run on **runtime introspection**: `Model._meta.fields`, `getattr(instance, field.name)`, etc. Rust has none of that. Every one of those four subsystems needs the same information about a model — field names, types, nullability, defaults, relations — and needs it *before* any instance exists (e.g. `makemigrations` needs field metadata with zero rows in the database).

`ModelMeta` is that information, generated once per model by `#[derive(Model)]`, and it is the **single source of truth** every other crate reads. Get this wrong and every downstream crate (migrations, admin, forms, rest) either can't be built cleanly or ends up re-deriving the same metadata its own way — exactly the fragmentation this design doc exists to prevent.

## Data shape

```rust
// djangors-orm/src/meta.rs

pub struct ModelMeta {
    /// Rust struct name, e.g. "Question".
    pub struct_name: &'static str,
    /// Owning app label, e.g. "polls" — from #[djangors(app = "polls")].
    pub app_label: &'static str,
    /// Database table name. Defaults to `{app_label}_{struct_name_snake_case}`
    /// (Django's own default), overridable via Meta.
    pub table_name: &'static str,
    pub fields: &'static [FieldMeta],
    pub relations: &'static [RelationMeta],
    pub indexes: &'static [IndexMeta],
    pub unique_together: &'static [&'static [&'static str]],
    pub ordering: &'static [&'static str], // "-pub_date" = DESC
}

pub struct FieldMeta {
    pub name: &'static str,           // Rust field name
    pub column_name: &'static str,    // defaults to `name`, overridable
    pub kind: FieldKind,
    pub nullable: bool,
    pub primary_key: bool,
    pub auto: bool,                   // auto-increment / auto-generated
    pub unique: bool,
    pub db_index: bool,
    pub default: Option<DefaultValue>,
    pub max_length: Option<u32>,      // CharField only
    pub verbose_name: Option<&'static str>,
    pub help_text: Option<&'static str>,
    pub choices: &'static [(&'static str, &'static str)], // (db value, display label)
}

pub enum FieldKind {
    Char, Text, Integer, BigInt, Float, Decimal { max_digits: u32, decimal_places: u32 },
    Boolean, Date, DateTime, Time, Duration, Uuid, Email, Url, Slug, Ip, Binary, Json,
}

pub struct RelationMeta {
    pub field_name: &'static str,
    pub kind: RelationKind,           // ForeignKey | OneToOne | ManyToMany
    pub target: fn() -> &'static ModelMeta,  // late-bound: see "the ordering problem" below
    pub on_delete: OnDelete,          // Cascade | Protect | SetNull | Restrict | DoNothing
    pub related_name: Option<&'static str>,
}
```

Everything is `&'static` / `const`-friendly on purpose: `ModelMeta` for a given model is built **once**, at first access, and never mutated. This is what makes it cheap to pass around and safe to share across threads without locking.

## The ordering problem (why `target` is a function pointer, not a direct reference)

`Choice::META` needs a reference to `Question::META` (its `ForeignKey<Question>` target). But `#[derive(Model)]` expands independently per struct, in whatever order the compiler processes them — there is no guarantee `Question`'s expansion happens "before" `Choice`'s, and Rust has no forward-declaration mechanism for `static` items across that ordering.

**Resolution:** `RelationMeta::target` is `fn() -> &'static ModelMeta`, not `&'static ModelMeta` directly. Each model's metadata is itself built lazily behind a `OnceLock` (see below), so `target` is just `Question::meta as fn() -> &'static ModelMeta` — a function *pointer* is `'static` and orderless even when what it points to is built lazily. This is the same trick that makes `LazyLock`/`OnceLock` chains between arbitrary types work in stable Rust without a build-order dependency.

## How `#[derive(Model)]` builds this

Per model struct, the macro generates:

```rust
impl Question {
    pub fn meta() -> &'static ModelMeta {
        static META: std::sync::OnceLock<ModelMeta> = std::sync::OnceLock::new();
        META.get_or_init(|| ModelMeta {
            struct_name: "Question",
            app_label: "polls",
            table_name: "polls_question",
            fields: &[/* ... generated from struct fields + #[djangors(...)] attrs ... */],
            relations: &[],
            indexes: &[],
            unique_together: &[],
            ordering: &["-pub_date"],
        })
    }
}

impl djangors_orm::Model for Question {
    fn meta() -> &'static ModelMeta { Self::meta() }
    // + typed field accessor generation for the QuerySet system, see 4.2
}
```

Registration into the **app registry** (so `makemigrations`/the admin/the app system can discover "every model in this app") happens via the `inventory` crate (compile-time distributed registration, no manual list to keep in sync) — each `#[derive(Model)]` expansion also emits:

```rust
inventory::submit! { djangors_orm::ModelRegistration { meta_fn: Question::meta } }
```

and the app registry queries `inventory::iter::<ModelRegistration>()` at startup. This avoids the alternative (a build-time codegen step scanning the crate for model structs), which is slower, harder to get right with incremental compilation, and worse for IDE support.

## What each downstream crate reads and nothing else

This is the actual point of the exercise — enumerate it explicitly so future work doesn't reinvent a subset of `ModelMeta` inside its own crate:

| Crate | Reads |
|---|---|
| `djangors-migrations` | Full `ModelMeta` (fields + relations + indexes + unique_together) to diff against migration-replayed historical state. |
| `djangors-admin` | `fields` (for changelist columns/change-form generation), `relations` (for inline/FK widget rendering), `verbose_name`/`help_text` (for labels). |
| `djangors-forms` | `fields` only — `ModelForm` is generated purely from `FieldMeta`, no relation-awareness needed at the form-field level (relations become a `ForeignKey` field type, handled like any other field kind from forms' perspective). |
| `djangors-rest` | `fields` + `relations`, to generate serializers and OpenAPI schemas. |
| `djangors-orm` (itself) | `fields` for the typed `Fields` struct (4.2) and SQL column generation; `table_name` for every generated query. |

## Field attribute surface (what `#[derive(Model)]` actually parses)

```rust
#[djangors(
    primary_key,           // marks this field as the PK
    auto,                  // auto-increment (only valid combined with primary_key today)
    max_length = 200,      // required for Char, ignored elsewhere (compile error if misused)
    default = 0,           // literal or path to a const/fn
    unique,
    db_index,
    verbose_name = "date published",
    help_text = "...",
    column = "custom_col_name",
    foreign_key(to = Question, on_delete = "cascade", related_name = "choices"),
)]
```

Struct-level `#[djangors(app = "polls", ordering = "-pub_date", table_name = "...", unique_together = [...])]`.

**Compile-time validation the macro must perform** (this is the entire point of doing this in Rust instead of Python): `primary_key` field type must be an integer or UUID kind; `max_length` required on `Char`, forbidden elsewhere; `foreign_key(to = X)` requires `X` to itself derive `Model` (checked via trait bound, not string matching); duplicate `column` names within one struct; more than one `primary_key` field. Every one of these is a runtime `ImproperlyConfigured` exception in Django — here they're compile errors, which is the actual pitch of this framework to a banking/school buyer.

## Open questions for implementation time (not blocking, but flag before writing `q!()`)

- Composite primary keys: out of scope for v1 (matches Django's historical position — Django only got composite PK support in 5.2). `primary_key` is single-field only for now.
- `choices` field validation: compile-time enum-backed choices vs. runtime `&[(&str, &str)]` — leaning runtime (simpler, matches Django's flexibility of choices coming from a DB-backed source sometimes), revisit if it becomes an admin-rendering pain point.
