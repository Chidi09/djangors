# 9.4 — real `dj shell` via evcxr (closing the documented gap from 9.3)

## Scope

9.3 (commit `1a9d086`) documented `dj shell`'s current behavior honestly: it connects to the
database then prints "an interactive Rust REPL is not yet available (requires evcxr
integration)." The user has now explicitly asked for the real feature instead of leaving it as a
documented gap: **"well do evcxr then, why not have the feature."** This slice replaces
`crates/djangors-cli/src/commands.rs`'s `shell()` stub (currently lines ~627-641) with a real,
working interactive Rust REPL.

**Deliberately excluded from this dispatch**: bundling `evcxr` itself into the `dj` binary or
auto-installing it — mirror `dj dbshell`'s existing precedent exactly (that function execs the
user's own `psql` binary via `std::process::Command`, with a clear error message if it's not on
`PATH`, rather than vendoring a Postgres client). Do the same thing here: exec the user's own
`evcxr` binary (installed via `cargo install evcxr_repl`, which provides the `evcxr` binary — verify
this crate/binary name is actually correct by checking real evcxr documentation/crates.io metadata
before writing the error message, don't guess), with a clear, actionable error message if it's
missing.

## The real, structural constraint that still applies (same one from 6.3/PLAN.md)

`dj` is a separate binary from any project it operates on — it cannot introspect a target
project's registered models or import them automatically (this is the exact same constraint that
makes `dj makemigrations` return an explicit "cannot introspect across binary boundaries" error,
confirmed in 6.3). **This dispatch does not remove that constraint** — don't attempt any scheme
that tries to dynamically link against or inspect the calling project's compiled model registry.
What it CAN and SHOULD do: hand the user a real, working `evcxr` session, launched with the current
project directory as its working context, so the user can immediately do something like
`:dep <project_name> = { path = "." }` themselves (evcxr's REPL supports adding path dependencies
at runtime — verify the exact real evcxr command syntax before documenting it, don't guess) and
then `use <project_name>::models::*;` to bring their own models into scope manually. This is a
real, useful v1: a genuine Rust REPL scoped to the project, not model auto-import, and the design
should say so honestly in both the CLI's own printed banner and the doc-comparison guide.

## Environment note from a failed first attempt (2026-07-23)

A first attempt at this dispatch ran `cargo install evcxr_repl` with default features and hit two
real problems, independently diagnosed after the dispatch process died on an `agy` print-timeout:
(1) `evcxr_repl`'s default feature set pulls in rust-analyzer's own internal crates (`ra_ap_hir_def`
and friends) for code-completion — an enormous, slow-to-compile dependency tree, not a small
utility install; (2) this environment's disk is already tight (was at 92-95% full even before this
attempt), and the install was consuming disk fast enough to be a real risk of repeating an earlier
incident in this project's history where disk exhaustion crashed the local Postgres cluster.
**Two required changes this time**:
- Try installing with `cargo install evcxr_repl --no-default-features` first (check evcxr_repl's
  real Cargo.toml/crates.io feature list to confirm this is the right flag and that a
  no-default-features build still produces a working core REPL without the heavy completion
  feature — verify for real, don't assume the flag name). Only fall back to the full default-
  features install if the lighter one is genuinely broken/insufficient for basic REPL use.
- **Cap how much time/disk the live verification install is allowed to spend.** Check `df -h /`
  before starting the install and again periodically during it; if free space drops below ~3GB,
  stop the install immediately (kill it and any child `rustc` processes — a `cargo install` SIGTERM
  does NOT cascade to its child `rustc` process, confirmed the hard way this session, so check
  `ps -ef` for orphaned `rustc` processes after killing the parent) rather than letting it run to
  exhaustion. If the lighter install still can't complete cleanly within a reasonable time/disk
  budget in this environment, it's acceptable to verify the `dj shell` code path's *logic* (the
  exec-with-clear-error-if-missing pattern) without a full live end-to-end evcxr session — say so
  honestly rather than forcing it.

## Implementation

- Investigate real `evcxr`/`evcxr_repl` behavior first (read its actual README/help output if
  installable in this environment, or its crates.io page) rather than assuming API shape. Key
  things to confirm for real: (1) the correct `cargo install` invocation and resulting binary name,
  (2) whether it accepts an "eval this at startup" mechanism (an init file, a piped set of initial
  lines before handing off to the interactive TTY, or similar) so `dj shell` can print a helpful
  one-time banner or optionally pre-seed a `:dep` line, (3) whether it needs to run from a specific
  working directory to correctly resolve local path dependencies.
- Replace `shell()` in `crates/djangors-cli/src/commands.rs`: keep the existing
  `require_project_root()` + `DATABASE_URL` connectivity check (useful early validation, matches
  `dbshell`'s own pattern of validating the environment before handing off), then exec the real
  `evcxr` binary via `std::process::Command` with inherited stdio (same pattern as `dbshell`'s
  `psql` exec — the whole point is a real interactive TTY session, not a captured pipe), working
  directory set to the project root. On `evcxr` not being found on `PATH`, return a clear error
  naming the exact install command (mirroring `dbshell`'s "is psql installed and on PATH?" style).
  Print a short banner beforehand explaining the project-import limitation honestly (one or two
  lines, e.g. "This is a plain Rust REPL — your project's models aren't auto-imported; add
  `:dep <name> = { path = \".\" }` yourself if you need them").
- If real investigation finds evcxr genuinely cannot be driven this way (e.g. it fundamentally
  can't run non-interactively enough to inherit stdio cleanly, or the crate is unmaintained/broken
  in this environment), **don't force a broken integration** — report back honestly what was found
  and what the real blocker is, the same "investigate before assuming, report reality" discipline
  every prior CLI slice (6.2's `dj new-app`, 6.3's `dj makemigrations`) already established. A
  working `dj shell` that execs evcxr cleanly is the goal; a half-working shim that hangs or
  crashes is worse than the honest current stub.
