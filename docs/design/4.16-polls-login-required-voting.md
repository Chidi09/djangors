# Design 4.16 — make `examples/polls` real, login-gate voting (Phase 4 part 4g, closes Phase 4 DoD)

**Status:** draft, pre-implementation. This is the last piece of Phase 4's own DoD line: "polls
requires login to vote." Builds on everything already real: the ORM (`djangors-orm`,
`ForeignKey<T>`, `F()`/`set!()` atomic updates — all confirmed real by reading
`crates/djangors-orm/src/queryset.rs` and `crates/djangors-orm/src/expr.rs` while scoping this
doc, contrary to `examples/polls/README.md`'s own stale "ASPIRATIONAL — Phase 2" annotations
written back when Phase 2 hadn't landed yet), `djangors-auth` (`AuthBackend`/`ModelBackend`/
`login`/`logout`/`Auth<U>`), `djangors-sessions` (`SessionLayer`), `djangors-core`'s `CsrfLayer`,
and [[4.15-middleware-stack-wiring]]'s new `RouterService`/`Djangors::serve_service` (the only way
any of the above actually apply to real traffic).

## Real scope check — read before writing any code

`examples/polls/README.md` says most of `models.rs`/`views.rs` is "ASPIRATIONAL — Phase 2
territory" and that the crate is "deliberately excluded [from workspace members] so it doesn't
break `cargo build --workspace`" until it compiles for real. **That's now mostly false** — Phase 2
landed since the README was written. Re-verify each aspirational marker against real code before
assuming it's still a gap:

- `Question::objects().filter(q!(pub_date__lte = ...)).order_by("-pub_date").limit(5).all(db)` —
  real (`QuerySet::filter`/`order_by`/`limit`/`all` all exist,
  `crates/djangors-orm/src/queryset.rs`).
- `Question::objects().get_or_404(db, id)` — **does NOT exist**, no `get_or_404` method anywhere
  in `djangors-orm`. Real equivalent: `.filter(q!(id = question_id))?.get(db).await`, mapping
  `OrmError::NotFound` to `DjangorsError::NotFound` (the exact same mapping pattern
  `djangors-auth`'s own `Auth<U>::from_request` already uses for `OrmError::NotFound` — copy that,
  substituting `Unauthorized` for `NotFound`; `DjangorsError::NotFound` already exists per
  `crates/djangors-core/src/error.rs`).
- `Choice::objects().filter(q!(question = question.id, id = vote.choice)).update(db, set!(votes =
  F("votes") + 1))` — **real**, almost verbatim (`QuerySet::update`, `SetExpr::FieldOp`, `F`, the
  `set!` macro all exist in `crates/djangors-orm/src/expr.rs`). Verify the exact filter syntax for
  a foreign-key column against real `djangors-orm` tests before assuming `question = question.id`
  is the right spelling — it may need to be `question_id = question.id` or similar depending on
  how the `#[derive(Model)]` macro names FK columns; check `crates/djangors-macros/src/model.rs`
  or an existing real model with a `ForeignKey<T>` field and its own tests for the actual generated
  column/filter name.
- `req.db()` — does not exist as a `Request` method. Real equivalent: `req.state::<djangors_db::
  Database>()` (returns `Option<&Database>`, per `crates/djangors-core/src/request.rs`) — handle
  the `None` case as `DjangorsError::Internal` (app misconfiguration), same as
  `djangors-auth`'s `Auth<U>` extractor already does.
- `reverse!("polls:results", question_id)` — named-route reversal does not exist (confirmed by
  `urls.rs`'s own doc comment — Router has no named-route table). Real equivalent for this task:
  build the redirect path with a plain `format!("/{question_id}/results/")` — an honest
  simplification, not a framework feature to build here. Note this in a code comment where the
  `reverse!()` call used to be, referencing this doc, so it's clear it's a deliberate stand-in and
  not a forgotten TODO.
- **Migrations**: no crate in this entire project has a real, hand-authored migration file yet —
  not even `djangors-auth`'s own `auth_user` table (its tests create it via raw
  `CREATE TABLE IF NOT EXISTS` SQL, not through `djangors_migrations::migrate()`). `dj
  makemigrations` (the autodetector) is an explicit `not yet implemented` stub
  (`crates/djangors-cli/src/commands.rs`). **This task does not change that.** `examples/polls`
  gets the same treatment: its own integration test creates `polls_question`/`polls_choice` tables
  via raw SQL at test setup, exactly mirroring the pattern every other crate's Postgres-backed
  tests already use (see `crates/djangors-auth/src/tests.rs`'s own `CREATE TABLE` calls for the
  precedent). A real migration file for polls is future work, unblocked only once the
  migrations-file-authoring story itself gets built for the first time anywhere in this project —
  out of scope here, and explicitly noted as a gap rather than silently worked around.

## What this task builds

1. **`examples/polls/src/models.rs`**: make `Question`/`Choice` real
   (`#[derive(Model)]`/`ForeignKey<Choice, Question>` per the real macro syntax — mirror
   `crates/djangors-auth/src/lib.rs`'s own real `User` struct's `#[djangors(...)]` attributes
   exactly, don't guess at syntax). Keep `was_published_recently()` as-is (it's already plain
   Rust, no framework dependency).
2. **`examples/polls/src/views.rs`**: make every handler body real per the "real scope check"
   above. Add a new requirement not in the original aspirational sketch — **`vote` must require
   login**: extract `Auth<djangors_auth::User>` at the top of the handler (via the existing manual
   `FromRequest::from_request(&req).await?` call pattern, matching how `djangors-auth`'s own
   `Auth<U>` doc comment says to use it today, since automatic parameter injection isn't built)
   before doing anything else; an unauthenticated POST to `/vote/` must fail with
   `DjangorsError::Unauthorized` (401) via `Auth<U>`'s own existing extraction failure, not a
   custom check. `index`/`detail`/`results` stay unauthenticated (matches Django's own polls
   tutorial — only voting requires login, not viewing).
3. **`examples/polls/src/urls.rs`**: unchanged in shape (still real), but add a **login route**:
   `.post("/accounts/login/", views::login_view)` and `.post("/accounts/logout/", views::
   logout_view)` — two new, small, polls-app-specific handlers in `views.rs` (this is the
   "app-specific plumbing" [[4.11-auth-backend-login]] explicitly deferred to whoever needed it
   first — that's now this task). Minimal scope: `login_view` takes a `Form<LoginForm { username,
   password }>`, calls `ModelBackend.authenticate(...)`, and on success calls `djangors_auth::
   login(&session, &user)` then redirects home; on failure, redirects back with a query-string
   error flag (`/accounts/login/?error=1`) — no template/HTML form rendering in this task (plain
   `Response::html` with an inline `<form>` is enough, matching the existing `index`/`detail`
   handlers' own inline-HTML style, not a regression in styling quality). `logout_view` calls
   `djangors_auth::logout(&session).await` and redirects home.
4. **`examples/polls/src/main.rs`**: wire the real serving path from [[4.15-middleware-stack-wiring]]:
   ```rust
   let db = /* connect via djangors_db::Database, DATABASE_URL env var, same pattern
                crates/djangors-cli/src/commands.rs's migrate() already uses */;
   let router = urls::urls().with_state(db);
   let router_service = djangors_core::router::RouterService::new(router, settings.debug);
   let secret_key = /* from settings - check DjangorsSettings for an existing secret-key field
                        before inventing a new settings mechanism; if none exists, a hardcoded
                        dev-only constant with a loud comment is an acceptable v1 stand-in, same
                        as this project's other "settings wiring is future work" deferrals */;
   let service = tower::ServiceBuilder::new()
       .layer(djangors_core::middleware::security_headers_layer())
       .layer(djangors_sessions::SessionLayer::new(
           djangors_sessions::SignedCookieStore::new(secret_key.as_bytes())
       ))
       .layer(djangors_core::middleware::csrf_layer())
       .service(router_service);
   Djangors::new(settings, Router::new()).run_service(service).await
   ```
   Check `DjangorsSettings`'s real field list (`crates/djangors-core/src/settings.rs`) before
   assuming a secret-key field exists or inventing its name.
5. **Workspace membership**: per `examples/polls/README.md`'s own stated exit criteria, once
   `models.rs`/`views.rs`/`urls.rs`/`main.rs` all compile together for real, add
   `"examples/polls"` to the root `Cargo.toml`'s `members` list (currently just `["crates/*"]` —
   this needs to become `["crates/*", "examples/polls"]` or similar) so it's included in
   `cargo build --workspace`/`cargo test --workspace` going forward, matching the README's own
   "the polls example always compiling in CI" requirement from `PLAN.md`.
6. **Update `examples/polls/README.md`**: the "what's real vs. aspirational" section is now stale
   (written when Phase 2/3/4 didn't exist) — rewrite it to reflect actual current state: HTTP
   layer real (unchanged), ORM real (updated), auth/login-gating real (new), named-route reversal
   still aspirational, migrations still raw-SQL-in-tests (not real migration files) — don't just
   delete the file's honesty about what's still a stand-in, update it.

## What this task does NOT include

- `admin.rs` — stays fully aspirational (Phase 5, not started).
- Template rendering via `djangors-template` — plain `Response::html` + inline HTML/`format!`
  stays, matching the existing style already used and marked "REAL" in the current file; adopting
  templates here is a separate, later polish pass, not required by the DoD line this task closes.
- Named-route reversal (`reverse!()`) — stays a hardcoded path string with a comment explaining
  why, per the "real scope check" above.
- Real migration files — raw-SQL test setup, same as every other crate, per the "real scope check"
  above.
- Rate limiting on the new `login_view` — could wrap `ModelBackend` in
  `RateLimitedBackend::default_login_throttle`, and doing so is encouraged if it's a small,
  obvious addition once `login_view` exists, but is not the primary point of this task; use
  judgement, don't let it block finishing the core DoD requirement if something about wiring it up
  turns out non-trivial.
- Settings-driven secret-key/`DATABASE_URL` production hardening — dev-only wiring is enough here,
  same bar the rest of this project's example/test code already holds itself to.

## Required tests

A real integration test (new file, e.g. `examples/polls/tests/voting.rs`, or inline
`#[cfg(test)] mod tests` in `main.rs`/a test-support module — use judgement on which is cleaner
given how `main.rs` is structured) against real Postgres, raw-SQL `CREATE TABLE polls_question,
polls_choice` setup (mirroring `crates/djangors-auth/src/tests.rs`'s own precedent), driving
requests through the **real layered service** (not just calling handler functions directly —
the whole point of this task is proving the login gate actually works over the real serving path
built in [[4.15-middleware-stack-wiring]], mirror that doc's own `real_socket_layered_middleware_response`
test pattern: real `TcpListener`, real `TcpStream`, raw HTTP text), covering:

- Unauthenticated `POST /{question_id}/vote/` → `401 Unauthorized` (no vote recorded — verify the
  choice's `votes` count is unchanged in the DB afterward).
- `POST /accounts/login/` with correct credentials → redirect + a `Set-Cookie` for the session
  cookie present in the response.
- Authenticated `POST /{question_id}/vote/` (real session cookie from the login step above, plus
  the CSRF cookie/header dance `CsrfLayer` requires — reuse the same GET-then-POST-with-token
  pattern `crates/djangors-core/src/middleware.rs`'s own `test_end_to_end_router_csrf` test
  already demonstrates) → success, and the choice's `votes` count actually incremented by exactly
  1 in the database afterward.
- `GET /` and `GET /{question_id}/` remain accessible with no session/auth at all (proving the
  login gate is scoped to voting only, not the whole app).
