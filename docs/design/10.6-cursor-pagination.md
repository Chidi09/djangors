# 10.6 — cursor (keyset) pagination

## Scope

Item #8 of the architecture-parity initiative (see `/root/.claude/plans/concurrent-inventing-glacier.md`
for the full 4-item roadmap this belongs to; items 1-4 are already done — `docs/design/10.2`
through `10.5`). Today `crates/djangors-core/src/pagination.rs`'s `Paginator` is pure offset/page-
number arithmetic (`total_items`, `page_size`, `offset(page) = (page-1)*page_size`) — used
identically by `djangors-rest`'s `ViewSet`/`ScopedViewSet::list_with_config`
(`crates/djangors-rest/src/lib.rs`, `?page=N`, `QuerySet::limit().offset()`) and
`djangors-admin`'s changelist view. Offset pagination has two real, well-known problems this item
fixes: pages shift under concurrent inserts/deletes (row N can appear on two pages or vanish
entirely), and `OFFSET` gets slower as the offset grows on large tables. Zero cursor/keyset concept
exists anywhere in the workspace today (grep-confirmed).

**Deliberately excluded**: replacing offset pagination anywhere (this is purely additive, opt-in
per endpoint); `djangors-admin`'s changelist getting the same treatment (optional stretch only if
time remains — do REST first, and if you don't get to admin, say so plainly rather than leaving it
ambiguous whether it was attempted); bidirectional bidirectional bookkeeping beyond a simple
next/previous pair of opaque tokens.

## The real design

### `QuerySet<T>::after` — the actual keyset query (`crates/djangors-orm/src/queryset.rs`)

Read `filter_datetime_range` in full first (queryset.rs:144-169) — it is the **exact existing
precedent** for what you need to build: it pushes a raw `Expr::And(vec![Expr::Compare{field, op:
CompareOp::Gte, value}, Expr::Compare{field, op: CompareOp::Lt, value}])` directly onto
`self.filters`, using the crate-internal `Expr`/`CompareOp` types (which support `Gt`/`Lt`
directly), NOT the public equality-only `UnresolvedExpr`/`q!` macro path (`UnresolvedCompare` has
no `op` field — it's hardcoded to `=` and is the wrong tool here). Mirror that pattern exactly for
a new method:

```rust
/// Restricts results to rows strictly after the given keyset position, for stable
/// (non-shifting) pagination through an ordered result set. `order_field` must be the same
/// field the queryset is (or will be) ordered by. Builds a standard keyset predicate:
/// `order_field > cursor_value OR (order_field = cursor_value AND pk_field > cursor_pk)`
/// (reversed to `<`/`<` for descending order), using `pk_field` as a tiebreaker so rows with
/// duplicate `order_field` values are never skipped or repeated.
pub fn after(
    mut self,
    order_field: &'static str,
    order_value: Value,
    pk_field: &'static str,
    cursor_pk: i64,
    descending: bool,
) -> Result<Self, OrmError> {
```

Validate `order_field`/`pk_field` exist on `T::meta()` first (same validation `order_by` already
does at queryset.rs:182-200 — reuse that exact lookup logic, don't skip it, this is the same "never
let unvalidated field names reach generated SQL" concern `order_by`'s own doc comment already
states). Build the OR-expansion with `Expr::Or`/`Expr::And`/`Expr::Compare` (all already exist,
confirmed in `crates/djangors-orm/src/expr.rs:95-111`) using `CompareOp::Gt`/`Lt` and `CompareOp::Eq`
per the direction, exactly mirroring `filter_datetime_range`'s structure.

### Opaque cursor encoding (`crates/djangors-core/src/pagination.rs`)

```rust
pub fn encode_cursor(pk: i64, order_value: Option<&str>) -> String   // base64 of "pk|order_value" (or similar delimited/JSON form — your choice, just document it)
pub fn decode_cursor(cursor: &str) -> Result<(i64, Option<String>), CursorError>
```

`order_value` is a **string**, not a typed `Value` — reuse `djangors-rest`'s existing
`parse_filter_value::<M>(field_name, raw_val) -> Option<Value>` (lib.rs, already used for
`?field=value` query filtering) to turn the decoded string back into a typed `Value` for whichever
field the cursor is being used against, rather than inventing a second parsing mechanism.
`CursorError` should map cleanly to a 400-class `DjangorsError` at the call site (malformed
base64, wrong number of parts, etc. must never panic).

Add `CursorPage<T> { pub items: Vec<T>, pub next_cursor: Option<String>, pub previous_cursor:
Option<String> }` alongside `Paginator` — purely additive to this file.

### Wiring into `djangors-rest` (`crates/djangors-rest/src/lib.rs`)

Add a new field to `ViewSetConfig` (currently `filterable_fields`/`orderable_fields` only, both
`&'static [&'static str]`, `Default`-derived): `pub cursor_pagination: bool` (default `false` via
the existing `#[derive(Default)]`). In `list_with_config`, when `cursor_pagination` is true AND the
request has a `?cursor=` query param, decode it and call the new `.after(...)` instead of
`.limit().offset()`; when false (the default) or no `?cursor=` present, **behavior must be
byte-for-byte identical to today** — this must be a pure addition to the existing function, not a
restructuring. The ordering field to key the cursor on is whatever the current `?ordering=`
allowlist resolves to (reuse the existing allowlist-checking logic already in
`list_with_config` rather than adding a second one) — apply the same "reject anything not in
`orderable_fields`" discipline to a cursor request as already exists for `?ordering=`.

## Required verification

- **Duplicate ordering-value correctness**: seed rows where the chosen ordering field has ties
  (e.g. 3+ rows with an identical `view_count`), page through with cursors, and prove no row is
  skipped or repeated — this is the actual keyset bug class (offset pagination doesn't have this
  failure mode at all; keyset pagination does, specifically if the pk tiebreaker in `.after()` is
  ever dropped or misapplied).
- **Concurrent insert during pagination**: fetch page 1, insert a new row that would sort before
  the cursor position, fetch page 2 via the cursor, and prove no duplicate/skip occurs — this is
  the actual selling point over offset pagination; assert it directly with a real interleaved
  test, don't just assert the happy path.
- **Tampered/malformed cursor** (invalid base64, wrong part count, non-numeric pk) returns a clean
  400-class error, never panics.
- **Non-allowlisted ordering field** used to construct/decode a cursor is rejected the same way
  `?ordering=` already is.
- A full DB-backed integration test through `djangors-rest`'s HTTP layer (`Router::handle`/
  `viewset_routes`), not just a `QuerySet::after` unit test — mirror the existing
  `test_viewset_filtering_and_ordering_end_to_end` test's fixture-setup style
  (`crates/djangors-rest/src/lib.rs`) for a consistent pattern.
- Confirm the existing offset-pagination tests and `ViewSetConfig`'s current callers are
  completely unaffected. **Concretely**: the existing test construction at
  `crates/djangors-rest/src/lib.rs:2065-2068` (`ViewSetConfig { filterable_fields: ...,
  orderable_fields: ... }`) is a bare struct literal with no `..Default::default()` — adding a
  third field to `ViewSetConfig` WILL fail to compile at that call site (and any other such
  literal anywhere in the workspace, check `examples/` too) unless you either add
  `..Default::default()` there or add the new field explicitly. Grep for every
  `ViewSetConfig {` construction site and fix all of them, don't rely on the compiler error at
  only one location to reveal the others.
- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace` all clean.

what works and what doesn't, do not fabricate a finished result).
