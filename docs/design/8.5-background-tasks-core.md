# 8.5 — Background tasks core: `#[task]` macro + DB-backed queue + worker

## Scope

Continues Phase 8 after 8.1-8.4 (`djangors-rest` core/auth/filtering/OpenAPI,
`djangors-core` SSE/groups — commits `a3f2257`, `e77c3cd`, `1014ce1`, `9b24042`). PLAN.md's
"Background tasks" bullet bundles several substantial pieces (`#[task]` functions, a DB-backed
queue, a Redis backend, cron-syntax scheduled tasks, admin visibility) — this slice ships the
core: the `#[task]` macro, the DB-backed queue (Postgres `SELECT ... FOR UPDATE SKIP LOCKED`,
PLAN.md's own named default), a worker loop, and admin visibility.

**Deliberately excluded from this dispatch, left for a follow-up slice**: a Redis-backed queue
alternative, and cron-syntax scheduled/recurring tasks. Both are real, separable features on top
of a working core queue — shipping a half-working version of either alongside a rushed core queue
would be worse than a solid core + an honest "not yet" for the rest.

## Design: mirror the existing `#[derive(Model)]` → `inventory` pattern, don't invent a new one

`crates/djangors-macros/src/lib.rs` currently only has `#[proc_macro_derive]` macros (`Model`,
`Form`) — this is the first `#[proc_macro_attribute]` in the crate, but the *registration*
mechanism it should use already exists and is proven: `#[derive(Model)]` emits an
`inventory::submit! { ... }` call (read `crates/djangors-macros/src/model.rs` around line 718 for
the exact real pattern) collected via `inventory::collect!(ModelRegistration)` in
`crates/djangors-orm/src/meta.rs`. A `#[task]` function should register itself into an analogous
`inventory`-based `TaskRegistration` registry the same way, not build a new discovery mechanism.

```rust
// in a new djangors-tasks crate
pub struct TaskRegistration {
    pub name: &'static str,
    pub handler: fn(serde_json::Value) -> Pin<Box<dyn Future<Output = Result<(), TaskError>> + Send>>,
}
inventory::collect!(TaskRegistration);
```

```rust
// crates/djangors-macros/src/lib.rs — new attribute macro
#[proc_macro_attribute]
pub fn task(attr: TokenStream, item: TokenStream) -> TokenStream {
    // wraps an `async fn name(payload: T) -> Result<(), TaskError>` (T: DeserializeOwned) into:
    // - the original function, renamed or kept as an inner fn
    // - a generated wrapper `fn(serde_json::Value) -> BoxFuture<Result<(), TaskError>>` that
    //   deserializes the JSON payload into T and calls the real function
    // - an `inventory::submit! { djangors_tasks::TaskRegistration { name: "...", handler: ... } }`
    //   using the function's own name (or an explicit `#[task(name = "...")]` override) as the
    //   task name
}
```

**Read the real, current `#[derive(Model)]` macro implementation in full before writing this** —
the exact syntax for emitting an `inventory::submit!` from within a proc-macro (which crate path,
how the generated tokens are structured) is already solved there; copy the real pattern, don't
reinvent it.

## Part A — new crate `djangors-tasks` + `#[task]` macro

- `djangors-tasks` crate: `TaskRegistration`/`inventory::collect!`, `TaskError`, and the queue/
  worker machinery below.
- `djangors-macros`: the new `#[task]` attribute macro (Part of this same dispatch — attribute
  macros must live in the proc-macro crate, same as the existing derive macros).

A real `Task` model for the queue table:
```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_tasks", table_name = "djangors_task_queue")]
pub struct QueuedTask {
    #[djangors(primary_key, auto)]
    pub id: i64,
    #[djangors(max_length = 255)]
    pub task_name: String,
    pub payload: String, // JSON-encoded, stored as TEXT — check whether this ORM has a real
                          // JSONB column type via FieldKind::Json (it's listed in the enum) and
                          // use that instead of a plain TEXT column if it's actually wired up to
                          // a real Postgres column type end-to-end; if FieldKind::Json isn't
                          // fully implemented in the SQL-generation path yet, TEXT + manual
                          // serde_json::to_string/from_str is an honest, working fallback —
                          // verify which is true before choosing, don't assume either way
    pub status: String, // "pending" | "running" | "completed" | "failed" — a plain string is
                         // fine for v1, not worth a new enum-mapping FieldKind feature for this
    pub attempts: i32,
    pub max_attempts: i32,
    pub created_at: chrono::DateTime<chrono::Utc>,
    pub scheduled_at: chrono::DateTime<chrono::Utc>, // when it becomes eligible to run — set to
                                                       // now() for immediate enqueue, allows a
                                                       // simple "run later" capability even
                                                       // without full cron support
    pub error_message: Option<String>,
}

pub async fn enqueue(
    db: &djangors_db::Database,
    task_name: &str,
    payload: &impl serde::Serialize,
) -> Result<i64, TaskError>;
    // scheduled_at = now(), status = "pending", attempts = 0
```

## Part B — the queue claim + worker loop

The actual "DB-backed queue (Postgres SKIP LOCKED)" mechanism PLAN.md names specifically:

```rust
/// Atomically claims one pending, due task (status = 'pending' AND scheduled_at <= now()),
/// using `SELECT ... FOR UPDATE SKIP LOCKED` so multiple concurrent workers never claim the
/// same row — this is the real mechanism, not just naming it in a doc comment. Marks it
/// 'running' and increments attempts within the same transaction as the claim.
pub async fn claim_next_task(db: &djangors_db::Database) -> Result<Option<QueuedTask>, TaskError>;
```

Read `crates/djangors-db/src/database.rs`'s `transaction`/`transaction_with_isolation` methods
(already real, used elsewhere — e.g. `djangors-migrations::migrate()`) for the exact pattern to
build this on, since the claim-and-mark-running step must be atomic (a raw
`SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` followed by an `UPDATE` in the same transaction,
committed together — don't do the SELECT and UPDATE as two separate, non-transactional queries,
that would reopen the exact race condition SKIP LOCKED exists to prevent).

```rust
pub struct Worker {
    db: djangors_db::Database,
    poll_interval: std::time::Duration,
}
impl Worker {
    pub fn new(db: djangors_db::Database) -> Self; // reasonable default poll interval, e.g. 1s
    /// Runs forever: claim a due task, look it up in the `TaskRegistration` inventory registry
    /// by `task_name`, execute its handler with the deserialized payload, mark
    /// completed/failed (with attempts-vs-max_attempts retry logic: a failed task under
    /// max_attempts goes back to 'pending' for a later claim, matching Django-ecosystem-task-
    /// queue conventions like Celery's own retry behavior; a failed task at max_attempts stays
    /// 'failed' permanently), sleep poll_interval if nothing was claimed, repeat.
    pub async fn run(&self) -> !;
    /// Runs one claim-and-execute cycle without looping — the real, testable unit this is built
    /// from; `run()` is just this in a loop, don't duplicate the logic.
    pub async fn run_once(&self) -> Result<bool, TaskError>; // Ok(true) if a task was claimed
}
```

**A panicking task handler must not crash the worker** — mirror `Router::handle`'s own existing
panic-isolation discipline (spawning the handler call in a `tokio::spawn` and catching a JoinError/
panic, converting it to a `TaskError` and marking the task failed) rather than letting a panic
propagate out of `run_once`/`run`.

## Part C — admin visibility

Register `QueuedTask` with `djangors_admin::AdminSite` the normal way
(`site.register_with::<QueuedTask>(ModelAdminConfig { list_display: Some(&["id", "task_name",
"status", "attempts", "scheduled_at"]), list_filter: Some(&["status"]), ..Default::default() })`)
— real, working changelist/detail views with zero new admin mechanism, the same pattern
`djangors-contrib-flatpages`/`-redirects` already established.

## Required tests

- `#[task]` macro: a real task function registered via the macro, confirm it's discoverable via
  `inventory::iter::<TaskRegistration>()` under the expected name, and that calling its generated
  wrapper with a real JSON payload actually invokes the original function (assert an observable
  side effect, e.g. incrementing a counter behind a `Mutex`/`AtomicUsize`).
- `enqueue`/`claim_next_task`: a real test against Postgres proving a task enqueued is claimable
  once, and — this is the actual point of `SKIP LOCKED` — that two concurrent claim attempts
  (spawn two tasks both calling `claim_next_task` against the same queued row) never both succeed
  in claiming the same row (assert exactly one gets `Some`, the other gets `None` or a different
  row if a second one exists).
- `Worker::run_once`: a real end-to-end test — enqueue a task via a `#[task]`-registered handler,
  run one worker cycle, assert the task's status becomes 'completed' and the handler's side effect
  actually happened; a second test for a handler that returns `Err`/panics, asserting the task is
  marked 'failed' (or requeued to 'pending' if under `max_attempts` — test both the
  under-max-attempts requeue case and the at-max-attempts permanent-failure case).
