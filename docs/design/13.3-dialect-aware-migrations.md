# 13.3 — Dialect-aware migrations (`dj makemigrations`, `dj migrate`, plan/DDL)

## Why

13.1 made the ORM dual-backend and 13.2 did the same for production raw SQL. What is
still Postgres-only is the piece that *creates the schema in the first place*. Today a
SQLite project can run its ORM and its admin — but only against tables the user
hand-wrote. `dj migrate` panics on the first line, because the migration runner calls
`Database::pool()`, which panics on a SQLite handle.

This closes the `dj new` → SQLite → running admin story.

## Scope correction

The v0.5.0 notes said "plan.rs hardcodes `Dialect::Postgres` in two places". That was a
grep for `Dialect::Postgres` only, and undercounted. The real surface:

| File | What is Postgres-only |
| --- | --- |
| `crates/djangors-migrations/src/plan.rs` | 4 hardcoded `Dialect::Postgres` |
| `crates/djangors-migrations/src/lib.rs` | 5 `db.pool()` sites, `SERIAL`/`TIMESTAMPTZ`/`now()` history DDL, `= ANY($1)`, `db.transaction()` |
| `crates/djangors-migrations/src/operation.rs` | `ALTER COLUMN … TYPE … USING …::type` |
| `crates/djangors-cli/src/commands.rs` | 2 `db.pool()` sites, 1 hardcoded `Dialect::Postgres`, `db.transaction()` |
| `crates/djangors-db/src/database.rs` | `transaction()` **returns `Err` on SQLite** |

## The blocker: `Database::transaction` does not work on SQLite

`Database::transaction` and `transaction_with_isolation` take
`FnOnce(&'c mut PgConnection)`. On a SQLite handle they return
`DbError::TransactionFailed`. Every migration apply/rollback path runs inside one, so
nothing downstream can be ported until this is solved.

`Conn` already has the variants needed (`PgTx`, `SqliteTx`) — there is just no
`Database` method that hands one out. Add:

```rust
/// Run `f` inside a transaction on either backend.
pub async fn transaction_conn<F, T, E>(&self, f: F) -> Result<T, DbError>
where
    F: for<'c> FnOnce(&'c mut Conn<'c>) -> BoxFuture<'c, Result<T, E>> + Send,
    T: Send,
    E: Into<DbError> + Send,
```

Commit on `Ok`, roll back on `Err`, same shape as the existing method. **Do not change
or remove `transaction` / `transaction_with_isolation`** — they are public API with
passing tests (`test_transaction_commit`, `test_transaction_rollback`,
`test_transaction_isolation_levels`, restored in 13.1 review after a dispatch deleted
them). This is a new method alongside them.

## Dialect additions

The migration-history table DDL is currently one Postgres string in three places. Add
to `Dialect` in `crates/djangors-db/src/dialect.rs`:

```rust
/// Column type for an auto-incrementing integer primary key.
/// Postgres: `SERIAL PRIMARY KEY`; SQLite: `INTEGER PRIMARY KEY AUTOINCREMENT`.
pub fn auto_pk_type(&self) -> &'static str;

/// Column type for a timezone-aware timestamp.
/// Postgres: `TIMESTAMPTZ`; SQLite: `TEXT`.
pub fn timestamp_type(&self) -> &'static str;

/// SQL expression for the current timestamp.
/// Postgres: `now()`; SQLite: `CURRENT_TIMESTAMP`.
pub fn current_timestamp(&self) -> &'static str;

/// Infer the dialect from a database URL without connecting.
pub fn from_url(url: &str) -> Dialect;
```

`timestamp_type` is `TEXT` on SQLite, not `TIMESTAMP`: sqlx's SQLite `DateTime<Utc>`
codec reads and writes ISO-8601 **text**, and `TEXT` affinity is what stores that
losslessly. A `TIMESTAMP` declared type gets NUMERIC affinity and would try to coerce.

`from_url` must reuse the detection already inline at `database.rs:64`
(`sqlite://` prefix, `.sqlite`/`.db` suffix, `sqlite::memory:`) — extract that into
`from_url` and have `connect` call it, so there is exactly one definition. Do not write
a second, subtly different copy.

## Plan and DDL generation

Thread the dialect through instead of hardcoding it:

```rust
pub fn build_create_all_plan(dialect: Dialect) -> Result<Vec<Operation>, MigrationError>;
pub fn build_create_plan_from_snapshots(
    snapshots: &[ModelSnapshot],
    dialect: Dialect,
) -> Result<Vec<Operation>, MigrationError>;
```

`Operation::to_sql` becomes dialect-aware **and fallible**:

```rust
pub fn to_sql(&self, dialect: Dialect) -> Result<String, MigrationError>;
pub fn to_down_sql(&self, dialect: Dialect) -> Option<Result<String, MigrationError>>;
```

Fallible because `Operation::AlterColumnType` has **no SQLite equivalent**. SQLite's
`ALTER TABLE` cannot change a column's type; the real workaround is the 12-step
table-rebuild dance, which is out of scope here and cannot be done from a single
statement. Emitting the Postgres `ALTER COLUMN … TYPE … USING` string on SQLite would
produce a migration file that fails at apply time with a syntax error — a silent lie in
generated output. Instead add:

```rust
MigrationError::UnsupportedOnDialect { operation: String, dialect: String }
```

and return it. The plan builders never construct `AlterColumnType` today, so this
changes no working path — it makes an already-broken one report itself.

`CreateTable`, `AddColumn`, `DropColumn`, `RenameColumn`, `DropTable` need no SQL
change: SQLite supports `RENAME COLUMN` (3.25+) and `DROP COLUMN` (3.35+), and sqlx
bundles a newer libsqlite3 than both.

## Runner porting

`crates/djangors-migrations/src/lib.rs`:

- `ensure_history` / `migrate`: build the history DDL from `Dialect` helpers rather than
  the literal `SERIAL PRIMARY KEY … TIMESTAMPTZ … DEFAULT now()`.
- All 5 `db.pool()` sites → `db.conn()` with `Vec<BindValue>` and
  `dialect.placeholder(n)`, mirroring `crates/djangors-orm/src/queryset.rs`.
- `db.transaction(...)` → `db.transaction_conn(...)`.
- `rollback_from_dir` uses `WHERE name = ANY($1)` with a `Vec<String>` bind. **SQLite has
  no array binding.** Expand to `WHERE name IN (?, ?, …)` with one placeholder per name,
  built through `dialect.placeholder(n)` so Postgres still gets `$1, $2, …`. Guard the
  empty case — `IN ()` is a syntax error in both dialects; if `known_names` is empty
  there is nothing to roll back, so return `Ok(())` early.
- `query_as::<_, (String,)>` has no `Conn` equivalent — fetch rows and read column 0
  with `DbRow::try_string`.

`crates/djangors-cli/src/commands.rs`:

- `migrate_with_plan`: same treatment (history DDL, `db.conn()`, `transaction_conn`).
- `makemigrations` is **synchronous and never connects to a database** — it introspects a
  built binary and writes a `.sql` file. It gets its dialect from
  `Dialect::from_url(&std::env::var("DATABASE_URL").unwrap_or_default())`, defaulting to
  Postgres when unset so existing behaviour is unchanged.

## Scope

**In scope:** `djangors-db` (`dialect.rs`, `database.rs`), `djangors-migrations`
(`lib.rs`, `plan.rs`, `operation.rs`, `type_mapping.rs` if needed), `djangors-cli`
(`commands.rs`).

**Out of scope:** the `djangors-test` harness (still Postgres-only — its advisory-lock
isolation is inherently a Postgres mechanism); any `#[cfg(test)]` SQL in other crates;
re-doing 13.1/13.2 work.

## Definition of done

1. `cargo build --workspace --all-targets` clean.
2. `cargo clippy --workspace --all-targets -- -D warnings` clean.
3. `cargo test --workspace` — **all 401 currently-passing tests still pass**, none
   weakened, ignored, or deleted. Call sites may change where a signature changed;
   assertions may not.
4. A new test that runs the **real generated plan** against real in-memory SQLite:
   build a plan from model snapshots with `Dialect::Sqlite`, execute every
   `Operation::to_sql` against `sqlite::memory:`, then insert and read back a row.
   Asserting on the SQL string alone is not sufficient — the point is that SQLite
   accepts it.
5. A new test that `ensure_history` + a full `migrate_from_dir` cycle works on
   in-memory SQLite, including recording the applied migration name.
6. A new test that `Operation::AlterColumnType.to_sql(Dialect::Sqlite)` returns
   `UnsupportedOnDialect` rather than Postgres syntax.
7. A new test that `Database::transaction_conn` commits on `Ok` and rolls back on `Err`,
   on **both** backends.
