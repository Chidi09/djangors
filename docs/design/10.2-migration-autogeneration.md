# 10.2 — real migration autogeneration (and a newly-confirmed `dj migrate` bug fix)

## A real bug found while scoping this, not just a missing feature

`dj makemigrations` has always been documented as structurally blocked ("`dj` cannot introspect
model registrations across binary boundaries"). While scoping this slice, **the identical bug was
confirmed in `dj migrate` itself**, which nobody had flagged before: `commands::migrate()`
(`crates/djangors-cli/src/commands.rs`) runs inside the `dj` CLI's own process and calls
`djangors_migrations::migrate(&db)`, which calls `build_create_all_plan()` →
`djangors_orm::meta::all_registered_models()`. That function only ever returns whatever's
registered via `inventory::submit!` **within the calling process** — and `djangors-cli`'s own
`Cargo.toml` only depends on `djangors-auth`'s built-in models (User/Group/Permission/etc.), never
a real project's own business models. **This means `dj migrate`, run today against any real project
with custom models (e.g. a hypothetical `Question`/`Choice`, or a `Student`/`Course`), would create
tables for the framework's own built-in models only and silently miss every one of the project's own
models — a genuine functional bug**, not previously caught because `examples/polls`/`examples/school`
create their test tables via raw SQL directly in test setup, never through `dj migrate`, and 6.1's
own generated-project test scaffold has zero custom models to begin with.

**This slice fixes both `dj migrate` and `dj makemigrations` with the same real mechanism.**

## The real fix: run introspection inside the target project's own binary, not `dj`'s

`dj` (the CLee binary) can never see a project's registered models from its own process — that
constraint is real and doesn't go away. What CAN see them: **the project's own compiled binary**,
since that's the process that actually links in and executes every `#[derive(Model)]`-generated
`inventory::submit!` call for its own models. The fix: give every project generated by `dj new` a
lightweight, hidden introspection mode in its own binary, and have `dj migrate`/`dj makemigrations`
(running as the external `dj` process) invoke that mode via `cargo run` inside the target project's
directory, capturing its output, instead of trying to do the introspection themselves.

### Part A — the introspection hook in generated projects

Add a small, reusable function to `djangors-core` (or wherever makes sense architecturally — your
call, but it needs to be callable from every generated project's own `main.rs` without requiring
project authors to write custom code) that:
- Checks for a specific environment variable at the very start of the process, before any normal
  server startup — e.g. `DJANGORS_INTROSPECT_MODELS=1`.
- If set, serializes every entry from `djangors_orm::meta::all_registered_models()` to JSON
  (design the JSON schema yourself: table name, app label, ordering, every field's name/kind/
  nullability/max_length/default/db_index, every relation's kind/target/on_delete/related_name,
  `unique_together`) and prints it to stdout, then exits with code 0 — **before** connecting to a
  database or starting the server, so this mode works even without `DATABASE_URL` set.
- If not set, proceeds with normal `main()` behavior, completely unchanged.
- Wire this into `dj new`'s generated project template (`crates/djangors-cli/src/commands.rs`'s
  `new()` scaffolder) so every freshly-generated project gets this hook automatically, and update
  the currently-existing `examples/polls`/`examples/school` example apps' own `main.rs` files to
  add the same hook (since they predate this feature and should demonstrate it working end-to-end).

### Part B — `dj migrate` real fix

Change `commands::migrate()` to no longer call `djangors_migrations::migrate(&db)` directly.
Instead: `cd` into (or use `--manifest-path`/`cwd` for) the current project directory, run
`cargo run --quiet` with `DJANGORS_INTROSPECT_MODELS=1` set, capture the JSON model metadata from
stdout, build the same kind of `CREATE TABLE` plan `build_create_all_plan()` already builds — but
now driven by the captured JSON instead of a direct in-process `all_registered_models()` call — and
execute that plan against the database exactly as `djangors_migrations::migrate()` already does
(same tracking-table/`0001_initial` mechanism; reuse `Operation::to_sql()` and the existing
transaction-wrapped execution, don't reinvent that part). You may need to add a JSON-deserializing
counterpart to `ModelMeta` (or a plain intermediate struct) in `djangors-migrations` or
`djangors-orm` to reconstruct enough information from the captured JSON to drive
`build_create_all_plan`-equivalent logic — investigate the cleanest real design, don't just bolt
JSON parsing onto the existing in-process-only code path.

### Part C — real `dj makemigrations`

With the same introspection JSON available, `dj makemigrations` can now do real, incremental
schema-diffing:
- Store a schema snapshot per project (e.g. `migrations/.schema_snapshot.json` inside the generated
  project, checked into the project's own version control) representing the last-known model state.
- On `dj makemigrations`, capture the current introspection JSON the same way `dj migrate` does,
  diff it against the stored snapshot (new models → CREATE TABLE, removed models → DROP TABLE,
  changed fields on existing models → ALTER TABLE ADD/DROP/ALTER COLUMN — scope exactly how deep
  this v1 diff goes; a v1 that correctly detects "new model" and "new field on existing model" is
  already a huge improvement over the current total-block, even if it doesn't yet handle every
  possible field-type-change edge case — say explicitly what's in v1 scope vs. deferred).
- Write a new migration file (naming convention: `NNNN_description.sql` or similar — your choice,
  document it) containing the generated `ALTER`/`CREATE` SQL, and update the stored snapshot.
- `--check` flag (already parsed in the CLI, confirm its current behavior) should report whether
  there are undetected/unmigrated model changes without writing a file, matching Django's own
  `--check` semantics.
