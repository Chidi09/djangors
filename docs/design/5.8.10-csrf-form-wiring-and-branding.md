# 5.8 part 10 — wire CSRF into admin forms; default favicon; logo/accent-color overrides

**Status:** design, not yet dispatched. Follows 5.8.9 (CSRF core-middleware fallback, commit
`8a448db`). Combines three previously-separate roadmap items into one dispatch, per an explicit
instruction to move faster through the remainder of Phase 5 by batching related, individually
low-risk pieces instead of one hyper-granular slice per sub-feature. All three parts below are
admin-crate/template-only, each independently low-risk, and touch overlapping files
(`crates/djangors-admin/src/lib.rs`, `crates/djangors-admin/templates/admin/base.html`) — this is
why they're bundled rather than three separate dispatches.

**Do all three parts in one pass, but keep them clearly separated in the diff and in your final
summary** (which files/functions belong to which part), so review can verify each independently.

## Part A — wire `csrfmiddlewaretoken` into the admin's actual `<form>` elements

**Context:** 5.8.9 (core-only, `djangors-core`) taught `Router::dispatch`/`dispatch_debug` to
accept a `csrfmiddlewaretoken` form field as a fallback when the `X-CSRFToken` header is
missing — but **nothing in `djangors-admin` emits that field yet**, so the mechanism 5.8.9 built
is currently unreachable from any real admin page. This part closes that gap.

`crates/djangors-core/src/middleware.rs` already inserts `CsrfToken(pub String)` into every
unsafe-method request's extensions unconditionally (both the header-valid fast path and the new
deferred-fallback path from 5.8.9) — confirmed by re-reading `CsrfService::call` directly. It is
also inserted for safe (GET) requests too — re-verify this yourself by reading the full
`CsrfService::call` method before assuming it, since a GET-rendered form page needs the token
available even though GET requests never go through the unsafe-method branch at all (check
whether `CsrfLayer` sets it on GET too, or whether a different mechanism does — read the whole
function, don't guess from the unsafe-method branch alone).

`djangors_core::middleware::CsrfToken` is `pub` and `middleware` is `pub mod middleware` in
`djangors-core/src/lib.rs`, so it's reachable as `djangors_core::middleware::CsrfToken` from
`djangors-admin` without any new dependency.

**Four templates have a real `<form method="post">` that needs the hidden field:**

1. `crates/djangors-admin/templates/admin/render_form.html` — `<form method="post">` (add/change
   pages), rendered by `render_form()` (shared by `admin_add_get`, `admin_add_post`'s error
   branch, `admin_change_get`, `admin_change_post`'s error branch).
2. `crates/djangors-admin/templates/admin/delete_confirm.html` — rendered by `admin_delete_get`.
3. `crates/djangors-admin/templates/admin/bulk_delete_confirm.html` — rendered by
   `admin_bulk_delete_post`'s confirm-step branch (the one that renders HTML; its delete-step
   branch is a bare redirect, untouched).
4. `crates/djangors-admin/templates/admin/changelist.html` — the ONE shared `<form method="post"
   action="bulk-delete/">` used by both the bulk-delete button and (via `formaction`) the
   `list_editable` save button, rendered by `admin_changelist`.

**Do NOT touch**: `admin/index.html` and `admin/save_changelist_error.html` — re-verify by reading
both, but they contain no `<form>` at all (confirmed by direct read while writing this doc).
`admin_delete_post` and `admin_export_csv` — no template rendering, nothing to change.

**Pattern for each:**

- Add `csrf_token: String` to the relevant context struct (`RenderFormContext`,
  `DeleteConfirmContext`, `BulkDeleteConfirmContext`, `ChangelistTemplateContext`) — mirror exactly
  how `site_header`/`site_title` were added to these same four structs in 5.8.8, same style.
- In each handler (or in `render_form()` itself, since it's the one function shared by four call
  sites), extract the token: `req.ext::<djangors_core::middleware::CsrfToken>().map(|t| t.0.clone()).unwrap_or_default()`.
  **Use `unwrap_or_default()`, not `.expect(...)` or a hard error** — the admin's own existing test
  suite calls `router.handle(req)` directly (bypassing `CsrfLayer` entirely, confirmed via grep of
  the test module — every test builds `Request::new(...).with_extensions(...)` by hand without a
  `CsrfLayer` in front of it), so `CsrfToken` will be absent in every existing test's request
  extensions. An empty string is the correct, harmless fallback for that case (no `CsrfLayer`
  means no CSRF enforcement is happening for that request anyway — the hidden field being empty
  changes nothing observable). Do not change this test-bypass behavior; that's out of scope.
- `render_form()` gains one new parameter, `csrf_token: String` (or thread it via the existing
  `branding: &SiteBranding` parameter's call sites — your choice, whichever is the smaller diff;
  a plain extra `String` param mirrors how `branding` itself was added in 5.8.8, that's probably
  simplest) — update all 4 call sites.
- In each template, add **immediately after the opening `<form ...>` tag**:
  ```html
  <input type="hidden" name="csrfmiddlewaretoken" value="{{ csrf_token }}">
  ```
  Ordinary autoescaped interpolation (no `|safe`) — a token is an opaque generated string with no
  special HTML characters in practice, but there's no reason to bypass autoescape here and every
  reason not to (this is the one field on the page that's the most security-sensitive to get
  exactly right; don't introduce an unnecessary escape-bypass next to it).
- `changelist.html` has exactly one `<form>` — the hidden input goes right after
  `<form method="post" action="bulk-delete/">`, before the `<table>`. Do not add anything to the
  separate `<form method="get">` search box above it (GET requests don't need CSRF protection —
  re-verify this reasoning holds by confirming `CsrfService::call` only ever enters its
  unsafe-method branch for POST/PUT/PATCH/DELETE, never GET).

**Required new test**: add one new test (or extend an existing one, your judgment on which reads
better) that manually inserts a `CsrfToken` into a request's extensions before calling
`router.handle(req)` — mirror the exact `Extensions::new(); extensions.insert(...);
.with_extensions(extensions)` pattern every existing test in this file already uses for
`Session` (read `test_admin_index_endpoints` — or whatever the real first test in the file is
called — for the exact pattern) — then assert the rendered HTML body of each of the 4 pages above
contains `name="csrfmiddlewaretoken" value="<the exact token you inserted>"`. This is the proof
the wiring actually works, not just that it compiles.

**Also verify (do not skip)**: every one of the existing 11 `djangors-admin` tests still passes
with **zero assertion changes** — they never inserted a `CsrfToken` extension before, so
`csrf_token` will render as an empty string (`value=""`) in their output, which none of their
existing `.contains(...)` substring assertions should be sensitive to (re-confirm this by reading
each assertion, don't just assume). `examples/polls/tests/voting.rs` and
`examples/school/tests/admin_crud.rs` must also still pass with **zero modification** — both
already send a valid `X-CSRFToken` header on every POST (confirmed in 5.8.9), so they take the
unchanged fast path regardless of whether a hidden field is also now present in the form HTML
they're not even parsing.

## Part B — a real default favicon for the admin (using the asset set at
`crates/djangors-admin/static/branding/`)

A user-supplied favicon/PWA-icon set already lives at
`crates/djangors-admin/static/branding/` (7 files: `favicon.ico`, `favicon-16x16.png`,
`favicon-32x32.png`, `apple-touch-icon.png`, `android-chrome-192x192.png`,
`android-chrome-512x512.png`, `manifest.json` — committed, not tracked elsewhere). Today
`admin/base.html` has no `<link rel="icon">` at all, so the admin has no favicon in any browser.

**Why these can't be embedded as `data:` URIs in every page** (rejected approach, don't do this):
`android-chrome-512x512.png` alone is ~87KB, which base64-inflates to ~116KB — inlining the full
set into every single admin page response (already the case for every other embedded template
asset in this crate) would add well over 100KB to every page load with zero HTTP caching benefit
(a `data:` URI is part of the HTML document, not a separately cacheable resource). Serve them as
real files at real routes instead, exactly like any other favicon on the web.

**Why these can't be served through `AdminSite::urls()` itself** (rejected approach): routes
registered inside `AdminSite::urls()` are mounted at whatever prefix the embedding application
chooses (`Router::new().mount("/admin", site.urls())` in both example apps — could be anything),
and `AdminSite` has no way to know that prefix from inside itself. Favicons are conventionally
requested by browsers from the true domain root (`/favicon.ico`), regardless of what page the user
is currently on — mounting them under `/admin/...` would make `<link rel="icon" href="/favicon.ico">`
resolve correctly only if the app happens to mount the admin at `/`, which isn't guaranteed and
isn't how either example app does it today.

**The design**: a new, small, standalone piece of `djangors-admin`'s public API — a function that
takes a `Router` (the application's own top-level router, the same one `Router::new()...` builds
in each example's `urls()`) and returns it with 7 new `GET` routes chained on, serving the 7 files
from embedded bytes (`include_bytes!`, mirroring `ADMIN_TEMPLATES`'s `include_str!`-based
embedding rationale from 5.8.1 — a published library crate's assets can't be resolved from a
filesystem path relative to whatever downstream project depends on it):

```rust
pub fn favicon_routes(router: Router) -> Router {
    router
        .get("/favicon.ico", favicon_ico)
        .get("/favicon-16x16.png", favicon_16)
        .get("/favicon-32x32.png", favicon_32)
        .get("/apple-touch-icon.png", favicon_apple_touch)
        .get("/android-chrome-192x192.png", favicon_android_192)
        .get("/android-chrome-512x512.png", favicon_android_512)
        .get("/manifest.json", favicon_manifest)
}
```

Each handler is a one-liner along these lines (verify `Response::bytes`'s exact signature yourself
by reading `crates/djangors-staticfiles/src/serve.rs`'s `StaticFiles::serve` before using it — it
was `Response::bytes(status: StatusCode, content_type: &str, body: impl Into<Bytes>)` when this
doc was written, re-check since exact signatures matter):

```rust
async fn favicon_ico(_req: Request, _params: PathParams) -> Result<Response, DjangorsError> {
    Ok(Response::bytes(
        StatusCode::OK,
        "image/x-icon",
        include_bytes!("../static/branding/favicon.ico").as_slice(),
    ))
}
```

Repeat for each file (`image/png` for the four `.png` files, `application/json; charset=utf-8` for
`manifest.json`). Mirror `djangors-staticfiles/src/serve.rs`'s existing content-type table for the
exact string values rather than inventing new ones.

Before embedding `manifest.json`, **edit its `name`/`short_name` fields** from the current
placeholder text (`"Your App Name"` / `"Your App"` — read the file, it's genuinely a generic
placeholder as committed) to something that isn't obviously an unfinished template default —
`"Djangors"` for both is fine, since this manifest is served once per application (not
per-`AdminSite`, no branding context available at this layer — see Part C for why per-site
theming of this specific file is explicitly out of scope) and there's no mechanism in this slice to
make it dynamic per embedding application. Leave `theme_color`/`background_color` as `#ffffff`
(matches `base.html`'s own default `--bg`).

**Wire it into both example apps** — one line each, chaining `favicon_routes(...)` around the
existing `Router::new()...` chain in `urls()`:

- `examples/polls/src/urls.rs`
- `examples/school/src/urls.rs`

Read both files (short, already shown in this doc's context) before editing — the change is
wrapping the existing return expression, not restructuring it.

**Add `<link>` tags to `admin/base.html`'s `<head>`**, root-absolute paths (this only works
correctly because Part B's routes are mounted at the true domain root by the embedding app, not
under `/admin/` — that's the whole point of doing it this way instead of nesting under
`AdminSite::urls()`):

```html
<link rel="icon" href="/favicon.ico" sizes="any">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32x32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16x16.png">
<link rel="apple-touch-icon" href="/apple-touch-icon.png">
<link rel="manifest" href="/manifest.json">
```

**Required new tests**: build a bare `Router` via `favicon_routes(Router::new())` (no `AdminSite`
involved at all — these routes don't need one) and assert each of the 7 routes returns `200 OK`
with the expected `Content-Type` header and a non-empty body (comparing exact byte length against
`std::fs::metadata` of the source file is a reasonable, simple way to prove the right bytes are
embedded, or just assert `body().len() > 0` plus content-type if that's simpler — your call).

## Part C — optional per-site logo and accent-color overrides

Extends `SiteBranding` (added in 5.8.8: `site_header: String`, `site_title: String`) with two new
**optional** fields, following the exact same builder pattern already established:

```rust
#[derive(Clone)]
pub struct SiteBranding {
    pub site_header: String,
    pub site_title: String,
    pub logo_url: Option<String>,
    pub accent_color: Option<String>,
}
```

`Default` gets `logo_url: None, accent_color: None` alongside the existing two fields (re-verify
the exact current `Default` impl by reading it — line ~648 in `lib.rs` as of commit `8a448db`,
line numbers shift, search for `impl Default for SiteBranding` — before editing it).

Two new builder methods on `AdminSite`, same shape as `with_site_header`/`with_site_title`:

```rust
pub fn with_logo_url(mut self, url: impl Into<String>) -> Self {
    self.branding.logo_url = Some(url.into());
    self
}

pub fn with_accent_color(mut self, color: impl Into<String>) -> Self {
    self.branding.accent_color = Some(color.into());
    self
}
```

**Threading**: `logo_url`/`accent_color` only need to reach `base.html` (unlike `site_header`/
`site_title`, which are used by all 6 context structs) — but `base.html`'s variables come from
whichever child template's context is active (minijinja `{% extends %}` resolves variables from
the child's own render context, there's no separate "layout context"), so **every one of the 6
existing context structs still needs these two new fields**, mirroring exactly how
`site_header`/`site_title` were threaded through all 6 in 5.8.8 (same per-closure-clone
mechanism in `AdminSite::urls()`, same `branding.clone()` pattern — re-read 5.8.8's actual diff in
`git show ad23e39` if you need the exact mechanism refreshed, don't reinvent it). Use
`Option<String>` in the context structs directly (serde serializes `None` to a value minijinja's
`{% if %}` treats as falsy — confirm this is actually true by testing it, rather than assuming;
if it isn't, use `.unwrap_or_default()` to an empty string and check for emptiness in the template
instead, matching how `csrf_token` and other optional-ish strings are handled elsewhere in this
codebase).

**`base.html` template changes**:

1. Logo: change `<h1>{{ site_header }}</h1>` to conditionally prepend an `<img>`:
   ```html
   <h1>{% if logo_url %}<img src="{{ logo_url }}" alt="" class="site-logo">{% endif %}{{ site_header }}</h1>
   ```
   Add a small CSS rule to the existing `<style>` block: `.site-logo { height: 1.5em;
   vertical-align: middle; margin-right: 0.5rem; }`.
2. Accent color override: after the existing `<style>...</style>` block (which defines `--accent`
   inside `:root { ... }` and again inside the dark-mode media query), add a **third**, conditional
   `<style>` block that only renders when an override is set, applying to both light and dark
   (a per-site override should win regardless of OS color scheme — that's the point of an explicit
   site owner choice):
   ```html
   {% if accent_color %}<style>:root { --accent: {{ accent_color }}; }</style>{% endif %}
   ```
   Placed after the main `<style>` block so CSS cascade/source-order makes it win over both the
   light-mode default and the dark-mode media-query override without needing `!important`.

**Default (no builder calls) must render byte-identical to today** for the logo/`<h1>` line and
must not emit the second `<style>` block at all — re-verify this by reading the `{% if %}` you
write, and confirm no existing test asserts an exact match on the current `<h1>{{ site_header
}}</h1>` line that would break if the surrounding conditional syntax changes whitespace (read the
existing tests' assertions on this line first; if none check the `<h1>` line's exact bytes, this
is safely non-blocking, matching the standing pattern from every prior 5.8.x slice).

**Required new test**: one new test constructing an `AdminSite` with **both**
`.with_logo_url(...)` and `.with_accent_color(...)` set, asserting the rendered index (or any
templated) page contains both the `<img src="...">` and the override `<style>` block; plus
confirming a **default** `AdminSite` (no builder calls) contains neither — the negative case is
just as important as the positive one here, since it's the proof this is genuinely opt-in and
doesn't regress every existing site that hasn't adopted it.

## What NOT to touch in this slice

- `djangors-core` — nothing in this slice touches core middleware/routing again; 5.8.9 already
  did the CSRF core work, this slice only consumes it from the admin side.
- Per-`AdminSite` favicon customization — Part B's favicon set is one global default for the whole
  embedding application (served at the domain root, outside any `AdminSite`), not configurable
  per-site. A future slice could add a `favicon_url` override to `SiteBranding` mirroring
  `logo_url`, but that's explicitly out of scope here — don't build it preemptively.
- Full per-CSS-custom-property theming (separate `--bg`/`--fg`/`--border`/etc. overrides) —
  `accent_color` is deliberately the only override in this v1, matching this project's established
  pattern of shipping the single highest-leverage option first (5.8.8 did the same for
  `site_header`/`site_title` before anything more elaborate).
- History/audit log entries — unrelated, tracked separately, not part of this dispatch.
