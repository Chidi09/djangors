# 5.9 — School example (Phase 5 DoD)

**Status:** design, not yet dispatched. Follows 5.7.2 (admin permission enforcement, commit
`b9aed08`). Phase 5's own Definition of Done (`PLAN.md`): *"the school example runs its entire
back-office (students, enrollment, grades) through the admin with zero custom views; a
non-programmer can CRUD comfortably."* This example does not exist yet — `examples/polls` is the
only example app so far, and it has real custom views (voting) alongside its admin mount, so it
doesn't itself satisfy "zero custom views" for the CRUD surface. This slice builds the school
example as a genuinely new `examples/school` crate.

## Scope: three models, admin-only CRUD, one real end-to-end integration test — mirror `polls`' shape exactly

`examples/school` mirrors `examples/polls`' file layout and `Cargo.toml` shape file-for-file
(`src/models.rs`, `src/admin.rs`, `src/urls.rs`, `src/views.rs`, `src/lib.rs`, `src/main.rs`,
`tests/*.rs`) — there is no reason to invent a different structure for the second example app in
this repo. **The one deliberate difference from `polls`: `views.rs` contains ONLY `login_view`/
`logout_view`, copied close to verbatim from `polls/src/views.rs`'s own versions** (this
framework has no built-in login route anywhere in `djangors-admin` itself — confirmed via grep,
the only hits for "login" in that crate are unrelated `last_login` column references — so a
login/logout view is unavoidable infrastructure, not a "custom CRUD view" in the DoD's sense).
**No other custom views** — every actual Student/Course/Enrollment CRUD operation goes through
the generic admin, proving the DoD's "zero custom views" claim for real rather than by assertion.

## Models (`examples/school/src/models.rs`)

Three models — "students, enrollment, grades" per the DoD, modeled as `Student`, `Course`, and
`Enrollment` (which carries the grade directly, rather than a fourth trivial join-only model —
"enrollment" and "grade" are naturally one record: a specific student's registration in a
specific course, with a grade field that starts empty and gets filled in later). This still gives
three real admin-registered models with FK relations between them, enough to exercise
`list_display`/`search_fields`/`list_filter`/`date_hierarchy` for real in a genuinely different
domain than `polls`.

```rust
use chrono::{DateTime, Utc};
use djangors_macros::Model;
use djangors_orm::ForeignKey;

#[derive(Model, Debug, Clone)]
#[djangors(app = "school", table_name = "school_student")]
pub struct Student {
    #[djangors(primary_key, auto)]
    pub id: i64,

    #[djangors(max_length = 100)]
    pub first_name: String,

    #[djangors(max_length = 100)]
    pub last_name: String,

    #[djangors(max_length = 254, unique)]
    pub email: String,

    #[djangors(verbose_name = "date enrolled", db_index)]
    pub enrolled_date: DateTime<Utc>,

    pub is_active: bool,
}

#[derive(Model, Debug, Clone)]
#[djangors(app = "school", table_name = "school_course")]
pub struct Course {
    #[djangors(primary_key, auto)]
    pub id: i64,

    #[djangors(max_length = 20, unique)]
    pub code: String,

    #[djangors(max_length = 200)]
    pub name: String,

    pub credits: i32,
}

#[derive(Model, Debug, Clone)]
#[djangors(app = "school", table_name = "school_enrollment")]
pub struct Enrollment {
    #[djangors(primary_key, auto)]
    pub id: i64,

    #[djangors(foreign_key(on_delete = "cascade", related_name = "enrollments"))]
    pub student: ForeignKey<Student>,

    #[djangors(foreign_key(on_delete = "cascade", related_name = "enrollments"))]
    pub course: ForeignKey<Course>,

    #[djangors(verbose_name = "date enrolled", db_index)]
    pub enrolled_on: DateTime<Utc>,

    /// Empty string until a grade is recorded - kept as a plain (non-nullable)
    /// text field rather than `Option<String>` so it works with
    /// `list_editable` (5.6.5 scoped that feature to non-Boolean, non-null
    /// text/numeric fields; this keeps Enrollment usable with it without
    /// fighting that constraint - a blank grade is display-equivalent to "no
    /// grade yet" and is simpler than introducing a nullable text field this
    /// early).
    #[djangors(max_length = 5)]
    pub grade: String,
}
```

The `#[djangors(foreign_key(on_delete = "cascade", related_name = "...))]` attribute syntax
matches `examples/polls/src/models.rs`'s own `Choice.question` field exactly — mirror that, not
5.7.1's bare `ForeignKey<T>` fields (which omitted the attribute and got the default `on_delete`;
both compile, but matching `polls`' explicit style here is more idiomatic for a second
demonstration app meant to show realistic usage).

## Admin registration (`examples/school/src/admin.rs`)

Unlike `polls/src/admin.rs` (which just calls bare `site.register::<T>()` for both models — its
own doc comment even says customization is "a later Phase 5 feature," which is now stale since
5.6.x/5.7.x landed all of it), **this example should actually use the customization surface
that's been built**, since demonstrating a realistic, comfortable back-office is the entire point
of this DoD:

```rust
use crate::models::{Course, Enrollment, Student};
use djangors_admin::{AdminSite, ModelAdminConfig};

pub fn admin_site() -> AdminSite {
    let site = AdminSite::new();

    site.register_with::<Student>(ModelAdminConfig {
        list_display: Some(&["last_name", "first_name", "email", "is_active"]),
        search_fields: Some(&["first_name", "last_name", "email"]),
        list_filter: Some(&["is_active"]),
        date_hierarchy: Some("enrolled_date"),
        ..Default::default()
    });

    site.register_with::<Course>(ModelAdminConfig {
        list_display: Some(&["code", "name", "credits"]),
        search_fields: Some(&["code", "name"]),
        ..Default::default()
    });

    site.register_with::<Enrollment>(ModelAdminConfig {
        list_display: Some(&["student", "course", "grade", "enrolled_on"]),
        list_editable: Some(&["grade"]),
        date_hierarchy: Some("enrolled_on"),
        ..Default::default()
    });

    site
}
```

**Verify `list_display` including `"student"`/`"course"` (FK fields) still works** before relying
on it — `Model::field_values()` includes relation fields as the related id (per the 5.2-era "FK
display beyond raw id" ledger entry, this shows a raw integer, not the related object's name; that
is a known, already-documented limitation, not a bug to fix in this task). If listing a relation
field name in `list_display` doesn't actually work today (it should, since `field_values()`
includes them, but confirm with a real test rather than assuming), drop `"student"`/`"course"`
from `Enrollment`'s `list_display` and note the finding in the roadmap ledger instead of silently
reducing scope without saying why.

**`Enrollment`'s `grade` field as `list_editable`**: it's a `Char`-kind field (via `max_length`),
which 5.6.5 already supports for `list_editable`. This is a deliberate choice to exercise that
feature in a second app, not just `list_display`/`search_fields`.

## `urls.rs`, `views.rs`, `lib.rs`, `main.rs`, `Cargo.toml`

Copy `examples/polls`' versions near-verbatim, adjusted for the school app:

- `lib.rs`: `pub mod admin; pub mod models; pub mod urls; pub mod views;` (identical).
- `views.rs`: only `login_view`/`logout_view`, copied from `polls/src/views.rs` lines ~162-194 —
  same `LoginForm` struct, same `ModelBackend`/`djangors_auth::login`/`djangors_auth::logout`
  calls, same redirect behavior. Do not port `polls`' `index`/`detail`/`results`/`vote` view
  functions — this app has none of those.
- `urls.rs`:
  ```rust
  use djangors_core::Router;
  use crate::views;

  pub fn urls() -> Router {
      Router::new()
          .post("/accounts/login/", views::login_view)
          .post("/accounts/logout/", views::logout_view)
          .mount("/admin", crate::admin::admin_site().urls())
  }
  ```
  No `GET /` route at all — there is genuinely nothing to show outside the admin in this example,
  which is the whole point.
- `main.rs`: identical to `polls/src/main.rs` (same `DjangorsSettings::load()`, same
  `DATABASE_URL` handling, same `security_headers_layer`/`SessionLayer`/`csrf_layer` tower stack).
- `Cargo.toml`: same dependency set as `examples/polls/Cargo.toml`, `name = "school"`, `[[bin]]
  name = "school"`, adjust `description`.
- Add `examples/school` to the workspace `Cargo.toml`'s `members` list (check how `examples/polls`
  is registered there and mirror it).

## Required test: one real end-to-end integration test, socket-level, mirroring `polls`' style

`examples/polls/tests/voting.rs` is a **real socket-level integration test** — it spins up an
actual `TcpListener`, sends raw HTTP request strings, and parses `Set-Cookie` headers by hand
(`send_request`/`get_cookie_value` helpers, ~line 17-38) — deliberately exercising the *entire*
wired `tower::ServiceBuilder` stack (CSRF layer, session layer, security headers), not just the
bare `Router` the way `djangors-admin`'s own crate-internal tests use `router.handle()` directly.
`examples/school/tests/admin_crud.rs` should follow this exact same socket-level pattern — copy
the `send_request`/`get_cookie_value` helpers close to verbatim, and the `TcpListener::bind
("127.0.0.1:0")` + spawned-service setup (~line 134 onward) — since this is the only way to prove
the DoD's claim against the *real* deployed shape of the app (including CSRF), not a shortcut
around it.

Test flow (one `#[tokio::test]`, same `DB_MUTEX`-guarded, real-`CREATE TABLE`/`DROP TABLE`
Postgres style as `voting.rs`'s own test):

1. Create a superuser directly via the DB (same pattern `voting.rs` already uses for its staff
   user — `User { ..., is_staff: true, is_superuser: true, ... }.save(&db)`) — a superuser is the
   correct choice here (not a staff-with-specific-grants user): this test is proving the CRUD
   *mechanism* works end-to-end through real HTTP, not re-testing 5.7.2's permission logic (which
   already has its own dedicated coverage in `djangors-admin`'s test suite) — using `is_superuser:
   true` avoids needing to also seed `Permission`/`UserPermission` rows just to make this test
   pass, which would be unrelated setup noise for what this test is actually checking.
2. `POST /accounts/login/` with that user's credentials, capture the session cookie from
   `Set-Cookie` (mirror `voting.rs`'s exact cookie-extraction approach).
3. Using that cookie on every subsequent request: `POST /admin/school/student/add/` with a real
   student's fields → confirm a `302` redirect (success).
4. `POST /admin/school/course/add/` with a real course's fields → `302`.
5. `POST /admin/school/enrollment/add/` referencing the student/course ids just created → `302`.
6. `GET /admin/school/enrollment/` (changelist) → `200`, response body contains the enrollment
   just created.
7. `POST /admin/school/enrollment/save-changelist/` with `edit-{pk}-grade=A` → `302`, then GET
   the changelist again and confirm the grade shows `A` (exercises `list_editable` end-to-end,
   not just through `djangors-admin`'s own unit tests).
8. `POST /admin/school/student/{pk}/delete/` with `confirm=1` → `302`, then GET the student
   changelist and confirm that student no longer appears (exercises delete end-to-end).

This single test function is intentionally the whole DoD proof — "zero custom views" is proven by
the fact that every one of these operations goes through `/admin/...` routes this example never
defines a handler for itself (they all come from `AdminSite::urls()`).

## What NOT to touch in this task

- No changes to `examples/polls` (its stale admin.rs doc comment is not this task's concern).
- No changes to `djangors-admin`, `djangors-auth`, `djangors-orm`, or any other crate — this is a
  pure example-app slice, entirely new files plus one workspace `Cargo.toml` member addition.
- No FK-display-as-related-object's-`__str__` fix (the 5.2-era ledger item) — if `list_display`
  including `"student"`/`"course"` shows raw ids, that's expected and already documented, not a
  bug to fix here.
- No fieldsets/inlines/raw_id widgets for the `Enrollment` add form (student/course pickers stay
  plain integer-id text inputs, matching every other FK field in every existing admin add/change
  form today — this is a pre-existing, framework-wide limitation, not specific to this example).

## Verification commands (unchanged standing process)

`cargo fmt --all` → `cargo build --workspace --all-targets` → `cargo clippy --workspace
--all-targets -- -D warnings` → `cargo test --workspace`. Postgres test DB as above. Additionally
run `cargo test -p school` specifically and read its output directly (not just the workspace
summary) to confirm the new integration test's own pass/fail, the same way `voting.rs`'s test can
be run in isolation via `cargo test -p polls`.
