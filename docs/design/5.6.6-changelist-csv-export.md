# 5.6 part 6 — Changelist CSV export (v1)

**Status:** design, not yet dispatched. Follows 5.6.5 (`list_editable`, commit `27bce9e`). See
`docs/design/phase-5-roadmap.md` for full Phase 5 context.

## Scope revision from the roadmap's prior note — read this first

When 5.6.5 landed, the roadmap ledger predicted CSV export would be "a smaller lift" because it
could reuse 5.6.5's `formaction`-per-`<button>` pattern as a third bulk action on checked rows
("export selected as CSV"). **This design doc takes a different, simpler v1 instead: export
every row matching the *current* search/filter/order/date-hierarchy state — the whole filtered
queryset, ignoring pagination, not just the checked rows.** Reasoning: Django itself doesn't ship
CSV export as a built-in action at all (it's a common third-party recipe, not core Django), so
there's no parity pressure toward the selected-rows shape specifically. "Export what I'm
currently looking at" is a more broadly useful v1 than "export what I happened to check," is
simpler (a plain `GET` link carrying the current query string — no checkbox reading, no new
`<form>`/`formaction` wiring, no interaction with the bulk-delete/list_editable form at all), and
is still a real, useful feature on its own. Update the roadmap ledger to reflect this scope
decision when this lands. A future "export selected rows only" mode remains a reasonable add-on,
not required here.

## Two small, justified refactors first — both are prerequisites, not scope creep

The CSV export needs to run the *same* filtered-and-ordered query the changelist view already
builds (same search/`list_filter`/`date_hierarchy` state), just without `limit`/`offset`, and it
needs to read the *same* `?o=`/`?q=`/filter/`?year=`/`?month=`/`?day=` query parameters
`admin_changelist` already parses. Copy-pasting either block into a second ~60-80 line handler
would be exactly the kind of "a dispatch added a redundant thing that already exists elsewhere"
duplication this project's review process specifically watches for — so both get extracted into
shared code used by *both* the existing changelist handler and the new export handler. This
mirrors 5.6.2's own precedent (`build_query_string()` was introduced as a justified refactor of
5.6.1's hand-spliced link code once a second/third link site needed the same logic).

### Refactor 1: extract query-state parsing out of `admin_changelist`

`admin_changelist` currently parses `o`, `q`, the active `list_filter` values, and `year`/
`month`/`day` (plus computing `date_range` from them) inline, near its top. Extract this into a
new struct + free function in `crates/djangors-admin/src/lib.rs`:


`admin_changelist` calls this once near the top (where its own parsing currently lives), then
continues to use `state.order`, `state.search`, `state.filters`, `state.date_range` exactly where

drilldown-nav rendering and the link-forwarding at every existing link site) from `state.year`/
`state.month`/`state.day` — that derivation and all the link-building stays in
`admin_changelist`, only the *parsing* moves. **Do not change any existing behavior of
`admin_changelist` in this refactor** — this must be a pure extraction, verify by diffing
rendered output before/after is unchanged (the existing tests for 5.6.1-5.6.5 all exercise this
handler already and must all still pass unmodified).

## New `ModelAdmin` trait method: `export_csv_rows`

```rust
async fn export_csv_rows(
    &self,
    db: &djangors_db::Database,
    order: Option<&str>,
    search: Option<&str>,
    filters: &[(&'static str, bool)],
    date_range: Option<(chrono::DateTime<chrono::Utc>, chrono::DateTime<chrono::Utc>)>,
) -> Result<(Vec<&'static str>, Vec<Vec<String>>), DjangorsError>;
```

`DefaultModelAdmin` implements it using the three helpers above, with no `limit`/`offset`:

```rust
async fn export_csv_rows(
    &self,
    db: &djangors_db::Database,
    order: Option<&str>,
    search: Option<&str>,
    filters: &[(&'static str, bool)],
    date_range: Option<(chrono::DateTime<chrono::Utc>, chrono::DateTime<chrono::Utc>)>,
) -> Result<(Vec<&'static str>, Vec<Vec<String>>), DjangorsError> {
    let qs = self.build_filtered_queryset(order, search, filters, date_range)?;
    let items = qs
        .all(db)
        .await
        .map_err(|e| DjangorsError::Internal(e.to_string()))?;
    let columns = self.effective_columns();
    let rows = items
        .iter()
        .map(|item| self.row_values(item, &columns))
        .collect();
    Ok((columns, rows))
}
```

**No row cap in v1** — every matching row is loaded into memory and written to one buffered CSV
response, same "no cap yet" honesty this codebase already has elsewhere (e.g. bulk delete has no
upper bound on how many pks one request can carry). Note in the roadmap ledger as a deferred item
when this lands: a true streaming CSV response (write rows to the HTTP body as they're fetched,
instead of buffering the whole result set) is the real fix for very large tables, and isn't
needed for this framework's current scale.

## CSV formatting: minimal hand-rolled RFC 4180 escaping, no new dependency

Every field in this codebase's rows is already a plain `String` (`Model::field_values()`'s
`Display`-rendered form, the same strings the changelist table already shows). RFC 4180's escaping
rule is genuinely small: wrap a field in `"..."` if it contains a comma, a double-quote, or a
newline, and double any internal `"`. This codebase already hand-rolls small, well-scoped
escaping utilities rather than reaching for a crate for something this size (`html_escape`,
`url_encode_query_value`) — do the same here rather than adding a new `csv` dependency for a
one-function-sized problem. (Contrast with XLSX, a binary zip-based format — that genuinely needs
a real crate if it's ever added, and is explicitly still deferred, unaffected by this decision.)

```rust
fn csv_escape_field(s: &str) -> String {
    if s.contains(',') || s.contains('"') || s.contains('\n') || s.contains('\r') {
        format!("\"{}\"", s.replace('"', "\"\""))
    } else {
        s.to_string()
    }
}

fn rows_to_csv(columns: &[&'static str], rows: &[Vec<String>]) -> String {
    let mut out = String::new();
    out.push_str(
        &columns
            .iter()
            .map(|c| csv_escape_field(c))
            .collect::<Vec<_>>()
            .join(","),
    );
    out.push_str("\r\n");
    for row in rows {
        out.push_str(
            &row.iter()
                .map(|v| csv_escape_field(v))
                .collect::<Vec<_>>()
                .join(","),
        );
        out.push_str("\r\n");
    }
    out
}
```

(`\r\n` line endings are the RFC 4180-correct choice, not a stylistic pick — most spreadsheet
tools expect it.)

## New route + handler: `GET /{app}/{model}/export-csv/`

```rust
.get(
    "/{app:slug}/{model:slug}/export-csv/",
    move |req: Request, params: PathParams| {
        admin_export_csv(req, params, export_csv_admins.clone())
    },
)
```

Same closure-capture-a-cloned-vec pattern as every other admin route.

```rust
async fn admin_export_csv(
    req: Request,
    params: PathParams,
    admins: Vec<Arc<dyn ModelAdmin>>,
) -> Result<Response, DjangorsError> {
    require_staff(&req).await?;

    let app = params.get("app").unwrap_or("");
    let model = params.get("model").unwrap_or("");
    let admin = admins
        .iter()
        .find(|a| {
            let meta = a.model_meta();
            meta.app_label == app && meta.struct_name.to_lowercase() == model
        })
        .ok_or(DjangorsError::NotFound)?;

    let db = req
        .state::<djangors_db::Database>()
        .ok_or_else(|| DjangorsError::Internal("Database connection not found".to_string()))?;

    let state = parse_changelist_query_state(&req, admin.as_ref())?;
    let (columns, rows) = admin
        .export_csv_rows(db, state.order, state.search, &state.filters, state.date_range)
        .await?;
    let csv_body = rows_to_csv(&columns, &rows);

    let filename = format!("{}.csv", admin.model_meta().struct_name.to_lowercase());
    Ok(
        Response::bytes(StatusCode::OK, "text/csv; charset=utf-8", csv_body.into_bytes())
            .header(
                "Content-Disposition",
                &format!("attachment; filename=\"{}\"", filename),
            ),
    )
}
```

`Response::bytes(status, content_type, Vec<u8>)` + the builder-style `.header(name, value)`
(`crates/djangors-core/src/response.rs` ~line 40, ~line 99) are both pre-existing — no
`Response` API changes needed. `filename` is built purely from `struct_name` (a compile-time
`&'static str` from `ModelMeta`, never user input), so no header-injection concern in the
`Content-Disposition` value.

## Changelist page: one plain link, not a form button

In `admin_changelist`'s final HTML assembly, add an "Export CSV" link — **a plain `<a href>`,
not a third `<button formaction>`** (this doesn't touch the shared bulk-delete/list_editable
`<form>` at all, since it's a `GET` carrying the current view's query string, not a POST acting on
selected/edited rows):

```rust
let mut export_pairs = vec![("o", o), ("q", q)];
for &(f, val) in &active_filters {
    export_pairs.push((f, Some(if val { "true" } else { "false" })));
}
export_pairs.push(("year", year_str.as_deref()));
export_pairs.push(("month", month_str.as_deref()));
export_pairs.push(("day", day_str.as_deref()));
let export_link = build_query_string(&export_pairs);
let export_html = format!("<a href=\"export-csv/{}\">Export CSV</a>", export_link);
```

Place `export_html` right next to `pager_html` in the final `format!` (e.g. immediately before
the closing `</form>`, outside the `<table>` — it's not a per-row control). **This link always
renders** (unlike the Save button, which only appears when `list_editable` is configured) — CSV
export is a whole-model feature, not tied to any per-model config flag. It must carry the current
`o`/`q`/filters/`year`/`month`/`day` forward via `build_query_string`, same as every other
changelist link — the whole point of this feature is "export what I'm currently looking at," so
losing the current filter state on the link would silently break that.

## What NOT to touch in this task

- No "export selected rows only" mode (see scope revision at the top).
- No XLSX export, no new `csv`/spreadsheet crate dependency.
- No true streaming response — the whole CSV is buffered in memory first (see the row-cap note
  above).
- No changes to `bulk-delete/` or `save-changelist/` routes/handlers, and no changes to the
  shared `<form>` those two live in — CSV export is a separate `GET` link entirely.
- No behavior changes to `admin_changelist`/`changelist()` beyond the two refactors specified
  above — both are pure extractions, not opportunities to also fix or improve anything else
  noticed along the way. If something else looks wrong while doing this, note it, don't fix it
  here.
- No changes to `djangors-macros`.
