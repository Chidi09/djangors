# 5.8 part 1 — Introduce `djangors-template` into the admin (mechanism only, zero visual change)

**Status:** design, not yet dispatched. Follows 5.9 (school example, Phase 5 DoD met, commit
`259c448`). Begins 5.8 (theming/history/extension points), the one remaining unstarted top-level
Phase 5 bullet. See `docs/design/phase-5-roadmap.md`.

## Scope: prove the mechanism on one page, byte-for-byte-equivalent output, no visual redesign yet

Every admin page today is a hand-rolled `format!()` HTML string in `crates/djangors-admin/src/lib.rs`.
"Theming" (real CSS, dark mode, per-site branding) needs `djangors-template` wired in first —
but converting the rendering *mechanism* and doing a *visual redesign* are two separable risks,
and this slice deliberately only takes the first one. **This slice converts exactly one page
(`admin_index`, the smallest and simplest — a bare `<ul>` of links) to render through
`djangors-template` instead of `format!()`, producing output containing the exact same
substrings the current implementation does, so every existing test that asserts against
`admin_index`'s output keeps passing unmodified.** This proves the plumbing (crate dependency,
template file discovery, escaping, response construction) works correctly before any other page
is touched or any real visual design work happens — mirroring 5.6.6's own precedent of doing a
"prove this refactor changes nothing" pass before building the new feature on top of it. Real
theming (CSS, layout, dark mode, branding) and converting the remaining pages (changelist,
add/change forms, delete confirm) are follow-up slices (5.8.2+), out of scope here.

## The real problem this slice has to solve first: how does a *library* crate ship templates?

`djangors-template`'s `TemplateEngine::new(search_dirs: Vec<PathBuf>)` (`crates/djangors-template/src/engine.rs`
~line 22) only loads templates from filesystem directories, resolved at *runtime* relative to
wherever the search paths point. That's the right model for an *application*'s own
`templates/` directory (matches Django's `TEMPLATES['DIRS']`), but `djangors-admin` is a
*library* crate — once this project is actually published to crates.io (the explicit, tracked
end goal — see `[[git-authorship-prefs]]`/project memory on the cargo-login blocker), a
downstream consumer's build has no reason to have `djangors-admin`'s own source-tree `templates/`
directory sitting at some predictable filesystem path relative to *their* project. A filesystem
loader pointed at a path computed from `CARGO_MANIFEST_DIR` or similar would work inside this
monorepo during development and silently break for a real external consumer — exactly the kind
of thing that's easy to miss because it works fine in every test run inside this repo.

**The fix: embed the templates into the compiled binary at compile time via `include_str!()`**,
the same way Django itself ships its admin's templates as installed package data inside the
`django` wheel rather than expecting them to exist at some external path. `minijinja::Environment`
already supports this directly — `Environment::add_template(name: &'static str, source: &'static
str)` (confirmed in the `minijinja` crate's own source, `environment.rs` ~line 180) registers an
in-memory template from a `'static` string, no filesystem access at render time at all.
`djangors-template`'s `TemplateEngine` just doesn't expose this yet; it's a real, justified small
extension to a core crate, not scope creep for an admin-only task — any other crate that ever
wants to ship its own embedded templates will want the same constructor.

## `djangors-template`: new `TemplateEngine::from_embedded` constructor

`crates/djangors-template/src/engine.rs`, alongside the existing `new()`:

```rust
/// Create a new `TemplateEngine` from templates embedded at compile time
/// (e.g. via `include_str!`), rather than loaded from the filesystem at
/// runtime. This is what library crates that ship their own templates
/// (like `djangors-admin`) should use — `new()`'s filesystem `search_dirs`
/// only make sense for an application's own project-level template
/// overrides, not for templates that need to work correctly once this
/// crate is consumed as a published dependency with no guaranteed
/// filesystem layout relative to the consumer's project.
pub fn from_embedded(templates: &[(&'static str, &'static str)]) -> Result<Self, TemplateError> {
    let mut env = Environment::new();

    env.set_auto_escape_callback(|name| {
        if name.ends_with(".html") || name.ends_with(".htm") {
            AutoEscape::Html
        } else {
            AutoEscape::None
        }
    });

    for (name, source) in templates {
        env.add_template(name, source)
            .map_err(TemplateError::MiniJinja)?;
    }

    env.add_filter("date", filters::date);
    env.add_filter("floatformat", filters::floatformat);
    env.add_filter("pluralize", filters::pluralize);
    env.add_filter("truncatewords", filters::truncatewords);

    Ok(TemplateEngine { env })
}
```

(The filter-registration and auto-escape-callback blocks are identical to `new()`'s own — if
`new()`'s body has drifted at all from what's shown above by the time this is implemented, copy
its *actual* current filter list rather than this snippet, so both constructors stay in sync.)
Template names passed to `from_embedded` must still end in `.html`/`.htm` for auto-escaping to
apply (e.g. `"admin/index.html"`), exactly like the filesystem loader's own naming convention —
this is not a new rule, just confirming it still applies here.

## `djangors-admin`: new dependency, one template file, one converted handler

`Cargo.toml`: add `djangors-template = { path = "../djangors-template" }` as a direct dependency.

New file `crates/djangors-admin/templates/admin/index.html`:

```html
<ul>{% for m in models %}<li><a href="{{ m.href }}">{{ m.label }}</a></li>{% endfor %}</ul>
```

This must render **byte-for-byte identical output** to the current `admin_index`'s
`format!("<li><a href=\"{}/{}/\">{}.{}</a></li>", meta.app_label, meta.struct_name.to_lowercase(),
meta.app_label, meta.struct_name)` loop wrapped in `<ul>{}</ul>` — construct `href` as
`"{app_label}/{struct_name_lowercase}/"` and `label` as `"{app_label}.{struct_name}"` in Rust
before handing them to the template (matching exactly what the old `format!` produced), rather
than trying to replicate the string concatenation inside the Jinja template itself. Confirm the
rendered bytes match exactly (a real diff against the pre-change output, not just "looks similar")
before considering this done — any whitespace difference is a real regression here, not
acceptable "close enough," since the entire point of this slice is *zero* observable change.

In `crates/djangors-admin/src/lib.rs`, a module-level lazy-constructed engine:

```rust
static ADMIN_TEMPLATES: std::sync::LazyLock<djangors_template::TemplateEngine> =
    std::sync::LazyLock::new(|| {
        djangors_template::TemplateEngine::from_embedded(&[(
            "admin/index.html",
            include_str!("../templates/admin/index.html"),
        )])
        .expect("admin templates are compiled into the binary and must always be valid")
    });
```

The `.expect(...)` is deliberate, not a shortcut: these templates are compile-time constants
shipped with the crate, not user-supplied or runtime-loaded content — if `from_embedded` ever
fails here, that's a bug in this crate that should fail loudly at first use (effectively a
"this should be caught by CI/tests," not a runtime condition a real deployment could hit from
valid input), the same reasoning `ModelMeta`-derived `panic!`s in `register_with` already use for
programmer errors vs. `Result` for real runtime failure modes.

`admin_index` (`crates/djangors-admin/src/lib.rs`, already updated by 5.7.2 to filter by `view`
permission) changes its rendering tail only — everything before the final HTML construction
(the `require_staff`/`db`/per-model `has_perm` filtering loop) is unchanged:

```rust
#[derive(serde::Serialize)]
struct IndexModelLink {
    href: String,
    label: String,
}

// ... existing require_staff / db / permission-filtering loop stays exactly as-is,
// but instead of pushing directly into a `body: String`, push into:
let mut models = Vec::new();
// (inside the existing loop, replacing the `body.push_str(&format!(...))` call:)
models.push(IndexModelLink {
    href: format!("{}/{}/", meta.app_label, meta.struct_name.to_lowercase()),
    label: format!("{}.{}", meta.app_label, meta.struct_name),
});

// ... after the loop, replacing `Ok(Response::html(StatusCode::OK, format!("<ul>{}</ul>", body)))`:
#[derive(serde::Serialize)]
struct IndexContext {
    models: Vec<IndexModelLink>,
}
djangors_template::render(&ADMIN_TEMPLATES, "admin/index.html", IndexContext { models })
```

`djangors_template::render` already returns `Result<Response, DjangorsError>` matching
`admin_index`'s own return type exactly (`crates/djangors-template/src/render.rs`) — no error
mapping needed at this call site.

## What NOT to touch in this task

- **No other page converted** — `admin_changelist`, `admin_add_get`/`post`,
  `admin_change_get`/`post`, `admin_delete_get`/`post`, `admin_bulk_delete_post`,
  `admin_save_changelist_post`, `admin_export_csv` all keep their existing `format!()` HTML
  exactly as-is. One page, proven correct, is the whole point of this slice.
- **No visual/CSS changes, no layout, no dark mode, no branding** — the rendered HTML must be
  behaviorally and textually equivalent to today's output, not "similar." Real theming is a later
  5.8.x slice, once this mechanism is proven safe to build on.
- **No changes to `ModelAdmin`, `AdminSite`, `ModelAdminConfig`, or any route/handler other than
  `admin_index`'s own rendering tail.**
- **No changes to `djangors-macros` or the ORM.**
- Do not add a base/layout template, `{% extends %}`, or any Jinja templating feature beyond a
  single `{% for %}` loop — there's exactly one page here, no shared layout to factor out yet.

## Required tests

1. New test in `crates/djangors-template/src/engine.rs`'s existing `#[cfg(test)] mod tests`
   (mirror its current test style, e.g. how the filesystem-loader constructor is tested there
   already): `TemplateEngine::from_embedded(&[("hello.html", "Hello {{ name }}!")])` then
   `.render("hello.html", context)` produces the expected escaped output, proving the new
   constructor works and auto-escaping still applies (e.g. a `name` value containing `<script>`
   renders escaped, not raw — this is the one place in this slice worth actually exercising
   escaping, since `admin_index`'s own real content has nothing user-controlled to escape).
2. `crates/djangors-admin/src/lib.rs`'s existing `test_admin_index_endpoints` (and the
   `admin_index`-touching assertions inside 5.7.2's `test_admin_permissions_enforcement`) must
   **pass completely unmodified** — do not touch either test's assertions. If either fails after
   this change, the template's output doesn't actually match the old `format!()` output byte-for-
   byte, which is a real bug in this task, not something to fix by loosening the test.
