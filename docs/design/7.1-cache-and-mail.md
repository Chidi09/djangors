## Part A — `djangors-cache` (new crate)

Create `crates/djangors-cache/` (picked up automatically by the workspace's `members = ["crates/*",
...]` glob — no root `Cargo.toml` edit needed, confirm this by reading it, don't assume). Mirror the
existing crate boilerplate conventions exactly — read `crates/djangors-mail/Cargo.toml` for the
`[package]` section shape (`version.workspace = true`, etc.) and copy it.

**Core trait**, `Cache`:
```rust
#[async_trait::async_trait]
pub trait Cache: Send + Sync {
    async fn get(&self, key: &str) -> Result<Option<Vec<u8>>, CacheError>;
    async fn set(&self, key: &str, value: Vec<u8>, ttl: Option<Duration>) -> Result<(), CacheError>;
    async fn delete(&self, key: &str) -> Result<(), CacheError>;
    async fn get_or_set<F, Fut>(&self, key: &str, ttl: Option<Duration>, f: F) -> Result<Vec<u8>, CacheError>
    where
        F: FnOnce() -> Fut + Send,
        Fut: std::future::Future<Output = Result<Vec<u8>, CacheError>> + Send;
}
```
(Raw `Vec<u8>` values, not generic `T: Serialize` — keeps the trait object-safe (`dyn Cache`,
matching how `dyn MailBackend`/`dyn AdminSite`-adjacent traits are used elsewhere in this
codebase) and lets callers choose their own serialization; provide a small `CacheExt` extension
trait or free functions for the common `T: Serialize + DeserializeOwned` JSON-via-`serde_json`
case, layered on top of the raw byte trait, not replacing it.)

**Backends**:
1. **`InMemoryCache`** (default, zero external services needed): use the `moka` crate (async,
   TTL-aware, widely-used, no reasonable hand-rolled equivalent provides real per-entry TTL +
   eviction correctly) — confirm the current stable `moka` version and add it to
   `crates/djangors-cache/Cargo.toml`.
2. **`DatabaseCache`**: reuses the existing `djangors_db::Database` connection (no new
   infrastructure dependency for testing — this environment already has Postgres wired up
   everywhere else). A simple `djangors_cache_entries` table (`key TEXT PRIMARY KEY, value BYTEA
   NOT NULL, expires_at TIMESTAMPTZ`), lazily created the same `CREATE TABLE IF NOT EXISTS` way
   `djangors-migrations`' own tracking table already does (read `djangors_migrations::migrate()`
   for the exact pattern to mirror). `get` must check `expires_at` and treat an expired row as a
   miss (deleting it lazily is fine, don't require a background sweeper for v1).
3. **`RedisCache`**: use the `redis` crate (async, `tokio-comp` feature). **This environment may
   not have a Redis server available for testing** — check for a `REDIS_URL` env var convention
   (mirroring `DATABASE_URL`) and if a real Redis isn't reachable, mark `RedisCache`'s own
   connectivity-requiring tests `#[ignore]` (mirroring how `#[ignore]`d tests are already used for
   slow/environment-dependent cases elsewhere in this project, e.g. `djangors-cli`'s end-to-end
   tests) rather than making the whole crate fail to test. Gate the `redis` dependency behind a
   Cargo feature (e.g. `feature = "redis"`, not enabled by default) so a project that never wants
   a Redis dependency doesn't pull it in transitively — confirm this is a reasonable, idiomatic
   pattern (optional dependency + matching feature flag) before implementing.

**Per-view middleware**: a `CacheLayer` (`tower::Layer`, mirroring the exact shape of
`SecurityHeadersLayer`/`CsrfLayer` in `crates/djangors-core/src/middleware.rs` — read that file for
the real pattern to copy) that caches full GET responses keyed by request path + query string, with
a configurable TTL, skipping any request carrying a `Set-Cookie`-relevant session (don't cache a
response that set a session cookie meant to be unique per-request — check what's actually
observable from a `Response` at the point this layer would run, and if there's no clean signal to
avoid caching authenticated/session-bearing responses, restrict this v1 to only caching responses
when explicitly opted in via a marker (e.g. a special response extension/header the handler sets),
not a blanket "cache every GET," which would be a real security footgun default-caching someone's
personalized page — flag this decision explicitly in your final report, don't silently ship a
naive blanket-cache-everything default.

**Template fragment caching**: not a new minijinja template-tag syntax (`{% cache %}`) — that
needs extending minijinja's custom-tag machinery, a materially bigger lift or a real reasonability
question to check first (does the version of minijinja already a dependency support custom block
tags at all? verify before assuming). **Deliberate v1 scope**: a plain Rust helper function callable
from view code — `cache.get_or_set_fragment(&cache, key, ttl, || render_a_template(...))` — using
the `get_or_set` trait method already designed above. This is a real, useful, honest v1; note the
real `{% cache %}` template-tag syntax as a ledgered future enhancement if minijinja doesn't
trivially support it.

**Required tests**: `InMemoryCache` and `DatabaseCache` both need real tests for get/set/delete/
get_or_set/TTL-expiry (use a short TTL like 50ms + a sleep past it, matching how other short-TTL
tests in this codebase are written, if any exist — check). `RedisCache`'s tests may be `#[ignore]`d
per above. `CacheLayer` needs a real test proving a second identical GET request is served from
cache (not re-executing the handler — have the handler increment a shared counter and assert it's
only called once across two requests).

## Part B — complete `djangors-mail`

Extend `crates/djangors-mail/src/lib.rs` in place — the existing `Message`, `MailError`,
`MailBackend`, `ConsoleBackend` all stay (don't rewrite what's already correct). **The one existing
caller** (`crates/djangors-auth/src/lib.rs`'s `request_password_reset`, confirmed by reading it
directly — constructs `Message { to, from, subject, body }` with a positional/named struct literal
using all four current fields) will need a small, explicit update to include whatever new field(s)
you add to `Message` (e.g. `html_body: None`) — do this update yourself as part of this dispatch,
verify `djangors-auth`'s existing password-reset tests still pass unmodified afterward.

Add:
1. **`html_body: Option<String>`** field to `Message` (plain-text `body` stays required and is
   always sent as the `text/plain` part; when `html_body` is `Some`, backends that support it send
   a proper `multipart/alternative` MIME message with both parts — this is genuinely what "HTML+text
   multipart helpers" means, not just an extra unused field).
2. **`SmtpBackend`**: use the `lettre` crate (the standard, actively-maintained Rust SMTP client
   with TLS support) — confirm its current stable API shape by checking its actual documentation/
   source rather than guessing method names from memory, since mail-crate APIs are exactly the kind
   of thing that's easy to misremember. Constructed from a host/port/credentials config (mirror
   `djangors_db::config::DatabaseConfig`'s builder-style shape for consistency:
   `SmtpConfig::new(host).port(587).credentials(user, pass).use_tls(true)` or similar — use your
   judgment on the exact builder shape, consistency with `DatabaseConfig`'s pattern matters more
   than matching this exactly). Real TLS (`lettre`'s built-in `Tls`/`Tokio1Executor` support) —
   don't ship a backend that silently sends plaintext SMTP when TLS was requested but unavailable;
   fail with a clear `MailError` instead.
3. **`FileBackend`**: writes each sent message to a new file in a configured directory (mirroring
   Django's own `filebased.EmailBackend` — one file per message, human-readable, useful for local
   dev without a real mail server). Include enough fields (to/from/subject/both bodies) in the
   written file to be genuinely useful for inspection.
4. **`InMemoryBackend`** (test backend, Django's own `locmem` equivalent): collects every sent
   `Message` in a `Vec<Message>` behind a `Mutex` (or `RwLock`), with a way to inspect what was
   "sent" after the fact (`fn sent_messages(&self) -> Vec<Message>` or similar) — this is what lets
   a test assert "an email was sent to X with subject Y" without a real mail server or even the
   console/file side effects, useful for `djangors-test`'s own future fixture story (not built here,
   just don't preclude it).

**Required tests**: `FileBackend` and `InMemoryBackend` get real tests (write-then-read-back for
File, send-then-inspect for InMemory). `SmtpBackend` cannot be fully tested without a real SMTP
server — check whether one is reachable in this environment (a local `mailhog`/`smtp4dev`-style
test server, or skip); if none is available, at minimum test `SmtpConfig`'s construction/validation
logic directly (e.g. that an empty host is rejected) without requiring a live connection, and mark
any connectivity-requiring test `#[ignore]`, mirroring the `RedisCache` approach above. The
`html_body` multipart construction logic itself (does it actually produce a well-formed
`multipart/alternative` MIME structure?) should be tested by inspecting the raw message bytes
`lettre` would produce, if that's inspectable without a live send — check `lettre`'s API for a way
to build the message and serialize it without actually connecting/sending, which is the right way
to test MIME structure correctness without needing network access.
