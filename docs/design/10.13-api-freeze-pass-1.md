## The real work

For each of the 3 crates, go through every `pub` top-level item (`pub fn`, `pub struct`, `pub
trait`, `pub enum`, `pub const`, `pub static`, `pub mod`, `pub type`) and classify it as one of:

1. **Keep public as-is** — genuinely part of the intended stable API surface.
2. **`pub(crate)`** — an internal implementation detail that's currently fully public by mistake,
   with no legitimate reason for downstream code to use it directly.
3. **`#[doc(hidden)]`** — needs to stay technically `pub` (e.g. used across crate boundaries
   internally, or by generated macro code) but should not appear as part of the documented public
   contract.
4. **Flag for a human decision** — genuinely ambiguous; add a `// FREEZE-REVIEW:` comment
   explaining the ambiguity rather than guessing. Do not silently leave ambiguous items
   unclassified — every item must get one of these four outcomes.

**Four specific items were already identified during investigation and must be resolved, not
left for the flag-for-decision bucket** (these have a clear right answer, use it):

- `djangors_core::html_escape` (`crates/djangors-core/src/lib.rs`) → `pub(crate)`. It's only ever
  used internally by `debug_page.rs`. Confirm this is still true (grep for external usage first,
  including in `examples/`) before changing it.
- `djangors_core::debug_page::render_debug_page` → add `#[doc(hidden)]`. Its own doc comment
  already says "must only be served when `debug = true`" — this is security-sensitive and
  currently has zero compiler/doc-level guard against a downstream project calling it directly by
  mistake. Also check `render_production_error_page` in the same file — if it has the same
  dev/security sensitivity, apply the same treatment; if it's genuinely meant to be callable
  directly (e.g. by a project implementing a custom `ErrorRenderer`), leave it public but say why
  in your summary.
- `djangors_orm::queryset::prefetch_related` → keep public, but you must write a one-line
  rationale in your summary confirming it's intentionally first-class (it's the main
  reverse-relation batch-loading API, documented in `docs/src/guides/orm.md` — check this before
  writing the rationale, don't assume).
- `djangors_core::signals` (`BoxedFuture`, `CallbackFn<T>`, the static `REQUEST_STARTED`/
  `REQUEST_FINISHED` instances) → make a deliberate, stated decision (sealed vs. open) rather than
  leaving it as an implicit "whatever's already public stays public" non-decision. Read the
  module in full first; either choice is defensible, but it must be an explicit call with a
  one-line rationale in your summary, not silence.

For every other item beyond these four, use your own judgment per the 4-way classification above,
but be conservative: when genuinely unsure, use bucket 4 (flag), don't guess at bucket 2 or 3 for
something that might actually be load-bearing for existing users (the example apps, guides, or
tutorials referencing it is a strong signal it should stay public).
