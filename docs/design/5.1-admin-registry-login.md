# Design 5.1 — AdminSite + registry, auto-URLs, `is_staff`-gated login (Phase 5 part 1)

**Status:** draft, pre-implementation. First slice of Phase 5 (`PLAN.md`: "AdminSite + registry;
auto-URLs; login gated by `is_staff`."). `djangors-admin` (`crates/djangors-admin/`) is currently a
pure empty placeholder (`Cargo.toml` + a 4-line `lib.rs`) — this is the first real code in it.
Phase 5 as a whole is large (changelist, change forms, inlines, history, theming — each its own
future design doc); this task is deliberately narrow: a model registry, one auto-generated admin
index route listing registered models, and a login gate. **No CRUD, no changelist, no change
forms yet** — those are separate, later PLAN.md bullets with their own design docs once this
foundation lands.

## Real building blocks to use (read before writing code)

- `djangors_orm::meta::{Model, ModelMeta}` (`crates/djangors-orm/src/meta.rs`): every real model
  (`djangors-auth`'s `User`, `examples/polls`'s `Question`/`Choice`) already implements `Model`
  with `fn meta() -> &'static ModelMeta`. `ModelMeta` is `Copy`, holds `struct_name`, `app_label`,
  `table_name`, `fields`, etc. — everything needed to list a registered model by name, nothing
  more, for this v1.
- `djangors_auth::{Auth, User}` (`crates/djangors-auth/src/lib.rs`): the real login-gating
  mechanism, already built and proven in `examples/polls`. `User` (the concrete, default
  `AuthUser` impl) has a public `is_staff: bool` field.
- `djangors_core::{Router, extract::FromRequest, DjangorsError}`: same real router/extractor
  pattern used throughout `examples/polls`.

## Scope decision: don't touch `AuthUser` trait for `is_staff`

`AuthUser` (the generic trait apps can implement instead of using the built-in `User`) only
exposes `is_active()` today, not `is_staff()` — extending it would be the "textbook" generic
approach but is unnecessary scope for this task and touches `djangors-auth` again for a feature
only the admin needs. **v1 scope: the admin login gate is hardcoded to `Auth<djangors_auth::
User>`** (the concrete type), checking `.is_staff` as a plain field read after extraction succeeds.
Document this as a deliberate v1 constraint (admin only works with the built-in `User` model for
now, not a custom `AuthUser` impl) — matches this project's established pattern of picking the
narrowest correct thing and noting what's deferred, same shape as sessions shipping signed-cookie
only or rate limiting being single-process only.

## What this task builds

```rust
// crates/djangors-admin/src/lib.rs

/// A single registered model in the admin site. v1: just enough to list it
/// by name on the admin index page. No changelist/CRUD yet.
pub trait ModelAdmin: Send + Sync {
    fn model_meta(&self) -> &'static djangors_orm::meta::ModelMeta;
}

/// Blanket impl so any real Model can be registered with zero boilerplate:
/// `site.register::<Question>()` should just work without a caller having
/// to hand-write a ModelAdmin impl for the common case (Django's own
/// `admin.site.register(Question)` with no custom ModelAdmin also works
/// this way - only customization requires a real ModelAdmin impl, deferred
/// to a later phase-5 task once changelist/list_display exist to customize).
struct DefaultModelAdmin<M: djangors_orm::meta::Model>(std::marker::PhantomData<M>);
impl<M: djangors_orm::meta::Model + Send + Sync> ModelAdmin for DefaultModelAdmin<M> {
    fn model_meta(&self) -> &'static djangors_orm::meta::ModelMeta { M::meta() }
}

pub struct AdminSite {
    registry: std::sync::Mutex<Vec<Box<dyn ModelAdmin>>>,
}

impl AdminSite {
    pub fn new() -> Self { ... }

    /// Register a model with the default (no customization) ModelAdmin.
    pub fn register<M: djangors_orm::meta::Model + Send + Sync + 'static>(&self) {
        // push a DefaultModelAdmin<M> into the registry, locked
    }

    /// Build a Router mounted at whatever prefix the caller chooses (the
    /// caller does `.mount("/admin", site.urls())`, matching Router::mount's
    /// existing real API - don't hardcode "/admin" inside this crate).
    ///
    /// v1: exactly one real route, GET "/" (relative to wherever it's
    /// mounted) - the admin index, listing every registered model's
    /// app_label/struct_name, gated behind Auth<User> + is_staff. Anyone
    /// authenticated but not staff gets 403 (DjangorsError doesn't have a
    /// Forbidden variant yet - check crates/djangors-core/src/error.rs; if
    /// it's missing, adding it is small/precedented, same as Unauthorized
    /// was added in part 4b - follow that exact pattern: add the variant,
    /// the Display arm, the status_code() arm mapping to
    /// StatusCode::FORBIDDEN, the into_response() arm). Anyone not
    /// authenticated at all gets the existing Unauthorized (401) from
    /// Auth<User>'s own extraction failure, unchanged.
    pub fn urls(&self) -> djangors_core::Router {
        djangors_core::Router::new().get("/", /* index handler closing over self's registry snapshot */)
    }
}
```

The index handler needs access to the registry. `Router`'s handlers are plain `async fn(Request,
PathParams) -> Result<Response, DjangorsError>` (or closures satisfying `Handler`'s blanket impl —
check `crates/djangors-core/src/handler.rs` for the exact bound) — a registry snapshot (`Vec<(app_
label, struct_name)>`, cheap to clone since `ModelMeta` is `Copy`) can be captured by a closure, or
attached via `Router::with_state` and read back via `req.state::<T>()` inside a plain handler
function — check both real patterns already in this codebase (`examples/polls`'s `.with_state(db)`
for the state approach; any existing closure-based handler registration in `djangors-core`'s own
tests for the closure approach) and pick whichever is a smaller, more obviously-correct diff. State
is likely simpler and more consistent with how `examples/polls` already injects the DB.

Render output: plain `Response::html` + `format!()` listing `<li>{app_label}.{struct_name}</li>`
per registered model — no `djangors-template` integration yet (matches this project's own
established v1-first pattern; theming is an explicit later Phase 5 bullet, not this task).

## What this task does NOT include

- Changelist (list_display, sorting, pagination, filters, search, bulk actions, CSV/XLSX export) —
  separate, later `PLAN.md` bullet, needs a real `ModelAdmin` customization API this task
  deliberately keeps minimal.
- Change forms, delete confirmation, inlines, history/audit-log integration, theming, custom admin
  views, `createsuperuser` command — all separate, later bullets.
- Extending `AuthUser` with `is_staff()` — deliberately out of scope per the scope decision above.
- Wiring the admin into `examples/polls` (`admin.rs` there stays fully aspirational, unchanged,
  same as every prior Phase 4 task left it) — a future task once changelist/change-forms exist
  makes admin worth actually wiring into an example.

## Required tests

- `AdminSite::register::<M>()` then `AdminSite::urls()` produces a router where `GET /` (real
  request, no auth) → `401 Unauthorized` (reuse the same test pattern `Auth<U>`'s own tests in
  `djangors-auth` already use for the no-session case, adapted here).
- Authenticated as a real user with `is_staff = false` → `403 Forbidden`.
- Authenticated as a real user with `is_staff = true` → `200 OK`, response body contains every
  registered model's `app_label`/`struct_name` (register at least two different real models —
  e.g. reuse `djangors_auth::User` itself and `examples/polls`'s `Question` if that's importable
  from `djangors-admin`'s test target without a circular dependency; if a circular/awkward
  dependency would result from importing `examples/polls`'s types into a `djangors-admin` test,
  define two small test-only model structs in the test module instead, mirroring how
  `djangors-auth/src/tests.rs`'s own `TestUser` pattern already avoids exactly this kind of
  cross-crate test dependency awkwardness — use judgement, don't force an import that creates a
  workspace dependency cycle).
- Real Postgres test setup (raw SQL `CREATE TABLE`, same established precedent as every other
  crate's Postgres-backed tests) for whichever real user rows the staff/non-staff test cases need.
