# 11.4 — Real per-test database isolation + a fixtures loader for `djangors-test`

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_4` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

`crates/djangors-test/src/lib.rs`'s `TestDatabase` (~line 130) has an honest doc comment on itself:
*"A thin database fixture. It intentionally does not provide transactional rollback: ORM
querysets currently require `&Database` and execute directly through its pool."* This is Phase 11's
last remaining test-infrastructure gap. Fixing it properly matters beyond this one crate — this
whole Phase 11 effort has repeatedly hit real, time-consuming test-isolation bugs caused by tests
sharing one persistent database with fixed table/row names (a 9-test mutex-based fix in
`djangors-tasks`, a scoping fix in the new migration-rollback rollback query, manual unique-suffix
naming schemes in several new tests written this phase) — a real per-test isolation mechanism
would make all of that unnecessary going forward.

**Why "wrap each test in one transaction, rolled back at the end" (the literal Django-style
approach, and what the task name might suggest) is the wrong direction to force here — verify this
yourself, don't take it on faith:** every `QuerySet<T>` method in `crates/djangors-orm/src/queryset.rs`
(`all`, `get`, `insert_raw`, `update`, `bulk_create`, `delete_by_pk`, `select_related`, etc. - 60
call sites of `.pool()` in this one file) takes `db: &djangors_db::Database` and calls `db.pool()`
to get a `&PgPool`, then executes each query directly against that pool. sqlx's `PgPool` checks out
a (potentially different) physical connection **per query** - there is no "current transaction"
concept threaded through `Database`/`QuerySet` today. Making "each test runs inside one open,
never-committed transaction" work would require either (a) changing `Database::pool()`'s return
type/contract to something that can transparently be either a real pool or an already-open
transaction (a change that ripples through **17 different crate/file locations**, confirmed via
`grep -rln '\.pool()' crates/*/src/*.rs` - `djangors-cache`, `djangors-auth`, `djangors-cli`,
`djangors-admin`, `djangors-rest`, `djangors-tasks`, `djangors-migrations`, and more), or (b) adding
a parallel "transactional" code path alongside every existing method (doubling the API surface).
Both are large, invasive, high-blast-radius changes to already-API-frozen crates (see
`docs/api-stability.md`) for what is fundamentally a *test-infrastructure* problem.

**The recommended approach: per-test throwaway databases, not per-test transactions.** Give each
test its own freshly `CREATE DATABASE`-d, uniquely-named Postgres database, run the test against
it exactly as today (zero changes needed to `Database`/`QuerySet`/any query call site - `TestDatabase`
just connects to a different URL), then `DROP DATABASE` it when the test is done. This achieves the
*actual goal* (no test can ever see another test's data, full stop) with **zero changes** to the
ORM/query layer, at the cost of `CREATE DATABASE`/`DROP DATABASE` being slower per-test than a
transaction rollback would be (a real, acceptable trade-off - this is exactly how several
established Rust ORM test-support crates, e.g. `sqlx-db-tester`, solve this same problem, for
exactly this reason). This is the recommended direction; only deviate from it if you find a
concretely better option that's still low-blast-radius - don't reach for the transaction-threading
rewrite.

## Scope — what to build

1. **`TestDatabase::connect()` (and a new explicit `TestDatabase::isolated()` or similar, your
   naming call) creates a real, uniquely-named database** (e.g. `djangors_test_{random suffix}`)
   using an admin connection to the base `DATABASE_URL` target (a `CREATE DATABASE` must be issued
   outside a transaction, and can't run on a connection to the database being created/dropped -
   connect to the existing target database or `postgres` to issue it, then open a fresh connection
   directly to the new database for the actual `Database`/pool the test uses).
2. **Cleanup**: since Rust doesn't have async `Drop`, decide a pragmatic mechanism - a `TestDatabase`
   method like `pub async fn cleanup(self)` that tests call explicitly at the end (least magic,
   most predictable), and/or a `Drop` impl that best-effort spawns the `DROP DATABASE` onto the
   ambient tokio runtime handle if one is available (`tokio::runtime::Handle::try_current()`) as a
   defensive fallback for tests that forget - document clearly which is the primary mechanism vs.
   the fallback. Terminate any lingering connections to the throwaway database before dropping it
   (`SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = $1 AND pid <>
   pg_backend_pid()`) so `DROP DATABASE` doesn't fail with "database is being accessed by other
   users."
3. **Keep the existing `TestDatabase::connect()`/`connect_url()`/`database()`/`create_table()`
   API working for existing callers** (many existing tests across the workspace call
   `TestDatabase::connect()` directly and expect the shared, persistent `djangors_test` database -
   don't break them). Add the new isolated-database capability as new methods, don't replace the
   existing behavior wholesale - existing tests opt in to isolation, they aren't forced into it.
4. **A fixtures loader**: a way to load a set of rows into a freshly-created table from a
   structured source (JSON is the simplest, most Rust-idiomatic choice given `serde_json` is
   already a dependency everywhere in this workspace) - e.g. `pub async fn load_fixtures<T:
   Model + serde::de::DeserializeOwned>(&self, json: &str) -> Result<Vec<T>, ...>` that deserializes
   a JSON array of objects and inserts each one (reuse `QuerySet::bulk_create` from Phase 11 item 3,
   already shipped - don't reinvent bulk insertion).

## Deliberately excluded

- Do not attempt the transaction-threading rewrite of `Database`/`QuerySet` - the "Context"
  section above explains why that's out of scope for this task.
- Do not change any existing test in the workspace to use the new isolated-database mechanism -
  this task ships the *capability*, adopting it project-wide is separate, future work.
- Fixture format beyond JSON (YAML, CSV, Django-style multi-app fixture directories) - JSON only.
- A fixtures *dumper* (the reverse direction, serializing existing rows to JSON) - loading only.

Run yourself against the real Postgres instance at `DATABASE_URL=postgres://postgres:postgres@localhost/djangors_test` (used as the admin/base connection to issue `CREATE DATABASE`/`DROP DATABASE` against) before finishing:

  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` all clean -
  **and confirm existing tests using the old `TestDatabase::connect()` behavior still pass
  unchanged**, proving this is additive, not a breaking change.
- New tests (in `djangors-test`) proving, against the real Postgres server:
  - Two tests both requesting an isolated database concurrently get genuinely separate databases
    (query `current_database()` from each and assert they differ), and each can create a table
    with the *same name* as the other without collision.
  - After cleanup, the throwaway database is actually gone (attempting to connect to its exact
    name fails / it no longer appears in `SELECT datname FROM pg_database`).
  - The fixtures loader genuinely inserts real rows from a JSON string into a real table backed by
    a `#[derive(Model)]` struct, and they're queryable afterward via the normal `QuerySet` API.

  output.
