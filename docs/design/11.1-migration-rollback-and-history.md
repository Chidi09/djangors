# 11.1 — Real migration history, forward-application, and rollback

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_1` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

This is Phase 11 item 1 (see `PLAN.md`'s new "Phase 11 — Django-parity gap closure" section) — the
biggest, most foundational of the Django-parity gaps found in a fresh self-assessment. Verified
directly against current source before writing this doc (do not trust this summary over the real
files — re-read them):

- `crates/djangors-migrations/src/operation.rs`: `Operation` has **exactly one variant**,
  `CreateTable { table_name, columns }`. `to_sql()` only handles that arm. There is no
  `AddColumn`/`DropColumn`/`AlterColumn`/`RenameColumn`, and no down/rollback SQL generation
  anywhere in this crate.
- `crates/djangors-cli/src/commands.rs`, `makemigrations()` (~line 525): diffs the current
  `introspect_models()` output against `migrations/.schema_snapshot.json` (the previous run's
  snapshot). For a genuinely new table, it calls `build_create_plan_from_snapshots` (a real
  `Operation::CreateTable`). For a new *field* on an *existing* table, it does **not** go through
  `Operation` at all — it directly `format!("ALTER TABLE {} ADD COLUMN {} {};", ...)`s a raw SQL
  string. Both kinds of statements get written to `migrations/{n:04}_auto.sql` on disk.
- **The critical bug**: `commands.rs`'s `migrate()` / `migrate_with_plan()` (~line 465, ~line 614)
  and `djangors-migrations/src/lib.rs`'s `migrate()` **never read the generated
  `migrations/NNNN_auto.sql` files at all**. They check one single hardcoded row,
  `djangors_migrations` table containing a name equal to the literal string `'0001_initial'`. If
  that row exists, `migrate()` is a permanent no-op — forever, regardless of how many new
  `NNNN_auto.sql` files `makemigrations` has since generated. If it doesn't exist, `migrate()`
  re-derives a **fresh CreateTable-only plan directly from the current live model state** (not from
  any file on disk) and applies that once. **This means every `ALTER TABLE ADD COLUMN` migration
  `makemigrations` has ever generated has never actually been executed by `dj migrate` in this
  project's history** — the files sit on disk, inert. (This is a real, previously-undiscovered
  bug this design doc surfaces — confirm it yourself by reading both files before starting, don't
  take this paragraph on faith.)
- No `examples/*/migrations/` directories exist on disk yet (checked via `find`), so there is no
  real on-disk migration history anywhere in this repo to preserve backward compatibility with —
  you are free to change the on-disk migration file format/tracking-table schema without a
  migration-of-migrations concern.
- `djangors_orm::ModelSnapshot`/`FieldSnapshot` (`crates/djangors-orm/src/meta.rs` ~line 240) is
  the full metadata available for diffing: `table_name`, `fields: Vec<FieldSnapshot>` (each with
  `name`, `column_name`, `kind: FieldKind`, `nullable`, `primary_key`, `auto`, `unique`,
  `db_index`, `default: SnapshotDefault`, `max_length`), `relations`, `unique_together`, `ordering`.

## Scope — what to build

### 1. Real, typed `Operation` variants (`djangors-migrations/src/operation.rs`)

Add variants alongside the existing `CreateTable`:
- `AddColumn { table_name, column: ColumnDef }`
- `DropColumn { table_name, column_name: String }`
- `AlterColumnType { table_name, column_name: String, new_sql_type: String }` (Postgres:
  `ALTER TABLE t ALTER COLUMN c TYPE new_type [USING c::new_type]` — use a `USING` cast so
  changing e.g. `TEXT` → `INTEGER` doesn't just blindly fail on non-castable data; document that
  some type changes are inherently lossy/require manual data migration, don't try to solve that
  generally).
- `RenameColumn { table_name, old_name: String, new_name: String }`
- `DropTable { table_name: String }`

Every variant needs both `to_sql()` (forward) **and** a way to produce the reverse operation for
rollback. Don't bolt "reverse" onto `Operation` as a runtime inverter for arbitrary SQL strings
(too fragile) — instead, each *migration file* (see below) records both its forward operations
and, where mechanically invertible, an explicit reverse operation list generated at
`makemigrations` time (when the "before" state is still known). `AddColumn` reverses to
`DropColumn`; `CreateTable` reverses to `DropTable`; `RenameColumn` reverses to the swapped rename.
`DropColumn` and `AlterColumnType` are **not safely auto-invertible** in general (you don't know
the old column's exact prior type/nullability/default once it's gone) — for these, `to_down_sql()`
should return `None` and the tooling must refuse to roll back past such a migration with a clear
error naming the file, rather than silently generating wrong/lossy "down" SQL.

### 2. Real per-migration file tracking, not a single bootstrap flag

Replace the single-hardcoded-`'0001_initial'` check with real history:
- `djangors_migrations` tracking table keeps one row **per applied migration file** (by its real
  filename/name, e.g. `0001_initial`, `0002_auto`), not one synthetic row.
- `migrate()` must: read every `migrations/NNNN_*.sql`-equivalent file that exists on disk
  (see format below), determine which have *not* yet been recorded as applied (in filename order),
  and apply exactly those, each in its own transaction (or the whole batch in one transaction —
  your call, document which and why), recording each as applied as it succeeds.
  **This directly fixes the "ALTER TABLE ADD COLUMN never actually runs" bug** — every generated
  migration file must genuinely execute now, in order, exactly once.
- Decide and document a real on-disk migration file format that can hold forward *and* down SQL
  (a plain `.sql` file with a `-- up` / `-- down` marker convention is fine, or split into
  `NNNN_name.up.sql` / `NNNN_name.down.sql` pairs — pick one, but it must support "no down
  available" explicitly, not just an empty down file that would silently no-op).
- `makemigrations` must now emit files in this new format (forward *and* down where invertible),
  and continue writing/reading `.schema_snapshot.json` for diffing (keep that part; it works).

### 3. `dj migrate --rollback [N]`

Add a rollback path to `dj migrate`: with no argument, roll back the single most-recently-applied
migration; with `--rollback N`, roll back the last N. For each migration being rolled back (most
recent first), look up its down SQL; if any migration in the requested range has no down SQL
(a `DropColumn`/`AlterColumnType`-based migration), refuse the entire rollback with a clear error
naming the offending migration file, rather than partially rolling back. On success, delete that
migration's row from `djangors_migrations` (per-file tracking makes this natural now).

## Deliberately excluded (do not build these here)

- Squashing migrations into one file.
- Data migrations (Python-style `RunPython`-equivalent custom migration steps) — this pass is
  schema/DDL only.
- Cross-app migration dependency ordering beyond what already exists (topological sort in
  `plan.rs` — leave that as-is unless it's genuinely in the way).
- Renaming/dropping a whole *table* via `makemigrations`' auto-diff (it currently only detects new
  tables/new fields; detecting dropped/renamed tables or columns automatically is a much harder,
  separate autodetector problem — `DropColumn`/`RenameColumn`/`DropTable` operations should exist
  and be independently testable, but `makemigrations` itself doesn't need to auto-generate them
  from a diff yet; a hand-written migration file using these operations is enough for this pass).
- Any change to `examples/polls`/`examples/school` beyond what's needed to prove this works
  end-to-end (see verification below) — don't scope-creep into unrelated example-app changes.

## Required verification

Run these yourself against a real Postgres database (`DATABASE_URL=postgres://postgres:postgres@localhost/djangors_test` is already configured and running in this environment) before printing the done marker:

- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` **all clean**.
- Write and run new tests in `djangors-migrations` (and/or `djangors-cli` if the rollback command
  needs its own integration test) proving, against a real database, not mocks:
  - A multi-migration sequence (create table, then add a column in a second migration) applied via
    `migrate()` actually results in the column existing in the real database — this is the
    regression test for the bug this doc describes; it must fail before your fix and pass after.
  - `dj migrate --rollback` actually reverses the most recent migration's schema change in the
    real database (e.g., an added column is genuinely gone afterward).
  - Attempting to roll back a migration with no down SQL (e.g. one containing a `DropColumn`)
    is refused with a clear error and does **not** partially apply.
  - Running `migrate()` twice in a row is still idempotent (already-applied migrations are
    correctly skipped both by old and newly-added ones).
- Do not claim a specific empirical result you have not actually observed in real committed
  output — if you cite a specific behavior, the actual test output must show it.
