# 5.8 part 2 — Convert the delete confirmation page to a template

**Status:** design, not yet dispatched. Follows 5.8.1 (template engine pilot, commit `eb1a916`).
See `docs/design/phase-5-roadmap.md`. Continues the "convert one page at a time, prove zero
behavior change, defer real visual theming" approach 5.8.1 established.

## Scope: `admin_delete_get` only, same byte-identical-output discipline as 5.8.1

This slice converts exactly one more page — the delete confirmation page
(`GET /{app}/{model}/{pk}/delete/`, handler `admin_delete_get`) — to render through
`djangors-template` instead of hand-rolled `format!()`. Same rules as 5.8.1: **no other page
touched, no visual/CSS changes, output must match the current implementation's rendered bytes
exactly** (verified by the existing `test_admin_delete_endpoints` passing with zero modification
to its own assertions). `admin_delete_post`, every other route, and the shared `ADMIN_TEMPLATES`
static's registration list (which just gains one more entry) are the only other things this
touches.

This page is a better next target than the changelist (the most complex remaining page) because
it has genuinely dynamic, database-derived content — real field values that could contain
arbitrary text a user typed into a form — unlike 5.8.1's `admin_index`, which only ever renders
compile-time `ModelMeta` strings. Converting this page is the first real test of whether
`djangors-template`'s autoescaping correctly protects dynamic content end-to-end, not just proof
that the plumbing compiles.

## A real, already-identified subtlety: `html_escape`'s `/` escaping is not byte-identical to minijinja's

`djangors_core::html_escape` (`crates/djangors-core/src/lib.rs` ~line 48-62, used throughout the
current `admin_delete_get`) escapes six characters: `< > & " ' /`, the last as `&#x2F;` (uppercase
hex digit). `minijinja`'s own HTML autoescaping (confirmed empirically in 5.8.1's own new test,
`test_from_embedded_auto_escaping`) escapes the same six characters, but renders `/` as `&#x2f;`
(**lowercase** hex digit). Functionally these are identical — any browser decodes both back to a
literal `/` — but they are not byte-identical strings, which matters given this task's stated
"byte-identical output" requirement.

**This does not actually block the requirement for this specific task**: `test_admin_delete_endpoints`'s
own test data (`crates/djangors-admin/src/lib.rs` ~line 3099-3102) uses the literal string
`"Parent Object"` for the field value under test — no `/`, and no other character `html_escape`
treats specially. Confirm this stays true (re-read the test's actual data before relying on it,
in case it's shifted) rather than assuming; if it does contain a `/` by the time this is
implemented, that's the one case where "byte-identical" and "letting minijinja autoescape do the
work" are in real tension — if so, STOP and consult the fallback below rather than picking one
silently:
- **Preferred fallback if this ever comes up**: this hex-case difference is cosmetic only, so if
  a real conflict is found, update `test_admin_delete_endpoints`'s specific assertion to expect
  `&#x2f;` (matching Django/Jinja2/minijinja's own convention) rather than trying to force
  minijinja to match `html_escape`'s exact casing — the template mechanism's own escaping
  convention should be the one that wins going forward, not the old hand-rolled one being phased
  out. Note this as a deliberate, understood change in the commit message, don't just quietly
  adjust the assertion without comment.

## Template file: `crates/djangors-admin/templates/admin/delete_confirm.html`

```html
<div>{% for f in fields %}<div><strong>{{ f.name }}:</strong> {{ f.value }}</div>{% endfor %}</div>{% if related %}<h3>Related Objects:</h3><ul>{% for r in related %}<li>{{ r.struct_name }} (table: {{ r.table_name }}, count: {{ r.count }}, on_delete: {{ r.on_delete }})</li>{% endfor %}</ul>{% endif %}<form method="post"><input type="submit" value="Confirm Delete"></form>
```

One continuous line, no added whitespace between tags — matching 5.8.1's own `index.html`
convention exactly, since `{% for %}`/`{% if %}` blocks preserve template-source whitespace
outside the tags verbatim, and any stray newline/indentation here would show up as an observable
difference from the current `format!()`-concatenated output (which has none).

This must produce the same structure as the current implementation's three concatenated pieces
(`crates/djangors-admin/src/lib.rs`, `admin_delete_get`, ~line 1919-1951): the `<div>{{ per-field
divs }}</div>` wrapper, the conditional `<h3>Related Objects:</h3><ul>...</ul>` block (only when
`related` is non-empty — matches the existing `if !related.is_empty()` check), and the static
confirm `<form>`.

## Context structs and the handler change

```rust
#[derive(serde::Serialize)]
struct DeleteConfirmField {
    name: String,
    value: String,
}

#[derive(serde::Serialize)]
struct DeleteConfirmRelated {
    struct_name: String,
    table_name: String,
    count: i64,
    on_delete: String,
}

#[derive(serde::Serialize)]
struct DeleteConfirmContext {
    fields: Vec<DeleteConfirmField>,
    related: Vec<DeleteConfirmRelated>,
}
```

In `admin_delete_get`, replace the manual `html_escape`/`format!`/`push_str` loop building
`obj_html` with building a `Vec<DeleteConfirmField>` (one per `(name, val)` pair from `row_vals`,
`name: name.to_string(), value: val.to_string()` — **no manual `html_escape` call anymore**,
autoescaping handles it now that this renders through the template). Same for `related`: replace
the `warnings_html` string-building loop with a `Vec<DeleteConfirmRelated>` (`struct_name:
rel.struct_name.to_string(), table_name: table_name.to_string(), count: rel.count, on_delete:
format!("{:?}", rel.on_delete)` — same values the current code already computes, just pushed into
a struct instead of formatted into HTML by hand). Replace the final
`Ok(Response::html(StatusCode::OK, full_html))` with
`djangors_template::render(&ADMIN_TEMPLATES, "admin/delete_confirm.html", DeleteConfirmContext { fields, related })`.

Everything before that point in `admin_delete_get` (params, admin lookup, `db`, `require_perm`,
`get_by_pk`, `collect_related_objects`) is unchanged.

## `ADMIN_TEMPLATES`: add the new template to the existing static

`crates/djangors-admin/src/lib.rs`'s `ADMIN_TEMPLATES` (introduced in 5.8.1) currently registers
one template. Extend its `from_embedded` call to a second entry:

```rust
static ADMIN_TEMPLATES: std::sync::LazyLock<djangors_template::TemplateEngine> =
    std::sync::LazyLock::new(|| {
        djangors_template::TemplateEngine::from_embedded(&[
            (
                "admin/index.html",
                include_str!("../templates/admin/index.html"),
            ),
            (
                "admin/delete_confirm.html",
                include_str!("../templates/admin/delete_confirm.html"),
            ),
        ])
        .expect("admin templates are compiled into the binary and must always be valid")
    });
```

Do not create a second `LazyLock`/engine — one shared engine registering every template this
crate ships is the intended pattern (this is exactly why 5.8.1 built it as a single static rather
than a per-page one).

  this task only calls it with one more entry).

  not-yet-converted page.
