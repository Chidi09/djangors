# Design 4.3 — Migrations engine (v1 scope)

**Status:** draft, pre-implementation. Depends on [4.1 — Model metadata](4.1-model-meta.md), which is fully real as of `djangors-orm`'s `ModelMeta`. Read `PLAN.md` Part 4.3 first — this narrows it into an achievable first slice.

## The problem, narrowed

Django's `makemigrations` diffs "models as currently written" against "state after replaying every existing migration" and emits the delta as a new migration file — full autodetection across renames, field-type changes, and cross-app dependency ordering. That is genuinely the hardest part of this entire framework (`PLAN.md` calls it exactly that) and is not achievable in one pass. **This document scopes a v1 that is honest about what it can't do yet**, rather than attempting the whole autodetector at once.

**v1 scope: CREATE TABLE only.** Given the current set of registered models (via `djangors_orm::all_registered_models()`), generate a migration that creates every table from scratch, matching each model's `ModelMeta`. No diffing against a previous state, no `AddField`/`AlterField`/`DropField`, no renames. This is deliberately just "the first migration a fresh project would ever run" — genuinely useful on its own (every new project needs exactly this), and it exercises the full pipeline (`ModelMeta` → SQL DDL → an applied/tracked migration) end to end before autodetection-across-history gets layered on top in a follow-up.

## Migration representation

A migration is a Rust value, not a generated file, for v1 (Django's migrations are Python files containing `Operation` lists; the Rust equivalent will eventually be generated source files too, but that's a `djangors-macros`/codegen concern layered on top — v1 works with an in-memory operation list so the *execution* engine can be built and proven first):

```rust
// djangors-migrations/src/operation.rs

pub enum Operation {
    CreateTable {
        table_name: String,
        columns: Vec<ColumnDef>,
    },
    // AddColumn, DropColumn, AlterColumn, DropTable, CreateIndex, etc. — v2+
}

pub struct ColumnDef {
    pub name: String,
    pub sql_type: String,       // Postgres type, e.g. "BIGSERIAL", "TEXT", "BOOLEAN"
    pub nullable: bool,
    pub primary_key: bool,
    pub unique: bool,
    pub default_sql: Option<String>,  // raw SQL default expression, e.g. "0", "''"
    pub references: Option<ForeignKeyRef>,  // for FK columns
}

pub struct ForeignKeyRef {
    pub table: String,
    pub column: String,       // almost always the referenced table's PK column
    pub on_delete: String,    // "CASCADE" | "RESTRICT" | "SET NULL" | ...
}
```

## FieldKind → Postgres type mapping

This is the other piece of real design work v1 needs (beyond "just CREATE TABLE") — a table, not prose, since it's the actual thing to implement:

| `FieldKind` | Postgres type |
|---|---|
| `Char` | `VARCHAR(n)` (n = `FieldMeta.max_length`, required — compile/runtime error if absent, mirrors the macro's own existing validation) |
| `Text` | `TEXT` |
| `Integer` | `INTEGER` |
| `BigInt` | `BIGINT` (or `BIGSERIAL` if `auto: true` — see below) |
| `Float` | `DOUBLE PRECISION` |
| `Decimal { max_digits, decimal_places }` | `NUMERIC(max_digits, decimal_places)` |
| `Boolean` | `BOOLEAN` |
| `Date` | `DATE` |
| `DateTime` | `TIMESTAMPTZ` (always timezone-aware — matches the project's `USE_TZ`-by-default posture noted in `PLAN.md` Part 2) |
| `Time` | `TIME` |
| `Duration` | `INTERVAL` |
| `Uuid` | `UUID` |
| `Email` / `Url` / `Slug` | `VARCHAR(n)` (same as Char — these are Char-family types with extra *application-level* validation, not distinct SQL types; `max_length` still required) |
| `Ip` | `INET` |
| `Binary` | `BYTEA` |
| `Json` | `JSONB` (not `JSON` — `JSONB` is universally the right default on Postgres: indexable, faster equality/containment checks; there is no reason to default to plain `JSON`) |

**`auto` fields**: when `FieldMeta.auto == true` and the kind is `Integer`/`BigInt`, use `SERIAL`/`BIGSERIAL` instead of the plain integer type — Postgres's auto-increment mechanism. (`djangors-orm`'s current `Decimal`/`Uuid`/`NaiveDate`/`NaiveTime`/`Duration` save/update codegen restriction, noted in the ORM's own commit history as a known temporary gap, does NOT block migrations from creating tables with those column types — a table can exist with a column the ORM's save/update can't populate yet; that's an ORM-layer gap to close separately, not a migrations-layer blocker.)

**Primary key columns** get `PRIMARY KEY` appended regardless of the `unique`/`db_index` flags on `FieldMeta` (which the `#[derive(Model)]` macro already sets to `true` for primary-key fields as an implied default — redundant with `PRIMARY KEY` itself, harmless).

**Foreign key columns**: for each `RelationMeta` on a model, add an `INTEGER`/`BIGINT` column (matching the *referenced* model's primary key column type — resolve via `(relation.target)().fields` to find the target's primary-key `FieldMeta` and read its kind) named after the relation's `field_name` (matching the ORM's own existing convention of using the field's Rust name as its column name for relations, established in the `from_row`/`save` codegen), with a `REFERENCES {target_table}({target_pk_column}) ON DELETE {on_delete_sql}` clause. `OnDelete` → SQL: `Cascade → CASCADE`, `Protect`/`Restrict → RESTRICT` (Postgres doesn't distinguish Django's PROTECT/RESTRICT at the SQL level the way Django's ORM-layer PROTECT does via a pre-delete check — RESTRICT is the closest native SQL equivalent for both; a true PROTECT with Django's exact "raise before attempting the DELETE at all" semantics is application-layer and out of scope for v1's DDL), `SetNull → SET NULL` (only valid if the FK column is nullable — v1 can make relation columns nullable when `on_delete: SetNull` is specified, NOT nullable otherwise), `DoNothing → NO ACTION`.

## Ordering: tables must be created in dependency order

A model with a `ForeignKey<Other>` must have `Other`'s table created first (the `REFERENCES` clause needs the target table to exist). This is a topological sort over the models returned by `all_registered_models()`, using each model's `RelationMeta.target` (already a `fn() -> &'static ModelMeta`, resolvable at migration-generation time same as everywhere else it's used) as the dependency edge. A cycle (A references B references A) is a real error to surface clearly — Django handles this by deferring FK constraints or splitting into multiple ALTER statements after all tables exist; v1 can take the simpler path of detecting a cycle and erroring out with a clear message naming the cycle, deferring "add FKs in a second pass after all tables exist" to v2 alongside real ALTER TABLE support.

## Execution and tracking

A `djangors_migrations` tracking table (Django's own `django_migrations` table, renamed) records which migrations have been applied: `(id SERIAL PRIMARY KEY, name TEXT UNIQUE NOT NULL, applied_at TIMESTAMPTZ NOT NULL DEFAULT now())`. v1's single generated "create everything" migration gets one fixed name (e.g. `"0001_initial"`). Running `dj migrate` (the CLI command already stubbed in `djangors-cli`, per `PLAN.md` Phase 6 / the already-shipped `djangors-cli` skeleton): checks whether `"0001_initial"` is recorded as applied; if not, run every `CreateTable` operation inside one transaction (via `djangors_db::Database::transaction`, already real) and record it as applied on success. Running it again is a no-op (already applied). This is the full extent of v1 — no `sqlmigrate`, no `--fake`, no squashing, no per-app migration files; those are v2+ once the diffing/autodetection layer exists to actually produce more than one migration.

## What v1 explicitly does not attempt (write these down so nobody "fixes" them as bugs)

- No diffing against previous migration state — there is no "previous state" in v1, only "create everything from the current models." Running `dj makemigrations` twice produces the identical single migration both times (not a new one for whatever changed since — because v1 has no concept of "since").
- No `AddField`/`DropField`/`AlterField`/rename detection.
- No squashing, no per-app migration graphs/dependencies between separate migration files (there's only ever one file in v1).
- No data migrations (`RunRust`/`RunSQL` closures).
- PROTECT and RESTRICT collapse to the same SQL (`RESTRICT`) — Django's true PROTECT semantics (an application-level pre-check with a specific Python exception) is future work.

## Why this scope, not less

Even this narrow slice requires: the full `FieldKind`→SQL type table above, dependency-ordered table creation (a real topological sort, not a trivial loop), and a genuine transactional apply-and-track mechanism — that's enough real engineering to prove the whole pipeline (`ModelMeta` → DDL → tracked execution) works, which is the foundation every later diffing/autodetection feature builds on. Anything narrower than "create the tables and track that it happened" wouldn't be a usable v1 at all.
