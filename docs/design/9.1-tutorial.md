# 9.1 — Phase 9 begins: the tutorial (mirroring Django's own polls tutorial)

## Scope

Phase 8's core is done (`docs/design/8.5-background-tasks-core.md`, commit `0e4a3a0`). This
begins Phase 9 (Docs, tutorial, website) with the single highest-value deliverable named in its
own DoD: **"a Django dev completes the tutorial without asking a question in chat."** Mirrors
Django's own official tutorial structure (parts 1-8) exactly, since PLAN.md's own text calls it
"the best framework tutorial ever written" and asks to mirror it, not reinvent the structure.

**Deliberately excluded from this dispatch, left for later 9.x slices**: topic guides, the full
rustdoc reference/100%-public-API-coverage enforcement, how-tos, the "Djangors for Django
developers" side-by-side guide, doctest-in-CI extraction, and the `djangors.rs` landing page. Each
is a real, separate, substantial deliverable.

## The one rule that matters most: every code example must be real, not aspirational

**This project's own `docs/design/*.md` files have repeatedly found and flagged "aspirational"
markers going stale in older prose docs** (e.g. `examples/polls/README.md`'s own historical
"what's real vs aspirational" section, referenced in multiple earlier design docs this project) —
a tutorial is read by someone with zero context who will copy-paste every snippet and expect it to
compile and run exactly as shown. **Every single code snippet in the tutorial must be copied
directly from, or trivially adapted from, the real, current, already-committed code in
`examples/polls`** (its `Cargo.toml`, `src/models.rs`, `src/views.rs`, `src/urls.rs`,
`src/admin.rs`, `src/main.rs`, `tests/voting.rs`) — read every one of those files in full before
writing a single word of tutorial prose. Do not write a snippet from memory of "how Django's
tutorial usually goes" and assume the Rust equivalent looks similar; check the actual API against
the actual file every time. Where the real code differs from what a napkin-sketch Django-tutorial
port would suggest (e.g. this framework's actual error-handling style, actual macro attribute
syntax, actual `Router` composition), the tutorial must describe what's really there, not a
prettied-up hypothetical.

If a step described in Django's real tutorial doesn't have a working equivalent yet in this
framework (e.g. Django's tutorial parts 7-8 lean heavily on the admin's `list_display`/customization
UI and the generic views framework, both of which exist here in some form — verify exactly what
does and doesn't exist by reading the real `djangors-admin` crate and its own test suite, not by
assuming parity), **say so explicitly in the tutorial text** rather than describing something that
doesn't work. A tutorial step that silently doesn't work when followed is worse than one that's
honest about a gap.

## Structure — mirror Django's own tutorial's real part breakdown

Create `docs/tutorial/` with one Markdown file per part (`01-requests-and-responses.md` through
`08-testing-and-admin-customization.md`, or whatever exact split fits this framework's own
capabilities — read Django's real tutorial structure for the canonical 8-part breakdown as the
starting template, but adapt the exact boundaries between parts if this framework's own
capabilities don't map perfectly, and say so). Each part should:

1. Start from the state the previous part left off in (a reader following along builds up
   `examples/polls` from scratch, part by part) — or, since `examples/polls` already exists
   fully-built in this repo, structure each part as "here's what you'd write to reach this state,
   and here's why," referencing the real, current file contents as the source of truth for what
   the end state of that part looks like.
2. Include a short "what's real vs. what Django has that this doesn't yet" callout wherever this
   framework's actual capability differs from Django's own (e.g. no `reverse()`/named-URL
   resolution yet — views hand-format URLs, confirmed by reading `examples/polls/src/views.rs`
   directly; no real migration files yet — this project uses raw-SQL-in-tests still, or has it
   changed? verify against the real current `djangors-migrations` state before asserting either
   way, don't rely on stale prior knowledge).
3. End with something the reader can actually run and see working (matching Django's own
   tutorial's "run the dev server, see the page" rhythm at the end of each part).

## Required verification (this is a docs slice, but "verification" still means something concrete)

- Every named file path, function name, struct name, and macro attribute mentioned in the tutorial
  must be checked against the real, current source at the time of writing — grep for each one
  after writing to confirm it exists exactly as described (e.g. if the tutorial says
  `#[djangors(app = "polls", table_name = "polls_question")]`, grep `examples/polls/src/models.rs`
  to confirm that's the literal real attribute on `Question`, not a guess).
- Every shell command shown (e.g. `cargo run`, `dj createsuperuser`, `dj migrate`) must be a real,
  currently-working command — confirm against `crates/djangors-cli`'s real subcommands (6.1-6.3
  landed real implementations for `new`/`new-app`/`run`/`check`/`makemigrations`/`dbshell`/`test`/
  `shell`, plus the pre-existing `migrate`/`createsuperuser`/`createpermissions`/`collectstatic` —
  read `crates/djangors-cli/src/cli.rs` for the exact real subcommand list and their exact real
  flags before citing any of them in the tutorial).
- Report, in your final summary, the exact list of tutorial files created, and confirm you
  re-read each one after writing it once more against the real source to catch any drift.

Print `DONE_MARKER_9_1_TUTORIAL` when finished (or when stopping early — say exactly how many
parts landed and which, if any, needed an honest "this doesn't exist yet" callout instead of a
real worked example).
