# 11.6 — Real multipart/form-data file upload parsing

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_6` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

`djangors_orm::meta::FieldKind::FileField` exists and a `#[djangors(file_field)]` model field
today only stores a path/key **string** — nothing in this codebase actually parses a real
`multipart/form-data` HTTP request body. `crates/djangors-core/src/extract.rs`'s `Json` extractor
explicitly *rejects* `multipart/` content types (it's not JSON) but no `Multipart` extractor exists
to handle them. Confirmed via `grep -rn "multer\|multipart" Cargo.lock` - **no multipart-parsing
crate is in the dependency tree at all** yet; this needs a real one added (`multer` is the
standard, well-maintained choice - used internally by `axum` and several other Rust web
frameworks for exactly this).

**Critical dependency-direction constraint, verified directly against `Cargo.toml` files before
writing this doc - re-verify yourself, don't take it on faith:** `crates/djangors-staticfiles`'s
real `[dependencies]` includes `djangors-core = { path = "../djangors-core" }`. The dependency
graph is `djangors-staticfiles → djangors-core`. **This means the actual multipart *parsing*
extractor must live in `djangors-core` (it cannot depend on `djangors-staticfiles`'s `Storage`
trait without creating a cycle), while the piece that takes a parsed file and writes it through a
`Storage` backend (`crates/djangors-staticfiles/src/storage.rs`'s `pub trait Storage`) must live in
`djangors-staticfiles` instead** (which already depends on `djangors-core`, so it can freely use
the new extractor type from there). This project has hit this exact class of mistake multiple
times this phase (rate limiting's `ByAuthenticatedUser`, model signals needing a duplicated
`Signal<T>` rather than an import) — don't repeat it. Confirm the direction yourself with `grep -n
djangors- crates/djangors-staticfiles/Cargo.toml crates/djangors-core/Cargo.toml` before writing a
single line of code.

## Scope — what to build

1. **Add `multer` as a real dependency of `djangors-core`** (check crates.io / already-cached
   registry for the current stable version - don't guess a version number, the workspace already
   has a precedent of a dispatch getting a crate version wrong by conflating two similarly-named
   crates; verify the real, currently-published version before pinning it in `Cargo.toml`).

2. **A `Multipart` extractor in `crates/djangors-core/src/extract.rs`** (alongside the existing
   `Json`/`Query`/`Form` extractors, implementing the same `FromRequest` trait): parses the
   request's `Content-Type` header for the `multipart/form-data; boundary=...` parameter, feeds
   `req.body_bytes()` into `multer`, and yields an iterable/collectible set of parsed fields. Each
   field needs at minimum: its form field name, an optional filename (present only for actual file
   parts, absent for plain text fields in the same multipart body), an optional content-type, and
   the raw bytes. Design the returned type so a caller can distinguish "this was a file part" from
   "this was a plain text field" (Django's own `request.FILES` vs `request.POST` split - mirror
   that distinction, don't conflate the two).

3. **A "write an uploaded file through a `Storage` backend" helper in
   `crates/djangors-staticfiles`** (a new module, e.g. `crates/djangors-staticfiles/src/upload.rs`):
   takes a parsed file part (from the new `djangors-core` extractor) plus a `&dyn Storage` and a
   destination path/key, calls `Storage::save`, and returns the stored path string - this is the
   value a `FileField` should actually be set to. Pick a sensible collision-avoidance naming
   scheme for the stored path (e.g. incorporating a random/hash component alongside the original
   filename) rather than saving under the raw, attacker-controlled filename verbatim (a real
   security consideration - don't let a client dictate the exact on-disk/on-bucket path unmodified).

4. **A size limit.** Real multipart file uploads need a maximum-size guard (both for the overall
   request body and, ideally, per-file) to avoid an easy memory-exhaustion DoS - `multer` has
   built-in support for this (check its real API, e.g. `SizeLimit`), use it rather than reading an
   unbounded body into memory first.

## Deliberately excluded

- Wiring this into `#[derive(Model)]`'s generated `save()`/ModelForm (Phase 11 item 5, already
  shipped) so that a `FileField` gets automatically populated end-to-end from an incoming request -
  that's real, separate integration work (likely belonging to a future generic-CBV task tracked in
  `PLAN.md`); this task ships the *parsing + storage-writing* primitives, not the full pipeline
  wiring.
- Streaming directly to storage without buffering the whole file in memory first - `multer`'s
  streaming API can support this eventually, but don't over-engineer a fully zero-copy streaming
  path in this pass; buffering a size-limited upload into memory before handing it to `Storage` is
  an acceptable v1 scope.
- Image processing/thumbnailing, virus scanning, or any content validation beyond size limits.
- Changing `FieldKind::FileField`'s current string-path representation, or anything in
  `#[derive(Model)]`'s existing FileField handling - this task is additive (a new way to *produce*
  a valid path string via a real upload), not a change to how that string is stored/retrieved.

## Required verification

Run yourself (`DATABASE_URL` is not needed for this task - no database interaction; if any test
needs it anyway, `postgres://postgres:postgres@localhost/djangors_test` is live and reachable)
before finishing:

- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` all clean.
- New tests (in `djangors-core` for the extractor, `djangors-staticfiles` for the storage-writing
  helper) proving, with real data (construct a real, valid `multipart/form-data` body byte-for-byte
  yourself in the test, don't rely on an untested helper to build it):
  - A multipart body with both a plain text field and a file part parses correctly - the text
    field's value is accessible separately from the file part, and the file part's filename,
    content-type, and raw bytes are all correct.
  - A multipart body exceeding the configured size limit is rejected with a real error, not
    silently truncated or OOM-inducing.
  - The storage-writing helper actually writes real bytes through a real `Storage`
    implementation (`LocalDiskStorage` is the simplest to test against a real temp directory) and
    the returned path can be used to `Storage::open()` the same bytes back.
  - The generated storage path does not equal the raw, client-supplied filename verbatim (proving
    the collision-avoidance naming scheme is actually applied, not a no-op).
- Do not claim a specific empirical result you have not actually observed in real committed test
  output.
