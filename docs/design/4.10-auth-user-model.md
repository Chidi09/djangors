# Design 4.10 — djangors-auth: User model + password hashing (Phase 4 part 4a)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 4's auth bullet first. Phase 4's auth
work is large enough to need its own multi-part breakdown, same as sessions/CSRF/security did as
parts 1-3. **This is part 4a**, the foundation everything else in `djangors-auth` builds on:

- 4a (this doc): the `User` model itself, the swappable-user mechanism, password hashing.
- 4b (separate future task): `AuthenticationBackend` trait, login/logout logic, the
  `Auth<User>` extractor, session integration (calling `Session::cycle_key` on login - the actual
  fixation-protection payoff for [[4.7-sessions]] having built that method already).
- 4c (separate future task): permission guards, password-reset email flow, rate limiting,
  audit signals (login/logout/failed-login).

Do not attempt 4b/4c work in this task. A `User` type with no way to log in yet is a normal,
reviewable intermediate state — same as `Session` existed and was fully tested before `CsrfLayer`
consumed it.

## The swappable-user question (design this now, per PLAN.md - it's the whole point of doing 4a first)

Django's `AUTH_USER_MODEL` swap works because Python resolves model classes dynamically at
runtime from a settings string. Rust has no equivalent runtime type resolution, so a direct port
doesn't make sense - and pretending otherwise here would be the "retrofitted later and it hurts"
mistake `PLAN.md` is explicitly warning against, just moved to a different failure mode instead of
avoided. The Rust-idiomatic equivalent is **compile-time genericity over a trait**, not a
settings string:

```rust
/// Anything djangors-auth's login/session/permission machinery (built in
/// parts 4b/4c) can operate on. Real apps that need custom user fields
/// implement this on their own struct instead of using the built-in `User`.
pub trait AuthUser: djangors_orm::Model + djangors_orm::FromRow + Send + Sync + 'static {
    fn id(&self) -> i64;
    fn username(&self) -> &str;
    fn password_hash(&self) -> &str;
    fn set_password_hash(&mut self, hash: String);
    fn is_active(&self) -> bool;
}
```

Part 4b's backend/login machinery will be `AuthenticationBackend<U: AuthUser>` /
`Auth<U: AuthUser>`, generic over this trait, rather than hardcoded to the concrete `User` struct
below. **This task only defines the trait and the default implementation** — no part of 4a
depends on the generic machinery existing yet, so this is a safe, reviewable piece to land on its
own. State this reasoning in the crate's top-level doc comment so "why isn't this a settings
string like Django" isn't rediscovered later.

## The default `User` model

```rust
use djangors_macros::Model;

#[derive(Model, Debug)]
#[djangors(app = "djangors_auth", table_name = "auth_user")]
pub struct User {
    #[djangors(primary_key, auto)]
    pub id: i64,

    #[djangors(max_length = 150)]
    pub username: String,

    #[djangors(max_length = 254)]
    pub email: String,

    /// PHC-format hash string (algorithm + params + salt + hash all
    /// self-contained) - never the plaintext password. See the hashing
    /// section below for exactly how this gets produced/checked.
    pub password: String,

    pub is_active: bool,
    pub is_staff: bool,
    pub is_superuser: bool,

    pub date_joined: chrono::DateTime<chrono::Utc>,
    pub last_login: Option<chrono::DateTime<chrono::Utc>>,
}
```

**Ground truth constraint that shapes this** — read `crates/djangors-macros/src/model.rs` around
its "unsupported types for save/update codegen" check before writing any field: it currently
hard-rejects `Uuid`, `NaiveDate`, `NaiveTime`, `Duration`, and `Decimal` at compile time for any
`#[derive(Model)]` struct (a `syn::Error`, not a runtime failure - the whole crate won't compile
if violated). **Do not use `Uuid` for `id`** even though it's a common choice for a `User` primary
key elsewhere - use `i64` with `#[djangors(primary_key, auto)]`, matching every other model in
this codebase (see `QuerySetTestModel` in `crates/djangors-orm/src/tests.rs` for the exact
attribute syntax to copy). `chrono::DateTime<Utc>` **is** supported (`FieldKind::DateTime`) - that
one already works fine, only the four types above are rejected.

Implement `AuthUser for User` by hand (not derived) - it's four trivial method bodies, not worth
macro machinery for one type.

## Password hashing: argon2id via the `argon2` crate, not hand-rolled

Unlike sessions/CSRF (which deliberately avoided new crypto dependencies because their schemes
were simple enough to audit by hand), password hashing is exactly the case where you use an
audited, purpose-built crate instead of composing primitives yourself - a KDF with proper work
factors, salt handling, and PHC string encoding is real, easy-to-get-wrong complexity. Use the
`argon2` crate (RustCrypto), which re-exports `password_hash` and implements the `PasswordHasher`/
`PasswordVerifier` traits from it:

```rust
use argon2::{Argon2, PasswordHash, PasswordHasher, PasswordVerifier};
use argon2::password_hash::{SaltString, rand_core::OsRng};

pub fn hash_password(password: &str) -> Result<String, AuthError> {
    let salt = SaltString::generate(&mut OsRng);
    let hash = Argon2::default()
        .hash_password(password.as_bytes(), &salt)
        .map_err(|e| AuthError::Hashing(e.to_string()))?;
    Ok(hash.to_string()) // full PHC string - self-describing, store this whole thing
}

pub fn verify_password(password: &str, phc_hash: &str) -> Result<bool, AuthError> {
    let parsed = PasswordHash::new(phc_hash).map_err(|e| AuthError::Hashing(e.to_string()))?;
    // Argon2::default().verify_password already does the comparison in
    // constant time internally - do not add your own comparison on top.
    Ok(Argon2::default().verify_password(password.as_bytes(), &parsed).is_ok())
}
```

`verify_password` returning `Ok(false)` (not `Err`) for a wrong password is deliberate - a wrong
password is an expected outcome for this function to report, not a failure of the function
itself; reserve `Err` for actually-malformed hash strings (e.g. corrupted DB data), which is a
real distinct condition callers may want to handle differently (log loudly - that's not supposed
to happen - versus "wrong password," which is routine).

**Legacy verifiers** (`PLAN.md` mentions these, for supporting old hash formats when migrating an
existing user base) are **explicitly out of scope for 4a** - this is a brand-new framework with
no existing user base to migrate, so building a multi-algorithm verifier chain now is pure
speculation. Leave a doc comment noting the extension point (a future `PasswordHasher` trait
`hash_password`/`verify_password` could become methods of, with `User`'s default wired to an
argon2id impl) rather than building unused abstraction now.

## Crate shape

`djangors-auth` (existing empty placeholder). Dependencies to add: `djangors-orm`,
`djangors-macros`, `argon2` (check crates.io for the current stable version, this is a fresh
dependency not yet anywhere in `Cargo.lock` - verify with `grep '"argon2"' Cargo.lock` before and
after, there should be exactly one version resolved), `chrono` (check `Cargo.lock` for an
already-resolved version first - `sqlx`/`djangors-orm` likely already pull it in transitively,
reuse that version rather than pinning a new one), `thiserror` (for `AuthError`, matching every
other crate's error-handling convention in this codebase).

```rust
#[derive(thiserror::Error, Debug)]
pub enum AuthError {
    #[error("password hashing error: {0}")]
    Hashing(String),
}
```

## What this task does NOT include

- `AuthenticationBackend` trait, login/logout, `Auth<U>` extractor, session integration - part 4b.
- Permissions (groups, per-model add/change/delete/view), password-reset flow, rate limiting,
  audit signals - part 4c.
- Any actual database migration/table-creation for `auth_user` - `djangors-migrations` exists but
  wiring a real model into it is separate from this task (matches how other models in this
  codebase are tested: tests create their own table directly via `sqlx::query` against a real
  Postgres, see `QuerySetTestModel`'s test for the pattern - do the same here for `User`'s tests).

## Required tests

- `User` derives correctly and compiles (the macro's own compile-time checks are the real test
  here - if `id: Uuid` had been used by mistake, this step is where it would be caught; using the
  correct `i64` should compile cleanly).
- `hash_password` produces a valid PHC string (starts with `$argon2id$`), and calling it twice on
  the same password produces two *different* strings (proves the salt is actually random per
  call, not reused - a real, demonstrable property, not just "it returns Ok").
- `verify_password` with the correct password returns `Ok(true)`; with an incorrect password
  returns `Ok(false)` (not an error - a wrong password is not a malformed-input condition).
- `verify_password` against a corrupted/malformed hash string (not a valid PHC string at all)
  returns `Err`, distinguishing this from the wrong-password case above.
- A real end-to-end round trip against Postgres (same pattern as `QuerySetTestModel`'s test):
  create the `auth_user` table directly via `sqlx::query`, construct a `User` with a hashed
  password via `hash_password`, `.save()` it (the `Model` derive already generates this),
  `.get()` it back via a `QuerySet`, and `verify_password` the original plaintext against the
  round-tripped `password` field - proves the whole path end-to-end, not hashing and ORM
  persistence as separate, never-connected units.
