# Design 4.11 — djangors-auth: AuthBackend, login/logout, Auth<U> extractor (Phase 4 part 4b)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 4's auth bullet and
[[4.10-auth-user-model]] (part 4a, already built and committed) first. This is **part 4b**: the
`AuthUser`/`User`/`hash_password`/`verify_password` foundation from 4a is real; this task builds
the login mechanics on top of it. Part 4c (groups, model-level permissions, password-reset email
flow, rate limiting, audit signals) is separate future work, not part of this task.

## What this task builds

1. `AuthBackend` trait + `ModelBackend` default implementation (credential verification against
   the DB, generic over `AuthUser`).
2. `login()`/`logout()` session-helper functions (not full HTTP view handlers — see scope note
   below) that connect a successful `AuthBackend::authenticate` call to `djangors-sessions`'s
   `Session`, including the actual fixation-protection payoff [[4.7-sessions]] built `cycle_key`
   for.
3. An `Auth<U>` extractor implementing `djangors_core::extract::FromRequest`, so a handler
   declaring `Auth<User>` as a parameter *is* the `login_required` story for v1 — no separate
   guard/middleware needed, matching how `Json<T>`/`Query<T>`/`Form<T>` already work in
   `crates/djangors-core/src/extract.rs`.

**Not included**: an actual `POST /login` HTTP view (form parsing, rendering a login page) —
that's app-specific plumbing (which template, which form fields beyond username/password) better
left to an example app or a follow-up, not a one-size-fits-all handler this crate ships. What
*is* shipped here — `AuthBackend`/`login()`/`logout()`/`Auth<U>` — is exactly the reusable part a
real view would call into.

## New dependencies for `djangors-auth`

This crate currently depends only on `djangors-orm`/`djangors-macros`/`argon2`/`chrono`/
`thiserror` (see `crates/djangors-auth/Cargo.toml`, already committed). This task adds:
`djangors-core` (for `Request`/`DjangorsError`/`extract::FromRequest`/`Request::ext`/
`Request::state` — read `crates/djangors-core/src/extract.rs` for the exact `FromRequest` trait
shape to implement, and `crates/djangors-core/src/request.rs` for `ext`/`state`), `djangors-db`
(for `Database`, `AuthBackend::authenticate`'s DB parameter type), `djangors-sessions` (for
`Session` — read `crates/djangors-sessions/src/lib.rs` for its real public API: `get`/`set`/
`clear`/`cycle_key`, all already built), `async-trait` (check `Cargo.lock` for an already-resolved
version — `djangors-core` already depends on it, reuse that exact version, do not introduce a
second one).

## `AuthBackend` trait

```rust
#[async_trait::async_trait]
pub trait AuthBackend {
    type User: AuthUser;

    async fn authenticate(
        &self,
        db: &djangors_db::Database,
        username: &str,
        password: &str,
    ) -> Result<Option<Self::User>, AuthError>;
}

pub struct ModelBackend;

#[async_trait::async_trait]
impl AuthBackend for ModelBackend {
    type User = User;

    async fn authenticate(
        &self,
        db: &djangors_db::Database,
        username: &str,
        password: &str,
    ) -> Result<Option<User>, AuthError> {
        // Look up by username with `.all(db)`, not `.get(db)` - `User` has
        // no DB-level unique constraint on `username` yet (see 4.10's own
        // note on this pre-existing ORM gap). `.get()` would itself error on
        // >1 match; `.all()` lets this function treat ">1 match" the same
        // as "no match" (Ok(None)) deliberately, rather than surfacing a
        // distinct error an attacker could use to distinguish "this
        // username exists twice" from "this username doesn't exist."
        //
        // Timing-safety requirement (do not skip this): whether or not a
        // matching user was found, always call verify_password with SOME
        // hash - use the found user's real hash if there's exactly one
        // match, otherwise verify against a fixed dummy Argon2id hash
        // (hash any constant string once, hardcode the resulting PHC
        // string as a const). This keeps the failed-username and
        // wrong-password code paths doing the same expensive work, so a
        // login endpoint doesn't respond measurably faster for usernames
        // that don't exist - a real, exploitable timing oracle for
        // username enumeration if skipped. Only after that verification
        // step runs do you decide whether to actually return Some(user).
    }
}
```

## Session integration: `login()`/`logout()`

```rust
const SESSION_USER_ID_KEY: &str = "_auth_user_id";

/// Establish an authenticated session for `user`. Rotates the session
/// identity first (session-fixation protection: an attacker who fixed a
/// session ID before login gains nothing from the now-authenticated
/// session, since its identity changed), then stores the user's id.
pub fn login<U: AuthUser>(session: &djangors_sessions::Session, user: &U) {
    session.cycle_key();
    session.set(SESSION_USER_ID_KEY, user.id());
}

/// Clear the authenticated session. `Session::clear()` already regenerates
/// the session's internal key as part of clearing (see
/// crates/djangors-sessions/src/lib.rs's `clear()`), so this alone already
/// gives logout a fresh, unrelated session identity - no separate
/// `cycle_key()` call needed here.
pub fn logout(session: &djangors_sessions::Session) {
    session.clear();
}
```

Verify both of these claims against the real `Session` API in
`crates/djangors-sessions/src/lib.rs` before writing this code — read `clear()`'s actual body,
don't take the doc comment above on faith while implementing.

## `Auth<U>` extractor

```rust
/// Extracts the currently-authenticated user of type `U`. Declaring this as
/// a handler parameter (once `FromRequest`-based parameter extraction is
/// wired into `Handler` - check whether that's landed yet; if not, this
/// still works via the existing manual `FromRequest::from_request(&req)`
/// call pattern shown in `crates/djangors-core/src/extract.rs`'s own doc
/// comment) *is* the `login_required` story for v1: if there's no valid
/// session, or the session has no `_auth_user_id`, or that id doesn't match
/// a real active user row, extraction fails with `DjangorsError::Unauthorized`
/// (401) rather than producing an empty/placeholder `Auth`.
pub struct Auth<U: AuthUser>(pub U);

#[async_trait::async_trait]
impl<U: AuthUser> djangors_core::extract::FromRequest for Auth<U> {
    async fn from_request(req: &djangors_core::Request) -> Result<Self, djangors_core::DjangorsError> {
        // 1. req.ext::<djangors_sessions::Session>() - Unauthorized if absent
        //    (SessionLayer wasn't applied, or this genuinely has no session).
        // 2. session.get::<i64>(SESSION_USER_ID_KEY) - Unauthorized if absent.
        // 3. req.state::<djangors_db::Database>() - Internal error if absent
        //    (this is an app misconfiguration, not an auth failure - don't
        //    conflate "no DB configured" with "not logged in").
        // 4. U::objects().filter(q!(id = user_id))?.get(db).await -
        //    Unauthorized (not Internal) if the row doesn't exist anymore
        //    (e.g. account deleted after the session cookie was issued) or
        //    if `!user.is_active()`.
    }
}
```

**`DjangorsError::Unauthorized` does not exist yet** — check `crates/djangors-core/src/error.rs`.
Adding a new variant there (401, alongside the existing `NotFound`/`BadRequest`/`Internal`/
`Panicked`) is in scope for this task, small and precedented (matches how `Response::bytes` and
`Request::ext` were added to `djangors-core` as part of earlier, non-core-focused tasks when the
task genuinely needed them). Follow the exact existing match-arm pattern in that file for
`status_code()` and `into_response()` - add `Unauthorized(String)` (carry a short reason, e.g.
`"not authenticated"` / `"session expired"` / `"account inactive"`, never anything containing
password or hash data) mapped to `StatusCode::UNAUTHORIZED`.

## What this task does NOT include

- Groups, per-model permissions (add/change/delete/view), permission guards — part 4c.
- Password-change/password-reset views and any email-sending story — part 4c (and depends on a
  minimal email backend existing, which doesn't yet - see 4.10's own deferral note).
- Rate limiting / login throttling, audit signals (login/logout/failed-login) — part 4c.
- An actual `POST /login` HTTP view/handler, or wiring `Auth<U>`/`ModelBackend` into any example
  app — see the scope note at the top.
- `FromRequest`-based automatic parameter injection into `Handler` itself, if that doesn't
  already exist — `crates/djangors-core/src/extract.rs`'s own doc comment says extractors are
  currently used by manually calling `from_request(&req)` inside a handler body, with automatic
  injection as declared future work for `Handler`. If still true, `Auth<U>` works the same way
  (manual call inside a handler body) - do not build automatic parameter injection as a side
  effect of this task; that's its own separable piece of work.

## Required tests

- `ModelBackend::authenticate` (real Postgres, same test-table pattern as 4.10's
  `test_user_db_round_trip` - a fresh table, not `auth_user`): correct credentials → `Some(user)`;
  wrong password → `None`; nonexistent username → `None`; inactive user with correct password →
  `None`.
- A timing-shape sanity check is not required as an automated assertion (flaky by nature, same
  reasoning 4.10 used for hashing) - instead, structurally prove the dummy-hash path is real code
  that executes, not dead code: a test for the nonexistent-username case should be able to assert
  something like "authenticate took at least as long as one real Argon2id verification" is
  unnecessary, but the code path itself must be exercised by that test (i.e. don't early-return
  before calling `verify_password` in the not-found case) - review this by reading the
  implementation, not by asserting timing in the test suite.
- `login()` sets the session's `_auth_user_id` to the user's id, and the session's key/identity
  differs before vs. after (reuse the same before/after encode-and-compare approach
  `djangors-sessions`'s own `test_cycle_key` uses, imported/adapted here since `login()` is
  exactly a thin wrapper around that mechanism plus one `session.set` call).
- `logout()` clears `_auth_user_id` (subsequent `session.get::<i64>(SESSION_USER_ID_KEY)` is
  `None`) and the session becomes `is_empty()` again.
- `Auth<U>::from_request`: no session extension present → `Err(Unauthorized)`; session present
  but no `_auth_user_id` set → `Err(Unauthorized)`; valid `_auth_user_id` pointing at a real
  active user (real Postgres) → `Ok(Auth(user))` with the right user data; valid
  `_auth_user_id` pointing at an inactive user → `Err(Unauthorized)`; valid `_auth_user_id`
  pointing at a since-deleted row → `Err(Unauthorized)`, not `Err(Internal)`.
