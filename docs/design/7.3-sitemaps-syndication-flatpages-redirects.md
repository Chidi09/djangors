## Part A — `djangors-contrib-sitemaps` (new crate)

Django's `sitemaps` framework: generates a `sitemap.xml` (the standard XML sitemap protocol —
`<urlset>` of `<url><loc>...</loc><lastmod>...</lastmod><changefreq>...</changefreq></url>`
entries) from a set of registered "sitemap providers." A provider is anything implementing a small
trait:

```rust
pub trait Sitemap: Send + Sync {
    /// Called once per request to produce every URL entry this sitemap contributes.
    fn items(&self) -> Vec<SitemapEntry>;
}
pub struct SitemapEntry {
    pub loc: String, // absolute or relative URL
    pub lastmod: Option<chrono::DateTime<chrono::Utc>>,
    pub changefreq: Option<String>, // "daily", "weekly", etc. — free-form per the spec, don't over-validate
    pub priority: Option<f32>, // 0.0-1.0 per spec
}
```

A `pub fn sitemap_route(providers: Vec<Arc<dyn Sitemap>>) -> impl Handler` (or a
`pub fn sitemap_routes(router: Router, providers: ...) -> Router` mirroring the
`djangors_admin::favicon_routes(router: Router) -> Router` convention already used elsewhere —
read that function for the exact pattern) mounting `GET /sitemap.xml`, correctly XML-escaping every
`loc` value (reuse `djangors_core::html_escape` if it's suitable for XML-escaping too — XML and
HTML share the same five special characters `& < > " '`, confirm this is actually true and the
function is public/reusable before assuming it, otherwise write a small dedicated XML-escape
helper).

A real, testable provider needs a real model to point at — write one small example provider (e.g.
one that wraps a `Vec<String>` of static paths, or a trivial model-backed one if a model is easy to
stand up in the test) and a real test asserting the generated XML is well-formed and contains the
expected `<loc>` entries.

## Part B — `djangors-contrib-syndication` (new crate)

Django's `syndication` framework: RSS 2.0 / Atom feed generation from a similar provider pattern.

```rust
pub trait Feed: Send + Sync {
    fn title(&self) -> String;
    fn link(&self) -> String;
    fn description(&self) -> String;
    fn items(&self) -> Vec<FeedItem>;
}
pub struct FeedItem {
    pub title: String,
    pub link: String,
    pub description: String,
    pub pub_date: Option<chrono::DateTime<chrono::Utc>>,
}
pub fn render_rss(feed: &dyn Feed) -> String; // a well-formed RSS 2.0 XML document
pub fn render_atom(feed: &dyn Feed) -> String; // a well-formed Atom XML document
```

Hand-roll the XML generation (this is simple, well-specified, templated string output — matches
this project's established "hand-roll something this achievable rather than adding a dependency"
precedent, e.g. 5.6.6's CSV escaping) rather than adding a new XML-building crate dependency.
Correctly escape every text field. A route-mounting helper mirroring Part A's shape
(`feed_route`/`feed_routes`).

**Required tests**: a real `Feed` impl with at least two items, asserting the RSS output contains
well-formed `<item>` entries with correctly escaped text (include a title/description containing
`&`/`<` in the test data specifically, to prove escaping actually happens, not just that plain
text round-trips), and the same for Atom.

## Part C — `djangors-contrib-flatpages` (new crate)

Django's `flatpages` app: simple, admin-editable static content pages (a title + HTML/text body)
served by URL path, for things like an About/Terms/Privacy page that doesn't need a real view.

A real `#[derive(Model)]` struct:
```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_contrib_flatpages", table_name = "djangors_flatpage")]
pub struct FlatPage {
    #[djangors(primary_key, auto)]
    pub id: i64,
    #[djangors(max_length = 255, unique)]
    pub url: String, // e.g. "/about/"
    #[djangors(max_length = 255)]
    pub title: String,
    pub content: String, // rendered as-is (trusted admin-authored HTML) or escaped plain text —
                          // decide and document which, matching Django's own "trusted staff
                          // content, rendered as HTML" convention, and say so explicitly in the
                          // module doc since serving raw admin-authored HTML unescaped is a
                          // deliberate trust decision, not an oversight
}
```
A handler (`pub async fn flatpage_handler(req, params) -> Result<Response, DjangorsError>`) that
looks up a `FlatPage` by the request's own path (needs the router to pass the actual matched path
through — check how an existing catch-all/wildcard route works in `djangors-core`'s `Router`, if
one exists, since flatpages need to match *any* unregistered path as a fallback, not a fixed
pattern — if no wildcard/catch-all route mechanism exists yet, document this as a real, honest v1
limitation: flatpages must be registered at specific known paths passed in by the caller, not a
true Django-style "falls through to flatpages for anything else" catch-all, since building a new
router catch-all mechanism is out of scope for this crate). Register `FlatPage` with
`djangors_admin::AdminSite` the normal way (`site.register::<FlatPage>()`) so it's editable through
the existing generic admin — no new admin mechanism needed.

**Required tests**: a real test creating a `FlatPage` row and asserting the handler serves its
content for the matching path and 404s for a non-matching one.

## Part D — `djangors-contrib-redirects` (new crate)

Django's `redirects` app: a `Redirect { old_path, new_path }` model + a lookup helper for
permanent/temporary URL redirects (useful when reorganizing a site's URL structure).

```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_contrib_redirects", table_name = "djangors_redirect")]
pub struct Redirect {
    #[djangors(primary_key, auto)]
    pub id: i64,
    #[djangors(max_length = 255, unique)]
    pub old_path: String,
    #[djangors(max_length = 255)]
    pub new_path: String,
}
```

A middleware or handler helper (mirror whichever pattern is more consistent with how this
framework's request pipeline already composes — read `crates/djangors-core/src/middleware.rs` for
the `tower::Layer` shape used by `SecurityHeadersLayer`/`CsrfLayer`, since a redirect check
naturally wants to run early in the pipeline before normal routing, or decide a plain handler
function is more appropriate if wiring a new generic Layer into arbitrary user router
compositions is more invasive than this crate's scope warrants — explain your choice) that looks up
the current request path in the `Redirect` table and returns a `301`/`308` redirect `Response` if
found, or falls through otherwise. Register `Redirect` with `AdminSite` the normal way.

**Required tests**: a real test proving a registered redirect actually returns the correct redirect
status and `Location` header, and that a non-matching path correctly falls through (doesn't 404 or
error, just doesn't redirect — the exact fallthrough behavior depends on whether this ships as
middleware or a handler, make sure whichever you chose has a real, testable "no redirect configured
here" path).
