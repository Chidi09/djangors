# 10.1 — honest benchmarks: Djangors vs Django, vs axum/actix

## Scope

Phase 9 is done except the landing page (deliberately deferred — needs real domain/hosting
decisions, not autonomously completable). This begins Phase 10 (Hardening & 1.0) with its first
bullet: **"Benchmarks published honestly: vs Django (expect 10–50x), vs axum/actix (target: within

## The non-negotiable rule: real numbers, real methodology, no cherry-picking

**"Published honestly" is the load-bearing word in PLAN.md's own text.** Every number in the final
report must come from an actual benchmark run you executed in this environment, with the exact
command used to produce it shown alongside the number — never write a plausible-sounding number
from general knowledge of how Rust/Python performance "usually" compares. If a comparison framework
can't be set up cleanly in this environment (e.g. Django itself needs installing, an axum
comparison app needs writing), do that setup for real rather than estimating. If a fair comparison
turns out to be harder than expected for a specific case (e.g. Django's response involves the ORM
+ template rendering while your first Djangors test only hits routing), say so explicitly and
either fix the comparison to be apples-to-apples or clearly label the caveat — do not quietly let
an apples-to-oranges comparison produce a misleadingly large number.

## What to build and measure

1. **A minimal, comparable "hello world" HTTP benchmark** across three targets:
   - **Djangors**: a route returning a simple response (use `examples/polls`'s own `index` view or
     a new minimal route in a scratch project — your choice, but document which).
   - **axum**: a minimal axum app with an equivalent route (add a scratch benchmark project under
     `benchmarks/` — not part of the main workspace's published crates — with axum as a dev-only
     comparison target).
   - **Django**: install Django in this environment (`pip install django`, confirm it actually
     installs and runs — if Python/pip isn't available or Django can't be installed here, say so
     explicitly and explain what was tried, don't fabricate Django numbers from memory) with an
     equivalent minimal view, run via its standard `runserver` or (for a fairer prod-like number)
     `gunicorn`/`uvicorn` if installable.
2. **A "full-stack path" benchmark**: a request that hits the database (e.g. `examples/polls`'s
   `index` view, which does a real `Question::objects().filter(...).order_by(...).limit(5).all(db)`
   query) — this is the comparison PLAN.md's own text calls out specifically ("within 15-25% on
   full-stack paths"), so a routing-only benchmark alone doesn't satisfy this bullet.
3. **Load-test tool**: use a real HTTP load-testing tool available in this environment (check what's
   actually installed — `wrk`, `oha`, `hey`, `ab`, or install one via cargo/apt if none exist and
   installation is quick/small) rather than hand-rolling a benchmarking loop, since a mature tool's
   methodology (connection pooling, latency percentiles, concurrency ramp) is more credible than a
   custom script's numbers would be.
4. Run each target under the same load parameters (same concurrency level, same duration, same
   machine — this one, so note in the report that these numbers are single-machine/development-
   environment numbers, not a production cloud benchmark, since that's the honest caveat) and record
   requests/sec, p50/p95/p99 latency.

## Where results go

Write the real methodology and real results to a new `docs/src/benchmarks.md` (add it to
`docs/src/SUMMARY.md`'s nav too), including: exact versions of everything benchmarked (Rust
version, Django version, axum version), exact hardware/environment caveat, the exact commands used
to run each benchmark (so a skeptical reader could reproduce them), and the raw numbers — not just
a "10-50x faster" summary line, show the real requests/sec and latency numbers for all three
targets side by side.
