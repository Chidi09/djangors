# 5.8 part 3 — Convert the bulk-delete confirm page to a template

**Status:** design, not yet dispatched. Follows 5.8.2 (delete-confirm template, commit `dfe6ec0`).
See `docs/design/phase-5-roadmap.md`. Same discipline as 5.8.1/5.8.2: one page, byte-identical
output, no visual changes, proven by the existing test passing unmodified.

## Scope: only the confirm-step branch of `admin_bulk_delete_post`

`admin_bulk_delete_post` (`crates/djangors-admin/src/lib.rs` ~line 2010-2100) has two response
shapes: the confirm-step HTML (`if !is_confirm { ... }`, ~line 2048-2079) and a plain
`Response::redirect(...)` for the actual delete step (no HTML at all — nothing to convert there).
**This task converts only the confirm-step HTML.** Everything else in the handler (param/admin/db
resolution, `require_perm`, `Form` parsing, pk parsing, the empty-selection redirect, the actual
delete loop and its final redirect) is unchanged.

## Template file: `crates/djangors-admin/templates/admin/bulk_delete_confirm.html`

```html
<p>Delete {{ count }} selected object(s)?</p><ul>{% for item in items %}<li>{{ item }}</li>{% endfor %}</ul><form method="post">{% for pk in pks %}<input type="hidden" name="selected" value="{{ pk }}">{% endfor %}<input type="hidden" name="confirm" value="1"><input type="submit" value="Confirm Delete"></form>
```

One continuous line, matching the existing two templates' convention exactly. Must reproduce the
current `format!("<p>Delete {} selected object(s)?</p><ul>{}</ul><form method=\"post\">{}<input
type=\"hidden\" name=\"confirm\" value=\"1\"><input type=\"submit\" value=\"Confirm
Delete\"></form>", pks.len(), items_html, hidden_inputs)` byte-for-byte.

## Context struct and handler change

```rust
#[derive(serde::Serialize)]
struct BulkDeleteConfirmContext {
    count: usize,
    items: Vec<String>,
    pks: Vec<i64>,
}
```

Replace the `items_html`/`hidden_inputs`/final `format!` block with: build `items: Vec<String>`
from the same per-pk `row_vals.iter().map(|(_, v)| v.to_string()).collect::<Vec<_>>().join(", ")`
logic already there (one entry per pk that still exists — a concurrently-deleted pk is still
silently skipped, matching the existing comment/behavior exactly), `count: pks.len()`. **Use
`pks: pks.clone()`, not a move** — confirmed `pks` (the `Vec<i64>`) is used again after this `if`
block returns, in the step-2 delete loop (`for &pk in &pks { admin.delete_by_pk(db, pk).await?;
}`, a few lines below), so moving it into the context struct here would fail to compile. Replace
`Ok(Response::html(StatusCode::OK, html))` with
`djangors_template::render(&ADMIN_TEMPLATES, "admin/bulk_delete_confirm.html",
BulkDeleteConfirmContext { count, items, pks })`.

`pks: Vec<i64>` needs no `Safe`-wrapping — integers stringify to plain digits, nothing minijinja's
HTML autoescape ever touches. `items` is genuinely dynamic per-row display text (same class of
content as 5.8.2's `DeleteConfirmField.value`) — plain `String`, let autoescape handle it
normally, no `Safe`-wrapping there either.

## `ADMIN_TEMPLATES`: add the third entry

Same `from_embedded` call, one more `(name, include_str!(...))` pair:
`("admin/bulk_delete_confirm.html", include_str!("../templates/admin/bulk_delete_confirm.html"))`.

## What NOT to touch

- The delete-step branch of `admin_bulk_delete_post` (no HTML there — untouched).
- Any other handler or page.
- No CSS/visual changes.
- No changes to `djangors-template` itself.
