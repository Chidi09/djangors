# Design 4.6 — Static files (v1 scope)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 3's staticfiles bullet first.

## v1 scope

`PLAN.md` lists: dev serving, `collectstatic`, hashed-manifest storage (cache-busting), and an embed-in-binary option. All four are independently useful and don't have the same "depends on an unbuilt system" problem migrations/templates/forms hit — static file serving is genuinely self-contained. **v1 delivers all four**, but keeps each one's implementation intentionally simple:

- **Dev serving**: a `tower::Service` (or a plain async fn usable as a `djangors_core::Handler`, matching how the rest of this framework's HTTP layer works) that serves files directly from a configured directory, with the URL path mapped 1:1 to a file path underneath it. No directory-listing, no range-request/partial-content support in v1 (real but not blocking — most dev servers skip range support and it's rarely missed until video/large-file serving comes up, which isn't this project's immediate use case).
- **`collectstatic`**: walks one or more source directories (mirroring `djangors-template`'s multi-directory search-and-precedence pattern — reuse that exact ordered-directory-list idea here too, for consistency across the two systems) and copies every file into one output directory, matching Django's actual `collectstatic` behavior of gathering scattered app-level static directories into one deployable tree.
- **Hashed-manifest storage**: for each collected file, compute a content hash (short SHA-256 prefix is fine, matching the general shape of Django's `ManifestStaticFilesStorage` — `style.a1b2c3d4.css` naming), write the hashed-named copy into the output directory, and build a `manifest.json` mapping the original relative path to its hashed name — this is what enables safe far-future cache headers (`Cache-Control: max-age=31536000, immutable`) since the URL changes whenever the content does.
- **Embed-in-binary**: v1 achieves this via `include_dir!` (from the `include_dir` crate, or an equivalent) wrapped behind a Cargo feature flag (e.g. `embed`) so dev builds keep fast-reloading from disk (matching this project's Phase 1 dev-loop design goal of sub-3-second rebuilds) while release builds can opt into baking the collected+hashed static tree directly into the compiled binary for true single-file deployment.

## Crate shape

New crate `djangors-staticfiles` (already an empty placeholder). Depends on `djangors-core` (the dev-serving handler needs `Request`/`Response`/`Handler`), `sha2` (for content hashing — verify exact version), and optionally `include_dir` behind the `embed` feature flag.

```rust
pub struct StaticFiles {
    /// Ordered source directories, same override-precedence idea as
    /// djangors-template's loader: earlier directories win on a name
    /// collision during collectstatic.
    source_dirs: Vec<PathBuf>,
}

impl StaticFiles {
    pub fn new(source_dirs: Vec<PathBuf>) -> Self { ... }

    /// Serve a single file by its URL-mapped path directly from `source_dirs`
    /// (dev mode — no hashing, no manifest, just find-and-serve). Usable
    /// directly as a djangors_core::Handler.
    pub async fn serve(req: djangors_core::Request, params: djangors_core::PathParams) -> Result<djangors_core::Response, djangors_core::DjangorsError> { ... }

    /// Collect every file from `source_dirs` into `output_dir`, hashing each
    /// one's content into its filename and writing a manifest.json mapping
    /// original relative paths to hashed names. This is what `dj collectstatic`
    /// (djangors-cli, not built as part of this task) will eventually call.
    pub fn collect(&self, output_dir: &Path) -> Result<Manifest, StaticFilesError> { ... }
}

pub struct Manifest {
    /// original relative path -> hashed relative path
    pub mapping: std::collections::HashMap<String, String>,
}
```

## What this task does NOT include

Wiring `dj collectstatic` into `djangors-cli` (that CLI subcommand doesn't exist yet as a stub — `djangors-cli`'s existing stub list doesn't have it; adding it is a small follow-up once this crate exists, mirroring how `dj migrate` was wired to `djangors-migrations` after that crate was real). The `embed` feature's actual `include_dir!` integration can be deferred to a fast follow-up if it proves to need more design thought than expected once the core `collect()`/`serve()` functions are real — note this explicitly if cut, don't force it into scope at the cost of the core functionality's correctness.
