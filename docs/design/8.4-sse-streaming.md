# 8.4 — Server-Sent Events (SSE) streaming support (Phase 8, high-care slice)

## Why this is its own isolated, high-care slice

`crates/djangors-core/src/response.rs`'s `Response` is explicitly documented as "An HTTP response
with a fully buffered body" — its `body: Bytes` field, `into_hyper()`, and
`From<Response> for hyper::Response<http_body_util::Full<Bytes>>` are all hardcoded to a
non-streaming body type. **Every existing handler in the entire framework returns this exact
`Response` type**, and `crates/djangors-core/src/app.rs`'s `serve_connection`/
`serve_connection_service` both construct `hyper::server::conn::http1::Builder::new()
.serve_connection(io, svc)` against it. Real Server-Sent Events (a long-lived response that sends
chunks over time, `Content-Type: text/event-stream`) genuinely cannot be built on top of a
fully-buffered `Bytes` body — this requires real, careful core-crate work, the same class of
change as 6.4's graceful shutdown (isolated into its own slice given the blast radius, extra
verification care, not bundled with anything else).

**Deliberately excluded from this dispatch**: real WebSocket support. A WebSocket connection needs
hyper's raw `on_upgrade()` mechanism (intercepting the request *before* the normal
`Router::dispatch` path even runs, since an upgrade changes the connection's protocol entirely) —
a materially different, deeper change than adding a streaming response body type, and deserves its
own even-more-isolated future slice (8.5) once this one lands and is proven safe. Read this whole
doc, and `crates/djangors-core/src/app.rs`/`src/response.rs`/`src/router.rs` in full, before
writing any code — the exact current behavior matters here more than almost anywhere else in this
project.

## Design: additive only — do not change `Response`'s existing behavior for any current handler

**Do not modify `Response`'s existing fields, constructors, or `into_hyper()`.** Every one of the
~300+ existing tests across this workspace constructs a `Response` via `Response::text`/`html`/
`json`/`bytes`/`redirect` and expects the current fully-buffered behavior; none of that may change.
Instead, add a **new, separate** streaming response mechanism that the connection-serving loop
recognizes and handles differently, alongside the existing path, not replacing it.

Sketch (verify every piece against the real current code — hyper/http-body-util API surfaces are
easy to get subtly wrong, and this project's own `Cargo.lock`-pinned versions matter):

```rust
// A body type usable for a real streaming HTTP response, built from an async stream of
// Bytes chunks (an SSE event is encoded as `data: <payload>\n\n` per the SSE wire format;
// callers build a stream of already-encoded chunks or use a helper that encodes for them).
pub struct StreamingResponse {
    status: StatusCode,
    headers: HeaderMap,
    stream: Pin<Box<dyn Stream<Item = Result<Bytes, std::convert::Infallible>> + Send>>,
}

impl StreamingResponse {
    pub fn sse(stream: impl Stream<Item = String> + Send + 'static) -> Self {
        // maps each item to the SSE wire format ("data: {item}\n\n" as bytes), sets
        // Content-Type: text/event-stream, Cache-Control: no-cache, Connection: keep-alive
        // (check whether Connection: keep-alive is even meaningful/needed with HTTP/1.1's
        // own keep-alive default before adding it as a hardcoded header — verify, don't
        // just copy convention blindly)
    }
}
```

The connection-serving side needs a real, additive extension. Two realistic approaches — read the
current `serve_connection`/`serve_connection_service` code in full, then pick whichever is
genuinely lower-risk given what's actually there, and explain the choice:

1. **A separate `Handler` variant/enum** that a route can register (e.g.
   `Router::get_streaming(path, handler)` alongside the existing `Router::get`), where the
   returned `StreamingResponse` is converted to a hyper response using a *different* body type
   (e.g. `http_body_util::StreamBody` wrapping the stream, boxed into a common
   `http_body_util::combinators::BoxBody<Bytes, Infallible>` so both the existing `Full<Bytes>`
   path and this new streaming path can coexist under one boxed body type in
   `serve_connection`/`serve_connection_service` — this likely requires changing the hyper
   service's declared `Response` associated type from `hyper::Response<Full<Bytes>>` to
   `hyper::Response<BoxBody<Bytes, Infallible>>`, wrapping the *existing* `Full<Bytes>` case in a
   `BoxBody::new(...)` too so both cases produce the same output type — verify this is achievable
   without breaking the existing `tower::Service` bound signature used throughout
   `serve_service`/`RouterService`/the CSRF and security-headers layers, since those are generic
   over a specific `Response = hyper::Response<http_body_util::Full<Bytes>>` bound today (grep for
   this exact bound across `app.rs`/`router.rs`/`middleware.rs`) — if boxing the body type would
   require changing that bound everywhere it appears, that's a wider blast radius than this slice
   should take on; if so, prefer approach 2 instead.
2. **A fully separate, parallel serving path** specifically for streaming routes — e.g. SSE routes
   are registered and served through their own dedicated mechanism that doesn't need to unify with
   the existing `tower::Service`-bound plumbing at all (a project mounts SSE endpoints via a
   distinct API, not through the same `Router`/`RouterService` middleware-composable path). Lower
   risk to the existing test suite and existing `Response = Full<Bytes>` bound used everywhere,
   at the cost of SSE routes not being composable with the existing CSRF/security-headers `tower`
   layers the same way normal routes are — document this limitation clearly if you take this path.

**Decide based on what you actually find reading the real code, not this doc's speculation about
which is easier — report which approach you took and why.**

## Part B — in-process groups/broadcast primitive

A simple, real pub/sub mechanism usable by SSE handlers (and, later, WebSocket handlers once 8.5
lands) to broadcast messages to multiple connected clients — in-process only for this v1, a Redis
backplane is explicitly out of scope here (PLAN.md's own text lists "in-process + Redis backplane"
as the eventual goal; ship the in-process half first, for real, rather than a stub of both).

```rust
pub struct Groups {
    // a registry of named groups, each backed by a real tokio::sync::broadcast::Sender<String>
}
impl Groups {
    pub fn new() -> Self;
    pub fn group(&self, name: &str) -> GroupHandle; // creates the group's broadcast channel
                                                     // lazily on first access if it doesn't exist
    // GroupHandle: .send(msg: String) (fans out to every current subscriber, if any — a
    // broadcast channel with zero receivers should not error, matching tokio::sync::broadcast's
    // own real semantics, confirm this before relying on it), .subscribe() -> a Stream of
    // messages an SSE handler can forward to its own client
}
```

**Required tests**: a real end-to-end test proving an SSE response's stream actually delivers
multiple chunks over a real socket connection (not just that the stream type compiles) — spin up a
real listener (mirroring `app.rs`'s own existing `real_socket_request_response` test pattern),
mount an SSE route backed by a `Groups`-based broadcast, connect a real client, have a second
"publisher" send messages into the group, and assert the client actually receives them over the
wire, in order, as real SSE-formatted `data: ...` lines. This is the one test that actually proves
streaming works end-to-end, not just that the types compile — don't skip or fake it.

**Required regression check, mandatory**: the full existing test suite (`cargo test --workspace`)
must pass completely unmodified — this is the same "full-blast-radius regression check" discipline
required for 6.4's graceful shutdown, given `Response`/the connection-serving loop are exactly as
central here. Explicitly confirm both example apps' full-stack integration tests
(`examples/polls/tests/voting.rs`, `examples/school/tests/admin_crud.rs`) pass by name.
