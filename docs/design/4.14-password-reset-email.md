# Design 4.14 — minimal djangors-mail + password-reset flow (Phase 4 part 4d, slice 1)

**Status:** draft, pre-implementation. Closes the remaining piece of Phase 4's own DoD line
("full password-reset flow works via console email backend") that [[4.13-security-review-fuzzing]]
didn't cover. `PLAN.md` assigns a full `djangors-mail` (SMTP+TLS, console, file, in-memory
backends, HTML+text multipart) to **Phase 7**. This task does **not** build that. It pulls forward
only the minimal real slice Phase 4's own DoD needs — a `Message` struct, a `MailBackend` trait,
and a console backend — same pattern this project already used for sessions (signed-cookie only,
not database/cache backends) and rate limiting (in-memory only, not distributed). Groups and
model-level permissions remain **not** in scope here (no DoD line requires them yet) — still
deferred, unscheduled.

## Part 1: minimal `djangors-mail` crate (new crate, not a placeholder — check `Cargo.toml`
workspace members list, add it there)

```rust
pub struct Message {
    pub to: Vec<String>,
    pub from: String,
    pub subject: String,
    pub body: String, // plain text only — no HTML/multipart, that's Phase 7
}

#[async_trait::async_trait]
pub trait MailBackend: Send + Sync {
    async fn send(&self, message: &Message) -> Result<(), MailError>;
}

pub struct ConsoleBackend; // writes the message to stdout (or tracing::info!, pick
                           // whichever this project's existing logging convention
                           // favors — check crates/djangors-core/src/logging.rs
                           // for the established tracing setup before deciding)

#[async_trait::async_trait]
impl MailBackend for ConsoleBackend {
    async fn send(&self, message: &Message) -> Result<(), MailError> { /* print, Ok(()) */ }
}

#[derive(thiserror::Error, Debug)]
pub enum MailError {
    #[error("failed to send mail: {0}")]
    Send(String),
}
```

That's the entire crate. No SMTP, no file backend, no in-memory test backend beyond what's needed
to unit-test `ConsoleBackend` itself, no HTML. Explicitly note this scope limit in the crate's own
top-level `//!` doc comment so nobody mistakes this for the real Phase 7 deliverable.

## Part 2: password-reset token — self-contained in djangors-auth, no new crate/schema

Django's own scheme (`PasswordResetTokenGenerator`) is the right shape to mirror: a signed token
that embeds enough of the user's *current* state that it automatically becomes invalid the moment
the password actually changes (or the account is deactivated) — no separate `PasswordResetToken`
DB table/migration needed, which is why this doesn't require new ORM schema and can stay in part
4d instead of waiting on a real permissions-schema task.

```rust
/// HMAC-SHA256 over `user_id . expiry_unix_secs . password_hash_prefix`, base64-joined
/// the same `b64part.b64part.b64mac` shape `djangors-sessions`'s `SignedCookieStore`
/// already uses (read crates/djangors-sessions/src/lib.rs's encode/decode for the exact
/// pattern to mirror — do not import djangors-sessions itself for this, djangors-auth
/// already depends on the `hmac`/`sha2`/`base64` crates indirectly; check Cargo.lock for
/// already-resolved versions before adding them directly here, same discipline as every
/// prior task this session).
///
/// Including a prefix of the CURRENT password_hash in the signed payload (not the
/// user's id/email alone) is the actual security property: once the user's password
/// changes (whether via this same reset flow completing, or any other path), any
/// previously-issued token for them stops verifying, because the hash prefix embedded
/// in it no longer matches. This is what makes the token single-use in practice without
/// a database table tracking "used" tokens.
pub fn generate_password_reset_token<U: AuthUser>(user: &U, secret: &[u8], ttl: Duration) -> String { ... }
pub fn verify_password_reset_token<U: AuthUser>(user: &U, token: &str, secret: &[u8]) -> bool { ... }
```

Two async helper functions (mirroring how `login()`/`logout()` are session-helpers, not HTTP
views — [[4.11-auth-backend-login]]'s own scope boundary applies again here):

```rust
/// Look up `email`, and IF a matching active user exists, send them a reset email via
/// the given MailBackend containing a link/token built from generate_password_reset_token.
/// If no user matches, do nothing observable (same username/email-enumeration concern
/// ModelBackend::authenticate already handles - do not let this function's timing or
/// return value reveal whether the email was registered; always return Ok(()) regardless,
/// and only skip the actual send if there's no match - the caller-visible behavior must
/// be identical either way, matching Django's own "always show a generic success page"
/// UX pattern).
pub async fn request_password_reset<U: AuthUser>(
    db: &djangors_db::Database,
    mail: &dyn MailBackend,
    email: &str,
    secret: &[u8],
    reset_link_base: &str, // e.g. "https://example.com/reset-password" - caller-supplied,
                            // this crate doesn't know the app's own URL scheme
) -> Result<(), AuthError>;

/// Verify token against the user identified by user_id, and if valid, set their new
/// password (hash_password it) and save. Returns an error (reuse Unauthorized-shaped
/// semantics, or a new AuthError variant if that reads better - use judgement) if the
/// token doesn't verify.
pub async fn confirm_password_reset<U: AuthUser>(
    db: &djangors_db::Database,
    user_id: i64,
    token: &str,
    new_password: &str,
    secret: &[u8],
) -> Result<(), AuthError>;
```

New `djangors-auth` dependency: `djangors-mail` (path dep, the crate from Part 1). `djangors-auth`
already depends on `djangors-db` for the DB parameter type these functions need.

## What this task does NOT include

- SMTP/file/in-memory mail backends, HTML email — Phase 7's real `djangors-mail`.
- An actual `POST /password-reset` HTTP view/form/template, or wiring this into the polls example
  — app-specific plumbing, same boundary [[4.11-auth-backend-login]] drew around `login()`/
  `logout()` not shipping a `POST /login` view either.
- Groups, model-level permissions — still unscheduled, no DoD line needs them yet.
- A DB table tracking used/revoked reset tokens — deliberately avoided per Part 2's design (the
  password-hash-prefix-in-token trick makes tokens self-invalidating without one).

## Required tests

- `ConsoleBackend::send` doesn't error on a well-formed `Message` (and, if using `tracing`,
  reads back via whatever this project's existing tracing test-capture convention is if one
  exists — check other crates' tests for a precedent before inventing a new one; a simple
  "doesn't panic/error" assertion is acceptable if no capture precedent exists).
- `generate_password_reset_token`/`verify_password_reset_token`: valid token round-trips; token
  expired (past ttl) fails; token for a *different* user fails; token verifies fine before a
  password change, then fails after the password changes (this is the actual security property —
  test it explicitly, not just round-trip happy path).
- `request_password_reset`: existing active user → `MailBackend::send` is called (use a test
  double `MailBackend` with a call-recording `Vec<Message>`, same test-double pattern
  [[4.12-auth-rate-limit-signals]]'s own `RateLimitedBackend` test already used) with a message
  containing the generated token; nonexistent email → `send` is NOT called, but the function still
  returns `Ok(())` (real Postgres, same test-table pattern as prior djangors-auth tests).
- `confirm_password_reset`: valid token + new password → user's `password_hash()` changes to a
  hash of the new password (verify via `verify_password`); invalid/expired token → user's password
  is unchanged and the function returns an error.
