# Design 4.2 — QuerySet ergonomics

**Status:** draft, pre-implementation. Depends on [4.1 — Model metadata](4.1-model-meta.md). Read `PLAN.md` Part 4.2 first.

## The problem

Django's `Question.objects.filter(pub_date__lte=now, author__name__icontains="x")` is stringly-typed: `pub_date__lte` is a runtime-parsed string, and a typo (`pub_dat__lte`) is a `FieldError` at request time, sometimes in production. Rust can do much better — but "much better" has to still *feel* like Django's lookup syntax to a Django developer, or the framework's core pitch (Django's ergonomics, Rust's safety) is broken on day one of actually writing a query.

The resolution is two APIs over one shared expression tree: a **fluent typed API** for people who want pure-Rust IDE completion, and the **`q!()` macro** which accepts Django's exact `field__lookup` syntax but is validated against `ModelMeta` at compile time. Both compile down to the same `Expr` tree; neither is a "lesser" option.

## The shared expression tree

```rust
// djangors-orm/src/expr.rs

pub enum Expr {
    Compare { field: &'static str, op: CompareOp, value: Value },
    And(Vec<Expr>),
    Or(Vec<Expr>),
    Not(Box<Expr>),
    IsNull { field: &'static str, negated: bool },
    In { field: &'static str, values: Vec<Value> },
    Raw(String, Vec<Value>), // escape hatch — .raw_where("...", params)
}

pub enum CompareOp { Eq, Lt, Lte, Gt, Gte, Contains, IContains, StartsWith, EndsWith, Regex }

/// A dynamically-typed value the query builder can bind as a SQL parameter.
/// Backed by sqlx's `Encode`/`Type` traits per-database — this enum exists so
/// `Expr` doesn't need to be generic over every possible field type.
pub enum Value { I64(i64), F64(f64), Text(String), Bool(bool), DateTime(chrono::DateTime<chrono::Utc>), Decimal(rust_decimal::Decimal), Uuid(uuid::Uuid), Null }
```

`Q` (Django's `Q` object for combining filters with `|`/`&`/`!`) is just `Expr` with operator overloads:

```rust
impl std::ops::BitOr for Expr { fn bitor(self, rhs: Self) -> Expr { Expr::Or(vec![self, rhs]) } }
impl std::ops::BitAnd for Expr { fn bitand(self, rhs: Self) -> Expr { Expr::And(vec![self, rhs]) } }
impl std::ops::Not for Expr { fn not(self) -> Expr { Expr::Not(Box::new(self)) } }
```

so `q!(a) | q!(b)` and `!q!(c)` work with zero additional machinery — the macro's only job is producing an `Expr`, everything else is ordinary Rust operator overloading.

## `q!()` — the macro

```rust
q!(pub_date__lte = now, author__name__icontains = "x")
```

expands (roughly) to:

```rust
Expr::And(vec![
    Expr::Compare { field: "pub_date", op: CompareOp::Lte, value: Value::from(now) },
    Expr::Compare { field: "author__name", op: CompareOp::IContains, value: Value::from("x") },
])
```

**Compile-time validation is the entire point of building this as a proc macro instead of a runtime string parser.** At macro-expansion time, `q!()` needs to resolve `pub_date` and `author__name` against the target model's `ModelMeta` — which means `q!()` cannot be a free-standing macro with no type context; it must be invoked in a position where the target model is known. Two ways to get there, pick based on implementation cost:

1. **Turbofish-style explicit target:** `q!(Question, pub_date__lte = now)` — macro takes the model type as its first argument, calls `Question::meta()` at... no, `meta()` is a runtime function, and macros expand before running any code. This doesn't work directly.
2. **Two-phase: macro emits a closure, `.filter()` resolves it.** `q!(pub_date__lte = now)` expands to a marker type/closure that captures `(field_name: &'static str, op, value)` tuples *without* validating field names at macro-expansion time — instead, `QuerySet<T>::filter()` (which DOES know `T` and therefore `T::meta()`) validates the field names against `T::META.fields` **at first construction, via a `const`-context assertion or a build-time test**, not truly "compile error on typo" in the strictest sense, but effectively equivalent via CI-enforced `#[test]`-time checking plus a clear panic message during normal `cargo test`/`cargo build` of the *calling* crate.

**Decision: go with a hybrid.** `q!()` alone (no model context) expands to an `UnresolvedExpr` — field names as `&'static str`, not yet checked. `QuerySet<T>::filter(expr: impl Into<Expr>)` accepts `UnresolvedExpr` and resolves+validates it against `T::META` at *runtime*, but that runtime check happens unconditionally the moment a `QuerySet` is constructed — meaning any `#[test]` that touches the query (and the ORM's own test suite, plus the convention of "every model gets at least a smoke-test query" in project templates) catches a typo immediately, not "sometime in production" the way Django can. This is *not* a true Rust compile error and that's an honest limitation to document, not paper over — revisit for a v2 that explores whether `T::FIELD_NAMES: &'static [&'static str]` as an associated `const` could let `filter()` do a `const`-context lookup (`array::contains` is const-fn-eligible; whether the ergonomics survive is untested, don't block v1 on it).

Lookups supported day one: `__lte`, `__lt`, `__gte`, `__gt`, `__contains`, `__icontains`, `__startswith`, `__endswith`, `__in` (takes a `Vec`), `__isnull` (takes `bool`), `__regex`, and relation traversal (`author__name__icontains` walks the FK via a SQL `JOIN`, resolved using `RelationMeta` from 4.1 — this is also where `select_related` becomes necessary: a relation-traversing filter *implies* the join already, `select_related` is about eagerly fetching the related row's *columns* into the result, not about whether the join happens for filtering purposes).

## The fluent typed API (the other half of the "not a lesser option" promise)

`#[derive(Model)]` also generates a `Fields` struct per model:

```rust
impl Question {
    pub fn fields() -> QuestionFields { QuestionFields }
}
pub struct QuestionFields;
impl QuestionFields {
    pub fn pub_date(&self) -> FieldRef<DateTime<Utc>> { FieldRef::new("pub_date") }
    pub fn question_text(&self) -> FieldRef<String> { FieldRef::new("question_text") }
}
impl<T> FieldRef<T> where T: Into<Value> {
    pub fn lte(self, v: T) -> Expr { Expr::Compare { field: self.name, op: CompareOp::Lte, value: v.into() } }
    // .lt/.gte/.gt/.contains/.eq/... mirroring q!()'s lookup set
}
```

so `Question::fields().pub_date().lte(now)` produces the *identical* `Expr` as `q!(pub_date__lte = now)`, and **this one genuinely is compile-checked** — `pub_date()` doesn't exist on `QuestionFields` if the field was renamed/removed, full IDE autocomplete, no runtime resolution step at all. This is the API to recommend in docs for anyone who asks "how do I get a real compile error on a typo'd field" — the honest answer is "use the fluent API," not "trust `q!()`."

## `QuerySet<T>` — laziness and the built-in operation set

```rust
pub struct QuerySet<T: Model> {
    filters: Vec<Expr>,
    order_by: Vec<(String, bool)>, // (field, descending)
    limit: Option<u64>,
    offset: Option<u64>,
    select_related: Vec<String>,
    _marker: PhantomData<T>,
}
```

Every builder method (`.filter()`, `.order_by()`, `.limit()`, `.select_related()`, `.exclude()`) takes `self` by value and returns `Self` — a `QuerySet` is a **pure value** until one of the terminal methods executes it against a connection:

- `.all(&db) -> Result<Vec<T>, DjangorsError>`
- `.get(&db) -> Result<T, DjangorsError>` (errors if 0 or >1 rows — Django's `DoesNotExist`/`MultipleObjectsReturned`, collapsed into typed `DjangorsError` variants)
- `.get_or_404(&db) -> Result<T, DjangorsError>` (the framework's own convenience, not Django's — Django's `get_object_or_404` is a view-layer helper; here it's a QuerySet method since there's no separate "shortcuts" module planned)
- `.first(&db) -> Result<Option<T>, DjangorsError>`
- `.exists(&db) -> Result<bool, DjangorsError>` (compiles to `SELECT 1 ... LIMIT 1`, not a full row fetch)
- `.count(&db) -> Result<i64, DjangorsError>`
- `.update(&db, set!(...)) -> Result<u64, DjangorsError>` (returns rows affected)
- `.delete(&db) -> Result<u64, DjangorsError>`
- `.iterator(&db) -> impl Stream<Item = Result<T, DjangorsError>>` (streaming, for large result sets — backed by sqlx's own streaming query support)

Being a pure value until executed is what makes a `QuerySet` **reusable and composable** exactly like Django's: `let base = Question::objects().filter(q!(...)); let recent = base.clone().order_by("-pub_date").limit(5);` — reuse `base` for a second, different query without re-specifying the filter.

## `F()` expressions (race-safe updates)

```rust
pub struct F(pub &'static str);
impl std::ops::Add<i64> for F { type Output = SetExpr; fn add(self, rhs: i64) -> SetExpr { ... } }
```

`set!(votes = F("votes") + 1)` compiles to `UPDATE ... SET votes = votes + 1` — the increment happens **in the database**, not as a read-then-write from Rust, which is the entire point (avoids the lost-update race Django's `F()` exists to prevent). `set!()` mirrors `q!()`'s two-phase resolution story.

## Aggregation (addendum — written once filtering was real and proven, as planned above)

**v1 scope: `.aggregate()` only, no `.annotate()`.** Django's `.aggregate()` collapses a queryset to a single row of scalar results (`Question.objects.aggregate(Avg('votes'))` → one dict); `.annotate()` adds a *per-row* computed column via `GROUP BY` (`Question.objects.annotate(num_choices=Count('choice'))` → still N rows). `.annotate()` needs `GROUP BY` clause generation and interacts with `.filter()`/`.order_by()` in ways `.aggregate()` doesn't (Django's own `HAVING`-vs-`WHERE` distinction). Building that properly is real additional design work — defer it the same way `select_related` was deferred here originally.

## `select_related` addendum — a terminal method, not a chainable modifier (deliberate simplification from the original sketch above)

Django's `.select_related()` is chainable and mutates how `.all()`/`.get()`/etc. populate results — the related object gets attached directly onto the instance's attribute (`choice.question` becomes a real loaded `Question`, not a lazy descriptor). Building that in Rust means `ForeignKey<T>` needs somewhere to hold an optionally-loaded `T` — e.g. `ForeignKey<T> { id: i64, loaded: Option<Box<T>>, _marker: PhantomData<T> }`. That's a real, valid design, but it has a real cost: `ForeignKey<T>` is `Copy` today (it's tested — `djangors-orm`'s `test_foreign_key_clone_copy`), and `Option<Box<T>>` isn't `Copy`, so this would downgrade every model with a relation field from `Copy` to `Clone`-only, rippling into anywhere that currently relies on the `Copy` guarantee.

**v1 ships the actual value of `select_related` — avoiding an N+1 query — without that ripple**, via a distinct terminal method rather than a chainable modifier, the same pattern already used for `.aggregate()` and the bulk `.update()`:

```rust
impl<T: Model + FromRow> QuerySet<T> {
    pub async fn select_related<R: Model + FromRow>(
        &self,
        db: &Database,
        relation_field: &'static str,
    ) -> Result<Vec<(T, Option<R>)>, OrmError> { ... }
}
```

`relation_field` is validated against `T::meta().relations` (same discipline as every other field-name-taking method in this file). The query is a single `LEFT JOIN` between `T`'s table and `R`'s table on the relation's FK column, reusing the existing `self.filters` for the `WHERE` clause exactly like every other terminal method. Returns `(T, Option<R>)` per row — `None` for a nullable FK that's actually null, `Some` otherwise — rather than mutating a `ForeignKey<T>` field in place. This is an honest, understood API difference from Django (`(question, choice) = ...` instead of `choice.question`), not a hidden gap — the query-count win (one query instead of N+1) is the actual point, and it's fully delivered by this shape. Revisit the `ForeignKey<T>`-attached-instance design only if real usage shows the tuple return is genuinely awkward in practice, not preemptively.

```rust
pub enum AggExpr {
    Count { field: &'static str },       // COUNT(field) — use "*" for COUNT(*)
    Sum { field: &'static str },
    Avg { field: &'static str },
    Min { field: &'static str },
    Max { field: &'static str },
}

pub enum AggResult {
    I64(i64),
    F64(f64),
    Null,   // e.g. AVG/SUM/MIN/MAX over zero matching rows
}
```

`QuerySet<T>::aggregate(&self, db: &Database, aggs: Vec<AggExpr>) -> Result<Vec<AggResult>, OrmError>` — same validation discipline as `.filter()`/`.order_by()`: every `AggExpr::field` (except `Count`'s `"*"` sentinel) is checked against `T::meta().fields` before touching SQL, for the same injection-safety reason `order_by()` needed fixing. Compiles to `SELECT {agg_sql_1}, {agg_sql_2}, ... FROM {table} WHERE {existing filters}` (reusing `QuerySet`'s existing filter-compilation — aggregation composes with `.filter()` exactly like Django's does, no `.order_by()`/`.limit()`/`.offset()` applied since a single aggregate row has no ordering/pagination to apply), executed as one row fetch, with per-column type determined by the aggregate kind (`COUNT` → always `i64`; `SUM`/`AVG`/`MIN`/`MAX` → depends on the underlying column's SQL type, but for v1 assume numeric columns only and read back as `f64` falling back to `AggResult::Null` on a SQL `NULL` — `MIN`/`MAX` over a text column is valid SQL but out of scope for v1's `AggResult` shape, which is numeric-only; document this restriction rather than silently mishandling a text `MIN`/`MAX`).

## What this unblocks

`djangors-migrations`' autodetector doesn't touch `Expr`/`QuerySet` at all — it only reads `ModelMeta` (4.1) directly. `djangors-admin`'s changelist filtering/search *does* build `QuerySet`s dynamically from user-submitted GET params, which is exactly why the two-phase runtime-resolved path (not just the compile-checked fluent API) has to exist and be solid — the admin cannot know field names at Rust-compile time, they come from `ModelMeta` at admin-registration time. This is the strongest argument for building the `q!()`/two-phase path with real care rather than treating it as the "worse" option next to the fluent API — the admin depends on it structurally, it is not optional scaffolding.
