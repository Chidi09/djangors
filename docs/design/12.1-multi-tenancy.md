# Multi-tenancy support — design doc (Phase 12, task #71)

**Status:** proposed, not yet implemented. Per PLAN.md's own framing this is "the most
architecturally invasive item" in the Phase 12 hardening pass, deliberately sequenced last and
gated on a design doc before any code — this is that doc.

## Why this, and why now

Djangors targets exactly the workloads where multi-tenancy is the default shape, not an edge case:
school management SaaS (one deployment, many schools), banking backends (one deployment, many
institutions/branches), and B2B e-commerce platforms. PLAN.md Part 6 item 5 already names this
directly: "Object-level permissions + row scoping (a teacher sees only their class; a branch
officer only their branch) with a documented pattern." Right now that pattern doesn't exist as a
first-class concept anywhere in the framework — an application has to invent it from scratch, and
inventing it wrong (a forgotten filter on one query) is a real cross-tenant data leak, not a
cosmetic bug.

## Grounding this in a real reference, not guesswork

Rather than design this in the abstract, I read the user's own `school-management-saas-` Django
backend (`/root/dev/school-management-saas-/backend`), a real, substantial multi-tenant SaaS
already built and tested. Two things there directly inform this design:

1. **Isolation model actually used: shared schema, row-level scoping via a tenant foreign key**
   (`apps/schools/models.py`'s `School`, referenced by a `school = models.ForeignKey(...)` on
   `User`, `Invitation`, and presumably most domain models). Not schema-per-tenant, not
   database-per-tenant. This is the same model Django's own most common multi-tenancy libraries
   (`django-organizations`, plain shared-table patterns) use for the common case, reserving
   schema-per-tenant (`django-tenants`) for deployments with much stricter per-tenant compliance
   isolation requirements than a school SaaS or typical B2B app needs.
2. **Enforcement is currently manual and per-viewset, and that's the exact gap to close.**
   `apps/common/viewsets.py`'s `TenantScopedModelViewSet` requires every subclass to hand-write its
   own `get_queryset()` filtered by `user.school` (see `apps/academics/views.py`'s
   `AcademicSessionViewSet.get_queryset`, `TermViewSet.get_queryset`, etc. — the same
   `school=user.school` filter, copy-pasted per viewset, 6+ times in that one file alone). Nothing
   stops a future viewset from being added without that filter. This is precisely the kind of
   "discipline instead of a guarantee" gap Djangors should not repeat.

**Decision: shared schema + a `tenant` foreign key column on tenant-scoped models, matching the
proven real-world pattern above** — not schema-per-tenant, not database-per-tenant. Concretely,
this also avoids a much larger, currently-unsupported problem: `djangors-migrations` has no concept
of running a migration across N per-tenant schemas/databases; building that out would be its own
multi-week project and isn't warranted for the common case. An application with genuinely stricter
isolation needs (a bank wanting hard per-institution separation) can still layer Postgres
Row-Level Security on top of the shared-schema model as defense-in-depth — documented as an
advanced option, not built or auto-generated by this v1.

## What Djangors already has (and this design reuses, doesn't replace)

`djangors-rest` already ships almost exactly the enforcement primitive needed:
`crates/djangors-rest/src/lib.rs`'s `Scoped` trait —

```rust
pub trait Scoped: Model + FromRow + Send + Sync + 'static {
    fn scope(req: &Request, qs: QuerySet<Self>) -> Result<QuerySet<Self>, DjangorsError>;
}
```

— and `ScopedViewSet<M: Scoped>`, whose `list`/`retrieve`/`update`/`destroy` handlers all route
through `M::scope(&req, ...)` before touching the database. Crucially, `ScopedViewSet<M>` requires
`M: Scoped` as a **trait bound**, so a model without a `scope()` implementation cannot compile
against `ScopedViewSet` at all — this is already exactly the "impossible to misuse" guarantee the
reference Django project's manual `get_queryset()` pattern lacks (see the compile-time proof
already in that file's own test module, `crates/djangors-rest/src/lib.rs` ~L2799-2809). The real
existing example, `impl Scoped for TestNote` (~L2786), pulls a `CurrentOwner` value out of
`req.state::<CurrentOwner>()` and filters by it — this is the exact mechanism multi-tenancy needs,
just not yet wired up to a tenant concept specifically. **This design does not touch `Scoped`/
`ScopedViewSet` at all** — it adds a tenant-specific resolution mechanism and a helper that make
writing `Scoped for MyTenantScopedModel` a one-liner instead of hand-rolled boilerplate, and
extends the same enforcement idea into `djangors-admin` (which has no `Scoped` equivalent today).

## New crate: `djangors-contrib-tenancy`

Following the existing `djangors-contrib-*` convention (see `djangors-contrib-otp`,
`djangors-contrib-guardian` for structural precedent).

### `Tenant` model

```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_contrib_tenancy", table_name = "djangors_tenancy_tenant")]
pub struct Tenant {
    #[djangors(primary_key, auto)]
    pub id: i64,
    #[djangors(max_length = 255)]
    pub name: String,
    #[djangors(unique, max_length = 100)]
    pub slug: String,
    pub is_active: bool,
    pub created_at: chrono::DateTime<chrono::Utc>,
}
```

Deliberately generic (`name`/`slug`, not `school_name`/`bank_branch_name`) — the same model serves
a school, a bank branch, or an e-commerce seller account. Applications name their own domain
concept on top (a school app might alias `Tenant` conceptually to "School" in its own docs/UI
without the framework needing to know the difference).

### `TenantMembership` — a join model, not a direct FK on `User`

The reference Django project put `school` directly on its custom `User` model — viable there
because Django lets you swap `AUTH_USER_MODEL` entirely. `djangors-auth::User` is a concrete,
fixed `#[derive(Model)]` struct (`crates/djangors-auth/src/lib.rs` ~L467) that this design
deliberately does not modify — changing a core-crate struct used everywhere is exactly the kind of
wide-blast-radius change this project's own review discipline treats with extra care, and it isn't
necessary here. Instead:

```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_contrib_tenancy", table_name = "djangors_tenancy_membership")]
pub struct TenantMembership {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user: ForeignKey<djangors_auth::User>,
    pub tenant: ForeignKey<Tenant>,
    #[djangors(max_length = 50)]
    pub role: String,
    pub created_at: chrono::DateTime<chrono::Utc>,
}
```
(`unique_together = [["user", "tenant"]]` — one membership row per user per tenant, matching
`#[derive(Model)]`'s existing `unique_together` support used elsewhere in the codebase.)

This also more correctly models the real-world case the reference project's simpler direct-FK
approach can't: a user belonging to **more than one** tenant (a teacher consulting for two schools,
an accountant handling multiple client organizations) — the common single-tenant-per-user case is
just the degenerate case of one membership row per user, so nothing is lost for the simple case
and the general case is supported without a schema change later.

### Resolving "the current tenant" for a request

New middleware, `TenantResolutionLayer` (matching the existing `tower`-`Layer` style used
throughout `djangors-core::middleware`, e.g. `CspLayer`/`HstsLayer`):

1. Reads a tenant identifier from the request — v1 supports an explicit `X-Tenant-Id` header (the
   simplest, works identically for a browser session and an API client, and doesn't require DNS/
   subdomain infrastructure this framework doesn't otherwise assume). Subdomain-based resolution
   (`school-a.myapp.com`) is a natural v2 addition once there's a concrete deployment wanting it —
   deliberately not built speculatively here.
2. **Cross-checks the claimed tenant against the authenticated user's real `TenantMembership` rows**
   before trusting it — a request claiming `X-Tenant-Id: 7` when the current user has no
   membership row for tenant 7 is rejected (`403`), never silently scoped to the wrong tenant and
   never silently ignored. This is the one security-critical line in this whole design: trusting
   a client-supplied tenant ID without verifying real membership would defeat the entire point.
3. On success, inserts a `CurrentTenant(i64)` into request state (`req.set_state(...)`, the same
   mechanism `Scoped`'s own existing `CurrentOwner` example already uses) for downstream handlers
   to read.

### Closing the boilerplate gap: a helper, not a new macro (v1)

Rather than a new `#[djangors(tenant_scoped)]` derive attribute (a real option, but a larger,
riskier change to `djangors-macros` for a first slice), v1 ships a plain helper function:

```rust
pub fn tenant_scope<T: Model + FromRow>(
    req: &Request,
    qs: QuerySet<T>,
    tenant_field: &'static str,
) -> Result<QuerySet<T>, DjangorsError> {
    let tenant = req
        .state::<CurrentTenant>()
        .ok_or_else(|| DjangorsError::Unauthorized("no current tenant on request".into()))?;
    qs.filter(djangors_orm::q!(#tenant_field = tenant.0))
        .map_err(|e| DjangorsError::Internal(e.to_string()))
}
```
(exact `q!`/filter-by-dynamic-field-name mechanics to be confirmed against
`crates/djangors-orm/src/queryset.rs`'s real API during implementation — the `q!` macro as used
elsewhere in this codebase takes a literal `field = value` at the call site, so a dynamic field
name may need a different `UnresolvedCompare`-based construction; whichever it is, the point is a
single reusable one-line body, not one hand-written per model.)

An application then writes, per tenant-scoped model:
```rust
impl Scoped for SchoolClass {
    fn scope(req: &Request, qs: QuerySet<Self>) -> Result<QuerySet<Self>, DjangorsError> {
        tenant_scope(req, qs, "tenant_id")
    }
}
```
— one line, versus the reference project's full hand-written `get_queryset()` per viewset, while
still being a real, required, compiler-checked `impl` (via `Scoped`'s existing trait-bound
guarantee) rather than something that can be silently skipped.

### `djangors-admin` integration — the highest-value new piece

This is the gap the REST-side `Scoped`/`ScopedViewSet` mechanism does **not** already cover: the
auto-generated admin site has no concept of tenant scoping today, meaning an admin user for tenant
A could browse/edit tenant B's rows in the changelist or change form. New hook on
`ModelAdminConfig` (`crates/djangors-admin/src/lib.rs`): an optional
`tenant_field: Option<&'static str>` config value; when set, every changelist/change-form/delete
query the admin already builds gets an additional `AND {tenant_field} = {current_tenant}` clause,
sourced from the same `CurrentTenant` request-state value, unless the logged-in admin user has a
superuser/global-admin flag (mirroring Django admin's own `is_superuser` bypass). This closes the
concrete "cuts across ... admin" gap PLAN.md itself calls out, and is the single piece of this
design most worth getting right, since the admin is the most likely place for an accidental
cross-tenant leak to actually happen in practice (a raw, un-scoped changelist query).

## Explicitly out of scope for this slice

- Schema-per-tenant or database-per-tenant support — a real, much larger undertaking (per-tenant
  migration orchestration doesn't exist in `djangors-migrations` today); an application with that
  requirement isn't blocked, it just doesn't get first-party framework support for it.
- Automatic Postgres Row-Level Security policy generation — documented as an advanced, manual,
  defense-in-depth option for stricter compliance needs, not built or generated by this v1.
- Subdomain-based tenant resolution — v1 is header-based only; subdomain support is a natural
  additive follow-up once a real deployment needs it.
- A `#[djangors(tenant_scoped)]` derive-macro shortcut — the plain `tenant_scope()` helper covers
  the same need with a much smaller, lower-risk change; revisit only if the one-line-per-model
  `impl Scoped` pattern proves genuinely annoying in practice across many models.
- Cross-tenant reporting/analytics tooling (a superuser view spanning all tenants) — not part of
  "support," a separate future feature.

## Required verification before this is considered done

- Real multi-tenant test: two `Tenant` rows, two users each with a `TenantMembership` to a
  different tenant, a `Scoped` model using `tenant_scope()` — confirm user A's request never sees
  tenant B's rows via `ScopedViewSet`, and that a forged `X-Tenant-Id` header for a tenant the
  requesting user has no membership in is rejected with `403`, not silently scoped wrong.
- Same cross-tenant isolation proof against `djangors-admin`'s changelist for a `tenant_field`-
  configured `ModelAdminConfig`, plus confirming a superuser bypass genuinely sees both tenants'
  rows (proving the bypass is real, not that scoping is simply broken).
- `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings` clean, matching
  this project's standing verification bar.
