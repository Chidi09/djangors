# 9.5 — rustdoc reference with 100% public-API doc coverage

## Scope

9.1-9.4 covered the tutorial, mdBook site, topic guides, Django-comparison guide/how-tos, and a
real `dj shell`. This slice is PLAN.md's remaining Phase 9 reference-docs item: **"reference
(rustdoc, 100% public-API coverage enforced)."** Every public item (struct, enum, trait, fn,
method, field, module, macro) in every published-shaped crate under `crates/` needs a real,
accurate `///` doc comment, and that coverage needs to be **enforced**, not just achieved once and
left to rot.

**Deliberately excluded from this dispatch**: doc-code-block CI compilation (a separate PLAN.md
bullet — that's about compiling the *Markdown* doc examples in `docs/src/`, not rustdoc comments)
and the `djangors.rs` landing page.

## Enforcement mechanism

Add `#![warn(missing_docs)]` to every crate's `lib.rs` under `crates/` (NOT `examples/` — those are
sample apps, not a published API surface) as the enforcement lint. Once a crate is fully
documented, upgrade that crate's lint to `#![deny(missing_docs)]` so the coverage can never silently
regress — do this crate-by-crate as each one reaches 100%, not as one final workspace-wide flip at
the very end (safer: a crate that's already clean gets locked in immediately rather than staying at
`warn` while other crates are still being worked through).

Verify real coverage the authoritative way: `cargo doc --workspace --no-deps` with
`RUSTDOCFLAGS="-D missing_docs"` (or per-crate `#![deny(missing_docs)]`, whichever proves more
reliable — investigate which actually catches every public-item-without-docs case correctly, don't
assume) must complete with **zero warnings/errors** across every crate under `crates/`. This is the
literal, checkable definition of "100% public-API coverage enforced" — don't accept "looks mostly
documented" as good enough; the build-level lint is the actual gate.

## What "real" doc comments means here

This is the one item in Phase 9 where there is no "verify against real source" step in the usual
sense — you ARE the source, writing docs directly against the code you're reading. The discipline
that still applies: **every doc comment must accurately describe what the item actually does**,
not be filler text written just to satisfy the lint (e.g. `/// The name field.` on a field called
`name` is technically present but useless — Django's own docstring quality bar, and this project's
own existing doc comments on `djangors_orm::meta`/`djangors_admin`'s public structs, are the
standard to match). For anything non-obvious — a field/method whose behavior has a real subtlety
this project's own history has already surfaced (e.g. `ForeignKey`'s lazy-loading behavior, `Model`
derive's requirement for an explicit primary key, `CsrfLayer`'s header-first-with-form-fallback
mechanism, `QuerySet::filter()`'s macro-based `q!` syntax) — the doc comment should capture that
subtlety, not just restate the type signature in prose. Crate-level (`//!`) docs should give a
one-paragraph orientation for each crate matching what `docs/src/guides/*.md` (9.2) already
correctly describes for the 8 covered subsystems — reuse that established-accurate content as a
starting point/cross-check for crates that overlap with those guides, don't contradict them.

## Suggested approach given the scale (~20+ crates)

This is a large, mechanical, well-defined task — a good fit for one large, thorough dispatch rather
than many small slices, per the standing "batch a full phase's worth of scope" guidance. Suggested
order: start with the smaller/simpler crates to establish a consistent doc-comment style and
verify the enforcement mechanism works end-to-end, then move to the larger ones
(`djangors-core`, `djangors-orm`, `djangors-admin`, `djangors-auth`, `djangors-rest` are the biggest
public surfaces). Work through every crate under `crates/` — do not skip any because it seems small
or "obviously self-explanatory."

## Required verification

- `RUSTDOCFLAGS="-D missing_docs" cargo doc --workspace --no-deps` (or the equivalent
  per-crate-`deny` approach) completes with zero warnings across every crate under `crates/` — this
  is the real, load-bearing proof; paste the real command and real clean output.
- `cargo fmt --all -- --check`, `cargo build --workspace`, `cargo clippy --workspace --all-targets
  -- -D warnings`, `cargo test --workspace` all remain clean (doc comments shouldn't break anything,
  but confirm for real — a doc comment referencing a wrong item path, e.g. `[SomeType]` intra-doc
  links to something renamed/removed, can actually fail `cargo doc` even though it wouldn't fail a
  normal build).
- Spot-check (in your own summary) 5-10 doc comments on genuinely subtle items (not simple getters)
  to demonstrate real understanding was applied, not just lint-satisfying filler — name the specific
  items and quote the doc comment written for each.

Print `DONE_MARKER_9_5_RUSTDOC_COVERAGE` when finished (or when stopping early — say exactly which
crates reached full `deny(missing_docs)` coverage and which, if any, are still at `warn` with
remaining gaps, and how many warnings remain workspace-wide).
