# 10.12 — resolve the `djangors` facade crate gap (item 3, part A)

## Scope

The first of two design docs for the "API freeze review + deprecation policy" Phase 10 item (see
`/root/.claude/plans/concurrent-inventing-glacier.md`). This one must land and be committed before
the per-crate audit doc (10.13), since it determines what "the frozen 1.0 API surface" even means
for this project.

**The gap, confirmed by direct inspection**: `crates/djangors/src/lib.rs` — the top-level
"batteries-included" facade crate whose own doc comment says "The Django of Rust: batteries-
included web framework — ORM, migrations, admin, forms, auth, background tasks" (matching the
root README's pitch) — is exactly 4 lines:

```rust
#![deny(missing_docs)]
//! The Django of Rust: batteries-included web framework — ORM, migrations, admin, forms, auth, background tasks.

pub use djangors_tasks as tasks;
```

Its `Cargo.toml` has exactly one dependency: `djangors-tasks`. Every other crate the doc comment
claims to bundle (ORM, migrations, admin, forms, auth, and the whole HTTP/routing layer) is
**not** re-exported at all. This means `djangors::` is not actually usable as the single
batteries-included entry point its own pitch promises — a real user following the README today
would have to depend on `djangors-core`, `djangors-orm`, `djangors-rest`, `djangors-admin`,
`djangors-auth`, etc. directly, which is exactly what `examples/school` and `examples/polls`
already do (check their `Cargo.toml`s for the current real dependency list before assuming which
crates need re-exporting).

## The decision (already made — implement it, don't relitigate it)

Finish the facade: add real re-exports of every crate a "batteries-included" framework would be
expected to bundle, matching what the existing example apps already depend on directly. This is
the smaller, more honest fix — it makes `djangors::` genuinely match its own stated purpose,
versus the alternative (declaring the individual crates the "real" public surface and leaving the
facade permanently incomplete), which would mean either fixing the misleading doc comment/README
pitch instead, or shipping a 1.0 whose flagship entry point doesn't do what it says. Re-exporting
is strictly additive and low-risk (no new logic, just `pub use`), so do it.

## The real work

In `crates/djangors/Cargo.toml`, add path dependencies for (at minimum — check `examples/school`'s
and `examples/polls`' own `Cargo.toml` dependency lists first and include anything else they
depend on directly that looks like core framework surface, not example-specific glue):
`djangors-core`, `djangors-orm`, `djangors-migrations`, `djangors-rest`, `djangors-admin`,
`djangors-auth`, `djangors-forms`, `djangors-sessions`, `djangors-template`, `djangors-staticfiles`,
`djangors-cache`, `djangors-mail`, `djangors-i18n`, `djangors-db`.

In `crates/djangors/src/lib.rs`, add `pub use` re-exports for each, following the exact same
`pub use djangors_tasks as tasks;` pattern already there (module-aliased, e.g. `pub use
djangors_core as core;`, `pub use djangors_orm as orm;`, `pub use djangors_rest as rest;`, `pub use
djangors_admin as admin;`, `pub use djangors_auth as auth;`, and so on for the rest) — this crate
has `#![deny(missing_docs)]` already active, so each new `pub use` needs a doc comment (one line
each is fine, e.g. `/// Core HTTP types: Router, Request, Response, middleware, settings.`).

Do **not** re-export the contrib crates (`djangors-contrib-*`) or `djangors-cli`/`djangors-macros`/
`djangors-test` in this pass — those are either opt-in add-ons (contrib) or tooling/test-only
crates, not part of the "batteries-included core" pitch. If you're unsure whether a specific crate
belongs, err toward leaving it out and noting it in your summary rather than guessing.

## Deliberate exclusions

No changes to any re-exported crate's own internals — this is a pure facade/wiring change. No
attempt to migrate `examples/school`/`examples/polls` to use the new `djangors::` re-exports
instead of depending on the individual crates directly — that's a separate, optional future
cleanup, not required here (both patterns will work simultaneously; re-exports don't break direct
dependencies). No version bump.

## Required verification

- `crates/djangors/src/lib.rs` actually compiles with the new re-exports — this is the real test,
  not just "the doc comment now sounds right."
- `cargo doc -p djangors --no-deps` produces zero warnings (the crate's `#![deny(missing_docs)]`
  will hard-fail the build if any new `pub use` lacks a doc comment — confirm this by actually
  running it, not assuming the doc comments are sufficient).
- Write one small smoke test (e.g. in `crates/djangors/src/lib.rs`'s own `#[cfg(test)]` module, or
  a `tests/` integration test) that references at least one real item through each new re-export
  path (e.g. `djangors::core::Router::new()`, `djangors::orm::...`) to prove the re-exports
  actually resolve to real, usable items, not just that the crate compiles with unused imports.
- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace` all clean — run these yourself and
  report the real results.

Print `DONE_MARKER_10_12_FACADE_CRATE_DECISION` when finished (or when stopping early — say
exactly what works and what doesn't, do not fabricate a finished result).
