# 5.6 part 4 — Changelist date hierarchy (v1)

**Status:** design, not yet dispatched. Follows 5.6.3 (bulk delete, commit `47459ee`). See
`docs/design/phase-5-roadmap.md` for full Phase 5 context.

## Scope: single configured DateTime field, year → month → day drilldown, no cross-filter counts

Django's `date_hierarchy` is one field name (never a list — Django itself only supports one).
This part matches that: `ModelAdminConfig` gains `date_hierarchy: Option<&'static str>`, a single
field name that must be a `FieldKind::DateTime` field, validated at registration time (same
`assert`/`panic!` pattern `register_with` already uses for `list_display`/`search_fields`/
`list_filter` — a programmer error caught at startup, not a runtime `Result`).

**The drilldown link counts (which years/months/days have data) are computed from the whole
table on that one field alone — NOT combined with the current search term or `list_filter`
state.** Django's real implementation does intersect them; v1 here deliberately does not, for
the same reason 5.6.2's Boolean filters don't show per-option counts: doing it right means
folding the *entire* current filter/search state into an extra aggregate query, which is real
scope, not a one-line addition. The drilldown nav shows what years/months/days exist in the
table, full stop — a reasonable v1, not a wrong one, and it's still consistent (Django's own
`date_hierarchy` predates its own filter-aware counts by years). Note this as a candidate future
improvement in the roadmap ledger when this lands, don't build it now.

**Only three levels: year, month, day.** No hour/minute drilldown (Django stops at day too).

## New generic `QuerySet` method: `filter_datetime_range`

`crates/djangors-orm/src/queryset.rs`, right after `filter_or_icontains` (~line 133). This is
needed because `filter()`'s `__gte`/`__lt` lookup suffixes require a `&'static str` like
`"created_at__gte"` (see `UnresolvedCompare.field: &'static str` in `expr.rs`) — and the
date_hierarchy field name is only known at runtime (it comes from `ModelAdminConfig`, not a
compile-time literal), so it cannot be string-concatenated into a new `&'static str` without
leaking memory. A dedicated method sidesteps this the same way `filter_or_icontains` sidesteps
`filter()`'s macro-oriented API: construct `Expr` directly and push onto `self.filters`.

```rust
/// Restricts to rows where `field` (a real DateTime field on `T`) is in
/// `[gte, lt)`. Half-open on purpose: `lt` is the exclusive upper bound, so
/// callers pass "start of next unit" rather than doing inclusive-end math
/// against a field that also carries a time-of-day component.
pub fn filter_datetime_range(
    mut self,
    field: &'static str,
    gte: chrono::DateTime<chrono::Utc>,
    lt: chrono::DateTime<chrono::Utc>,
) -> Result<Self, OrmError> {
    let meta = T::meta();
    if !meta.fields.iter().any(|f| f.name == field) {
        return Err(OrmError::FieldNotFound {
            field: field.to_string(),
            model: meta.struct_name,
        });
    }
    self.filters.push(Expr::And(vec![
        Expr::Compare {
            field,
            op: CompareOp::Gte,
            value: Value::DateTime(gte),
        },
        Expr::Compare {
            field,
            op: CompareOp::Lt,
            value: Value::DateTime(lt),
        },
    ]));
    Ok(self)
}
```

No field-*kind* check here (mirrors `filter()` itself, which never checks kind — only
`register_with`'s admin-layer validation above checks `FieldKind::DateTime`, same division of
responsibility as everywhere else in this file: the generic ORM method trusts its caller on
type-appropriateness, the admin registration layer is where user-facing mistakes get caught
early). `chrono` is already a dependency of `djangors-orm` (`Cargo.toml` already has it with the
`std` feature) — no `Cargo.toml` change needed here.

## New free function: raw drilldown-value query

`crates/djangors-admin/src/lib.rs`, alongside `collect_related_objects` — same raw-SQL-with-
trusted-identifiers style (table/column names come from `&'static str` `ModelMeta`/config data,
never user input; only the bound `WHERE` values are request-derived):

```rust
/// Returns the distinct values one drilldown level below the given
/// `(year, month)` state, in ascending order: years if `year` is `None`,
/// months within that year if `month` is `None`, else days within that
/// year+month. Computed from the whole table on `col` alone — see the design
/// doc's scope note on why this isn't combined with the current
/// search/list_filter state.
async fn date_hierarchy_drilldown_values(
    db: &djangors_db::Database,
    table_name: &'static str,
    col: &'static str,
    year: Option<i32>,
    month: Option<u32>,
) -> Result<Vec<i32>, DjangorsError> {
    let (sql, bind_year, bind_month): (String, Option<i32>, Option<i32>) = match (year, month) {
        (None, _) => (
            format!(
                "SELECT DISTINCT EXTRACT(YEAR FROM {col})::int AS v FROM {table_name} \
                 WHERE {col} IS NOT NULL ORDER BY 1"
            ),
            None,
            None,
        ),
        (Some(y), None) => (
            format!(
                "SELECT DISTINCT EXTRACT(MONTH FROM {col})::int AS v FROM {table_name} \
                 WHERE {col} IS NOT NULL AND EXTRACT(YEAR FROM {col})::int = $1 ORDER BY 1"
            ),
            Some(y),
            None,
        ),
        (Some(y), Some(m)) => (
            format!(
                "SELECT DISTINCT EXTRACT(DAY FROM {col})::int AS v FROM {table_name} \
                 WHERE {col} IS NOT NULL AND EXTRACT(YEAR FROM {col})::int = $1 \
                 AND EXTRACT(MONTH FROM {col})::int = $2 ORDER BY 1"
            ),
            Some(y),
            Some(m as i32),
        ),
    };
    let mut query = sqlx::query_scalar(sqlx::AssertSqlSafe(sql));
    if let Some(y) = bind_year {
        query = query.bind(y);
    }
    if let Some(m) = bind_month {
        query = query.bind(m);
    }
    query
        .fetch_all(db.pool())
        .await
        .map_err(|e| DjangorsError::Internal(e.to_string()))
}
```

(Confirm the exact `sqlx::query_scalar` builder call chain compiles as written — it mirrors
`collect_related_objects`'s `sqlx::query_scalar(sqlx::AssertSqlSafe(sql)).bind(pk)` pattern
closely enough that it should, but the conditional-bind shape is new, verify it during review.)

## `admin_changelist` handler: parse `year`/`month`/`day`, compute the range, render the nav

Query params, parsed the same strict way `page` already is (bad value → 400, not silently
ignored — matches this handler's existing convention):

```rust
let year: Option<i32> = match req.query("year") {
    Some(s) => Some(s.parse().map_err(|_| DjangorsError::BadRequest("invalid year".into()))?),
    None => None,
};
let month: Option<u32> = match req.query("month") {
    Some(s) => Some(s.parse().map_err(|_| DjangorsError::BadRequest("invalid month".into()))?),
    None => None,
};
let day: Option<u32> = match req.query("day") {
    Some(s) => Some(s.parse().map_err(|_| DjangorsError::BadRequest("invalid day".into()))?),
    None => None,
};
```

`month`/`day` are meaningless without a `year` (and `day` without a `month`) — if a higher level
is absent, ignore the lower ones rather than erroring (a stray `?day=5` with no `year` just has
no effect, it isn't a malformed request). Only compute a `date_range` if `admin.date_hierarchy_field()`
is `Some` AND `year` is `Some`; use `chrono` to build the half-open `[gte, lt)` window for
whichever is the *most specific* level actually present:

```rust
use chrono::{Duration, TimeZone, Utc};

let date_range: Option<(chrono::DateTime<Utc>, chrono::DateTime<Utc>)> =
    match (admin.date_hierarchy_field(), year) {
        (Some(_), Some(y)) => {
            let (gte, lt) = match month {
                Some(m) => {
                    let start = Utc.with_ymd_and_hms(y, m, 1, 0, 0, 0).single()
                        .ok_or_else(|| DjangorsError::BadRequest("invalid year/month".into()))?;
                    let end = match day {
                        Some(d) => {
                            let s = Utc.with_ymd_and_hms(y, m, d, 0, 0, 0).single()
                                .ok_or_else(|| DjangorsError::BadRequest("invalid day".into()))?;
                            s + Duration::days(1)
                        }
                        None => {
                            if m == 12 {
                                Utc.with_ymd_and_hms(y + 1, 1, 1, 0, 0, 0).single()
                            } else {
                                Utc.with_ymd_and_hms(y, m + 1, 1, 0, 0, 0).single()
                            }
                            .ok_or_else(|| DjangorsError::BadRequest("invalid year/month".into()))?
                        }
                    };
                    let start = match day {
                        Some(d) => Utc.with_ymd_and_hms(y, m, d, 0, 0, 0).single()
                            .ok_or_else(|| DjangorsError::BadRequest("invalid day".into()))?,
                        None => start,
                    };
                    (start, end)
                }
                None => {
                    let start = Utc.with_ymd_and_hms(y, 1, 1, 0, 0, 0).single()
                        .ok_or_else(|| DjangorsError::BadRequest("invalid year".into()))?;
                    let end = Utc.with_ymd_and_hms(y + 1, 1, 1, 0, 0, 0).single()
                        .ok_or_else(|| DjangorsError::BadRequest("invalid year".into()))?;
                    (start, end)
                }
            };
            Some((gte, lt))
        }
        _ => None,
    };
```

(This is deliberately spelled out in full above rather than left to the dispatch to improvise —
`chrono`'s `with_ymd_and_hms(...).single()` returning `None` on an out-of-range date, e.g.
`month=13`, is the actual validation for bad values; do not let a bad year/month/day panic or
silently wrap. Feel free to restructure into a small local helper for readability, but the
validation behavior — bad date component → 400, not panic — is not optional.)

Pass `date_range` as `changelist`'s new last argument.

**Drilldown nav rendering** — a new HTML block, placed above the existing `search_html`/
`filter_html`/table, only rendered `if let Some(field) = admin.date_hierarchy_field()`:

- Query `date_hierarchy_drilldown_values(db, admin.model_meta().table_name, field, year, month)`
  for the *next* level's values (this is the "what to show as links" query — separate from
  `date_range`, which is "what to filter the changelist rows by").
- Render a breadcrumb of already-selected levels as plain text + a link to jump back up (drop
  the more specific params), then the current level's values as links going one level deeper.
  E.g. at year+month selected (day list showing): breadcrumb `<a href="?...">{year}</a> &rsaquo;
  <a href="?...year=Y">{month name}</a>` (back-up links), followed by day links
  `<a href="?...year=Y&month=M&day=D">{D}</a>` for each returned day value.
- Every drilldown link (breadcrumb back-links and forward day/month/year links alike) must go
  through `build_query_string`, carrying `o`, `q`, and `active_filters` forward exactly like
  every other link in this handler already does — a date-hierarchy link that drops the current
  sort/search/filter state on click would be a real, user-visible regression.

**Every existing link-building site in this handler (header sort links, prev/next pager links,
search-box hidden inputs, filter All/Yes/No links) must also carry `year`/`month`/`day` forward
when present** — the same class of bug 5.6.1 fixed for the pk column and 5.6.2 fixed for
composing filters: if a site is missed, sorting or paginating while a date-hierarchy drilldown
is active silently drops back to the unfiltered changelist. Concretely, every `pairs`/`pairs_*`
vec literal in `admin_changelist` gains three more conditional entries:

```rust
let year_str = year.map(|y| y.to_string());
let month_str = month.map(|m| m.to_string());
let day_str = day.map(|d| d.to_string());
// ... then at every existing pairs vec:
pairs.push(("year", year_str.as_deref()));
pairs.push(("month", month_str.as_deref()));
pairs.push(("day", day_str.as_deref()));
```

Enumerate every such site explicitly during review — do not trust a summary claiming "all links
updated," grep for every `build_query_string(&pairs` call site in the diff and check each one by
eye.

## What NOT to touch in this task

- No hour/minute drilldown levels.
- No combining drilldown link counts with the current search term or `list_filter` state (see
  scope section above).
- No changes to bulk delete (5.6.3), `list_filter` (5.6.2), or `list_display`/`search_fields`
  (5.6.1) logic beyond the new `changelist()` parameter threading required above.
- No `list_editable` — a separate, later slice (interacts with the bulk-delete `<form>` wrapping
  the table in a way that needs its own design).
- No changes to `djangors-macros`.
- No multiple `date_hierarchy` fields — Django itself only supports one; match that.

1. Insert 3 rows with `created_at` values in different months of the same year (e.g. one in
   January, two in March) and one row in a different year entirely. Register with
   `date_hierarchy: Some("created_at")`. GET the changelist with no `year`/`month`/`day` → 200,
   response body contains links for both years present, does not contain a month or day link
   list yet (year level only).
2. GET with `?year=<Y>` (the year containing 3 rows) → 200, response body's table only contains
   those 3 rows (the other year's row is excluded), and month links are rendered for the months
   that have data within that year (January and March, not February).
3. GET with `?year=<Y>&month=<M>` (March, which has 2 of the 3 rows) → 200, table contains
   exactly those 2 rows, day links rendered for the specific days present.
4. GET with `?year=<Y>&month=<M>&day=<D>` narrowed to a single row's exact day → 200, table
   contains exactly that 1 row.
5. GET with `?year=<Y>&o=name` (sort combined with a date-hierarchy filter) → 200, the header
   sort link in the response body includes `year=<Y>` in its `href` (the regression this design
   doc calls out above — sorting must not drop the active drilldown).
6. GET with an invalid `?month=13` (year present, month out of range) → 400 Bad Request.
7. Registering a model with `date_hierarchy: Some("name")` where `name` is a `Char` field (not
   DateTime) → panics. Match the existing pattern for this exactly (`test_phase5_list_display_and_search`,
   ~line 2515-2535): `std::panic::catch_unwind(|| { site.register_with::<ModelD>(...) })`, then
   `assert!(res.is_err())` — this codebase does NOT use `#[should_panic]` for these, it uses
   `catch_unwind` on a throwaway `AdminSite` inline within the broader test function.
