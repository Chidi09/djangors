## Deliberately excluded from this dispatch, and why

**Graceful shutdown in `Djangors::run_service`** (`crates/djangors-core/src/app.rs`) is *not* part
of this dispatch. It would touch the actual request-serving loop every single djangors app uses,
including both example apps' full-stack integration tests — real, wide blast radius, the same class
of thing that justified splitting 5.8.9's CSRF core-fix from 5.8.10 rather than bundling it. Held
back as its own future slice (6.4) so it gets isolated, careful review rather than being one part
of an already-large four-to-six-part dispatch. Do not touch `app.rs`/`run_service` in this dispatch.

## Two real scope decisions, read before writing code

**1. `dj makemigrations` cannot be Django's real incremental-diff `makemigrations`.**
`djangors-migrations` (read `crates/djangors-migrations/src/lib.rs` and `src/plan.rs` directly,
don't assume) has no stored "previous schema state" to diff the current model registry against —
`migrate()` computes a fresh create-all plan from the live `inventory`-based model registry every
time it runs and applies it once, tracked only by a single `0001_initial` marker row. There is no
migration-file-on-disk mechanism at all yet. Building real incremental migration generation (diff
current models against the last-known state, emit an `NNNN_description.sql`/similar file,
teach `migrate()` to apply files in order instead of always recomputing live) is a legitimately
separate, larger design project — **do not attempt it here.** **Deliberate v1 scope:** `dj
makemigrations` is a **dry-run preview** — it calls `djangors_migrations::build_create_all_plan()`
directly (the exact same function `migrate()` itself calls) and prints the resulting SQL
statements, writing nothing to disk. `--check` (already parsed, `Commands::Makemigrations { check:
bool }`) means: don't print the SQL, just exit `1` if the plan is non-empty (there's something
`dj migrate` would apply) or `0` if empty — useful for a CI gate proving nothing's pending, without
promising a stored-migration-history feature this slice doesn't build. Print a clear one-line note
in the non-check-mode output that this is a preview of what `dj migrate` will do, not a
generated file, and that incremental diffing against a prior state doesn't exist yet.

**2. `dj shell` cannot be a real Python-`manage.py shell`-equivalent REPL.** Rust has no
lightweight embeddable REPL; `evcxr` (mentioned in PLAN.md as a "stretch") is a heavy dependency
this slice should not add. **Deliberate v1 scope:** `dj shell` connects to the project's database
(via `DATABASE_URL`, the same convention every other DB-touching command already uses) to prove
connectivity, prints a clear message that an interactive Rust REPL isn't available yet (a future,
separate `evcxr`-integration project), and points the user at `dj dbshell` (this same dispatch,
Part B) as today's actual interactive option. Do not fake a REPL with a toy read-eval-print loop
that doesn't actually evaluate Rust — that would be worse than an honest "not yet" message.

## Part A — `dj makemigrations [--check]`

Replace the `commands::makemigrations()` stub. Signature: `pub fn makemigrations(check: bool) ->
Result<(), String>` (update `main.rs`'s call site the same way every other 6.1/6.2 command was —
`if let Err(e) = ... { eprintln!(...); exit(1); }`).

1. Verify current directory looks like a djangors project (`Cargo.toml` + `djangors.toml`) — same
   check `new_app`/`run`/`check` already use, factor into a shared helper if there isn't one yet
   (check whether 6.2 already extracted this into a function; if it appears duplicated 3+ times
   inline, pull it into one `fn require_project_root() -> Result<(), String>` and use it
   everywhere including this new call site — a real, small, in-scope cleanup, not scope creep).
2. Call `djangors_migrations::build_create_all_plan()`. This requires the *calling process's own
   binary* to have every model registered via `inventory` — but `dj` itself has no models
   registered (it's the generic CLI, not a specific project). **Verify this constraint directly
   by reading how `inventory`-based registration actually works in `djangors-orm`** before writing
   this part — if `build_create_all_plan()` can only ever see models that were statically linked
   into the *calling* binary (i.e. `dj` itself), then it will always report an empty plan for any
   real project, which would make this whole part useless. If that's the case, the honest,
   correct fix is: this command **cannot run as `dj makemigrations`** the same way `dj check`
   can't introspect a project's models (the identical structural constraint documented in 6.2's
   design doc, ledgered there and not solved). If genuinely blocked this way, do not force it —
   instead, make `Commands::Makemigrations` print a clear explanation of why (mirroring `dj
   check`'s own documented model-introspection limitation) and exit non-zero, and say so plainly
   in your final report so this is understood, not silently half-working. Try the straightforward
   implementation first and actually test it against a real generated project's models (create a
   real model in a generated app via `new()` + `new_app()`, exactly like 6.2's own
   `test_new_app_generates_module` does) before concluding either way — don't assume, verify.
3. If it does work: print each SQL statement from the plan, one per line, prefixed with `[dj
   makemigrations]`. If `check` is true, suppress the SQL output and just report the count,
   exiting `1` if non-zero.
4. If the plan is empty (no registered models, or genuinely nothing pending): print `[dj
   makemigrations] no changes detected` (or, if blocked per point 2, the explanation instead).

**Required tests**: whatever the outcome of the investigation in point 2, write a test proving it —
either a real test against a project with an actual registered model showing real SQL comes out,
or (if blocked) a test proving the command fails clearly and explains why rather than silently
reporting an empty plan that looks successful but is actually meaningless.

## Part B — `dj dbshell`

Replace the `commands::dbshell()`... **wait, this subcommand doesn't exist in `cli.rs` yet** — add
`Commands::Dbshell` (PLAN.md lists `dbshell` as a bullet; it was never added to the `Commands` enum
in any prior slice — confirm this by reading `cli.rs` directly) following the exact
`#[command(name = "...")]` pattern every other variant uses, and wire it in `main.rs`.

Implementation: read `DATABASE_URL` from the environment (same convention as `migrate`/
`createsuperuser`, clear error if unset). Postgres's own client (`psql`) accepts a full connection
URI directly as its first positional argument (`psql postgres://user:pass@host:port/dbname`) —
confirm this is genuinely true by actually running `psql --version` to confirm `psql` is installed
in this environment and, if a real test database is reachable, actually try `psql
"$DATABASE_URL" -c 'SELECT 1;'` yourself to prove URI-argument connection really works here before
relying on it in code — don't assume libpq's URI support is enabled just because it's commonly
true. Exec (replace the current process image via `std::os::unix::process::CommandExt::exec()` on
Unix, so Ctrl-C/signals reach `psql` directly and the CLI doesn't linger as a wrapper process) into
`psql "$DATABASE_URL"`. If `exec` fails (e.g. `psql` not on `PATH`), report a clear error. If
`std::os::unix::process::CommandExt::exec` feels like too large a platform-specific commitment
given every other command in this file is written portably, a plain spawn+wait is an acceptable,
simpler fallback — note which you chose and why in the final report.

**Required test**: since this replaces/execs into an external interactive program, a full
automated test of interactive behavior isn't practical. Write a narrower real test: confirm the
command correctly reports the DATABASE_URL-missing error case, and (if a test database is
reachable in this environment) confirm the constructed command/args are correct by running `psql
"$DATABASE_URL" -c 'SELECT 1;'` (non-interactively, with `-c`, not through `dj dbshell` itself) and
asserting it succeeds — proving the URI-argument approach genuinely works in this environment,
which is the load-bearing assumption this whole part depends on.

## Part C — `dj test`

`Commands::Test` already exists and parses (a bare unit variant, no args). Replace the
`commands::test()` stub with a thin wrapper: verify current directory is a project root (same
check as Part A), then run `cargo test` with `.status()` (not `.output()` — let its stdout/stderr
stream through live, matching how a user would run it directly), and exit with the same status
code cargo test itself returned (`std::process::exit(status.code().unwrap_or(1))`) so `dj test`

**Required test**: generate a real project via `new()`, run `commands::test(...)` (or whatever the
final function signature is) against it, assert success — the generated project has zero tests of
its own, so `cargo test` there should trivially succeed; this proves the wrapper and exit-code
propagation work, not that testing itself does anything interesting yet.

## Part D — `dj shell`

Per the scope decision above: connect to `DATABASE_URL` (reusing the exact same connection
pattern as `migrate`/`createsuperuser`), print a one-line confirmation it connected successfully,
then print a clear multi-line message explaining a real interactive Rust REPL isn't available yet

## Part E — deployment scaffolding, extending `dj new`

Extend `new()` in `crates/djangors-cli/src/commands.rs` (6.1's project scaffolder) to also
generate:

1. **A `/healthz` route** in the generated project itself — add a second handler to the generated
   `src/views.rs` (alongside the existing `welcome` handler): `pub async fn healthz(_req: Request,
   _params: PathParams) -> Result<Response, DjangorsError> { Ok(Response::text(StatusCode::OK,
   "ok")) }`, and mount it in the generated `src/main.rs`'s router (`.get("/healthz",
   views::healthz)` alongside the existing `.get("/", views::welcome)`). This is what a
   Dockerfile `HEALTHCHECK` directive or a systemd/orchestrator liveness probe would hit.
2. **`<name>/Dockerfile`**: a real multi-stage build — a `rust:1-slim` (or whatever the current
   MSRV/toolchain implies; check `rust-version` in the workspace root `Cargo.toml` if set,
   otherwise use a recent stable tag) builder stage running `cargo build --release`, copying only
   the resulting binary into a minimal runtime stage (`debian:bookworm-slim` or similar — full
   distroless is a nice-to-have but adds real complexity around dynamic linking/certs that this v1
   shouldn't chase; a slim Debian base with the binary copied in is an honest, working v1, not the
   ~20MB distroless target PLAN.md aspirationally mentions — note this explicitly as a v1 vs. the
   PLAN.md text, don't silently claim distroless when it isn't). Expose the port the generated
   `main.rs` listens on by default (`8000`), set `DJANGORS_PORT`/`DATABASE_URL` as documented
   `ENV`/build-arg placeholders (not baked-in secrets), and include a `HEALTHCHECK CMD` hitting
   `/healthz` (using `curl` or `wget` if available in the runtime base image — verify which is
   actually present in the chosen base image before writing the `HEALTHCHECK` line, don't guess).
3. **`<name>/deploy/djangors.service`**: a systemd unit file template (`[Unit]`/`[Service]`/
   `[Install]` sections) running the release binary, with `Restart=on-failure`, a placeholder
   `EnvironmentFile=` line pointing at where `DATABASE_URL`/`DJANGORS_SECRET_KEY` etc. would live
   in a real deployment, and a comment explaining it's a template to adapt (paths, user/group)
   before real use, not a drop-in-ready file.
4. Update the generated `README.md` (6.1's template) with a short "Deploying" section pointing at
   the Dockerfile and systemd unit, and mentioning `dj check --deploy` (Part F) as a pre-flight
   check.

**Required test**: extend (or add alongside) 6.1's own `test_new_generates_expected_files` — assert
the Dockerfile and systemd unit now exist, and that `src/views.rs`/`src/main.rs` reference
`healthz`. Also extend 6.1's `#[ignore]`d `test_new_generated_project_builds_and_serves` (or add a
new ignored test alongside it, whichever is cleaner given the existing test's structure) to also
request `/healthz` and assert it returns `200` — the real proof the new route actually works, not
just that a file mentioning "healthz" got written.

## Part F — `dj check --deploy`

Extend the existing `Commands::Check` variant (from 6.2) with an optional flag: `Check { #[arg(long)]
deploy: bool }` (check the exact current shape of `Commands::Check` in `cli.rs` before editing —
6.2 may have left it as a bare unit variant; adjust `main.rs`'s match arm accordingly). Extend
`check()` (or add a sibling function, whichever keeps the existing non-deploy behavior provably
unchanged — verify by confirming `dj check`'s existing tests from 6.2 still pass unmodified) with
deploy-specific checks, gated on `deploy`, mirroring Django's own `check --deploy` spirit using the
already-loaded `DjangorsSettings`:

- `debug == true` → issue: "DEBUG is true; must be false in production"
- `secret_key.is_empty()` → issue (this may already be caught by `.validate()` when `debug=false`
  — check for double-reporting the same issue and avoid it, don't just append blindly)
- `secret_key.len() < 32` (even if non-empty) → issue: "SECRET_KEY should be at least 32
  characters"
- `allowed_hosts` still exactly the default (`["127.0.0.1", "localhost"]`, i.e. unmodified from
  `DjangorsSettings::default()`) while `debug == false` → issue: "ALLOWED_HOSTS looks like the
  default; set it explicitly for production"

**Required tests**: a deploy-clean case (settings that pass all of the above) reports zero deploy
issues, and a deliberately bad case (default settings, `debug=false`) surfaces all the expected
issues by message substring — mirroring 6.2's own `test_check_generated_project_and_invalid_settings`
