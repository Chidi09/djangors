# 6.4 — Graceful shutdown for `Djangors::run`/`run_service` (Phase 6 close-out)

## Why this is its own slice, not bundled into 6.1/6.2/6.3

This touches `crates/djangors-core/src/app.rs`'s `serve`/`serve_service` accept loops — the exact
code path **every** djangors app runs through, including both example apps'
(`examples/polls`, `examples/school`) full-stack integration tests and every `dj new`-generated
project. Real, wide blast radius, the same class of thing that justified splitting 5.8.9's CSRF
core-fix from 5.8.10 rather than bundling it. Read this design doc fully, and read
`crates/djangors-core/src/app.rs` in its entirety, before writing any code — the exact current
behavior matters and is described precisely below; don't assume it, verify it against the real
file first.

## Current behavior (read `app.rs` directly to confirm, don't just trust this summary)

`Djangors::serve(self, listener)` and `Djangors::serve_service(self, listener, service)` are both
a bare `loop { match listener.accept().await { ... spawn a detached task ... } }` — no shutdown
signal handling exists anywhere in this codebase today. `tokio::task::spawn(...)`'s returned
`JoinHandle` is immediately dropped (fire-and-forget) — there is currently no way to know when
in-flight connections finish, and no way to stop the accept loop short of the whole process being
killed by the OS's default signal disposition (which drops every in-flight connection
mid-request, the definition of *not* graceful). `run()`/`run_service()` are thin wrappers that
`bind()` then call `serve`/`serve_service`.

## Design goal, and the key decision that keeps blast radius low

**Do not change the signatures or observable behavior of the existing public `run()`/`run_service()`
functions when no shutdown signal ever arrives.** Both example apps and every `dj new`-generated
project call `run_service(service)` today (confirmed: `examples/polls/src/main.rs:44`,
`examples/school/src/main.rs:44`, and the template in `commands::new()`) — these call sites must
not need to change at all. Instead, wire real signal-listening (SIGINT via `tokio::signal::ctrl_c()`
and SIGTERM via `tokio::signal::unix::signal(SignalKind::terminate())`, Unix-only — this whole
project already assumes Linux, see the `/proc`-based process matching added in 6.2) **inside**
`serve`/`serve_service` themselves, so the *existing* call sites transparently gain graceful
shutdown for free. Additionally expose a new, lower-level `serve_with_shutdown`/
`run_with_shutdown` (and `_service` variants) that accept an arbitrary `impl Future<Output = ()>`
as the shutdown trigger — this is what makes the behavior testable in-process (a test can pass a
manually-controlled `tokio::sync::oneshot::Receiver` or similar instead of a real OS signal, since
sending a real SIGTERM to the test process would kill the whole test binary, not what's wanted),
and gives advanced users an escape hatch. `serve`/`serve_service` become thin wrappers calling the
`_with_shutdown` variants with the real-signal future.

## Required Cargo change

`crates/djangors-core/Cargo.toml`'s `tokio` dependency currently has features `["net",
"rt-multi-thread", "macros", "io-util"]` — add `"signal"` (needed for both `ctrl_c()` and
`signal::unix::signal`).

## Implementation sketch — read as a strong guide, verify every API against real docs/source, don't copy blindly

```rust
use tokio::task::JoinSet;

/// Races SIGINT (Ctrl-C) and SIGTERM (Unix) and resolves when either fires.
/// The real signal source used by `serve`/`serve_service`'s default behavior.
async fn os_shutdown_signal() {
    let ctrl_c = async {
        let _ = tokio::signal::ctrl_c().await;
    };
    #[cfg(unix)]
    let terminate = async {
        let mut sig = tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("failed to install SIGTERM handler");
        sig.recv().await;
    };
    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        _ = ctrl_c => {},
        _ = terminate => {},
    }
}
```

For the accept loop itself, the critical correctness subtlety: **the shutdown future must be
created once and pinned/reused across every loop iteration**, not re-created fresh on each
iteration (a fresh `ctrl_c()`/`signal.recv()` future each iteration would still work for a
one-shot signal in practice for `ctrl_c()`, but is wasteful and fragile, and is definitely wrong if
the shutdown trigger is a `Future` that's only meant to fire once, e.g. a `oneshot::Receiver` —
polling a `oneshot::Receiver` that already resolved, after being re-created, would behave
incorrectly). Use `tokio::pin!` once before the loop:

```rust
pub async fn serve_with_shutdown<F>(
    self,
    listener: TcpListener,
    shutdown: F,
) -> Result<(), DjangorsError>
where
    F: std::future::Future<Output = ()>,
{
    let mut join_set: JoinSet<()> = JoinSet::new();
    tokio::pin!(shutdown);
    loop {
        tokio::select! {
            accepted = listener.accept() => {
                match accepted {
                    Ok((stream, _peer_addr)) => {
                        let router = self.router.clone();
                        let debug = self.settings.debug;
                        join_set.spawn(async move {
                            if let Err(e) = serve_connection(stream, router, debug).await {
                                eprintln!("Connection error: {e}");
                            }
                        });
                    }
                    Err(e) => eprintln!("Accept error: {e}"),
                }
            }
            _ = &mut shutdown => {
                println!("[djangors] shutdown signal received, draining in-flight connections...");
                break;
            }
        }
    }
    // Stop accepting new connections (already true — we broke the loop), then wait for
    // in-flight ones to finish, bounded by a timeout so a stuck connection can't hang
    // shutdown forever.
    let drain = async {
        while join_set.join_next().await.is_some() {}
    };
    if tokio::time::timeout(std::time::Duration::from_secs(30), drain)
        .await
        .is_err()
    {
        eprintln!("[djangors] graceful shutdown timed out after 30s, aborting remaining connections");
        join_set.abort_all();
    }
    Ok(())
}

pub async fn serve(self, listener: TcpListener) -> Result<(), DjangorsError> {
    self.serve_with_shutdown(listener, os_shutdown_signal()).await
}
```

Apply the exact same pattern to `serve_service`/`serve_service_with_shutdown` (parameterized the
same way `serve_service` already is, over the generic tower `Service` bound) — **this is the
higher-value target since it's the path every real app (`examples/polls`, `examples/school`, every
`dj new`-generated project once middleware is added) actually uses in production** via
`run_service()`. Consider whether the accept-loop-plus-join_set-plus-shutdown-select logic can be
factored into one shared internal generic helper parameterized over the per-connection handling
closure, to avoid writing this same signal/JoinSet/timeout logic twice with two chances to drift or
diverge subtly — a real, worthwhile refactor given the risk profile here, but only if it doesn't
make the generic bounds unreadable; use your judgment and explain the choice either way in your
final report.

`run()`/`run_service()` stay as thin wrappers: `bind()` then call the corresponding `serve*`
function — no signature change needed there at all.

## Required tests

**Must not break, verify explicitly by re-running them, not just by inspection:**
`real_socket_request_response` and `real_socket_layered_middleware_response` (both already in
`app.rs`'s own test module) — both currently `tokio::spawn(async move { app.serve(...).await
.unwrap(); })` and never wait for it to finish (the spawned task is simply dropped when the test
ends), then make one request over a real socket and assert the response. These must keep passing
completely unmodified — the refactor must not change `serve`'s behavior for the common case (no
shutdown signal ever arrives during the test's lifetime).

**New, real proof the graceful-shutdown mechanism actually works** (use `serve_with_shutdown`/
`serve_service_with_shutdown` with a manually-controlled shutdown future — e.g. a
`tokio::sync::oneshot::channel`'s `Receiver`, mapped to `async { let _ = rx.await; }` — NOT a real
OS signal, for exactly the reason stated above): spin up a real listener, start a slow handler
(one that holds the connection open for e.g. 300ms via `tokio::time::sleep` before responding),
send a real request over a real socket to that slow handler *without waiting for the response
yet* (spawn the client-side read into its own task, or just don't await the read before the next
step), then trigger the shutdown future (send on the oneshot sender) while that request is still
in flight, and assert: (a) the `serve_with_shutdown` future itself doesn't resolve until the
in-flight request actually completes (measure elapsed time — it should take at least as long as
the handler's artificial delay, not return instantly), and (b) the original in-flight request's
client-side read still gets a real, complete `200 OK` response (proving the connection wasn't
severed mid-request) rather than a connection reset. This is the real behavioral proof — a test
that only checks "the function returns eventually" without checking the in-flight request actually
completed successfully would not prove graceful shutdown, only that the loop exits.

**Also verify**: after a shutdown signal, no *new* connection is accepted — e.g. attempt a second
connection to the same address after triggering shutdown but before the drain completes, and
confirm it's refused/times out (the listener itself: dropping/no longer polling `accept()` should
naturally stop the OS from handing off new connections once the loop has broken, but verify this
is actually true rather than assuming it — a `TcpListener` that's simply not being polled anymore
still has the OS-level backlog accepting SYNs up to the backlog limit even if `accept()` is never
called again, so a client `connect()` might still succeed even though nothing will ever `accept()`
it — decide whether this distinction matters for a real test assertion, and if it's ambiguous/hard
to assert reliably, it's acceptable to skip this specific check and note why, as long as the
in-flight-request-completes-first proof above is solid).

**Full-blast-radius regression check, required, not optional**: both example apps' own full-stack
integration tests (`examples/polls/tests/voting.rs`, `examples/school/tests/admin_crud.rs`) must
pass completely unmodified — these are the two real callers of `run_service()` in this whole
codebase outside the test suite itself, and this change's entire risk profile is about not
breaking them.
