# 11.3 — Fix a genuine `FOR UPDATE SKIP LOCKED` double-claim race under load

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_3` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the

## Context

`crates/djangors-tasks/src/lib.rs`'s `tick_recurring_tasks` (~line 182) is supposed to guarantee
that when N workers call it concurrently against the same due row, **exactly one** of them claims
and processes it — the whole point of `SELECT ... FOR UPDATE SKIP LOCKED`. There is a real,
independently-reproduced bug where **both** concurrent callers claim and process the *same single
row*.

**Reproduction (already done — don't re-derive this, verify it yourself then move to root-causing
it):** `test_tick_recurring_tasks_dual_claim_race` (~line 925) passes reliably when run alone with
no other system load, but running it 6 times in a row *while a `cargo build -p djangors-admin
--all-targets` runs concurrently in the background* reproduced the double-claim **6 out of 6
times** — confirmed via temporary debug instrumentation (already removed) showing exactly one row
present in `djangors_recurring_task` both before and after, yet `enqueued1=1, enqueued2=1` (should
be `1, 0` or `0, 1`, never `1, 1`). Reproduce it yourself the same way before touching anything:

```bash
export DATABASE_URL="postgres://postgres:postgres@localhost/djangors_test"
(cargo build -p djangors-admin --all-targets > /tmp/bg_build.log 2>&1 &)
for i in 1 2 3 4 5 6; do
  cargo test -p djangors-tasks --lib test_tick_recurring_tasks_dual_claim_race -- --nocapture 2>&1 | tail -5
done
```

**Already ruled out — don't waste time re-checking these:**
- **Connection pool exhaustion**: `DatabaseConfig::new` (`crates/djangors-db/src/config.rs`)
  defaults to `max_connections: 10`, `min_connections: 1` — `TestDatabase::connect()`
  (`crates/djangors-test/src/lib.rs`) uses these defaults, so both concurrent `tick_recurring_tasks`
  calls have plenty of headroom to get genuinely separate connections; this isn't pool starvation
  forcing accidental serialization/reuse.
- **`Database::clone()` sharing a single connection instead of the pool**: `Database`
  (`crates/djangors-db/src/database.rs` ~line 21-24) is `#[derive(Clone)]` over a `PgPool` (sqlx's
  pool type is itself a cheap `Arc`-backed handle) plus an `Arc<AtomicUsize>` counter — cloning it
  correctly shares the *pool*, not a single checked-out connection. `db.transaction()`
  (~line 111) calls `self.pool.begin()` fresh each time, which checks out a genuinely separate
  physical connection per call. This part of the stack is not the bug.
- A separate, already-fixed, *unrelated* test bug: the test never cleaned up
  `djangors_task_queue` between runs, so repeated invocations with the literal task name
  `sample_task_fn_race_test` accumulated rows across process runs, independently causing the
  `assert_eq!(count, 1)` assertion (a few lines below the `enqueued1 + enqueued2` one) to fail with
  numbers like 9. That fix (`DELETE FROM djangors_task_queue WHERE task_name = ...` added at test
  start) is already applied directly, not part of this task — don't touch it, it's a distinct,
  confirmed, simple bug from the one you're solving here.

## What you're actually solving

Root-cause **why two concurrent Postgres transactions can both come away having "claimed" (SELECT
... FOR UPDATE SKIP LOCKED'd, then INSERTed into `djangors_task_queue`, then UPDATEd
`next_run_at`) the exact same single row**, and fix it. Candidate angles worth investigating (not
a prescriptive list — follow the evidence):

- Whether `db.transaction()`'s use of the Postgres default `READ COMMITTED` isolation interacts
  with `FOR UPDATE SKIP LOCKED` in a way that's actually unsafe for this specific access pattern
  (the standard job-queue idiom is supposed to be safe under `READ COMMITTED` — confirm whether
  this codebase's specific transaction/statement structure genuinely matches that idiom, or
  subtly deviates from it in a way that breaks the guarantee).
- Whether the SELECT-then-loop-then-separate-INSERT/UPDATE structure (three separate statements
  inside one transaction) has a real gap, versus the more atomic single-statement idiom
  (`UPDATE djangors_recurring_task SET next_run_at = ... WHERE id = (SELECT id FROM
  djangors_recurring_task WHERE ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *`) — if the
  current multi-statement structure is the actual problem, restructuring to a single atomic
  statement (claim-and-advance in one round trip) may be the right fix, not a band-aid.
  `sqlx` version in use is `0.9.0` (check `crates/djangors-tasks/Cargo.toml` /
  `crates/djangors-db/Cargo.toml` for the exact pin) - check whether this specific version has any
  known relevant behavior quirks.
- Whether this reproduces under literal concurrent `psql` sessions issuing the same SQL by hand
  (bypassing sqlx/tokio entirely) — if it does NOT reproduce at the raw-SQL level, the bug is in
  the Rust/sqlx/tokio layer (e.g. something about how the transaction's statements are pipelined
  or how `tokio::spawn` + `#[tokio::test]`'s default current-thread runtime interacts with two
  concurrent `.await`ed database round trips); if it DOES reproduce at the raw-SQL level, the bug
  is a genuine misunderstanding of `FOR UPDATE SKIP LOCKED` semantics somewhere in the actual
  query/transaction structure, not a Rust-level concurrency bug.
- Whether load (CPU contention) is a red herring that's really just widening a timing window for
  something that's always subtly possible (a real correctness bug, load-independent in principle)
  versus something that's genuinely only reachable under contention (e.g. a retry/backoff path,
  a connection-acquisition race, or a statement-pipelining issue that only manifests when I/O is
  slow).
