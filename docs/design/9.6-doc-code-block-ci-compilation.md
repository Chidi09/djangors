# 9.6 — every doc code block extracted and compiled in CI

## Scope

9.1-9.5 built the tutorial, mdBook site, topic guides, Django-comparison guide, how-tos, and
100%-enforced rustdoc coverage. This is PLAN.md's remaining Phase 9 bullet: **"Every doc code block
extracted and compiled in CI (doctests / skeptic-style)."** The goal is a real, automated mechanism
that catches the exact class of bug 9.3's independent review found by hand (7 fabricated API usages
in `docs/src/django-comparison.md` — `Response::render()` that doesn't exist, `DjangorsError::
NotFound("...")` with a bogus arg, etc.) automatically, in CI, on every future doc change — not
relying on a human (or a dispatch) manually cross-checking every snippet against source forever.

**This is specifically about the Markdown files under `docs/src/`** (tutorial, guides,
django-comparison, how-tos) — NOT the `///`/`//!` rustdoc comments inside `crates/*/src/*.rs`,
which already compile/run automatically via `cargo test --doc` (confirmed working: 9.5's
verification already ran `cargo test --workspace`, which includes doc-tests, and they passed).
Markdown code fences in `docs/src/*.md` are NOT rustdoc doctests and are NOT compiled or checked by
anything today — that's the real gap this slice closes.

**Deliberately excluded from this dispatch**: the `djangors.rs` landing page (a separate PLAN.md
bullet).

## Investigate the real approach before committing to one

PLAN.md's own text suggests "doctests / skeptic-style" as options. Investigate what's actually
available/appropriate in this environment before choosing:
- `skeptic` (the crate literally named in PLAN.md) — check its current maintenance status on
  crates.io/GitHub; it has historically had gaps (unmaintained periods, doesn't handle `bash`/`toml`
  fences, sometimes awkward with a workspace of many crates). Verify it actually still works with
  the current Rust toolchain in this environment before committing to it.
- A hand-rolled extraction script/build-time test: parse every ` ```rust ` fenced code block out of
  every file under `docs/src/`, write each to a temp file, and either (a) compile it directly via
  `rustc --edition 2021 --crate-type lib` with the right `--extern` flags for every djangors crate
  (mirroring how the tutorial/guide snippets already use `# use djangors_core::...`-style hidden
  lines, a real rustdoc convention — confirm the existing `docs/src/` files actually use this `#
  ` hidden-line convention already, since 9.1-9.3 might already have written snippets in a
  self-contained, standalone-compilable style, or might not have), or (b) generate a single
  `tests/doc_examples.rs` (or one per source `.md` file) with each block as its own `#[test]`- or
  plain-compiled fn, added to the workspace so `cargo test --workspace` picks it up automatically —
  this is the simpler, more idiomatic-Rust option and avoids a new external CI-only mechanism, so
  prefer it if it works cleanly.
- Whichever approach is chosen, it needs to run as a normal part of `cargo test --workspace` (or a
  clearly-documented separate `cargo` command this project's own CI — check if a CI config file
  exists anywhere in the repo, e.g. `.github/workflows/`, and confirm real current CI actually runs
  the check you build; if no CI config exists yet, note that clearly rather than assuming one does).

## What counts as "every doc code block"

Every ` ```rust ` fenced block across every file in `docs/src/` (tutorial parts, topic guides,
django-comparison, how-tos) that represents a **real, intended-to-compile snippet** — not every
single code block unconditionally. Some existing blocks are deliberately partial/illustrative
fragments (e.g. a snippet showing just one line of a `Cargo.toml`, or Python-side Django examples in
` ```python ` fences which obviously aren't Rust and should be skipped entirely). Read through the
existing `docs/src/` content first to understand which Rust blocks are meant to be genuinely
standalone-compilable vs. illustrative fragments needing a `# fn main() { ... }` wrapper or similar
convention — establish and document a clear, consistent convention (e.g. "every ` ```rust ` block
must be a complete, compilable item or use rustdoc's `#`-hidden-line wrapping to become one") and
apply it consistently, fixing any existing snippet that doesn't already follow it.

## Round 1 findings (investigation only, nothing committed — read before starting)

A first attempt investigated but stopped short of implementing, correctly judging that the existing
Markdown snippets need normalizing before a real compile-check would be meaningful. Its findings,
confirmed real and worth reusing directly rather than re-investigating from scratch:
- **No CI workflow exists anywhere in this repo** (no `.github/workflows/` or equivalent) — there is
  no existing CI to "integrate with"; this slice's own `cargo test --workspace` inclusion IS the
  enforcement mechanism (a local dev/CI-agnostic check, matching how every other test in this
  workspace already works).
- **`skeptic` 0.13.7 is installable in this environment but is a poor fit**: it's designed to treat
  Markdown as a single crate's own doctest-equivalent content and cannot cleanly resolve
  `crate::`-relative paths the way this multi-crate workspace's snippets need. Don't spend time
  re-evaluating `skeptic` — go straight to a hand-rolled, dependency-free workspace test.
- **No rustdoc hidden-line (`# `) convention is currently used** in any `docs/src/*.md` file, and
  most existing Rust-fenced blocks are genuinely context-dependent fragments (partial snippets
  assuming surrounding application code), not standalone-compilable units as written.
- A prior attempt's own draft approach (kept here as a starting point, not gospel): a
  `tools/doc-code-check` workspace member with a test that walks every `.md` file under `docs/src/`,
  requires every ` ```rust ` fence to be tagged either ` ```rust,compile ` (a real, standalone-
  compilable snippet checked by actually compiling it) or ` ```rust,illustrative ` (an intentionally
  partial fragment, exempted from compilation but still required to be explicitly tagged so nothing
  silently slips through unclassified) — panicking loudly on any bare ` ```rust ` fence found
  without one of those two tags. This is a reasonable, workable design; feel free to use it or
  improve on it, but the key deliverable is real and complete either way.
