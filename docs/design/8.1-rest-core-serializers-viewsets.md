# 8.1 — Phase 8 begins: `djangors-rest` core (serializers, ViewSets, routers)

## Scope

Phase 7 is fully done (`docs/design/7.5-i18n-and-otp.md`, commit `0aea94b`). This begins Phase 8
(API & real-time) — the largest remaining phase, comparable in scope to Django REST Framework +
Django Channels + Celery combined. Given that scale, Phase 8 is being built as a sequence of
slices, the same way Phase 5 (admin) was built incrementally rather than attempted whole. This
slice (8.1) is the functional foundation everything else in `djangors-rest` builds on: JSON
serialization derived from the same compile-time `ModelMeta` the admin already uses, generic
ViewSets (list/retrieve/create/update/delete), and router-mounting.

**Deliberately excluded from this dispatch, left for later 8.x slices**: OpenAPI 3.1 generation,
token/JWT auth, permission classes, throttling, the browsable API HTML page, `djangors-channels`
(WebSocket/SSE), background tasks. Each is independently large and builds on this slice's
foundation existing first.

`crates/djangors-rest` currently exists only as a name-reserving placeholder (`src/lib.rs` is a
4-line doc comment, confirmed by reading it directly) — this is the first real work in it.

## Design: reuse the same generic mechanism the admin already proved out

`djangors-admin`'s `DefaultModelAdmin<M>` already does exactly this shape of thing — generic
CRUD over any `Model` via `M::field_values()`/`field_names()`, `QuerySet<M>`, `parse_field_value`
(form-string → `Value`, reused/mirrored from `djangors-admin`'s own — read
`crates/djangors-admin/src/lib.rs`'s `parse_field_value` function for the exact real logic to
mirror for a JSON equivalent) — but rendering HTML. `djangors-rest` needs the same generic
machinery, rendering JSON instead. **Read `crates/djangors-admin/src/lib.rs`'s
`DefaultModelAdmin<M>` impl in full before writing this** — don't re-derive the generic-CRUD
pattern from scratch when a working, tested version already exists to mirror.

## Part A — generic JSON serialization

```rust
/// Serializes any Model's field_values() into a JSON object. Relation fields serialize as
/// their raw related id (matching how the admin already renders them — no nested/expanded
/// relation serialization in this v1, ledgered as a future enhancement).
pub fn serialize<M: djangors_orm::Model>(instance: &M) -> serde_json::Value;

/// Deserializes a JSON object into field values suitable for QuerySet::insert_raw/update,
/// using the same per-FieldKind parsing conventions djangors-admin's parse_field_value
/// already establishes (reuse or closely mirror that function's logic, adapted from
/// "form string value" to "serde_json::Value" input) — collecting ALL validation errors at
/// once, not failing fast, matching this codebase's established convention everywhere else
/// (5.4's change-form validation, `djangors-forms`, etc.).
pub fn deserialize<M: djangors_orm::Model>(
    json: &serde_json::Value,
) -> Result<Vec<(&'static str, djangors_orm::expr::Value)>, std::collections::HashMap<String, String>>;
```

**Required tests**: round-trip serialize→deserialize for a real model with at least one of each
common `FieldKind` (text, integer, boolean, datetime) and one relation field, plus a deserialize
failure case collecting multiple field errors at once (mirroring the admin's own
`parse_field_value` multi-error test pattern).

## Part B — generic ViewSet + router mounting

```rust
pub struct ViewSet<M: djangors_orm::Model + djangors_orm::error::FromRow> {
    _marker: std::marker::PhantomData<M>,
}
```

Handlers (plain async functions, matching every other handler shape in this codebase —
`Request`/`PathParams` in, `Result<Response, DjangorsError>` out):
- `list`: `GET` — all rows (paginated via the existing `djangors_core::Paginator` from 7.2, `?page=`
  query param, default page size a reasonable constant e.g. 100 matching the admin's own
  `CHANGELIST_PER_PAGE` convention — check that constant's actual value and reuse/match it),
  returns `{ "count": N, "page": N, "total_pages": N, "results": [...] }`.
- `retrieve`: `GET /{pk}` — single row by pk, 404 if missing.
- `create`: `POST` — deserialize body JSON, insert, 201 with the created row's JSON on success,
  422 with the collected field errors on failure (a real, structured JSON error body — e.g.
  `{ "errors": { "field": "message" } }` — not a bare string).
- `update`: `PUT`/`PATCH /{pk}` — deserialize + update, same success/error shape as create.
- `destroy`: `DELETE /{pk}` — delete by pk, 204 on success, 404 if missing.

**Deliberately no filtering/ordering query-param support in this slice** (PLAN.md's own text asks
for "filtering integration with QuerySet" as part of the full `djangors-rest` deliverable, but
that's a real design question — which fields are filterable, what operators, matching the admin's
own `list_filter`-style allowlist approach or something else — worth its own focused slice once
auth/permissions exist to protect it; ship list/retrieve/create/update/destroy with pagination only
here, note filtering/ordering as explicitly deferred).

**No auth/permission checks in this slice** — every ViewSet route is open. This is a real,
temporary gap, not silently ignored: **document loudly** (module doc + a code comment on
`viewset_routes` itself) that this v1 has zero access control and must not be mounted on any
route serving real data until 8.2 (auth/permissions) lands. This mirrors how 5.1's very first
admin slice was staff-gated from day one specifically to avoid ever having an unprotected admin
route exist even transiently — the same discipline should apply here in spirit, just impossible to
avoid entirely in a single slice given auth is explicitly slotted for 8.2. If it's low-risk to add
even a minimal "requires an authenticated session" check reusing `djangors_auth`'s existing
extractor (not full permission-class support, just "must be logged in") without meaningfully
expanding this slice's scope, do that; if it would meaningfully expand scope, don't, and rely on
the loud documentation instead.

**Required tests**: a real end-to-end test (mirroring `djangors-admin`'s own in-process
`router.handle()` test pattern) proving list/retrieve/create/update/destroy all work against a
real test model and real Postgres — including a create validation-failure case returning the
structured JSON error body, and a pagination test with enough rows to span two pages.

## Verification required before reporting done

- `cargo fmt --all`
- forced rebuild: `touch` every file you modify/create, then `cargo build --workspace
  --all-targets`
- `cargo clippy --workspace --all-targets -- -D warnings`
- Check `df -h /` before running tests; if any DB test fails with a connection-level error, check
  `pg_lsclusters` (cluster `16/main`) and `pg_ctlcluster 16 main start` if `down` before assuming a
  code regression. If disk is critically low, `cargo clean` on this project is a legitimate, safe,
  now-routine way to reclaim space (crate sources stay cached in `~/.cargo`, ~1-1.5 min rebuild).

  serialization/ViewSet code
