# 10.7 — cron/scheduled recurring background jobs

## Scope

Item #6 of the architecture-parity initiative (see `/root/.claude/plans/concurrent-inventing-glacier.md`
for the full roadmap; items 1, 2, 3, 4, 8 are already done — `docs/design/10.2` through `10.6b`).
`crates/djangors-tasks/src/lib.rs` already has a real, working Postgres-backed task queue:
`QueuedTask` (table `djangors_task_queue`), `enqueue`/`enqueue_scheduled(db, task_name, payload,
scheduled_at)` (one-time future execution only), and `Worker` (`run`/`run_once`, polling loop,
`claim_next_task` using `SELECT ... FOR UPDATE SKIP LOCKED`). Zero recurrence concept exists
anywhere (grep-confirmed: no cron parser, no "every N seconds," no `next_run_at` field) — this was
explicitly deferred in `docs/design/8.5-background-tasks-core.md` as a known follow-up. There is
also no CLI command to run a worker at all today (`crates/djangors-cli/src/cli.rs`'s `Commands`
enum has no `worker`/`runworker` variant) — a project must currently embed
`Worker::new(db).run().await` manually in its own binary.

**No cron-expression crate is present anywhere in this workspace, not even transitively**
(checked `Cargo.lock` directly) — this needs one new, small dependency. Use the `cron` crate
(crates.io, pure schedule-computation, no async/runtime dependencies of its own) — check what
version is current on crates.io and add it to `crates/djangors-tasks/Cargo.toml` only.

**Deliberately excluded**: distributed leader election for tick ownership (the existing `FOR
UPDATE SKIP LOCKED` claim pattern already prevents double-execution across multiple worker
processes — that's sufficient for v1, this isn't solving a different problem); non-standard cron
features (seconds field, timezone-aware schedules) — standard 5-field cron syntax, UTC only; any
admin UI for managing recurring tasks (a future, separate slice).

## The real design

### `RecurringTask` model + registration (`crates/djangors-tasks/src/lib.rs`)

Read `QueuedTask` (lib.rs:64-88) and `create_task_table` (lib.rs:91-110) first as the exact
structural template. Add:

```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_tasks", table_name = "djangors_recurring_task")]
pub struct RecurringTask {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub task_name: String,
    pub payload: String,
    pub cron_expr: String,
    pub next_run_at: chrono::DateTime<chrono::Utc>,
    pub last_run_at: Option<chrono::DateTime<chrono::Utc>>,
    pub enabled: bool,
}
```

`create_recurring_task_table(db) -> Result<(), djangors_db::DbError>` mirroring
`create_task_table`'s exact shape (`CREATE TABLE IF NOT EXISTS`). Validate `cron_expr` parses (via
the new `cron` crate) at registration time, not at tick time:

```rust
/// Registers a new recurring task. `cron_expr` must be a valid standard 5-field cron expression
/// (validated immediately — an invalid expression is rejected here, not discovered later at
/// tick time). The task's very first `next_run_at` is computed from `cron_expr` relative to
/// `chrono::Utc::now()` at registration time.
pub async fn register_recurring(
    db: &djangors_db::Database,
    task_name: &str,
    payload: &impl serde::Serialize,
    cron_expr: &str,
) -> Result<i64, TaskError>;
```

### `tick_recurring_tasks` — the concurrency-sensitive core

```rust
/// Finds all due, enabled `RecurringTask` rows, enqueues one `QueuedTask` per due row (via the
/// existing `enqueue` function, so it runs through the exact same worker/handler/retry machinery
/// as any other task), and advances each claimed row's `next_run_at`/`last_run_at`. Returns the
/// number of tasks enqueued.
pub async fn tick_recurring_tasks(db: &djangors_db::Database) -> Result<usize, TaskError>;
```

**This must use the same `SELECT ... FOR UPDATE SKIP LOCKED` claim pattern as `claim_next_task`**
(lib.rs:147-191) — read that function in full and mirror its transaction structure exactly
(`db.transaction(|tx| Box::pin(async move { ... }))`), claiming due `RecurringTask` rows
(`WHERE enabled = true AND next_run_at <= now() ... FOR UPDATE SKIP LOCKED`) the same way
`claim_next_task` claims due `QueuedTask` rows. **This is the item's direct concurrency-race
analog to a real bug class this project has hit before**: 10.4's dispatch introduced a genuine
test race by having two tests share a table without proper isolation; here the risk is two
concurrent `tick_recurring_tasks` calls (e.g. two worker processes both ticking) double-enqueuing
the same due row if the claim isn't properly locked. Treat this as a known, named risk going in,
not something to discover after the fact.

**Advance `next_run_at` from the row's own previous `next_run_at`, not from `now()`.** Using
`now()` as the basis for computing the next occurrence silently skips missed runs after downtime
(worker was down for an hour, cron said "every 5 minutes," `now()`-based advancement jumps straight
to "5 minutes from now" instead of catching up) and can double-fire after clock skew. Compute the
next occurrence strictly forward from the previously recorded `next_run_at` using the `cron`
crate's schedule iterator.

### `Worker` gets an additive recurring-tick cadence

```rust
impl Worker {
    /// Configures how often the worker checks for due recurring tasks (calls
    /// `tick_recurring_tasks` on this cadence, independent of the regular
    /// `poll_interval` task-claiming cadence). If never called, recurring tasks are
    /// never ticked automatically (existing `Worker` behavior for projects that don't use
    /// recurring tasks is completely unchanged).
    pub fn with_recurring_tick_interval(mut self, interval: std::time::Duration) -> Self;
}
```

Wire this into `Worker::run`'s existing loop (lib.rs:248-260) — purely additive, no signature
change to `Worker::new`/`run`/`run_once`. A reasonable implementation: track elapsed time since the
last recurring tick alongside the existing poll loop and call `tick_recurring_tasks` when due,
without disrupting the existing task-claiming cadence.

### CLI: `dj runworker`

Add to `crates/djangors-cli/src/cli.rs`'s `Commands` enum (read the existing variants, e.g.
`Dbshell`/`Check`, for the established doc-comment/attribute style):

```rust
/// Run the background task worker loop.
#[command(name = "runworker")]
RunWorker {
    /// Polling interval in seconds for claiming due tasks.
    #[arg(long, default_value_t = 1)]
    poll_interval_secs: u64,

```

Wire to a new handler in `crates/djangors-cli/src/commands.rs` (mirror the existing command
handlers' structure — connect via settings/`DatabaseConfig` the same way `migrate`/`dbshell` do)
that constructs `Worker::new(db).with_poll_interval(...).run().await`.

## Required verification

- **Dual-claim concurrency race on `tick_recurring_tasks` itself**, directly mirroring
  `test_concurrent_claim_skip_locked` (lib.rs:440+): one due `RecurringTask` row, two concurrent
  `tokio::spawn`s calling `tick_recurring_tasks` (or the underlying claim step) at the same time —
  assert exactly one `QueuedTask` gets enqueued from that row, never zero or two. This is the
  single most important test in this dispatch — call it out first in your own verification pass,
  don't leave it for last.
- **`next_run_at` advances from the previous scheduled time, not wall-clock `now`**: a task with
  `cron_expr = "*/5 * * * *"` ticked twice within the same 5-minute window must not double-enqueue;
  advance strictly forward from the row's own recorded `next_run_at` against a fixed, controlled
  instant in the test (not real wall-clock `now()`), so the test is deterministic and actually
  proves the "advance from recorded time" property rather than just "it doesn't crash."
- A disabled (`enabled = false`) task must never enqueue even when its `next_run_at` is in the
  past.
- `register_recurring` rejects an invalid cron expression immediately (at registration, not
  discovered later).
- A real end-to-end test: register a recurring task with a short-interval cron expression pointed
  at an existing `#[task]` fixture (reuse `sample_task_fn`/`SamplePayload` from the existing test
  module), tick it, confirm a real `QueuedTask` row was created with the correct payload, then run
  the existing `Worker`/`claim_next_task` machinery against it to confirm it actually executes —
  proving the two systems compose end-to-end, not just that `tick_recurring_tasks` inserts a row.
- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace` all clean — run these yourself and report
  the real results; if piped through anything, remember a bare `| tail` reports the pipe's own
  exit code, not cargo's.
