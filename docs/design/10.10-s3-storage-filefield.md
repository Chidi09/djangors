# 10.10 — S3Storage backend + FileField (item 7b, final architecture-parity item)

## Scope

Item #7 of the architecture-parity initiative, part b of two (see
`/root/.claude/plans/concurrent-inventing-glacier.md`; items 1-6, 8, 7a are already done — this is
the final item of the whole 8-item roadmap). `docs/design/10.9-storage-trait.md`'s dispatch
already added a real `Storage` trait (`save`/`open`/`exists`/`delete`/`url`, all `async` except
`url`) and `LocalDiskStorage` in `crates/djangors-staticfiles/src/storage.rs`. This item adds a
second, real backend (`S3Storage`) implementing the exact same trait, plus a `FileField` concept
in the ORM so a model can store a reference to something living in whichever `Storage` backend a
project configures.

**A real S3-compatible test endpoint is already running for this dispatch** — a MinIO container,
started specifically for this item's verification (not for any other purpose): endpoint
`http://localhost:19000`, root user `test`, root password `testtest`, no bucket created yet (the
required verification test must create its own bucket via the client, proving that path works
too). **Use this real endpoint for the required S3-backed integration test — do not write a
mocked/faked HTTP test instead, that would prove nothing about real wire-format/auth
correctness**, which is exactly the failure mode a fake test would hide.

**Dependency choice, already researched and decided — do not reach for `aws-sdk-s3`**: the
official AWS SDK for S3 is enormous (confirmed via its own crates.io listing: ~168,000 lines of
Rust across the crate plus its `aws-smithy-*`/`aws-credential-types`/`aws-runtime` dependency
tree) — this project has already been burned once this session by an unexpectedly heavy
dependency tree (`evcxr_repl`'s default features pulling in `rust-analyzer`'s own crates caused a
real disk/build crisis). Use the `s3` crate instead (crates.io name `s3`, i.e. `s3 = "0.37"` in
`Cargo.toml` — confirmed current as of this doc via the crates.io API: max/newest version
`0.37.2`), a small, focused, actively-maintained (9M+ downloads, updated within the last few
months) client purpose-built for S3-compatible endpoints including MinIO, without the official
SDK's dependency weight.

**Do not trust any pre-existing assumption about this crate's exact method names/signatures in
this doc** — none are given here, deliberately: verify the real API by reading the crate's actual
documentation/source after adding it as a dependency (`cargo doc -p <your-new-crate-usage>` or
reading its docs.rs page directly, or its README via `cargo add s3` then inspecting
`~/.cargo/registry`) before writing `S3Storage`'s implementation. This project has a strong,
repeated history of dispatches inventing plausible-but-nonexistent API names — for a brand-new
external dependency this project has never used before, that risk is highest, so verify everything
against the real crate rather than guessing from general S3-client familiarity.

**Deliberately excluded**: multipart/streaming upload for very large files (single-shot
save/open is fine for v1); signed-URL generation or private-bucket ACL nuances beyond a basic
public-read-style default; direct-to-S3 browser upload flows; automatic old-file deletion on
model update (a real feature, but needs signal/hook integration — a legitimate future follow-up,
not required here).

### `FileField` (ORM: `crates/djangors-orm/src/meta.rs` + `crates/djangors-macros/src/model.rs`)

Read `FieldKind` (`crates/djangors-orm/src/meta.rs:8+`) in full first — it's a plain enum inferred
by the macro from a field's Rust type (`String` → `Char`/`Text` depending on whether
`#[djangors(max_length = ...)]` is present, confirmed at
`crates/djangors-macros/src/model.rs:387-390`). Add a new variant:

```rust
/// A field storing a relative path/key into a configured [`Storage`] backend. Django's
/// `FileField`. The database column is a plain nullable text column (like `Text`) — the
/// distinct `FileField` kind exists for introspection/tooling (e.g. a future admin widget,
/// migration tooling that wants to treat it specially), not because it needs different SQL.
FileField,
```

In the macro (`crates/djangors-macros/src/model.rs`, near the existing `max_length` attribute
parsing at lines ~210-231): add a new `#[djangors(file_field)]` boolean flag attribute, parsed the
same way `max_length` is, valid only on `String`/`Option<String>` fields (mirror the existing
`max_length is only valid on String fields` validation at line ~344-347 — add an equivalent check).
When present, emit `FieldKind::FileField` instead of the inferred `Char`/`Text`.

In `crates/djangors-migrations/src/type_mapping.rs`'s `sql_type_for` (the single shared function
10.2 consolidated all SQL-type-mapping onto — read it first): add a `FieldKind::FileField => ...`
arm producing the exact same SQL type as `FieldKind::Text` does (a plain nullable text column —
this is a v1 design choice: FileField is a path string at the storage layer, nothing more).

A model uses it like:
```rust
#[djangors(file_field)]
pub attachment: Option<String>,
```
storing the storage-relative path; a project resolves the actual URL by calling
`storage.url(&model.attachment.unwrap())` explicitly wherever it renders the value (no automatic
resolution in this v1 — keep scope narrow, this is the final item of a long roadmap, don't add
scope beyond what's asked).
