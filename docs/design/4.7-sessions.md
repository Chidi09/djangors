# Design 4.7 — Sessions (v1 scope)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 4's sessions bullet first. This is
part 1 of Phase 4 ("the banking phase") — auth (part 2) depends on this crate existing first,
since login-fixation protection needs a real session to rotate.

## v1 scope

`PLAN.md` lists three session engines (signed-cookie, database, cache). **v1 ships only the
signed-cookie engine** — it's Django's own dev default, requires no extra infrastructure (no
`djangors-db` dependency, so `djangors-sessions` stays usable without a database), and it's the
one every other engine's `Session` API needs to be validated against first. Database/cache
engines are a follow-up once a real `SessionStore` trait exists to implement.

### Core mechanism this depends on (already built, not part of this task)

`djangors-core::Request` now has a per-request typed extension slot: `Request::ext::<T>()`,
populated by `Router::dispatch`/`dispatch_debug` from the incoming hyper request's own
`Extensions` (see the `djangors-core: per-request typed extensions on Request` commit). This is
the hook session middleware uses to hand a `Session` to handlers — it is **not** `AppState`
(`Request::state`), which is app-wide and configured once at startup. Do not add
session-specific fields to `djangors-core` itself; everything sessions-specific lives in this
crate and reaches handlers purely through `req.ext::<Session>()`.

## Threat model (read this before writing any code)

This is signed, **not encrypted**, storage — matching Django's own default cookie backend.
Consequences that must hold:

- The client can **read** session contents (base64, not secret). Never store anything in a
  session that would be a problem if the user's browser (or a browser extension, or anyone with
  local access to the machine) could read it in plaintext. This is a documented constraint, not
  a bug — same as Django's.
- The client **cannot forge or tamper with** session contents without invalidating the signature.
  A tampered cookie must be rejected and treated as "no session" (start fresh, empty session) —
  never as a parse error that 500s the request, and never silently trusted.
- Signature verification must be constant-time. Do not write a manual byte-by-byte `==` compare
  of MACs.
- Session rotation (`Session::cycle_key`) must produce an unrelated session identity, not a
  derivative of the old one — this is what protects against session fixation once `djangors-auth`
  calls it on login. v1 only needs to *expose* this method correctly; nothing calls it yet.

## Crate shape

New crate `djangors-sessions` (already an empty placeholder). Depends on `djangors-core` (for
`Request`/`Response`/`Extensions` plumbing), `hmac` + `sha2` (HMAC-SHA256 signing — both already
in the workspace's transitive dependency tree, pin them as direct deps), `base64` (already
transitively present, pin as direct dep), `serde`/`serde_json` (session value serialization),
`rand` (session-key generation for `cycle_key`), `subtle` if the `hmac` crate's own
constant-time `Mac::verify_slice` is not used directly (prefer relying on `hmac`'s built-in
verification — do not hand-roll comparison at all if it can be avoided).

**Do not add the `cookie` crate or any new signing dependency without checking first** — v1's
signing scheme is deliberately simple enough not to need one: HMAC-SHA256 over
`base64(json(session_data)) || "." || base64(expires_at_unix)`, producing
`base64(payload) + "." + base64(expires_at) + "." + base64(mac)`, verified by recomputing the MAC
over the same payload and comparing via `hmac::Mac::verify_slice` (which is constant-time
internally).

```rust
/// A per-request session handle. Cheaply `Clone` (wraps an `Arc<Mutex<..>>`)
/// so the same handle can be inserted into the request's extensions (for
/// handlers to read/mutate) and retained by SessionLayer (to serialize
/// after the handler returns) without any response-side round-trip.
#[derive(Clone)]
pub struct Session { /* Arc<Mutex<SessionInner>> */ }

struct SessionInner {
    data: std::collections::HashMap<String, serde_json::Value>,
    modified: bool,
    /// Set by `cycle_key`; on the next encode, forces a fresh session
    /// identity (not just re-signing the same data).
    cycled: bool,
}

impl Session {
    pub fn get<T: serde::de::DeserializeOwned>(&self, key: &str) -> Option<T> { ... }
    pub fn set<T: serde::Serialize>(&self, key: &str, value: T) { ... } // marks modified
    pub fn remove(&self, key: &str) { ... }
    pub fn clear(&self) { ... }
    pub fn is_empty(&self) -> bool { ... }
    /// Rotate session identity in place (auth calls this on login/logout).
    pub fn cycle_key(&self) { ... }
}

pub struct SignedCookieStore {
    key: Vec<u8>,       // from settings.SECRET_KEY, NOT hardcoded, NOT optional
    cookie_name: String, // default "djangors_sessionid"
    max_age: std::time::Duration, // default matches Django's 2-week default
}

impl SignedCookieStore {
    pub fn new(secret_key: &[u8]) -> Self { ... }
    fn encode(&self, session: &Session) -> String { ... }
    /// Returns `None` for missing/malformed/tampered/expired cookies —
    /// never an `Err` that would need special-casing by the layer.
    fn decode(&self, cookie_value: &str) -> Option<Session> { ... }
}

/// The tower Layer/Service that does the actual per-request work: parses
/// the `Cookie` request header, decodes+verifies the session cookie via
/// the store, inserts the `Session` into the hyper request's `Extensions`
/// before calling the inner service, and (only if `session.modified` or
/// newly created/cleared) sets `Set-Cookie` on the response afterward by
/// reading the same `Arc`-shared handle it kept.
pub struct SessionLayer { store: std::sync::Arc<SignedCookieStore> }
```

`SignedCookieStore::new` takes the secret key explicitly (a `&[u8]`) rather than reading a global
setting itself — matches this project's existing pattern of settings living in
`djangors-core::settings` and being read by the caller who constructs the layer, not by the
sessions crate reaching into global config on its own.

## What this task does NOT include

- Database and cache session engines (`SessionStore` trait should be shaped so these are
  addable later without changing `Session`'s public API, but no second implementation ships now).
- Anything in `djangors-auth` (login/logout, `User`, fixation-protection call site) — that is
  Phase 4 part 2, a separate task, dispatched after this one is real and reviewed.
- CSRF middleware and the broader security-headers work (HSTS, CSP, `ALLOWED_HOSTS` host
  validation) — Phase 4 parts 3+, separate tasks.
- Wiring `SessionLayer` into any example app — no example app consumes sessions yet.

## Required tests (must genuinely exercise the properties, not just check for `Ok`/`Err`)

- Round-trip: `set` a value, encode via the store, decode the resulting cookie string, `get` the
  same value back with the right type.
- **Tamper rejection**: encode a session, flip a byte in the resulting cookie string (or the
  data segment specifically), attempt to decode — must return `None`, and a value that was
  genuinely set before tampering must NOT be readable afterward. This must actually corrupt the
  MAC, not just produce an obviously-malformed string that a lenient parser might special-case.
- **Expiry**: a session encoded with `max_age = Duration::ZERO` (or a store with expiry already
  in the past) must fail to decode even though the signature itself is valid — proves expiry is
  checked from the signed payload, not just trusted from the client-supplied cookie's `Max-Age`.
- `cycle_key` produces a session that decodes to different internal identity/state framing than
  before rotation (exact mechanism depends on implementation, but the test must prove the
  pre-rotation encoded cookie no longer round-trips to the same session after rotation is
  triggered and re-encoded).
- **End-to-end through a real `Router`**: build a tiny two-route app (one handler that
  `session.set("count", n+1)` and returns the count, one that reads it) wrapped in
  `SessionLayer`, using `tower::ServiceBuilder`/`.oneshot()` (matching the existing
  `service_with_tower_middleware` test in `djangors-core/src/service.rs` as the pattern to
  follow) — issue two requests, manually carrying the `Set-Cookie` value from response 1 into
  the `Cookie` header of request 2, and confirm the count incremented. This is the test that
  actually proves the Extensions-based plumbing works for this crate specifically, not just in
  the abstract core test that already exists.
- No session cookie on the request at all → handler still gets a valid (empty) `Session`, no
  panic, no error.
