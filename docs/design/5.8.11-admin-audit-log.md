# 5.8.11 — Admin audit log (`LogEntry` + "Recent actions" panel)

**Status:** design doc, not yet dispatched.
**Depends on:** 5.7.2 (`require_perm` returning the acting `User`), 5.8.1-5.8.10 (template
conversion + branding, since `admin_index.html` gains a new panel).
**Scope for v1 (explicit, do not exceed):** record every successful mutating admin action
(add/change/delete/bulk-delete/list_editable save) as one `LogEntry` row each, and show the
current user's most recent entries on `admin_index.html`. **No per-object History page, no
diffing of field values, no IP/request-id capture** — those are v2+ items, listed at the bottom
under "Explicitly out of scope."

## Why this slice, why now

`docs/design/phase-5-roadmap.md`'s sequencing section lists history/audit as the next Phase 5
item now that 5.8.1-5.8.10 (template conversion, theming, branding, CSRF form wiring) are all
done. `PLAN.md` line 342 already carries this as a standing checklist item ("History: admin log
entries table; deep integration with djangors-contrib-audit for full record diffing" — the
`djangors-contrib-audit` deep-diffing piece is a separate, much larger Phase 6+ crate; this slice
is only the admin's own lightweight `django.contrib.admin.models.LogEntry` equivalent).

Investigated and confirmed before writing this doc (no design risk left unresolved):

- **No bespoke migration needed.** `djangors_migrations::plan::build_create_all_plan()` walks
  `djangors_orm::meta::all_registered_models()` — the same `inventory`-based global registry
  `collect_related_objects` (5.5) and `sync_permissions` (5.7.1) already use — and auto-generates
  DDL for any `#[derive(Model)]` struct in the binary, independent of whether it's registered with
  an `AdminSite`. `LogEntry` does not need to be (and should not be) registered with `AdminSite`
  in this slice — Django's own `LogEntry` has no default changelist either; it's read internally.
- **`require_perm` already returns the acting `User`** at all 10 existing call sites in
  `crates/djangors-admin/src/lib.rs`, currently always via `require_perm(...).await?;` with the
  return value discarded. Every mutating handler below needs `let user = require_perm(...).await?;`
  instead — a one-token change per call site, not a new plumbing mechanism.
- **`#[derive(Model)]` also derives `FromRow`** (confirmed in
  `crates/djangors-macros/src/model.rs` — the `Model` derive macro emits both the `Model` trait
  impl and a `FromRow` impl in one expansion), so `LogEntry` needs exactly one derive, no second
  `FromRow` derive like some ORMs require.
- **Name collision to avoid**: `crates/djangors-admin/src/lib.rs` already has
  `use djangors_orm::meta::{Model, ModelMeta};` (the `Model` *trait*) at the top of the file. The
  existing `#[cfg(test)] mod tests` block sidesteps this by aliasing the derive macro:
  `use djangors_macros::Model as MacroModel;`. Do the same in module scope (not test scope) for
  `LogEntry` — pick a distinct alias, e.g. `use djangors_macros::Model as DeriveModel;`, and
  `#[derive(DeriveModel, Debug, Clone)]`. Do **not** remove or rename the existing `use
  djangors_orm::meta::{Model, ModelMeta};` import — it's used throughout the file for the trait.
- **`object_repr` convention**: this codebase has no per-model `Display`/`__str__` equivalent (a
  known, already-ledgered gap — the delete-confirm page's related-object listing has the same
  limitation). Use Django's own generic fallback exactly: `format!("{} object ({})",
  meta.struct_name, pk)`. This needs no extra DB query (unlike fetching real field values), which
  matters specifically for `admin_delete_post`, which does not currently re-fetch the row before
  deleting it — see below.
- **`save()` is `&self`, not consuming**, and returns `Result<Self, OrmError>` with the
  DB-generated pk filled in (confirmed in `crates/djangors-macros/src/model.rs`: `pub async fn
  save(&self, db: &Database) -> Result<Self, OrmError> { ... }`). A `LogEntry` write is therefore
  `LogEntry { id: 0, ..., ..: ... }.save(db).await.map_err(|e|
  DjangorsError::Internal(e.to_string()))?;` — matches the exact pattern already used everywhere
  else in this file for a fresh insert.

## The `LogEntry` model

New struct, added to `crates/djangors-admin/src/lib.rs` near the top (alongside `SiteBranding`,
before the handler functions), **not** in `mod tests`:

```rust
use djangors_macros::Model as DeriveModel;

pub const ACTION_ADDITION: i32 = 1;
pub const ACTION_CHANGE: i32 = 2;
pub const ACTION_DELETION: i32 = 3;

#[derive(DeriveModel, Debug, Clone, serde::Serialize)]
#[djangors(app = "admin", table_name = "djangors_admin_log")]
pub struct LogEntry {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user_id: i64,
    pub action_time: chrono::DateTime<chrono::Utc>,
    pub app_label: String,
    pub model_name: String,
    pub object_id: i64,
    pub object_repr: String,
    pub action_flag: i32,
    pub change_message: String,
}
```

Notes:
- `user_id` is a plain `i64`, **not** a `#[djangors(relation = ...)]` FK field. This deliberately
  sidesteps the standing `AuthUser`-generic limitation (ledgered since 5.7.2/5.1): the admin's own
  `require_perm`/`require_staff` are hardcoded to `djangors_auth::User` today, and a real FK
  relation would need to name a concrete target type. A raw id column needs no such commitment and
  is exactly what Django's own migration-level FK column is physically anyway.
- `object_id` is `i64` (not Django's `CharField`) because every `#[derive(Model)]` primary key in
  this codebase observed so far is `i64` — matches the codebase's own convention rather than
  Django's, which has to support arbitrary pk types.
- `derive(..., serde::Serialize)` is needed because `admin_index`'s `IndexContext` will hold a
  `Vec` of a small display struct built from `LogEntry` rows (see below) — actually `LogEntry`
  itself is never serialized directly into a template context; a dedicated `RecentActionRow` is
  used instead (next section) so the template only ever sees rendering-ready `String`/`i32`
  fields, matching every other context struct in this file. Keep `serde::Serialize` on `LogEntry`
  anyway for parity with `User` and other model structs already deriving it — **do not** skip it,
  but also do not feed `LogEntry` directly into a template context.

## Writing entries

New private helper, placed right after `LogEntry`'s definition:

```rust
async fn log_action(
    db: &djangors_db::Database,
    user_id: i64,
    meta: &'static ModelMeta,
    object_id: i64,
    action_flag: i32,
    change_message: &str,
) -> Result<(), DjangorsError> {
    LogEntry {
        id: 0,
        user_id,
        action_time: chrono::Utc::now(),
        app_label: meta.app_label.to_string(),
        model_name: meta.struct_name.to_string(),
        object_id,
        object_repr: format!("{} object ({})", meta.struct_name, object_id),
        action_flag,
        change_message: change_message.to_string(),
    }
    .save(db)
    .await
    .map_err(|e| DjangorsError::Internal(e.to_string()))?;
    Ok(())
}
```

A logging failure becomes a real `500` for the whole request (via `?`), same as every other DB
call in this file — there is no existing "best-effort, swallow errors" pattern anywhere else in
`djangors-admin` to deviate toward, and a `LogEntry` write failing silently would be a worse
surprise than a loud one.

### The 5 call sites — exact edits

1. **`admin_add_post`** (around line 1944, success arm `Ok(_new_pk) => ...`): capture the acting
   user (`require_perm` at line 1939 already returns `User`; change
   `require_perm(&req, db, admin.model_meta(), "add").await?;` to
   `let user = require_perm(&req, db, admin.model_meta(), "add").await?;`), then on success:
   ```rust
   Ok(new_pk) => {
       log_action(db, user.id, admin.model_meta(), new_pk, ACTION_ADDITION, "Added.").await?;
       Ok(Response::redirect(&format!("/{}/{}/", app, model)))
   }
   ```
   (`new_pk` was previously named `_new_pk` — drop the underscore now that it's used.)

2. **`admin_change_post`** (around line 2050, success arm `Ok(()) => ...`): same
   `let user = require_perm(...)` change at line 2045, then:
   ```rust
   Ok(()) => {
       log_action(db, user.id, admin.model_meta(), pk, ACTION_CHANGE, "Changed.").await?;
       Ok(Response::redirect(&format!("/{}/{}/", app, model)))
   }
   ```

3. **`admin_delete_post`** (around line 2317-2324): same `let user = require_perm(...)` change,
   then log **before** redirecting but **after** confirming `deleted == true`:
   ```rust
   let deleted = admin.delete_by_pk(db, pk).await?;
   if deleted {
       log_action(db, user.id, admin.model_meta(), pk, ACTION_DELETION, "Deleted.").await?;
       Ok(Response::redirect(&format!("/{}/{}/", app, model)))
   } else {
       Err(DjangorsError::NotFound)
   }
   ```
   Do **not** try to fetch the row's field values first to build a "real" `object_repr` — the
   generic `"<Model> object (<pk>)"` fallback needs no query, and adding one here would be new,
   unasked-for scope (a real per-model `Display` mechanism is its own future item).

4. **`admin_bulk_delete_post`** (around line 2347 for the `let user = ...` change, and the step-2
   delete loop at line 2406-2408): one `LogEntry` per successfully-deleted pk, matching Django's
   own per-object granularity for bulk actions (not one combined entry):
   ```rust
   for &pk in &pks {
       if admin.delete_by_pk(db, pk).await? {
           log_action(db, user.id, admin.model_meta(), pk, ACTION_DELETION, "Deleted.").await?;
       }
   }
   ```
   (Note `delete_by_pk` returns `bool`; the existing code at line 2406-2408 discards it — check the
   already-gone-pk race case still needs no log entry, matching `admin_delete_post`'s existing
   "false = already gone, not a failure" reasoning for *not* erroring, extended here to also mean
   *not* logging.)

5. **`admin_save_changelist_post`** (around line 2450 for `let user = ...`, and the per-pk loop at
   line 2482-2487): log one `CHANGE` entry per pk that had **no** validation errors (i.e. actually
   got written), not per pk merely attempted:
   ```rust
   let mut row_errors: Vec<(i64, std::collections::HashMap<String, String>)> = Vec::new();
   for (pk, fields) in &by_pk {
       match admin.update_fields_from_form(db, *pk, fields).await? {
           Ok(()) => {
               log_action(db, user.id, admin.model_meta(), *pk, ACTION_CHANGE, "Changed.").await?;
           }
           Err(errors) => row_errors.push((*pk, errors)),
       }
   }
   ```

`admin_export_csv` is **not** a mutating action — no log entry, matching its existing
`require_perm(..., "view")` scoping (unchanged from today).

## The "Recent actions" panel

`admin_index` (line ~1222) already resolves `let user = require_staff(&req).await?;` and has `db`
in scope. Add a query for that user's most recent 10 `LogEntry` rows, newest first, right before
the existing `models` loop or after it (order doesn't matter, they're independent):

```rust
let recent_rows: Vec<LogEntry> = sqlx::query_as(sqlx::AssertSqlSafe(
    "SELECT id, user_id, action_time, app_label, model_name, object_id, object_repr, \
     action_flag, change_message FROM djangors_admin_log WHERE user_id = $1 \
     ORDER BY action_time DESC LIMIT 10",
))
.bind(user.id)
.fetch_all(db.pool())
.await
.map_err(|e| DjangorsError::Internal(e.to_string()))?;

let recent_actions: Vec<RecentActionRow> = recent_rows
    .into_iter()
    .map(|e| RecentActionRow {
        action_label: match e.action_flag {
            ACTION_ADDITION => "Added",
            ACTION_DELETION => "Deleted",
            _ => "Changed",
        },
        object_repr: e.object_repr,
        app_label: e.app_label,
        model_name: e.model_name,
        action_time: e.action_time.format("%Y-%m-%d %H:%M:%S").to_string(),
    })
    .collect();
```

Check the exact `sqlx`/`Database` accessor names used elsewhere in this file before writing this
(`db.pool()`, `sqlx::query_as`, `sqlx::AssertSqlSafe` are all already used in
`collect_related_objects` a few hundred lines below — mirror that exact style, don't invent a new
one). New context struct, next to `IndexModelLink`:

```rust
#[derive(serde::Serialize)]
struct RecentActionRow {
    action_label: &'static str,
    object_repr: String,
    app_label: String,
    model_name: String,
    action_time: String,
}
```

`IndexContext` gains one new field:

```rust
#[derive(serde::Serialize)]
struct IndexContext {
    models: Vec<IndexModelLink>,
    recent_actions: Vec<RecentActionRow>,
    site_header: String,
    site_title: String,
    logo_url: Option<String>,
    accent_color: Option<String>,
}
```

`admin/index.html` — currently one line:

```html
{% extends "admin/base.html" %}{% block content %}<ul>{% for m in models %}<li><a href="{{ m.href }}">{{ m.label }}</a></li>{% endfor %}</ul>{% endblock %}
```

Add a "Recent actions" section after the model list, gated on non-empty (matches the existing
`{% if %}`-gated-optional pattern `base.html` already uses for `logo_url`/`accent_color`):

```html
{% extends "admin/base.html" %}{% block content %}<ul>{% for m in models %}<li><a href="{{ m.href }}">{{ m.label }}</a></li>{% endfor %}</ul>{% if recent_actions %}<h2>Recent actions</h2><ul>{% for a in recent_actions %}<li>{{ a.action_time }} — {{ a.action_label }} {{ a.app_label }}.{{ a.model_name }}: {{ a.object_repr }}</li>{% endfor %}</ul>{% endif %}{% endblock %}
```

Every field here (`object_repr`, `app_label`, `model_name`, `action_time`) is either a compile-time
`&'static str` copied to `String` or a `format!`-built string with no user-controlled characters
beyond what `object_repr`'s `pk` (an `i64`, cannot contain markup) contributes — ordinary
autoescaping is correct and sufficient, no `|safe`/`html_escape` needed anywhere in this panel.

## Required tests

Add to `mod tests` in `crates/djangors-admin/src/lib.rs`, following the existing per-test
`CREATE TABLE`/`DROP TABLE` style (no shared fixture table across tests in this file):

1. **`test_audit_log_add_change_delete`**: register `ModelA` (or a fresh throwaway test model),
   create the `djangors_admin_log` table manually (same pattern as every other test in this file —
   do **not** rely on migrations), perform one add, one change, and one delete through the router
   (in-process `router.handle()`, same as every other test here), then query
   `djangors_admin_log` directly via `sqlx` and assert exactly 3 rows exist with the expected
   `action_flag` values (1, 2, 3 in that order) and `object_repr` matching
   `format!("ModelA object ({})", pk)` for the relevant pk each time.
2. **`test_audit_log_bulk_delete_and_list_editable`**: two rows, bulk-delete both through the
   two-step confirm flow (mirroring 5.6.3's existing bulk-delete test setup) → assert 2 `DELETION`
   entries; then for `list_editable`, edit one row's field successfully and one row's field with an
   invalid value (triggering `row_errors`) → assert exactly 1 `CHANGE` entry was written (the
   successful row only), not 2.
3. **`test_admin_index_recent_actions`**: perform 2-3 actions as one staff user, then `GET
   /admin/` as that same user → assert the response body contains a `"Recent actions"` heading and
   the expected `object_repr` strings, in newest-first order (assert index-of one substring is
   before another, the same "occurs before" assertion style already used for pager/ordering tests
   elsewhere in this file if that pattern exists — otherwise just assert both substrings are
   present, matching the simpler substring-only style most existing tests use). Also assert a
   **second** staff user with zero actions of their own sees no `"Recent actions"` heading at all
   (proves the `WHERE user_id = $1` scoping and the `{% if recent_actions %}` gate both work) —
   register this as a required negative-case test, following this project's established practice
   (5.8.10's `test_branding_overrides` had the same positive+negative shape) of never shipping only
   the happy path for a feature with a visible on/off condition.

All 11 pre-existing tests plus the 3 added in 5.8.10 (`test_csrf_token_wiring`,
`test_favicon_serving`, `test_branding_overrides`) must still pass with **zero modification** —
this slice only adds a `let user =` binding at 5 call sites (replacing a discarded return value,
not changing any handler's request/response contract) and one new optional template section gated
on non-empty data, so no existing assertion should be affected. `examples/polls/tests/voting.rs`
and `examples/school/tests/admin_crud.rs` must also pass unmodified — both exercise `admin_add_get`
et al. only incidentally via the mounted `AdminSite`, not the changelist/log query path directly,
so their existing assertions have no dependency on `djangors_admin_log` existing or not.

## Explicitly out of scope (do not build in this slice)

- A per-object **History** page (Django's `/admin/<app>/<model>/<pk>/history/`) — v2.
- Real field-level diffing / `change_message` beyond the fixed strings `"Added."`/`"Changed."`/
  `"Deleted."` — Django's own `change_message` is a JSON-serialized list of changed field names;
  matching that exactly needs `update_from_form`/`update_fields_from_form` to report which fields
  actually changed (they currently return `Result<(), HashMap<...>>` on error only, nothing on
  success), a real signature change to those two `ModelAdmin` trait methods — too large a blast
  radius for this slice.
- IP address / request-id capture on each entry.
- `djangors-contrib-audit` (deep per-field history table with rollback) — a separate, much larger
  future crate per `PLAN.md` line 124/362, not this slice.
- Global (not per-user) "Recent actions" across the whole install, or a paginated/filterable log
  viewer — Django's own admin index panel is per-user-scoped exactly as designed here; a
  site-wide viewer is a natural follow-up but not required for parity with Django's own default UI.
