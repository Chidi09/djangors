# 8.2 — `djangors-rest` auth (session/token/JWT) + permission classes

## Scope

Continues Phase 8 after 8.1 (`djangors-rest` core, commit `a3f2257`). Closes 8.1's most important
documented gap: **`ViewSet`/`viewset_routes` currently has zero access control.** This slice adds
three auth mechanisms and a permission-class system, and makes `ViewSet` actually enforce
something by default instead of being wide open.

**Deliberately excluded from this dispatch, left for later 8.x slices**: throttling,
filtering/ordering query-param integration, OpenAPI 3.1 generation, the browsable API HTML page.

## Part A — session auth (reuse, don't rebuild)

`djangors_auth::Auth<U>` (a `FromRequest` extractor, `crates/djangors-auth/src/lib.rs` ~line 214)
already does real session-based authentication — read it in full before writing any new code.
`djangors-rest`'s `ViewSet` handlers should be able to require it directly; this part is mostly
*wiring*, not new mechanism.

## Part B — token auth (new)

A new `AuthToken` model:
```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_rest", table_name = "djangors_rest_authtoken")]
pub struct AuthToken {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user: ForeignKey<djangors_auth::User>,
    #[djangors(max_length = 64, unique)]
    pub key: String, // a random, high-entropy token string
    pub created_at: chrono::DateTime<chrono::Utc>,
}
pub fn generate_token_key() -> String; // cryptographically random, e.g. via `rand`, already a
                                        // workspace dependency — don't add a new crate for this
```
A `TokenAuth` `FromRequest` extractor reading `Authorization: Token <key>` (mirror the exact header
name/scheme Django REST Framework itself uses, since that's the established convention this
project is porting), looking up the token, returning the associated user (404/401-equivalent
`DjangorsError::Unauthorized` if missing/not found — mirror `Auth<U>`'s own error-handling
convention exactly).

## Part C — JWT auth (new, feature-gated)

Add the `jsonwebtoken` crate (confirm its current real API before writing code) behind a new,
**not-default** Cargo feature (e.g. `feature = "jwt"`, mirroring `djangors-cache`'s own precedent
for `redis` — an optional dependency gated behind a matching feature flag) so a project that never
wants JWT support doesn't pull in the dependency. A `JwtAuth` extractor reading
`Authorization: Bearer <token>`, validating against a secret (reuse
`DjangorsSettings.secret_key` — read `crates/djangors-core/src/settings.rs` to confirm this is
the right existing secret to reuse rather than inventing a separate JWT-specific secret setting),
with a `user_id` claim. Provide a real `encode_jwt(user_id, secret) -> String` /
`decode_jwt(token, secret) -> Result<i64, ...>` pair — this needs both directions to be
genuinely testable and usable (a project needs to issue tokens, not just validate them).

## Part D — permission classes

```rust
#[async_trait::async_trait]
pub trait Permission: Send + Sync {
    async fn has_permission(&self, req: &Request) -> bool;
}
pub struct AllowAny;
pub struct IsAuthenticated; // true if ANY of session/token/JWT auth resolves a user
```
Wire a permission check into `ViewSet`'s handlers — the cleanest shape given `ViewSet<M>` is
already a generic struct: consider whether adding a second generic parameter
(`ViewSet<M, P: Permission = IsAuthenticated>`) or a builder/config struct passed into
`viewset_routes` fits this codebase's existing generic-parameter conventions better (check how
`djangors-cache`'s `CacheLayer`/`djangors-admin`'s `ModelAdminConfig` structure optional
configuration, for precedent) — use your judgment, but **the default must be `IsAuthenticated`,
not `AllowAny`**, closing 8.1's "zero access control" gap by making authentication-required the
out-of-the-box behavior, with `AllowAny` available as an explicit opt-out for genuinely public
endpoints. Update `viewset_routes`'s own doc comment (currently carries a loud "zero access
control" warning from 8.1) to reflect the new, safer default.

**Required tests**: a real end-to-end test proving an unauthenticated request to a
`viewset_routes`-mounted route is rejected (401/403) by default; one proving a request with a
valid session, a valid token, and a valid JWT each independently succeed; one proving an
explicitly-`AllowAny`-configured route accepts an unauthenticated request; token lookup rejecting
an unknown/malformed key; JWT round-trip (encode then decode recovers the same user_id) and
rejection of a tampered/invalid token.
