# 11.7 — Server-rendered generic class-based views (ListView/DetailView/CreateView/UpdateView/DeleteView)

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_7` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

`djangors-rest`'s `ViewSet<M: Model + FromRow>` (`crates/djangors-rest/src/lib.rs`, ~line 555:
`list`/`retrieve`/`create`/`update`/`destroy`, each `async fn(Request, PathParams) ->
Result<Response, DjangorsError>`) is the JSON-API equivalent of what this task builds — the
HTML/server-rendered equivalent (Django's `django.views.generic`, a *different, separate* module
from Django's DRF-equivalent). Mirror `ViewSet`'s method shape and generic-over-`M` structure;
don't invent a different pattern.

**A real architectural gap this task must fix first, in already-shipped code — read this
carefully before writing anything else:** Phase 11 item 5 (`docs/design/11.5-modelform.md`,
already shipped, `crates/djangors-macros/src/model.rs`) extended `#[derive(Model)]` to generate
`validate_form()`/`from_cleaned_form()`/`apply_cleaned_form()` and a per-struct
`{StructName}FormCleaned` type — but as **inherent methods on each specific struct**, not as a
trait. A generic `CreateView<M: Model + FromRow>` cannot call `M::validate_form(...)` today,
because Rust has no way to call an inherent method through a generic type parameter — only trait
methods work that way. Verify this yourself by trying to write a toy generic function calling
`M::validate_form` and confirming the compiler rejects it before proceeding.

**The fix**: add a new trait in `djangors-orm` (e.g. `pub trait ModelForm: Model { type
FormCleaned; fn validate_form(data: &std::collections::HashMap<String, String>) ->
Result<Self::FormCleaned, djangors_forms::FormErrors>; fn from_cleaned_form(cleaned:
Self::FormCleaned) -> Self; fn apply_cleaned_form(&mut self, cleaned: Self::FormCleaned); }`), then
have `#[derive(Model)]` (`crates/djangors-macros/src/model.rs`) additionally emit an `impl
ModelForm for #struct_name_ident` block whose trait methods simply delegate to the existing
inherent methods (`fn validate_form(data: &...) -> ... { Self::validate_form(data) }` etc. - the
inherent methods stay exactly as they are; this is a purely additive trait wrapper, not a rewrite).
This lets generic code elsewhere (this task's CBVs) be bound `M: Model + FromRow + ModelForm`.
Confirm this doesn't break any of the 5 existing ModelForm tests in
`crates/djangors-orm/src/tests.rs` (search for `test_modelform_`) - they call the inherent methods
directly (`ModelFormTestModel::validate_form(...)`) which must keep working unchanged.

## Scope — what to build

1. **The `ModelForm` trait + macro emission fix described above** (in `djangors-orm` and
   `djangors-macros` respectively) - do this first, it's a prerequisite for everything else.

2. **A new crate, `djangors-views`** (register it in the workspace root `Cargo.toml`'s `members`
   list, matching how every other crate is registered), depending on `djangors-core`,
   `djangors-orm`, and `djangors-template` (verify this three-way dependency doesn't cycle: `grep
   -n djangors- crates/djangors-template/Cargo.toml crates/djangors-rest/Cargo.toml` shows
   `djangors-template → djangors-core` and `djangors-rest → djangors-orm, djangors-core` already
   coexist safely - a new crate depending on all three the same way is architecturally identical,
   just re-verify it yourself rather than assuming). Mirror `djangors-rest`'s real
   `Cargo.toml`/crate-description conventions (see other crates for the exact boilerplate:
   `version.workspace = true`, etc.)

3. **Five generic view functions, each `async fn(Request, PathParams) -> Result<Response,
   DjangorsError>`** (matching `ViewSet`'s exact signature shape), generic over `M: Model +
   FromRow + ModelForm + Clone` (whatever bounds are actually needed - work them out from the real
   implementation, don't guess a bound list up front):
   - `ListView<M>`: fetches all `M` rows (reuse `QuerySet::all`/pagination - check
     `djangors-rest`'s existing pagination utility, likely shared/reusable rather than
     reinvented), renders them via a caller-provided template name and `djangors-template`'s
     `TemplateEngine::render`.
   - `DetailView<M>`: fetches one `M` row by primary key from `PathParams`, renders it via a
     template.
   - `CreateView<M>`: GET renders an empty form (a template gets the field list/errors context);
     POST parses form data from the request body, calls `M::validate_form()`, and on success
     calls `M::from_cleaned_form(...).save(db)` then redirects (a real HTTP redirect response, not
     a 200 with a body) - on validation failure, re-renders the form template with the real
     `FormErrors` in context.
   - `UpdateView<M>`: like `CreateView` but GET pre-fills the form from an existing row (fetched
     by pk), and POST calls `.apply_cleaned_form(...)` + `.update(db)` on the fetched instance
     rather than constructing a new one.
   - `DeleteView<M>`: GET renders a confirmation template; POST calls `QuerySet::delete_by_pk` (or
     the instance's own `.delete(db)`) and redirects.

4. **A way for the caller to configure things a fully-generic view can't know on its own**:
   template name(s), the redirect URL after a successful create/update/delete, and how to extract
   the raw form `HashMap<String, String>` from a request body (reuse the existing `Form` extractor
   in `crates/djangors-core/src/extract.rs` for URL-encoded bodies - the common case; multipart
   form submission, Phase 11 item 6, already shipped, is a separate concern, don't force CBVs to
   handle multipart in this pass unless it's trivial to also support). A small config struct
   passed into each view function (mirroring `ViewSetConfig` in `djangors-rest`, ~line 490 - follow
   that existing pattern rather than inventing a new configuration shape) is a reasonable design;
   don't over-engineer a builder API beyond what's actually needed.

## Deliberately excluded

- Wiring real HTML templates/CSS for these views into any example app - this task ships the
  *view logic*, not example-app template files. A caller supplies their own template name/content;
  don't author new templates in `examples/polls` or `examples/school`.
- Permission/auth checks (Django's `LoginRequiredMixin`/`PermissionRequiredMixin` equivalents) -
  out of scope, a caller can wrap these functions in their own middleware/auth check.
- Formsets, inline formsets (Django's nested-form-on-one-page pattern).
- Multipart/file-upload handling inside these views beyond what's trivial - if it's not
  straightforward to support given the existing `Multipart` extractor's shape, skip it and note
  the gap rather than half-implementing it.
- Pagination beyond what already exists and is reusable from `djangors-rest` - don't build a
  second pagination implementation.
