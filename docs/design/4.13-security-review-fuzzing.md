# Design 4.13 — Security review checklist, threat model, fuzz targets (Phase 4 part 4e)

**Status:** draft, pre-implementation. Final `PLAN.md` Phase 4 bullet:
"Security review checklist doc; threat model doc; fuzz targets for parsers (multipart, cookies,
query strings)." Everything else in Phase 4 that doesn't need new ORM schema or an email backend
is already built and committed: sessions ([[4.7-sessions]]), CSRF ([[4.8-csrf]]), security
middleware (HSTS/host validation/secure cookies, part 3), the `User` model
([[4.10-auth-user-model]]), `AuthBackend`/`login`/`logout`/`Auth<U>` ([[4.11-auth-backend-login]]),
and rate limiting + audit signals ([[4.12-auth-rate-limit-signals]]).

## Split: docs vs. code

This bullet has two different kinds of deliverable:

1. **Security review checklist doc + threat model doc** — prose that documents/audits the
   already-built code above. This is analysis-and-writeup over real, committed code, not new
   implementation — written directly (same as every other `docs/design/*.md` file this project has
   produced), not dispatched.
2. **Fuzz targets** — real code (a `cargo-fuzz` harness crate) — dispatched, same as all other
   implementation this project has done.

## Part 1: fuzz targets — real scope check first

`PLAN.md` says "parsers (multipart, cookies, query strings)". Checked against the actual codebase:

- **Query strings**: `Request::parse_query` (`crates/djangors-core/src/request.rs`) is a real,
  hand-rolled parser (splits on `&`/`=`, percent-decodes). Real fuzz target.
- **Cookies**: two real hand-rolled cookie-header parsers exist — `extract_session_cookie`
  (`crates/djangors-sessions/src/lib.rs`) and `extract_cookie`
  (`crates/djangors-core/src/middleware.rs`, used by both CSRF and host validation flows) — plus
  `SignedCookieStore::decode` (`crates/djangors-sessions/src/lib.rs`), which parses a
  fully attacker-controlled cookie *value* (base64, JSON, HMAC verification). All real, all
  attacker-facing (a browser sends whatever `Cookie` header it wants). Real fuzz targets.
- **Multipart**: **does not exist yet**. `crates/djangors-core/src/extract.rs`'s `Json`/`Form`
  extractors explicitly *reject* `multipart/*` content types rather than parsing them (see the
  `ct_lower.starts_with("multipart/")` check). Phase 3's PLAN.md line "body handling, multipart,
  form parsing" was only partially delivered — form/JSON exist, multipart (needed for file
  uploads) was not built. **There is no parser to fuzz.** This task does not add one (multipart
  parsing is real, scoped implementation work belonging to whichever future task actually adds
  file-upload support, likely revisiting Phase 3). Note this gap explicitly in the checklist doc
  written in Part 2 below, so it isn't silently lost.

So Part 1 ships fuzz targets for query strings and cookies (both the header-parsing layer and the
signed-value-decoding layer), and explicitly documents (not silently skips) that multipart has no
fuzz target because it has no implementation yet.

## Part 1: fuzz target implementation

Standard `cargo-fuzz` layout: a `fuzz/` directory at the workspace root, `fuzz/Cargo.toml` (not a
workspace member — `cargo-fuzz` convention is a separate, un-workspaced crate; check what
`cargo fuzz init` generates and follow it), `fuzz/fuzz_targets/*.rs`. Depends on `libfuzzer-sys`,
`djangors-core`, `djangors-sessions`.

Three targets, exercised through **public API only** — no visibility changes to existing crates
(`extract_session_cookie`/`extract_cookie` stay private; drive them indirectly through the real
public entry points that call them):

1. **`fuzz_targets/query_string.rs`**: feed the fuzzer's raw bytes as a query string appended to a
   fixed valid path (e.g. `format!("http://x/p?{}", <lossy-utf8-or-skip-on-invalid-uri>)`),
   attempt `Uri::try_from`, skip (return early, not a panic) if the fuzzer's bytes don't even form
   a valid URI — the interesting surface is `Request::parse_query` itself once a URI is
   constructed, not `Uri`'s own parser (that's `http`/`hyper`'s problem, not ours). Construct a
   `Request::new(...)` with that URI and assert it never panics; call `.query()` for a few
   arbitrary keys derived from the input to also exercise the lookup path.
2. **`fuzz_targets/cookie_header.rs`**: build a real `hyper::Request` with a `Cookie` header set to
   the fuzzer's bytes (lossy-UTF8 is fine — a real browser can send non-UTF8 bytes in a cookie
   header and the parser must not panic on it), drive it through a real `SessionLayer` wrapping a
   trivial inner `tower::Service` (mirror the exact construction
   `crates/djangors-sessions/src/lib.rs`'s own `#[cfg(test)]` tests already use to build a full
   `SessionService::call`), assert no panic. Do the same for `CsrfLayer`
   (`crates/djangors-core/src/middleware.rs`) in a second pass over the same input within the same
   fuzz target (both parsers read the same header, both are cheap to drive) — or as a separate
   target if that's cleaner to wire up; use judgement, either is fine.
3. **`fuzz_targets/session_cookie_decode.rs`**: `SignedCookieStore::decode(cookie_value: &str)` is
   already public — call it directly with the fuzzer's bytes (lossy-UTF8) against a
   `SignedCookieStore` built with a fixed test secret key, assert no panic. This is the highest-
   value target: it's the one path where a fully attacker-controlled string goes through base64
   decode → HMAC verify → JSON deserialize, and `decode` already has to return `Option` (not
   panic) for tampered/malformed input per its existing contract — a fuzz target is exactly what
   proves that contract holds, not just what the hand-written `test_tamper_rejection` unit test in
   the same file already covers for a few hand-picked cases.

No CI wiring in this task (running fuzz targets continuously/in CI is real infra work — a
`cargo fuzz run <target> -- -max_total_time=60` smoke invocation to prove each target builds and
runs cleanly for a short burst is enough to prove the harness itself is correct; add a note in the
checklist doc that continuous/scheduled fuzzing is future work, e.g. OSS-Fuzz integration or a
nightly CI job, not built here).

## Part 2: security review checklist doc + threat model doc (written directly, not dispatched)

Two new files: `docs/design/security-checklist.md` and `docs/design/threat-model.md` (not
`4.13-*` — these are living review documents, not a one-time design-then-build doc like the
`4.N-*` series, so they don't get a phase-part number; they'll be revisited as later phases add
attack surface).

**Threat model doc** covers, per already-built subsystem, referencing real file/function names
(not aspirational): trust boundaries (browser ↔ server via cookies/headers is the main untrusted
input surface so far — no API/token auth exists yet, that's Phase 8), what's mitigated where
(session fixation → `login()`'s `cycle_key()`; CSRF → double-submit cookie + header check;
username enumeration timing → `ModelBackend`'s dummy-hash path; login brute force →
`RateLimitedBackend`; XSS via signal payloads → the `LoginFailed.username` doc-comment warning),
and honestly-scoped known gaps (CSRF v1 is header-only, no form-field `csrfmiddlewaretoken`
support yet, see [[4.8-csrf]]'s own deferral note; rate limiting is single-process/in-memory only,
see [[4.12-auth-rate-limit-signals]]'s own deferral note; no multipart parser exists yet so no
file-upload attack surface to model yet; no CSP is emitted by default, only a helper — check
`HstsLayer`/`SecurityHeadersLayer` in `crates/djangors-core/src/middleware.rs` for exactly what
headers are and aren't set by default).

**Checklist doc** is the OWASP-Top-10-shaped self-assessment `PLAN.md`'s Phase 4 DoD explicitly
calls for ("OWASP top-10 self-assessment written") — one section per OWASP category, each either
"mitigated — how, where" or "not applicable yet — why" or "known gap — tracked, see [deferral]".
Do not mark anything "mitigated" without pointing at the real file/line/test that proves it; this
doc is only useful if it's honest about what's actually built vs. aspirational.

## What this task does NOT include

- Multipart parsing itself (no fuzz target possible without it — noted as a gap, not built here).
- CI wiring for continuous fuzzing (OSS-Fuzz, scheduled job) — a one-off local smoke run per
  target is enough to prove the harness works.
- Any change to existing crates' function visibility — fuzz targets drive everything through
  already-public API surfaces.
- Groups/permissions/password-reset (part 4d, separate, still not started).

## Required tests / acceptance

- `cargo fuzz build` succeeds for all three targets (compiles clean).
- Each target run locally for a short burst (e.g. `-max_total_time=30` or `-runs=100000`,
  whichever is faster to demonstrate) with **zero crashes/panics found** — if a target *does*
  find a real panic, that's a real bug: fix the underlying parser (small, targeted fix in the
  affected crate), re-run to confirm the fix holds, and note the finding + fix in the eventual
  commit message rather than silently weakening the fuzz target to avoid it.
- `docs/design/security-checklist.md` and `docs/design/threat-model.md` exist, reference real
  file/function names for every "mitigated" claim, and explicitly list every known gap already
  documented in prior deferral notes (CSRF, rate limiting, multipart) rather than omitting them.
