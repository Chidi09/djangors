# Design 4.4 — Template engine (v1 scope)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 3's template bullet first — this narrows it into an achievable first slice, the same way 4.3 narrowed migrations.

## v1 scope, and why it's narrower than the plan bullet

`PLAN.md` lists `{% url %}`, `{% static %}`, and `{% csrf_token %}` as day-one template tags. All three depend on framework pieces that don't exist yet: `{% url %}` needs named-route reversal (the router only does path *matching* today, not reversal — `PLAN.md`'s own router design explicitly deferred this); `{% static %}` needs `djangors-staticfiles` (not started); `{% csrf_token %}` needs sessions/auth (not started, Phase 4 in the original plan). Building stub versions of these tags that don't actually connect to anything real would be worse than not having them — v1 ships a genuinely working engine with the tags that are fully real today, and adds the other three as a follow-up once each dependency exists, rather than shipping hollow tags now.

**v1 delivers:** a working `Environment` wrapping `minijinja`, loader precedence (project `templates/` directory overrides app-provided templates), auto-escaping on by default, native Jinja template inheritance (`{% extends %}`/`{% block %}` — MiniJinja already implements this, no Djangors-side work needed beyond correct loader wiring), a `render()` shortcut producing a `djangors_core::Response`, and a small set of self-contained Django filters that don't depend on anything unbuilt (`date`, `floatformat`, `pluralize`, `default`, `truncatewords` — pure string/value transforms, no framework dependencies).

**Deferred, explicitly, to a follow-up once the dependency exists:** `{% url %}` (needs router reversal), `{% static %}` (needs staticfiles), `{% csrf_token %}` (needs sessions), hot-reload-on-file-change (a dev-loop nicety, not correctness-blocking for v1), `include_dir!`-based release embedding (also a packaging nicety, not blocking).

## Crate shape

New crate `djangors-template` (already exists as an empty placeholder in the workspace). Depends on `minijinja` (verify exact version) and `djangors-core` (for `Response`/`Request` — a `render()` shortcut needs to produce a real `Response`, so this crate, unlike `djangors-orm`/`djangors-db`, legitimately depends on the HTTP layer; this is fine and expected, template rendering is inherently HTTP-response-producing, not a lower layer other things build on).

## Loader precedence

Django's template loader checks each `INSTALLED_APPS` app's own `templates/` directory, but a project-level `templates/` directory (if configured) is checked *first* — this is what lets a project override one specific template from a third-party app (e.g. re-skinning the admin) without forking the whole app. v1's equivalent, without a full app-registry yet (that's Phase 2's `AppConfig` system, not built): a `TemplateLoader` that takes an ordered `Vec<PathBuf>` of directories to search, checked in order, first match wins. A project wires this up as `TemplateLoader::new(vec!["templates/", "some_app/templates/"])` — the *project* directory listed first is what achieves override behavior, matching Django's actual precedence rule, just configured explicitly today instead of derived from an app registry that doesn't exist yet.

```rust
pub struct TemplateEngine {
    env: minijinja::Environment<'static>,
}

impl TemplateEngine {
    /// Directories are searched in order; the first directory containing a
    /// requested template name wins — list project-level template
    /// directories before app-level ones to get Django's override behavior.
    pub fn new(search_dirs: Vec<PathBuf>) -> Result<Self, TemplateError> { ... }

    pub fn render(&self, name: &str, ctx: impl Serialize) -> Result<String, TemplateError> { ... }
}
```

## The `render()` shortcut

```rust
pub fn render(engine: &TemplateEngine, name: &str, ctx: impl Serialize) -> Result<Response, DjangorsError> {
    let html = engine.render(name, ctx).map_err(|e| DjangorsError::Internal(e.to_string()))?;
    Ok(Response::html(StatusCode::OK, html))
}
```

Django's `render()` also auto-injects a `RequestContext` (the current user, flash messages, CSRF token) into every template's context automatically. None of those exist yet (no auth, no sessions, no messages framework) — v1's `render()` takes exactly the context the caller passes and nothing more. This is an honest, temporary gap, not a design decision to revisit later: once auth/sessions/messages land, `render()` should gain a `req: &Request` parameter specifically to pull that context automatically, matching Django's real behavior — track this as a known follow-up, don't build a placeholder mechanism for it now.

## Filters — the small v1 set, exact behavior

| Filter | Django semantics to match | Notes |
|---|---|---|
| `date` | `{{ value\|date:"Y-m-d" }}` — format a `chrono::DateTime`/`NaiveDate` using Django's format-string mini-language (not `strftime`'s) | Only needs to support the format specifiers Django actually documents commonly used ones for v1 (`Y`, `m`, `d`, `H`, `i`, `s` at minimum) — not the full Django format-string table, note which subset is covered in the filter's own doc comment. |
| `floatformat` | `{{ value\|floatformat:2 }}` — round a float to N decimal places, or Django's default (1 decimal, trailing zeros trimmed) if no argument given | |
| `pluralize` | `{{ count }} item{{ count\|pluralize }}` — empty string if count == 1, `"s"` otherwise; optional custom suffix argument `pluralize:"es"` | |
| `default` | `{{ value\|default:"nothing here" }}` — the fallback if `value` is falsy/undefined | MiniJinja may already have an equivalent built-in filter under a different name — check before reimplementing; if MiniJinja's own `default` filter already matches Django's semantics closely enough, just document that it's available rather than re-registering a duplicate. |
| `truncatewords` | `{{ value\|truncatewords:30 }}` — truncate to N words, appending `"…"` if truncated | |

## What this unblocks

`djangors-forms`' `as_div`/`as_table` rendering (Phase 3, next after this) and the eventual admin (Phase 5) both render through this engine — get the loader precedence and auto-escaping right now, since both of those depend on template overriding actually working correctly.
