# 5.8 part 8 — Per-site branding: `site_header` / `site_title`

**Status:** design, not yet dispatched. Follows 5.8.7 (base layout + dark mode, commit `cdd64bf`),
which deliberately deferred branding to ship a clean, non-configurable default first. See
`docs/design/phase-5-roadmap.md`. Scope for this slice is intentionally narrow: **only
`site_header` (an on-page heading) and `site_title` (the `<title>` tag) — not logo, not per-site
color overrides**, which are separate, larger pieces of work (an upload/URL mechanism for a logo;
a way to inject per-site CSS custom-property overrides for colors) tracked as their own later
ledger items, not built here.

## Why this needs more than a template edit

`AdminSite::urls()` (`crates/djangors-admin/src/lib.rs`) builds a `Vec<Arc<dyn ModelAdmin>>`
snapshot of the registry and clones a separate copy into each of the 11 route closures (this is
the same pattern noted back in 5.1: "Registry snapshot captured in handler closures because
`Router::mount` never carries sub-router state"). Handlers never see the `AdminSite` instance
itself, only the registry snapshot passed as a plain parameter. `ADMIN_TEMPLATES` is also a single
process-wide `LazyLock<TemplateEngine>` shared by every `AdminSite` instance that exists in the
process (the test suite alone constructs dozens of independent `AdminSite::new()` instances) — so
minijinja's `Environment::add_global` (which would make a value available to every render from
that engine, with no per-call override) is the wrong tool here: it would leak one site's branding
into every other `AdminSite`'s pages. **Branding has to be threaded through the same
per-closure-snapshot mechanism `admins` already uses, into every context struct that gets
rendered**, not set once globally.

## New `SiteBranding` struct and `AdminSite` fields/builders (zero breaking changes)

```rust
#[derive(Clone)]
pub struct SiteBranding {
    pub site_header: String,
    pub site_title: String,
}

impl Default for SiteBranding {
    fn default() -> Self {
        Self {
            site_header: "Djangors Administration".to_string(),
            site_title: "Djangors site admin".to_string(),
        }
    }
}
```

Add a `branding: SiteBranding` field to `AdminSite` (alongside the existing `registry:
Mutex<Vec<Arc<dyn ModelAdmin>>>`). `AdminSite::new()`'s body changes to also initialize `branding:
SiteBranding::default()` — **its signature does not change**, so all 22 existing
`AdminSite::new()` call sites (across `djangors-admin`'s own tests and both example apps) keep
compiling and behaving identically, with the new default branding strings.

Add two builder methods, consuming `self` and returning `Self` (so they chain naturally right
after construction, before any `.register()`/`.register_with()` calls, which take `&self` and are
unaffected):

```rust
impl AdminSite {
    pub fn with_site_header(mut self, header: impl Into<String>) -> Self {
        self.branding.site_header = header.into();
        self
    }
    pub fn with_site_title(mut self, title: impl Into<String>) -> Self {
        self.branding.site_title = title.into();
        self
    }
}
```

Confirmed via grep that no existing code references `"Djangors Admin"` (the current hardcoded
`base.html` title default) or `site_header`/`site_title` anywhere — nothing to reconcile with an
existing convention.

## Threading `branding` through `urls()` into every template-rendering handler

Mirror the existing `admins`-snapshot pattern exactly: in `urls()`, add `let branding =
self.branding.clone();` once, then one `let <handler>_branding = branding.clone();` binding per
closure that needs it (same style as `let index_admins = snapshot.clone();` etc. immediately
above), and pass `<handler>_branding.clone()` as an additional argument into the handler call
inside each `move` closure.

**Only handlers that actually render a template need this** — `admin_delete_post` and
`admin_export_csv` never build a context struct (bare redirect / CSV bytes respectively), leave
them completely untouched. The handlers that DO need a new `branding: SiteBranding` parameter:

- `admin_index` (takes `registry: Vec<&'static ModelMeta>`, not `admins` — note its parameter type
  differs from the others, don't assume it matches)
- `admin_changelist`
- `admin_add_get`, `admin_add_post` (both call `render_form` — see below)
- `admin_change_get`, `admin_change_post` (both call `render_form`)
- `admin_delete_get`
- `admin_bulk_delete_post` (only its confirm-step branch renders a template; its delete-step branch
  is a bare redirect — but the function signature still needs the parameter since the router calls
  it uniformly regardless of which branch a given request takes)
- `admin_save_changelist_post` (same reasoning — only its error branch renders a template)

## `render_form`'s signature change

`render_form(meta, field_names, submitted_values, errors, is_add) -> Result<Response,
DjangorsError>` gains one more parameter: `branding: &SiteBranding` (a borrow is fine here since
`render_form` doesn't need to own it — it's only read to populate two `String` fields in the
context it builds). All 4 call sites (`admin_add_get`, `admin_add_post`'s error arm,
`admin_change_get`, `admin_change_post`'s error arm) pass `&branding` through.

## Context struct changes: add `site_header: String, site_title: String` to all 6

Every one of the 6 existing top-level context structs gets the same two new fields, populated from
the handler's `branding` parameter at the `djangors_template::render(...)` call site:

- `IndexContext` (`admin_index`)
- `ChangelistTemplateContext` (`admin_changelist`)
- `DeleteConfirmContext` (`admin_delete_get`)
- `BulkDeleteConfirmContext` (`admin_bulk_delete_post`'s confirm branch)
- `SaveChangelistErrorContext` (`admin_save_changelist_post`'s error branch)
- `RenderFormContext` (`render_form`, shared by all 4 add/change handlers)

This is a mechanical, repetitive addition — same two fields, same names, six times. Read each
struct's current field list directly before editing (they're at lines ~643, ~1108, ~1358, ~2013,
~2019, ~2206 as of commit `cdd64bf` — confirm against the real file, line numbers shift) and add
`site_header: String` + `site_title: String` alongside the existing fields, populated as
`branding.site_header.clone()` / `branding.site_title.clone()` (or moved, if the struct is only
built once and branding isn't reused after — check each call site rather than assuming; do not
introduce an unnecessary `.clone()` where a move works, but also don't fight the borrow checker
over two small `String`s — clone if it's simpler and there's no measurable cost).

## `base.html` changes

Two small, targeted edits to `crates/djangors-admin/templates/admin/base.html`:

1. `<title>{% block title %}Djangors Admin{% endblock %}</title>` becomes `<title>{% block title
   %}{{ site_title }}{% endblock %}</title>` — the block's *default* content becomes the dynamic
   `site_title` value instead of a hardcoded string; the (currently unused by every page) override
   mechanism stays available for future per-page titles.
2. Add a heading near the top of `<body>`, before `{% block content %}`: `<h1>{{ site_header
   }}</h1>`. Keep it simple — a bare `<h1>`, no extra wrapper `<div>`/nav structure; this is a v1,
   not a full admin chrome redesign. Optionally style it minimally in the existing `<style>` block
   (e.g. `h1 { font-size: 1.25rem; margin: 0 0 1rem; }`) to avoid an oversized default browser
   `<h1>` clashing with the rest of the compact layout — a small CSS addition, not a redesign.

## What NOT to touch

- `admin_delete_post`, `admin_export_csv` — no template rendering, no branding needed.
- Any existing test's fixtures or assertions.
- Logo or per-site color overrides — explicitly out of scope, separate future items.
- `AdminSite::new()`'s signature, `register`/`register_with`'s signatures — unchanged.
- Any of the 6 templates' existing `{% block content %}` bodies — untouched, this slice only adds
  two new top-of-page elements in `base.html` itself and two new context fields everywhere else.

## Required tests

Every existing `djangors-admin` test (all 11 — see 5.8.7's design doc for the full list) must pass
with **zero modification to their own assertions**. Confirmed via grep before writing this doc:
no test references `"Djangors Admin"`, `site_header`, or `site_title` today, so adding these new
elements to every page cannot conflict with any existing substring assertion — the same "no
existing test does an exact-body comparison" property 5.8.7 relied on holds here too.
