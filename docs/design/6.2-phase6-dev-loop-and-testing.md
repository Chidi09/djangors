## Two real architectural constraints found during scoping — read before writing code

**1. `dj new-app` cannot generate a new *crate* the way PLAN.md's literal text implies, because
6.1 established that `dj new` generates a single standalone crate, not a multi-crate workspace.**
Converting an existing single-crate project into a workspace on the fly (rewriting its `Cargo.toml`
from a `[package]` manifest into a `[workspace]` manifest while preserving the existing `[[bin]]`
target) is real, risky surgery this slice should not attempt. **Deliberate v1 scope decision:**
`dj new-app <name>` generates an app as a **Rust module inside the current project's `src/`
directory** — `src/<name>/mod.rs`, `src/<name>/models.rs`, `src/<name>/views.rs`,
`src/<name>/admin.rs` — matching how a Django app is actually just a subpackage of the project
(not a separately-distributed package, in the common case), not literally "a crate." Print a clear
reminder of the two manual wiring steps this can't safely automate: add `mod <name>;` to the
project's existing `src/main.rs` (or a lib.rs if one exists — check), and mount `<name>`'s routes
into the existing router. Do not attempt to auto-edit `main.rs`/`urls.rs` to wire this in
automatically in v1 — a text-based edit into a hand-written, arbitrary main.rs is exactly the kind
of fragile blind edit that's caused real damage on this project before (see the git-checkout
data-loss incident referenced in `docs/design/phase-5-roadmap.md`'s ledger, a different failure
mode but the same underlying lesson: don't have a tool blindly mutate a file it doesn't fully
control the shape of). Detect "am I inside a project `dj new` could have generated" by checking for
a `Cargo.toml` + `djangors.toml` in the current directory; error clearly if neither is found rather
than generating orphaned files.

**2. `dj check` cannot inspect a project's registered models/admin config, because that data only
exists at runtime inside *that project's own compiled binary* — the global `dj` CLI tool has no
way to load or introspect it.** Django's own `manage.py check` works because it's generated
per-project and imports the project's own code directly; this `dj` binary is a single
framework-level tool, structurally separate from any project it operates on. **Deliberate v1 scope
decision:** `dj check` only performs checks the external CLI can actually do — parsing
`djangors.toml`/environment for settings-consistency issues (reusing
`DjangorsSettings::load()`/`.validate()` directly, don't reimplement that logic) and basic
project-structure sanity (`Cargo.toml` exists and has a `[[bin]]` table, `src/main.rs` exists).
**Ledger, do not attempt:** model-level checks (missing migrations, FK issues, admin
misconfiguration) need a fundamentally different mechanism — likely a check registered as
something that runs *inside* the target project's own binary (a future management-command-style
hook), not the external `dj` tool. Note this explicitly in the design doc's own summary and in the
final commit message so a future session doesn't assume `dj check` already does this.

## Part A — `dj new-app <name>`

`crates/djangors-cli/src/cli.rs`'s `Commands::NewApp { name: String }` already exists (parsing is
done). Replace `commands::new_app()`'s stub with a real implementation, `Result`-returning like
6.1's `new()` (update `main.rs`'s call site the same way 6.1's `New` arm was updated — mirror it
exactly).

Behavior:
1. Verify the current directory looks like a djangors project (`Cargo.toml` and `djangors.toml`
   both present) — clear error if not.
2. Validate `name` the same way `validate_project_name` does (reuse that function directly — it's
   already generic enough for a module name, or extract a shared identifier-validation helper if
   `new_app` needs slightly different rules, e.g. Rust module names can't contain hyphens at all
   unlike Cargo package names, which do allow them — check this and adjust: a module name must be
   a valid Rust identifier, stricter than the crate-name check 6.1 wrote, don't just reuse it
   unmodified if the hyphen case actually differs).
3. Error if `src/<name>/` already exists (same non-destructive-by-default discipline as 6.1's
   `new()`).
4. Generate:
   - `src/<name>/mod.rs`: `pub mod admin;\npub mod models;\npub mod views;\n`
   - `src/<name>/models.rs`: a short comment-only stub with a real, working commented-out example
     `#[derive(Model)]` struct (copy the shape from `examples/school/src/models.rs`'s simplest
     model, e.g. `Student`, adapted — as a comment block showing real, correct syntax, not
     placeholder pseudocode) so a new user has a working reference immediately, not just an empty
     file.
   - `src/<name>/views.rs`: one real, working example handler (`pub async fn index(_req: Request,
     _params: PathParams) -> Result<Response, DjangorsError> { ... }` returning a simple
     placeholder page), so `cargo build` succeeds immediately after generation with zero required
     edits — this is important, verify it by actually building after generating in the required
     test below.
   - `src/<name>/admin.rs`: a short comment showing the `AdminSite::register::<Model>()` pattern,
     commented out (nothing to register yet since `models.rs`'s example model is commented out
     too — keep both consistent, either both real/uncommented or both commented, don't generate a
     file that references an admin registration for a model that doesn't actually exist yet).
5. Print next-steps reminder: `[dj new-app] created 'src/{name}/'`, then explicit manual steps:
   `[dj new-app] next: add 'mod {name};' to src/main.rs, and mount its routes`.

**Required test**: generate an app into a scratch copy of a 6.1-generated project (call `new()`
first to get a real project, then `new_app()` inside it), assert the expected files exist, and —
the real proof, mirroring 6.1's own `#[ignore]`d end-to-end test — assert `cargo build` still
succeeds on the whole project afterward even with the new (unwired, since main.rs isn't
auto-edited) module present but not yet declared via `mod` in main.rs... actually think this
through: if `src/<name>/mod.rs` exists but `main.rs` never adds `mod <name>;`, Rust simply won't
compile that module at all (dead code sitting in the tree, harmless, zero effect on the build) —
so confirm this test just proves the generated *files themselves* are syntactically valid Rust by
temporarily adding `mod {name};` to a scratch copy of main.rs for the purposes of the test only
(not something the real command does), building, and asserting success — this is what actually
proves the generated stub code compiles, not just that files got written.

## Part B — `dj run`

`crates/djangors-cli/src/cli.rs`'s `Commands::Run { port: u16 }` already exists. Replace the
`commands::run()` stub with a real hand-rolled watch/rebuild/restart loop — **no new dependency**
(no `notify` crate; this project has a consistent precedent of hand-rolling something this
achievable rather than adding a dependency for it, e.g. 5.6.6's hand-rolled CSV escaping). Must be
run from inside a project directory (same detection as `new-app`: `Cargo.toml` +
`djangors.toml` present, clear error otherwise).

Loop:
1. Run `cargo build` once up front; if it fails, print the compiler output and **keep watching**
   rather than exiting (a broken build on save shouldn't kill the dev server loop — the whole
   point is you fix the error and it picks back up).
2. If the build succeeded, spawn the built binary (`target/debug/<crate-name>` — the crate name is
   knowable by parsing the project's own `Cargo.toml` `[package] name` field, don't assume it
   matches the directory name since a user could rename either independently) with
   `DJANGORS_PORT=<port>` set from the `--port` flag (default `8000`, already parsed).
3. Poll `src/**/*.rs` and `Cargo.toml` file mtimes every ~500ms (walk the `src/` directory
   recursively with `std::fs::read_dir`, no new dependency needed for a simple recursive walk;
   track the max mtime seen).
4. On any mtime increase: kill the running child process, rebuild, and if the rebuild succeeds,
   respawn; if it fails, print the error and keep polling (don't respawn the old stale binary,
   but don't crash the watch loop either — go back to step 3 with no child running until a
   subsequent successful build).
5. On Ctrl-C (`SIGINT`) — verify what signal-handling mechanism, if any, already exists elsewhere
   in this codebase (grep for `ctrlc`/`signal` crates in any `Cargo.toml` before adding a new
   dependency for this specific need) — kill the child cleanly before exiting. If nothing suitable
   already exists as a dependency anywhere in the workspace and handling this properly would
   require a new dependency, it's acceptable to skip graceful SIGINT handling in this v1 (an
   orphaned child process on Ctrl-C is a real but minor rough edge, not a correctness bug) — note
   this explicitly as a known v1 gap in the code comment and the final commit message rather than
   silently shipping it un-flagged.

Print clear status lines matching the rest of this file's `[dj <subcommand>] ...` convention:
`[dj run] building...`, `[dj run] build failed, watching for changes...`, `[dj run] serving on
http://127.0.0.1:{port}`, `[dj run] change detected, rebuilding...`.

**Required test**: this is process/filesystem-heavy and slow like 6.1's own end-to-end test — mark
it `#[ignore]` the same way. Generate a real project (via `new()`), start the watch loop as a
background thread/process pointed at it, poll-confirm it serves once (same poll-retry-not-sleep
discipline as 6.1's test), then touch `src/views.rs` with a change that alters the response body,
wait for a rebuild (poll, don't sleep a fixed guess — watch for the new response body to appear,
with a generous timeout since a real `cargo build` involved), and assert the *new* content is now
served — this is the real proof the watch/rebuild/restart cycle actually works end-to-end, not
just that the loop's code compiles.

## Part C — `dj check`

Add `Commands::Check` to `cli.rs` (new — doesn't exist yet, add it following the exact same
`#[command(name = "...")]` pattern every other variant already uses) and wire it in `main.rs`.
Implementation, per the scope constraint above: load settings via `DjangorsSettings::load()`,
run `.validate()` (already exists — reuse it, don't reimplement), and print any warnings/errors it
returns. Additionally check: `Cargo.toml` exists in the current directory and contains a `[[bin]]`
table (parse with the `toml` crate, already a dependency of `djangors-core` — check whether
`djangors-cli` already depends on `toml` or needs it added), `src/main.rs` exists. Print `[dj
check] N issue(s) found:` followed by each, or `[dj check] no issues found` on a clean pass; exit
with a non-zero status if any issues were found (mirroring how a CI-friendly check command should
behave — this is the one place in this file where a non-error condition should still set the exit
code, make sure that distinction is clear in the implementation, not conflated with the
`eprintln!`+`exit(1)` "something went wrong internally" pattern used elsewhere).

**Required tests**: run `check()` against a real project generated via `new()` (should report zero
issues), and against a deliberately broken settings case (e.g. a `djangors.toml` with
`debug = false` and no `secret_key` — `DjangorsSettings::validate()` already rejects this, confirm
`dj check` surfaces that exact validation error).

## Part D — the `djangors-test` crate

Currently a fully empty placeholder (`crates/djangors-test/src/lib.rs` is doc-comment-only, no
real code — confirmed by reading it directly, don't assume otherwise). This is the first slice
that builds it for real.

**Important constraint to design around, not ignore:** true per-test transactional DB rollback
(begin a transaction, run the test against it, always roll back regardless of outcome) is **not
achievable today** without a larger change to `djangors-orm` — every `QuerySet` method
(`crates/djangors-orm/src/queryset.rs`) takes `db: &djangors_db::Database` and calls
`db.pool()` directly (a `&PgPool`), not an injectable executor/transaction type. Building a real
per-test-rollback fixture would require threading a generic executor type through the entire ORM
query-building surface — a legitimate, larger future project, explicitly **out of scope here**;
ledger it in the final commit/roadmap update as blocked on that ORM change, don't attempt a partial
or fake version of it.

**What real, in-scope value this slice can still deliver** (both genuinely DRY up patterns
hand-duplicated in nearly every existing test across `djangors-admin`/`djangors-auth`/
`djangors-cli` — confirmed by grep before writing this doc that the same
`Request::new(Method::POST, Uri::from_static(...), headers, Bytes::from(...))` /
`DROP TABLE IF EXISTS ... CREATE TABLE ...` boilerplate appears dozens of times verbatim):

1. **`TestClient`**: wraps a `djangors_core::Router`, calling its existing `.handle(req).await`
   in-process (no real socket — the same mechanism every `djangors-admin` test already uses
   directly). Ergonomic builder-style methods:
   - `TestClient::new(router: Router) -> Self`
   - `.get(path: &str) -> RequestBuilder` / `.post_form(path: &str, pairs: &[(&str, &str)]) ->
     RequestBuilder` (building the `application/x-www-form-urlencoded` body and
     `Content-Type` header automatically — this exact hand-assembly appears in essentially every
     admin POST test, confirm the exact header/body construction by reading a couple of real
     examples in `crates/djangors-admin/src/lib.rs`'s test module before writing this)
   - `RequestBuilder::with_session(session: djangors_sessions::Session) -> Self` (wraps the
     `Extensions::new(); ext.insert(session); req.with_extensions(ext)` pattern seen everywhere)
   - `RequestBuilder::with_state<T>(state: T) -> Self` (wraps `.with_state(AppState::new().insert(state))`)
   - `RequestBuilder::send(self) -> TestResponse` (async, calls the router)
   - `TestResponse` wraps the real `Response` plus assertion helpers: `.assert_status(code:
     StatusCode)` (panics with a clear message including the actual status and a body snippet on
     mismatch, not just a bare `assert_eq!`), `.assert_contains(needle: &str)`, `.body_str(&self)
     -> String`, `.status(&self) -> StatusCode`.
2. **`TestDatabase`** (NOT transactional rollback — a lighter-weight, honest helper): connects
   using the same `DATABASE_URL`-env convention every existing test already uses, and provides
   `.create_table(sql: &str)` / `.drop_table(name: &str)` thin wrappers around the exact
   `DROP TABLE IF EXISTS ...` then `CREATE TABLE ...` pattern already duplicated everywhere,
   **plus** a `.reset(tables: &[&str])` convenience that drops-then-the-caller-recreates in one
   call for the common "clean slate per test" case. This does not need to be clever — its entire
   value is eliminating literal copy-pasted SQL boilerplate, not adding new capability beyond what
   every test already does by hand.
3. **Real tests for `djangors-test` itself**, in `djangors-test`'s own crate, that actually exercise
   `TestClient` against a small real router (reuse or mirror `djangors-admin`'s own test model
   setup — check whether depending on `djangors-admin` from `djangors-test`'s `Cargo.toml` for this
   is reasonable, or whether a minimal standalone router with one or two trivial handlers defined
   inline in the test is cleaner and avoids a possibly-unwanted crate dependency; prefer the
   inline/standalone approach unless there's a strong reason not to, since `djangors-test` being a
   testing *utility* crate probably shouldn't depend on `djangors-admin`, an unrelated feature
   crate) — proving `TestClient` genuinely replaces the hand-rolled pattern for both a GET and a
   POST-with-form-body-and-session case, and that `.assert_status`/`.assert_contains` correctly
   pass on matching content and correctly panic (test this via `#[should_panic]`) on mismatched
   content.
