# Design 4.8 — CSRF middleware (v1 scope)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 4's CSRF bullet first. This is part 2
of Phase 4, following [[4.7-sessions]] (part 1, already built and committed).

## v1 scope, and the constraint that shapes it

`PLAN.md` asks for token generation, template tag, form + header validation, an exempt marker,
and "on by default." **v1 ships token generation, request-extension exposure for templates, and
header-based validation only.** Form-body-field validation (`csrfmiddlewaretoken` inside a
POST body) is explicitly deferred — here is why, stated up front so it isn't rediscovered
mid-implementation:

`SessionLayer` (already built) is a hyper-level `tower::Layer` wrapping the whole router,
operating on `hyper::Request<Incoming>` — it never touches the body, only headers, so it has no
conflict with `Router::dispatch`, which buffers the body itself afterward. CSRF's form-field
validation would need the *parsed body*, but at the point a `tower::Layer` wrapping the router
runs, the body is still an unbuffered `Incoming` stream — reading it means consuming it, and
`Router::dispatch` needs to read it too (once, into `djangors_core::Request`). Two independent
buffer reads of the same stream don't work; making them share one read means either changing
`Router::dispatch`'s signature to accept a pre-buffered body, or moving CSRF enforcement to run
*after* `djangors_core::Request` already exists (inside `Router::handle`, not as an outer
`tower::Layer`) — both are real design decisions, not "obviously right" ones, and rushing either
now to hit 100% of the PLAN.md bullet risks getting the body-sharing story wrong in a
security-critical path. **Header-based validation (`X-CSRFToken`) needs none of this** — headers
are available on `hyper::Request<Incoming>` without touching the body at all, so v1 ships that
correctly and completely, and form-field validation becomes a follow-up once the body-sharing
question above is deliberately answered (likely: CSRF enforcement moves inside `Router::handle`
once sessions/CSRF are both established enough to justify that core change).

This means v1's real-world coverage is: JSON/AJAX-style POST/PUT/PATCH/DELETE requests that set
`X-CSRFToken` are protected. Classic `<form method="post">` submissions without JS are **not**
protected by v1 — document this loudly in the crate's top-level doc comment, don't let it be a
silent gap.

## Scheme: double-submit cookie, not Django's masked-secret scheme

Django's actual CSRF implementation XORs the real secret with a per-request random mask before
embedding it in the page, specifically to defend against BREACH-style compression-oracle attacks
that could otherwise leak the token from an HTTPS response body over many requests. That masking
scheme is real complexity worth doing right, not approximating. **v1 uses the simpler, still
legitimate, widely-used double-submit-cookie pattern instead** (same category of defense as
Rails' or Express's CSRF middleware): a random token is set as a cookie; the same value must be
echoed back via `X-CSRFToken` on unsafe requests; an attacker's cross-origin request can't read
or set that cookie (same-origin cookie policy) so can't produce a matching header value.
BREACH-hardening via masking is a documented, explicit follow-up, not silently dropped — note it
in the crate doc comment as future work.

## Crate placement: `djangors-core::middleware`, not a new crate

Unlike sessions (which got its own crate because it needed `hmac`/`sha2`/`base64` and a
non-trivial `Session` type), CSRF v1 as scoped here needs only `rand` (already how
`djangors-sessions::generate_session_key` generates its random value) and header/cookie parsing
djangors-core already has patterns for. There is no pre-reserved `djangors-csrf` placeholder
crate on crates.io (check `ls crates/` — it isn't there), and minting a brand new crate name is
a bigger decision than this task should make unilaterally (this project has a whole naming saga
behind it). **Add `CsrfLayer`/`CsrfToken`/`constant_time_eq` to
`crates/djangors-core/src/middleware.rs`**, alongside the existing `SecurityHeadersLayer` and
`RequestIdLayer` it already defines — same file, same module, matching that established
pattern. This requires adding `rand` as a new direct dependency of `djangors-core` itself (check
`Cargo.lock` for the already-resolved version — `djangors-sessions` already resolved one, reuse
it, don't introduce a second).

```rust
/// Cheaply `Clone`, inserted into the request's extensions by `CsrfLayer`
/// (via the same `Request::ext::<T>()` mechanism `Session` uses) so
/// handlers/templates can read the current request's token value.
#[derive(Clone)]
pub struct CsrfToken(pub String);

pub struct CsrfLayer {
    cookie_name: String, // default "csrftoken"
    header_name: String, // default "x-csrftoken" (compare lowercased)
}

impl CsrfLayer {
    pub fn new() -> Self { ... }
}

// Layer<S> / Service<hyper::Request<Incoming>> impl, same shape as
// SessionLayer/SessionService in crates/djangors-sessions/src/lib.rs —
// read that file first and mirror its structure (Layer::layer,
// poll_ready delegating to inner, call() cloning inner + doing the
// real work in a boxed async block).
```

`CsrfLayer::call` behavior:

1. Read the `csrftoken` cookie from the incoming request (reuse the same hand-written
   `Cookie`-header-parsing approach `djangors-sessions` uses — do not add a new dependency for
   this, and do not duplicate-implement it differently; if it's worth sharing, that's a future
   refactor, not this task).
2. If present and non-empty, that's this request's token value. If absent, generate a fresh
   random token (32 bytes from `rand::RngCore`, hex or base64-encoded — match the exact style
   `djangors-sessions::generate_session_key` already uses for consistency) and remember to set
   it as a cookie on the response.
3. Insert `CsrfToken(value.clone())` into the request's extensions before calling the inner
   service.
4. **Before** calling the inner service, if the request method is one of `POST`, `PUT`, `PATCH`,
   `DELETE` (safe methods `GET`/`HEAD`/`OPTIONS`/`TRACE` are never checked, matching Django's own
   safe-method exemption), read the `X-CSRFToken` request header and compare it against the
   cookie-derived token value from step 1/2 using a constant-time comparison. Implement the
   comparison exactly like this (do not deviate — this is deliberately simple to keep it
   auditable, not because performance matters here):
   ```rust
   fn constant_time_eq(a: &[u8], b: &[u8]) -> bool {
       if a.len() != b.len() {
           return false;
       }
       a.iter().zip(b.iter()).fold(0u8, |acc, (x, y)| acc | (x ^ y)) == 0
   }
   ```
   If the header is missing, or doesn't match, **do not call the inner service** — return a 403
   response directly (build a `hyper::Response` by hand, status 403, short plain-text body like
   `"403 Forbidden: CSRF token missing or invalid"` — there's no `djangors_core::Response`
   available at this layer since we're below `Router::dispatch`; that's fine, `SessionLayer`
   doesn't have this problem because it never rejects, only annotates, so this is new — just
   build the `hyper::Response<Full<Bytes>>` directly, matching how `Router::dispatch` itself
   builds `hyper::Response`s).
5. After the inner service responds (only reached if step 4 passed or the method was safe), if a
   *new* token was generated in step 2 (i.e. no cookie existed), set it via `Set-Cookie` on the
   response: `csrftoken=<value>; Path=/; SameSite=Lax; Max-Age=<one year in seconds>` —
   **deliberately not `HttpOnly`** (unlike the session cookie): the token must be readable by
   client-side JS to populate the `X-CSRFToken` header on AJAX requests, matching Django's own
   `CSRF_COOKIE_HTTPONLY = False` default. Explain this exact reasoning in a doc comment so it
   doesn't look like an oversight next to the session cookie's `HttpOnly` — it's intentional and
   different for a reason.

## What this task does NOT include

- Form-body-field (`csrfmiddlewaretoken`) validation — see the constraint section above.
- Django's masked-secret/BREACH-hardened scheme — see the scheme section above.
- Any `#[csrf_exempt]`-style marker/attribute for opting individual views out — with only
  header-based checking in v1 and no automatic wiring into `Router` yet, there's nothing to
  exempt a view *from* yet; add this once CSRF is actually mandatory-by-default somewhere.
- Wiring into any example app, and no `{% csrf_token %}`-style template tag/filter in
  `djangors-template` yet (the design doc for that integration should reference a real,
  committed `CsrfToken` type as ground truth, same pattern as this doc referencing the real,
  committed `Session`/`Request::ext` — so it comes after this task, not inside it).

## Required tests

- Safe method (`GET`) with no cookie and no header still succeeds (200), and the response sets a
  fresh `csrftoken` cookie.
- Unsafe method (`POST`) with no cookie and no header is rejected (403), and the inner service
  is never actually invoked (assert this with a counter the handler increments, not just the
  response status — proves rejection happens *before* dispatch, not that the handler itself
  returned 403).
- Unsafe method with a cookie present but a missing/mismatched `X-CSRFToken` header is rejected
  (403) — construct this by actually setting a *different* valid-looking token in the header,
  not an empty one, so the test can't accidentally pass because of an empty-string special case.
- Unsafe method with a cookie and a matching `X-CSRFToken` header succeeds (200) and reaches the
  handler.
- End-to-end through a real `Router` (same pattern as `djangors-sessions`'s
  `test_end_to_end_router_session`): issue a `GET` first to obtain the `Set-Cookie` value, then
  issue a `POST` carrying both that cookie and the matching header, confirm success; issue
  another `POST` carrying the cookie but a wrong header value, confirm 403.
- `constant_time_eq` unit tests: equal slices → true, different lengths → false, same length but
  differing content → false, empty slices → true.
