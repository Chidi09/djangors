# Design 4.12 — djangors-auth: login rate limiting + audit signals (Phase 4 part 4c)

**Status:** draft, pre-implementation. Builds on [[4.10-auth-user-model]] and
[[4.11-auth-backend-login]] (both already built and committed). This is **part 4c**, scoped to
just the two remaining `PLAN.md` bullets that don't need new ORM schema: rate limiting and audit
signals. **Groups, model-level permissions, and the password-reset email flow are explicitly
deferred to a separate future part 4d** — permissions need a real `Group`/`Permission` schema
(new models, join tables) and password-reset needs a minimal email-sending story, both genuine
design decisions of their own, not something to fold into this task.

## Part 1: Audit signals

`djangors-core::signals::Signal<T>` already exists and is exactly the right tool (read
`crates/djangors-core/src/signals.rs` — it's generic, already used for `REQUEST_STARTED`/
`REQUEST_FINISHED`, panic-isolated per subscriber). Add three new signals **in djangors-auth**
(no djangors-core changes needed — `Signal<T>` is already public and generic):

```rust
pub struct LoginSucceeded { pub user_id: i64, pub username: String }
pub struct LoginFailed { pub username: String }
pub struct LoggedOut { pub user_id: Option<i64> }

pub static LOGIN_SUCCEEDED: djangors_core::signals::Signal<LoginSucceeded> = ...;
pub static LOGIN_FAILED: djangors_core::signals::Signal<LoginFailed> = ...;
pub static LOGGED_OUT: djangors_core::signals::Signal<LoggedOut> = ...;
```

Check `REQUEST_STARTED`'s exact `static` declaration (likely a `LazyLock`-wrapped `Signal`, given
`signals.rs` imports `std::sync::LazyLock`) and copy that pattern precisely.

Fire `LOGIN_SUCCEEDED`/`LOGIN_FAILED` from **`ModelBackend::authenticate`** (in
`crates/djangors-auth/src/lib.rs`, already built) at the point it decides the outcome — not from
`login()`, which only handles session mechanics and is called *after* a caller has already
decided to trust an `authenticate()` result, so it has no independent "did auth succeed" signal
of its own to fire correctly. Fire `LOGGED_OUT` from `logout()`. Do not put `user_id: Some(x)` in
`LoginFailed` — a failed attempt (wrong password, nonexistent username, or rate-limited) never
has a real user to attribute logging to; use `username` (the attempted, unverified string) only,
and note in a doc comment that this string is attacker-controlled input and must never be used
unescaped in a context where that matters (log lines are fine; do not, for instance, later build
a feature that renders it as HTML).

## Part 2: Login rate limiting

**Not an HTTP `tower::Layer`** — [[4.8-csrf]] already hit and documented the reason a layer
wrapping the router can't cheaply see which username is being attempted (it would need the
parsed body, which conflicts with `Router::dispatch`'s own body buffering). Rate limiting login
attempts doesn't have this problem at all: `AuthBackend::authenticate` already receives
`username: &str` directly as a parameter. **Scope this as a decorator around `AuthBackend`**
instead:

```rust
pub struct RateLimitedBackend<B: AuthBackend> {
    inner: B,
    limiter: std::sync::Mutex<HashMap<String, Vec<std::time::Instant>>>, // keyed by username
    max_attempts: u32,
    window: std::time::Duration,
}

impl<B: AuthBackend> RateLimitedBackend<B> {
    pub fn new(inner: B, max_attempts: u32, window: std::time::Duration) -> Self { ... }
}

#[async_trait::async_trait]
impl<B: AuthBackend + Send + Sync> AuthBackend for RateLimitedBackend<B> {
    type User = B::User;

    async fn authenticate(
        &self,
        db: &djangors_db::Database,
        username: &str,
        password: &str,
    ) -> Result<Option<Self::User>, AuthError> {
        // 1. Lock the limiter, prune entries for `username` older than `window`
        //    from now, count what's left.
        // 2. If count >= max_attempts: fire LOGIN_FAILED (still - it IS a
        //    failed attempt from the caller's perspective) and return
        //    Err(AuthError::RateLimited) WITHOUT calling inner.authenticate
        //    at all - this is the actual throttling; do not call through to
        //    the real (expensive, Argon2-hashing) backend once a caller is
        //    already over the limit, that's the whole point of the limiter
        //    existing (protecting the expensive path from being hammered).
        // 3. Otherwise: record this attempt's timestamp, call
        //    inner.authenticate(...), and return its result unchanged (the
        //    inner ModelBackend already fires LOGIN_SUCCEEDED/LOGIN_FAILED
        //    itself - RateLimitedBackend does not fire them a second time
        //    for the pass-through case, only for its own rejection case in
        //    step 2).
    }
}
```

Explicitly a **single-process, in-memory** limiter — matches this project's established v1
pattern of picking the simplest correct thing and documenting what's deferred (same shape as
sessions shipping signed-cookie only, not database/cache backends yet). A multi-process/
distributed limiter (Redis-backed, matching the `djangors-cache` crate that doesn't exist yet)
is real future work, not this task. Note this explicitly in the module doc comment.

`AuthError` needs a new `RateLimited` variant (currently `Hashing`/`Database` only, in
`crates/djangors-auth/src/lib.rs`) - add `#[error("too many login attempts, try again later")]
RateLimited`.

**"default-on" from `PLAN.md`** means `RateLimitedBackend` should have a `pub fn
default_login_throttle(inner: B) -> Self` convenience constructor with reasonable baked-in
defaults (e.g. 5 attempts / 15 minutes, Django's own historical default ballpark), not that
`ModelBackend` itself becomes rate-limited unconditionally — a caller opts in by wrapping
`ModelBackend` in `RateLimitedBackend::default_login_throttle(ModelBackend)` instead of using
`ModelBackend` bare. Wiring this default into any example app or scaffold is out of scope here.

## What this task does NOT include

- Groups, model-level permissions, permission guards — part 4d, needs real ORM schema design.
- Password-change/password-reset views and email flow — depends on a minimal email backend that
  doesn't exist yet, separate task.
- Wiring `RateLimitedBackend`/signals into any example app.
- Any change to `djangors-core` — both pieces build entirely on what already exists there
  (`Signal<T>`) or entirely within `djangors-auth`.

## Required tests

- `LOGIN_SUCCEEDED` fires (assert via a connected test callback incrementing an `AtomicUsize`,
  matching the exact pattern `crates/djangors-core/src/router.rs`'s own
  `test_router_signals_fire` test already uses) on a real successful `ModelBackend::authenticate`
  call (real Postgres, reuse the existing test-table pattern from `crates/djangors-auth/src/tests.rs`).
- `LOGIN_FAILED` fires on wrong password, on nonexistent username, and on an inactive user with
  correct password (three separate assertions/scenarios, not just one).
- `LOGGED_OUT` fires on `logout()`.
- `RateLimitedBackend`: `max_attempts` failed attempts for the same username are allowed through
  to the inner backend (each producing a real `LOGIN_FAILED` from the inner backend); the
  `max_attempts + 1`th attempt within the window is rejected with `Err(RateLimited)` **without**
  reaching the inner backend - prove this with a call counter on a fake inner `AuthBackend` test
  double, the same "prove it never got called" pattern already used for CSRF's
  `test_unsafe_method_no_cookie_no_header_rejected`, not just by checking the returned error type.
- A *different* username is unaffected by another username's exhausted rate limit (proves the
  limiter is keyed correctly, not a single global counter).
- After the window elapses, a previously-rate-limited username can attempt again - test this
  without a real `sleep` (flaky/slow); either accept a short real duration (e.g.
  `window = Duration::from_millis(50)` and a real but brief `tokio::time::sleep`) or, if that
  feels fragile, structure `RateLimitedBackend` to accept an injectable clock/time source for
  testability - use your judgement on which is less complexity for a v1 test, but the property
  must be genuinely demonstrated, not assumed.
