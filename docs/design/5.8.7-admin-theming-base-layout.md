# 5.8 part 7 — Real visual theming: a base HTML5 layout + CSS custom properties + dark mode

**Status:** design, not yet dispatched. Follows 5.8.6 (changelist template conversion, commit
`ab1363e`), which completed the *mechanism* — every admin page now renders through minijinja. This
slice is the first that changes what the admin actually **looks like**, not just how its HTML gets
built. See `docs/design/phase-5-roadmap.md`.

## Why this is needed: there is currently no page shell at all

Confirmed by reading `djangors_core::Response::html()` (`crates/djangors-core/src/response.rs`)
directly: it just sets `Content-Type: text/html; charset=utf-8` and writes the given string as the
body — no wrapping, no `<!DOCTYPE html>`, no `<head>`. Every one of the 6 admin templates
(`index.html`, `delete_confirm.html`, `bulk_delete_confirm.html`, `save_changelist_error.html`,
`render_form.html`, `changelist.html`) is a bare fragment of `<div>`/`<table>`/`<form>` markup with
no `<html>`/`<head>`/`<body>` around it at all. Browsers render bare fragments fine (lenient HTML5
parsing), but there is zero styling today — this slice is the first to actually add any.

## Scope: one shared base layout, dark-mode-aware CSS, all 6 pages wrapped in it

1. A new `crates/djangors-admin/templates/admin/base.html` — a real HTML5 document shell (
   `<!DOCTYPE html>`, `<html>`, `<head>` with `<meta charset>` + `<title>` + an embedded `<style>`
   block using CSS custom properties, `<body>`) with a `{% block content %}{% endblock %}` that
   each page template fills.
2. Each of the 6 existing page templates changes from a bare fragment to `{% extends
   "admin/base.html" %}{% block content %}<their existing, byte-identical content>{% endblock %}`
   — **the content inside the block does not change at all**, this is purely wrapping.
3. CSS is a `<style>` block embedded directly in `base.html` (no separate static-file serving
   pipeline exists yet — `djangors-staticfiles` is a separate, not-yet-integrated-with-admin crate;
   don't reach for it here, that's future scope). Uses CSS custom properties for colors, with a
   `@media (prefers-color-scheme: dark)` override — no JS toggle in this v1, just automatic
   OS-preference-based dark mode, matching the roadmap's "clean modern default (CSS custom
   properties, dark mode)" phrasing.
4. **Per-site branding (custom title/logo/colors via settings) is explicitly OUT of scope for this
   slice** — ship a clean, good-looking, non-configurable default first; branding hooks are a
   separate, later piece (already tracked as its own ledger item).

## Why `{% extends %}` "just works" here with zero extra plumbing

Confirmed by reading `crates/djangors-template/src/render.rs`: `render(engine, name, ctx)` is a
thin wrapper around `engine.render(name, ctx)`, itself just `env.get_template(name)?.render(ctx)`.
minijinja resolves `{% extends "admin/base.html" %}` by looking up that name in the *same*
`Environment` the child template was loaded into. Since `ADMIN_TEMPLATES` (`crates/djangors-admin/
src/lib.rs`) is already one shared `LazyLock<TemplateEngine>` with every admin template registered
via a single `from_embedded` call, adding `base.html` as a 7th entry in that same call makes it
resolvable from every child template automatically — no engine changes needed.

## Confirmed: no existing test does an exact-body comparison, only substring checks

Grepped the entire `djangors-admin` test module for `assert_eq!(body` or similar exact-equality
checks on a rendered body — **none exist**. Every admin test asserts `body.contains("...")` for
specific substrings. Since this slice only *wraps* each page's existing content (unchanged) inside
a layout, every existing substring assertion continues to find its target text somewhere in the
now-larger page — **no existing test's assertions need to change**. This is the same
byte-identical-content discipline as every 5.8.x slice, just scoped to "the existing content is
still present verbatim" rather than "the whole response is unchanged" (which was never going to be
true once real styling landed — that's the whole point of this slice).

  --bg: #ffffff;
  --fg: #111827;
  --muted: #6b7280;
  --accent: #2563eb;
  --border: #d1d5db;

    --bg: #0f1115;

  background: var(--bg);

  background: var(--input-bg);

  background: var(--accent);

One design note to preserve from the current output: `changelist.html` already emits a `<div
class="date-hierarchy">` — this CSS targets that existing class, don't rename or restructure it.

## Per-page changes

Each of the 6 templates becomes (content between `{% block content %}` and `{% endblock %}` is
their **current, unmodified** single-line body — do not touch a single character inside it):

```
{% extends "admin/base.html" %}{% block content %}<existing content, unchanged>{% endblock %}
```

Read each file's current exact content before editing it (they're all one continuous line already
except `changelist.html`'s `list_filter_blocks` loop, which has embedded newlines — preserve that
exactly, just wrap the whole thing).

Optionally set a more specific `{% block title %}` per page (e.g. `render_form.html` and
`changelist.html` could set a page-appropriate title) — this is a nice-to-have, not required; if
skipped, every page falls back to `base.html`'s default `Djangors Admin` title via the block's
default content. Keep this simple: either skip per-page titles entirely in this slice, or add one
uniform `{% block title %}Djangors Admin{% endblock %}` per file with no per-page customization —
don't invent a title-computation scheme now, that's out of scope.

## `ADMIN_TEMPLATES`: add the 7th entry

`("admin/base.html", include_str!("../templates/admin/base.html"))`. Order doesn't matter for
`from_embedded` (all templates are registered into the same `Environment` regardless of order), but
add it alongside the other 6 for consistency.

## What NOT to touch

- The content inside any of the 6 pages' `{% block content %}...{% endblock %}` — verbatim from
  today, just wrapped.
- Any Rust code in `crates/djangors-admin/src/lib.rs` — this slice is templates-only, no context
  struct or handler changes anywhere.
- `djangors-staticfiles` — not integrated with the admin in this slice; the stylesheet stays
  embedded inline in `base.html`'s `<style>` block.
- Per-site branding/settings — explicitly deferred, see above.
