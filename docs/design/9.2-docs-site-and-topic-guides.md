# 9.2 — mdBook site scaffold + topic guides

## Scope

9.1 (commit `5b29298`) shipped the 8-part tutorial as plain Markdown under `docs/tutorial/`. This
slice does two related things: (A) wires that content (plus this slice's new content) into a real,
buildable `mdBook` site so PLAN.md's "Docs site (Starlight or mdBook)" bullet has a real
implementation, not just loose files; (B) adds the topic guides PLAN.md names explicitly: **ORM,
templates, forms, auth, admin, testing, deployment, security**.

**Deliberately excluded from this dispatch**: the rustdoc reference (100%-public-API-coverage
enforcement is a separate, CI-tooling-heavy piece), how-tos, the "Djangors for Django developers"
side-by-side guide, doc-code-block CI extraction/compilation, and the `djangors.rs` landing page —
each is its own real deliverable, left for a later 9.x slice.

## Part A — mdBook scaffold

`mdbook` is not currently installed in this environment (confirmed via `which mdbook` — not
found). Install it first (`cargo install mdbook`, or check whether `cargo binstall mdbook` is
faster/available — either is fine, just confirm the binary actually works via `mdbook --version`
before relying on it). Then:

- Create `docs/book.toml` at the repo root of the docs tree (`docs/`), pointing `src` at a new
  `docs/src/` directory (mdBook's standard layout — do NOT try to make `docs/tutorial/` itself the
  `src` dir, since Part B adds sibling topic-guide content that needs its own place in the nav).
- `docs/src/SUMMARY.md` is mdBook's real nav structure — build it to mirror PLAN.md's own
  described IA: a top-level "Tutorial" section listing all 8 existing tutorial parts (move or
  symlink-equivalent — mdBook needs the actual files under `src/`, so either move
  `docs/tutorial/*.md` into `docs/src/tutorial/` and update any relative links, or make `docs/src/`
  the new canonical home and leave a note in `docs/tutorial/`'s old location if anything external
  references it — check `git grep -r "docs/tutorial"` across the repo first, including PLAN.md and
  any README, to see what needs updating if paths move), followed by a "Topic Guides" section for
  Part B's new content.
- Confirm the book actually builds: `mdbook build docs` (or `cd docs && mdbook build`) produces
  real HTML output with no broken internal links. Do not just create the files and assume it
  builds — run the actual build command and paste real output.
- Update `PLAN.md`'s Phase 9 section is NOT part of this dispatch — that's my own job after
  reviewing your work, don't touch `PLAN.md`.

## Part B — topic guides (mirror the tutorial's own accuracy discipline)

Create `docs/src/guides/` (or wherever Part A's `SUMMARY.md` structure puts them) with one file
per topic: `orm.md`, `templates.md`, `forms.md`, `auth.md`, `admin.md`, `testing.md`,
`deployment.md`, `security.md`. Each is a standalone reference guide (not tutorial-paced —
readers jump straight to the topic they need), and **the same non-negotiable rule from 9.1
applies: every code snippet, function/struct/macro-attribute name, and CLI command must be
checked against real, current source before being written down, not recalled from "how this kind
of framework usually works."** Read the real crate source before writing each guide:

- **ORM** (`djangors-orm`): `QuerySet` methods (`filter`, `order_by`, `limit`, `all`, `get`,
  `update`, `delete_by_pk`, aggregate/count if present), the `q!`/`set!`/`F` macros, `ForeignKey`,
  `#[derive(Model)]` attributes (`app`, `table_name`, `ordering`, `primary_key, auto`,
  `foreign_key(on_delete, related_name)`, `max_length`, `default`, `verbose_name`, `db_index`) —
  read `crates/djangors-orm/src/lib.rs` and `crates/djangors-macros/src/model.rs` directly, don't
  guess at attribute names.
- **Templates** (`djangors-template`): `TemplateEngine::new()` vs `from_embedded()`, real filters
  (grep `crates/djangors-template/src/filters.rs` for the actual registered list — `intcomma`,
  `filesizeformat`, `naturaltime`, plus whatever else is really there), autoescaping behavior.
- **Forms**: `Form<T>` extractor (`djangors_core::extract::Form`), how it deserializes
  `application/x-www-form-urlencoded` bodies — read `crates/djangors-core/src/extract.rs`.
- **Auth** (`djangors-auth`): `Auth<User>::from_request`, `ModelBackend`, `login`/`logout`,
  session integration, permissions (`has_perm`, `is_superuser`, `Group`/`Permission` model,
  `dj createpermissions`) — this is one of the largest real subsystems, read
  `crates/djangors-auth/src/lib.rs` in full.
- **Admin** (`djangors-admin`): `AdminSite::new()`/`register()`/`register_with()`,
  `ModelAdminConfig` fields (`search_fields`, `list_display`, `list_filter`, `list_editable`,
  `date_hierarchy`, `fieldsets`, `readonly_fields`, `raw_id_fields` — confirm the real current
  field list via `crates/djangors-admin/src/lib.rs`, don't assume every field named in this prompt
  still exists exactly as named), `SiteBranding`, favicon/branding routes.
- **Testing**: `djangors-test`'s `TestClient` (in-process `Router::handle()` wrapper) and
  `TestDatabase`, plus the real-socket integration-test pattern used by
  `examples/polls/tests/voting.rs` and `examples/school/tests/admin_crud.rs` — show both styles
  since this codebase genuinely uses both (in-process for admin-crate-internal tests, real-socket
  for full-stack example-app tests) and explain when each applies.
- **Deployment**: `dj new`'s generated Dockerfile/systemd unit/`/healthz` route, `dj check
  --deploy`, graceful shutdown (`run_with_shutdown`/`run_service_with_shutdown`, SIGINT/SIGTERM) —
  read `crates/djangors-cli/src/commands.rs`'s deployment-scaffolding code and
  `crates/djangors-core/src/app.rs`'s shutdown functions directly.
- **Security**: CSRF (`csrf_layer()`, the cookie+header+form-fallback mechanism from 5.8.9/5.8.10),
  `security_headers_layer()`, session cookie signing (`SignedCookieStore`) — read
  `crates/djangors-core/src/middleware.rs` directly for the real current CSRF mechanism rather
  than describing a generic "CSRF token" pattern that might not match what's actually implemented.

If a topic guide would need to describe something that doesn't exist yet (e.g. ORM many-to-many
query support — confirmed elsewhere in this project's history to be an unused stub), say so
explicitly rather than describing a hypothetical.
