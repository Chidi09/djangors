# 5.6 part 2 — Changelist customization: `list_filter` (Boolean fields, v1)

**Status:** design, not yet dispatched. Follows 5.6.1 (`list_display`/`search_fields`, commit
`a6ad28f`). See `docs/design/phase-5-roadmap.md` for full Phase 5 context.

## Scope: Boolean fields only, and why

The roadmap doc's original phrasing was "`list_filter` v1 (bool/choices fields)". Checking
`FieldMeta` (`crates/djangors-orm/src/meta.rs` ~line 74-95) confirms there is **no `choices`
metadata anywhere in this ORM** — no Django-style `choices=[...]` concept exists on any field
kind. Building a choices-based filter would mean inventing that metadata first, which is a
separate, much bigger change (macro attribute parsing, `FieldMeta` shape change, validation)
unrelated to what filtering itself needs. **This part is Boolean fields only.** Choice-field
filtering is deferred until choices metadata exists as its own framework-wide feature — add
that as a new bullet to the deferred-items ledger when this lands, do not attempt it here.

Boolean is also the *only* field kind where "exact match against a small, fixed set of values"
(true/false/unset) is meaningful without any new metadata — every other kind would need either
choices (doesn't exist) or a distinct-values-from-the-table query (a different, heavier
mechanism, also out of scope here).

## No new generic ORM method needed — this reuses existing infrastructure directly

Unlike 5.6.1's `search_fields` (which needed a new `filter_or_icontains` because `filter()`
only supports AND'd exact-match), Boolean list_filter needs **only** exact-match AND, which
`QuerySet::filter(UnresolvedExpr::And(Vec<UnresolvedCompare>))` already does today. `Value`
already has `impl From<bool> for Value` (`expr.rs` ~line 38). So applying an active filter is
just:

```rust
qs = qs
    .filter(djangors_orm::expr::UnresolvedExpr::And(vec![
        djangors_orm::expr::UnresolvedCompare { field: filter_field_name, value: Value::Bool(b) },
        // ...one entry per active filter
    ]))
    .map_err(|e| DjangorsError::Internal(e.to_string()))?;
```

Exactly the same construction technique `ModelAdmin::get_by_pk` already uses for its pk lookup
(`lib.rs` ~line 126-134) — no macro changes, no new `QuerySet` method, this part is pure
wiring on top of what 5.4/5.5/5.6.1 already proved works.

## `ModelAdminConfig` gains one field

```rust
pub struct ModelAdminConfig {
    pub list_display: Option<&'static [&'static str]>,   // unchanged, 5.6.1
    pub search_fields: Option<&'static [&'static str]>,  // unchanged, 5.6.1
    pub list_filter: Option<&'static [&'static str]>,    // NEW: Boolean field names only
}
```

`register_with`'s existing registration-time validation block (which already validates
`list_display` and `search_fields` with `assert!`/`panic!` — see `AdminSite::register_with`,
`lib.rs` ~line 538-586) gets one more block, same style:

```rust
if let Some(list_filter) = config.list_filter {
    for name in list_filter {
        let field = meta.fields.iter().find(|f| f.name == *name).unwrap_or_else(|| {
            panic!("list_filter field '{}' does not exist on model '{}'", name, meta.struct_name)
        });
        assert!(
            matches!(field.kind, djangors_orm::meta::FieldKind::Boolean),
            "list_filter field '{}' on model '{}' is not a Boolean field (choices-based \
             list_filter is not supported — this ORM has no choices metadata yet)",
            name,
            meta.struct_name
        );
    }
}
```

**Every other existing `ModelAdminConfig { ... }` struct literal in the codebase (there are
several — the 5.6.1 tests construct it directly multiple times, e.g. `ModelAdminConfig { list_display: ..., search_fields: None }`)
will fail to compile once this field is added**, since it's a plain struct with no `#[derive(Default)]`
shortcut applied at each call site. `ModelAdminConfig` already derives `Default` (5.6.1) — the
correct fix at every existing call site is `..Default::default()` in the struct-update
syntax (e.g. `ModelAdminConfig { list_display: Some(&[...]), ..Default::default() }`), not
manually adding `list_filter: None` to every literal. Grep for `ModelAdminConfig {` across
`crates/djangors-admin/src/lib.rs` and fix every hit this way — do not miss any, the build will
fail loudly if you do (a good verification signal, not a risk).

## `ModelAdmin` trait: one new method, `changelist()` gains one parameter

```rust
fn list_filter_fields(&self) -> &[&'static str]; // empty = no filter UI rendered
```

`changelist()` grows a `filters: &[(&'static str, bool)]` parameter — **already-validated,
already-parsed** active filters (field name + chosen bool value), computed by the route handler
below, not raw query-string data. `DefaultModelAdmin` doesn't need to re-validate these against
`self.config.list_filter` (the handler already did, see next section) — it just applies them.

```rust
async fn changelist(
    &self,
    db: &djangors_db::Database,
    order: Option<&str>,
    page: i64,
    per_page: i64,
    search: Option<&str>,
    filters: &[(&'static str, bool)],
) -> Result<ChangelistPage, DjangorsError> {
    let mut qs = M::objects();
    // ... existing order_by unchanged ...
    // ... existing search_fields block unchanged ...
    if !filters.is_empty() {
        let compares = filters
            .iter()
            .map(|(field, val)| djangors_orm::expr::UnresolvedCompare {
                field,
                value: djangors_orm::expr::Value::Bool(*val),
            })
            .collect();
        qs = qs
            .filter(djangors_orm::expr::UnresolvedExpr::And(compares))
            .map_err(|e| DjangorsError::Internal(e.to_string()))?;
    }
    // ... rest (total via cloned qs, limit/offset, columns projection, pks) all unchanged ...
}
```

Apply this **before** the `total` count clone (same ordering requirement 5.6.1 already
established for `search`: `total` must reflect every active filter, not just search — the
existing `qs.clone().count(db)` line naturally picks up both since both mutate `qs` before that
clone point; just make sure the filter block above runs before, not after, the `let total =
qs.clone().count(db)...` line).

`DefaultModelAdmin::list_filter_fields()` returns `self.config.list_filter.unwrap_or(&[])`,
same pattern as `search_fields()`.

## Route handler: parsing and validating which filters are active

**Security/correctness note, read before implementing:** the handler must only ever apply a
filter for a field name that is actually in `admin.list_filter_fields()`. Do not build the
active-filters list by blindly trusting arbitrary query parameter names as field names —
that would let any caller filter on any field via the query string (bypassing the entire point
of `list_filter` being an explicit, configured allowlist) and, if a field name happened to
collide with something SQL-relevant, is exactly the kind of unvalidated-string-into-a-field-
lookup mistake this codebase has been careful to avoid everywhere else (`order_by`, `filter()`,
`insert_raw` all validate field names against `ModelMeta` before use — this handler achieves
the same end by checking against `list_filter_fields()` instead, since the trait method exists
specifically to make that allowlist available to the handler).

In `admin_changelist` (`crates/djangors-admin/src/lib.rs`):

```rust
let list_filter_fields = admin.list_filter_fields();
let mut active_filters: Vec<(&'static str, bool)> = Vec::new();
for &field_name in list_filter_fields {
    if let Some(raw) = req.query(field_name) {
        match raw {
            "true" => active_filters.push((field_name, true)),
            "false" => active_filters.push((field_name, false)),
            _ => {} // anything else (including empty/"all") = not filtered on this field
        }
    }
}
```

then pass `&active_filters` as the new `changelist()` argument.

## Rendering: a query-string-builder helper, because this is now four independent dimensions

Order (`o`), search (`q`), pagination (`page`), and now filters must all compose correctly in
every link on the page — e.g. clicking a filter option must preserve the current search term
and sort order, not reset them. 5.6.1 already hand-built `o`+`q` composition three times
(header sort links, prev link, next link) via repeated `if let Some(...) { push_str(...) }`
blocks; adding a third and now variable-length fourth dimension (filters) by continuing to
hand-splice strings at each of those three sites (plus the new filter UI itself) is exactly the
kind of copy-paste surface that produces the encoding bug 5.6.1's review already had to fix
once. Add one small helper instead and use it everywhere a changelist link is built:

```rust
/// Builds a `?key=value&key=value...` query string from already-string-ish
/// parts, percent-encoding every value. Skips pairs whose value is `None`.
fn build_query_string(pairs: &[(&str, Option<&str>)]) -> String {
    let parts: Vec<String> = pairs
        .iter()
        .filter_map(|(k, v)| v.map(|val| format!("{}={}", k, url_encode_query_value(val))))
        .collect();
    if parts.is_empty() {
        String::new()
    } else {
        format!("?{}", parts.join("&"))
    }
}
```

Use this to replace the header/prev/next link construction from 5.6.1 (they currently each
independently splice `o`/`q` together — collapse them onto this helper, passing whatever `o`/
`q`/`page`/per-filter values are relevant to that particular link, with the one field that link
is actually changing overridden). This is a deliberate small refactor of 5.6.1's own code,
justified by this task's own requirement (composing a third and fourth dimension correctly),
not a gratuitous cleanup — do not expand it further than making the existing four link sites
(header sort, prev, next, plus the new filter UI) use it.

Filter UI itself: for each field in `list_filter_fields()`, render three links — All / Yes / No
— e.g.:

```
<div>Filter by is_staff:
  <a href="{base with is_staff removed}">All</a>
  <a href="{base with is_staff=true}">Yes</a>
  <a href="{base with is_staff=false}">No</a>
</div>
```

repeated per configured Boolean field, each link preserving `o`/`q`/other active filters,
resetting `page` to 1 (a new filter changes the result set, page 1 is the only sane target,
same reasoning Django's own filter sidebar uses). Plain `format!` HTML, html-escaped where any
value is interpolated as text content (field name is `&'static str` from `ModelMeta`, already
trusted/no escaping needed as text, same as existing column headers).

## What NOT to touch in this task

- No choices-based filtering (no metadata exists for it — see scope section above).
- No `date_hierarchy`, `list_editable`, bulk actions, CSV/XLSX export, or saved views.
- No computed-method `list_display` columns.
- No changes to `render_form`, add/change routes, or delete confirmation routes.
- No changes to `djangors-macros`.

## Required tests

Add to the existing `#[cfg(test)] mod tests` block in `crates/djangors-admin/src/lib.rs` (same
Postgres-backed socket-level style as every other test in this file):

1. `register_with` with `list_filter: Some(&["is_active"])` on a model with a Boolean field →
   registers successfully; changelist response contains the filter UI (All/Yes/No links for
   that field).
2. `register_with` with `list_filter` naming a field that doesn't exist → panics.
3. `register_with` with `list_filter` naming a real but non-Boolean field (e.g. an `i64` or
   `String` field) → panics.
4. Insert rows with mixed Boolean values (e.g. 2 with `is_active=true`, 1 with `false`); GET
   with `?is_active=true` → only the matching rows appear, and the pagination total reflects
   the filtered count (mirrors 5.6.1's equivalent search-total test — same bug class, verify it
   doesn't reappear here since `total` is computed from a shared code path but the filter logic
   is new).
5. Same setup, GET with `?is_active=true&q=<term>` (both a filter AND a search active at once,
   assuming the model also has a `search_fields`-configured text field) → only rows matching
   BOTH conditions appear. This is the test that actually proves filters and search compose
   correctly (AND together) rather than one silently overriding the other.
6. GET with a query parameter matching a field name that is real on the model but NOT in
   `list_filter` (e.g. `?some_other_bool_field=true` where that field exists but isn't
   configured) → ignored entirely, no filtering applied, all rows show. This is the security/
   allowlist test — it must fail loudly if the handler ever stops checking
   `list_filter_fields()` before trusting a query param name.
