**Correction to how this is scoped, found while investigating real wiring — read before starting**:
the existing `benchmarks/` crate (from item 10.1) is a plain **axum** app used specifically to
compare Djangors against axum/Django on identical trivial routes — it does not use `djangors-core`
at all and has no admin equivalent to add a route to. Do **not** add an admin route to
`benchmarks/`. Instead, the load-test *target* is `examples/school`'s own real, already-running
Djangors application — it already mounts a real `AdminSite` at `/admin` (confirmed:
`examples/school/src/urls.rs:9`, `.mount("/admin", crate::admin::admin_site().urls())`), registers
real models with real permissions (`examples/school/src/admin.rs`), and has a real login endpoint
already wired (`examples/school/src/urls.rs:7`, `POST /accounts/login/` →
`examples/school/src/views.rs`'s `login_view`, which calls `djangors_auth::login` on success and
sets a real session cookie). `benchmarks/`'s only role in this item is being the place the
seed script and raw result files live, for consistency with where 10.1's artifacts already are.

**Current state** (verified): `DatabaseConfig` (`crates/djangors-db/src/config.rs:8-19`) —
`max_connections` (default 10), `min_connections` (default 1), `connect_timeout_secs` (default
10), `idle_timeout_secs` (default `None`) — mapped onto `sqlx::PgPoolOptions` in
`Database::connect` (`database.rs:48-70`). `djangors-admin`'s changelist path
(`crates/djangors-admin/src/lib.rs:370-429` for the ORM query, `~1906+` for the HTTP handler) is
not classic N+1 (exactly 2 queries regardless of page size via `count`+`limit/offset`), but a
non-superuser request costs up to ~9 sequential DB round-trips per page load: `require_perm` (1
query) plus 3 sequential `has_perm` calls for add/change/delete
(`crates/djangors-auth/src/lib.rs:436-462`, each up to 2 queries — direct + via-group) plus the 2
changelist queries. All sequential, each acquiring/releasing a pool connection. This fixed
high-round-trip-count-per-request is the realistic "under concurrency" stress case — it amplifies
with concurrent request volume against a fixed pool size, unlike the query count (which doesn't
scale with row volume). A real Postgres 16 instance is already running natively
(`127.0.0.1:5432`); `djangors_test`/`djangors_bench` databases already exist — no new
infrastructure needed.

## The real work

### 1. Seed real data

Add a small seed script/binary (e.g. `benchmarks/seed_school.sql` or a one-off `cargo run`
invocation against `examples/school`'s own models) inserting ~5,000 `Student` rows into
`djangors_bench` (or a fresh dedicated database if that's cleaner — your call, document which) so
changelist pagination and `?q=` search have real data to walk, not an empty table.

### 2. Two real user fixtures

- A superuser: create via the existing `dj createsuperuser` CLI command
  (`crates/djangors-cli/src/commands.rs:698`) — exercises the 2-query fast path (`is_superuser`
  presumably short-circuits `has_perm`'s DB lookups; confirm this by reading `has_perm`'s actual
  implementation before assuming it).
- A staff user with explicit `add`/`change`/`view` permission grants on `Student` (via real SQL
  inserts into whatever permission-model tables `djangors-auth` uses — read
  `crates/djangors-auth/src/lib.rs`'s `Permission`/`UserPermission`/`GroupPermission` models
  first) — exercises the full ~9-round-trip path.

### 3. Real HTTP login flow, not a fabricated token

Script a real login via `curl` (or a small shell wrapper): `POST /accounts/login/` with the
correct form-encoded username/password for each fixture, capture the real `Set-Cookie` session
token from the response (`curl -c cookiejar.txt`), and pass it to `oha` via `-H "Cookie: ..."` for
the actual load-test requests — this must be a genuine authenticated session Djangors itself
issued, not a synthetic/faked cookie value.

### 4. The concurrency sweep

Run `examples/school`'s real binary (`cargo run -p school`, or the release build for realistic
numbers) pointed at the seeded database. Run `oha -c {8,16,32,64,128} -z 20s --no-tui -H "Cookie:
<real-session-cookie>" <changelist-url>` for each of: {superuser, staff-user} × {plain paginated
GET, GET with `?q=<search-term>` exercising `search_fields`}. Repeat the full sweep at 3
`max_connections` settings (5, 10, 25) by restarting the app with `DatabaseConfig::new(url)
.max_connections(N)` — read how `examples/school`'s `main.rs` currently constructs
`DatabaseConfig` (it currently just does `DatabaseConfig::new(db_url)` with no tuning — you'll need
to add a way to override `max_connections` for this test run, e.g. an env var, without
permanently changing `examples/school`'s own default config for other purposes). At least one
combination must deliberately undersize the pool relative to concurrency (e.g.
`max_connections=10` at `-c 64`) specifically to force a real, observable pool-exhaustion error —
not just higher latency.

### 5. The tuning guide

Write `docs/src/guides/pool-tuning.md` (add to `docs/src/SUMMARY.md`'s "Topic Guides" section,
alongside the existing `guides/deployment.md`/`guides/security.md` entries — read `SUMMARY.md`
first for the exact list format). Content, tied to the real fields and real measured numbers, not
generic advice:
- `max_connections`: a sizing formula using the real measured round-trip count as the worked
  example (e.g. "N concurrent admin users on the non-superuser path × ~9 round-trips each ÷
  acceptable per-round-trip hold time ≈ required pool size", refined with your actual sweep
  numbers).
- `min_connections`, `connect_timeout_secs`, `idle_timeout_secs`: what each one actually does
  operationally and when to change it from the default, referencing what you observed at the
  undersized-pool sweep point (what does a starved request actually see — a specific error
  variant, a specific latency spike — describe the REAL observed behavior).
- Explicitly name the gap: no `max_lifetime`/`test_before_acquire`/statement-cache knobs are
  exposed on `DatabaseConfig` today. State this as a follow-up recommendation, do **not** add new
  fields to `DatabaseConfig` in this dispatch — that would be scope creep beyond "measure and
  document."

## Deliberate exclusions

No changes to `DatabaseConfig`/the `PgPoolOptions` mapping itself — this is measurement +
documentation only. No separate synthetic ORM-only benchmark beyond the admin path (the admin path

it's a real bottleneck — name it as a candidate for a future optimization item in the doc, don't
fix it mid-dispatch.
