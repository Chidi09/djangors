# Design 4.15 — wire a real tower middleware stack into `Djangors::serve` (Phase 4 part 4f)

**Status:** draft, pre-implementation. Discovered while scoping "polls requires login to vote"
(Phase 4's own DoD line): `SessionLayer`, `CsrfLayer`, `SecurityHeadersLayer`, `HstsLayer`,
`HostValidationLayer` all exist and are individually tested (`crates/djangors-core/src/
middleware.rs`'s and `crates/djangors-sessions/src/lib.rs`'s own `#[cfg(test)]` modules build a
real layer around a `tower::service_fn` and call it directly), **but nothing in the real serving
path ever applies them.** Read `crates/djangors-core/src/app.rs`'s `serve_connection`: it builds a
`hyper::service::service_fn` closure that calls `router.dispatch_debug(req, debug)` directly — a
plain async method call, not a `tower::Service::call` — so there is no composition point where an
app could wrap its router in `ServiceBuilder::new().layer(SessionLayer::new(...)).layer(CsrfLayer::new())...`
today. Any app built so far (including `examples/polls`, once made real) would have **zero**
session/CSRF/security-header protection at runtime no matter how it's configured, because the
serve loop physically cannot see any layers. This is core framework work (blast radius: every
future app's server loop), not example-app-specific work, so it's split out as its own task before
touching `examples/polls`.

## Real current state (read before writing code)

- `crates/djangors-core/src/router.rs`: `Router` has `dispatch`/`dispatch_debug` as plain async
  methods (`pub async fn dispatch(&self, req: hyper::Request<Incoming>) -> hyper::Response<...>`
  — check the exact signature/body type). `Router` does **not** implement `tower::Service` itself.
- `crates/djangors-core/src/app.rs`: `Djangors { settings, router: Router }`, `serve_connection`
  builds `hyper::service::service_fn(move |req| { let router = router.clone(); async move {
  Ok::<_, Infallible>(router.dispatch_debug(req, debug).await) } })` and hands that directly to
  `hyper::server::conn::http1::Builder::new().serve_connection(io, svc)`.
- `crates/djangors-core/src/middleware.rs` and `crates/djangors-sessions/src/lib.rs`: every layer
  is a real `tower::Layer<S> where S: Service<hyper::Request<...>, Response = hyper::Response<...>,
  Error = Infallible>` — i.e. they're all designed to wrap *some* inner `tower::Service`, they just
  currently have nothing real to wrap in production.
- `crates/djangors-core/src/middleware.rs`'s own `test_end_to_end_router_csrf` test is the closest
  existing precedent for what "a layer wrapping a router" looks like — it does
  `service_fn(move |req| { let router = router.clone(); async move { Ok::<_, Infallible>(router.dispatch(req).await) } })`
  then `ServiceBuilder::new().layer(CsrfLayer::new()).service(svc_fn)`. This is exactly the shape
  that needs to become real inside `app.rs`, generically, for whatever stack of layers an app
  wants — not hardcoded to CSRF alone.

## What this task builds

The minimal, real fix: give `Djangors` a way to accept an already-built `tower::Service` (the
fully-layered stack an app assembled itself) instead of forcing every app through the router
directly. Two parts:

1. **`Router` needs to be usable as a `tower::Service`.** Either (a) implement
   `tower::Service<hyper::Request<Incoming>>` directly on `Router` (cleanest, most idiomatic —
   check whether `Response` type compatibility with the existing layers' bounds,
   `hyper::Response<Full<Bytes>>` vs whatever `dispatch`/`dispatch_debug` currently return, lines
   up or needs a thin adapter), or (b) keep `Router` as-is and provide a small
   `RouterService(Router, debug: bool)` newtype wrapper implementing `tower::Service` that just
   calls `dispatch_debug` internally, mirroring the existing test precedent almost exactly. Prefer
   (b) if (a) runs into signature mismatches — smaller, safer diff, and matches an already-proven
   test pattern instead of inventing a new one.
2. **`Djangors` needs an entry point that takes a pre-built `tower::Service` instead of (or in
   addition to) a bare `Router`.** Something like:
   ```rust
   impl Djangors {
       pub fn new(settings: DjangorsSettings, router: Router) -> Self { /* unchanged, existing */ }

       // New: allows an app to layer its router before handing it to Djangors.
       // Exact method name/shape is a judgement call - options include a
       // builder method (`.layer(some_layer)` repeated, matching
       // `tower::ServiceBuilder`'s own ergonomics) or a single method that
       // accepts an already-built `tower::Service` (simpler to implement
       // correctly on the first pass, if less ergonomic to call). Pick
       // whichever is a smaller, more obviously-correct diff against the
       // existing `serve_connection`/`serve`/`run` methods - do not
       // over-engineer a generic builder API in v1 if a single
       // "bring your own layered service" method covers the real need.
   }
   ```
   `serve_connection` (or whatever replaces it for the layered case) must then call the provided
   service's `Service::call` instead of `router.dispatch_debug` directly, handling `poll_ready`
   correctly per `tower::Service`'s own contract (check how the existing test code in
   `middleware.rs`/`djangors-sessions` calls a layered service — `svc.ready().await.unwrap().call(req)`
   — for the exact pattern; `serve_connection` runs per-connection in a spawned task already, so
   this is not a new concurrency concern, just needs the right tower calling convention).

**Backwards compatibility requirement:** `Djangors::new(settings, router).run()` (the existing,
already-tested, already-used-by-`examples/polls`'s `main.rs` shape) must keep working exactly as
today for apps that don't need any middleware — do not force every app to assemble a layer stack
just to keep compiling. The new layered path is additive.

## What this task does NOT include

- Changing what any individual layer does (`SessionLayer`, `CsrfLayer`, etc. are untouched).
- Wiring `examples/polls` itself to actually use `SessionLayer`/`CsrfLayer` — that's the next
  task, built on top of this one, once this lands and is verified working end-to-end over a real
  TCP socket (mirroring `app.rs`'s own `real_socket_request_response` test).
- A settings-driven "apply these middlewares by name from config" system (Django's
  `MIDDLEWARE = [...]` list) — that's speculative future ergonomics work, not required to unblock
  the DoD. An app wires its own layer stack in Rust code for v1, same as how every other
  opt-in layer (`HstsLayer`, `HostValidationLayer`) already works today.

## Required tests

- A real end-to-end test over an actual TCP socket (mirror `app.rs`'s own
  `real_socket_request_response` test exactly, including the `TcpListener::bind("127.0.0.1:0")` +
  spawned `serve`/whatever-the-new-method-is-called + raw `TcpStream` request/response pattern),
  but this time constructing the app with at least two real layers stacked (e.g.
  `SecurityHeadersLayer` + `CsrfLayer`) around a trivial router, and asserting the *response headers
  a real socket read back* actually show the layers' effects (e.g. `X-Frame-Options: DENY` present,
  a `Set-Cookie: csrftoken=...` present on the response) — not just a unit-level `Service::call`
  in isolation, since the whole point of this task is proving the real serve loop applies layers,
  not just that layers work when manually wired in a test (already proven repeatedly elsewhere).
- Confirm the existing no-layer path (`Djangors::new(settings, router).run()`) still passes its
  existing test (`real_socket_request_response`) unmodified — this is a regression check, not a
  new test to write, just something to verify stays green.
- If a debug-page/production-error-page distinction (`dispatch` vs `dispatch_debug`, `settings.debug`)
  needs to be threaded through the new layered path too, verify it the same way the un-layered path
  already does (do not silently drop this behavior for layered apps).
