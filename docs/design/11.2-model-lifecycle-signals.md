# 11.2 — Model-level lifecycle signals (pre_save/post_save/pre_delete/post_delete)

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_2` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

Phase 11 item 2 (Django-parity gap closure, see `PLAN.md`). Djangors already has a real,
generic, async pub/sub signals primitive — `crates/djangors-core/src/signals.rs`'s `Signal<T>` —
used today for `REQUEST_STARTED`/`REQUEST_FINISHED`. That file's own module doc literally says:
*"Model-lifecycle signals (`pre_save`, `post_save`, etc.) will be added once an ORM is available."*
An ORM now exists (`djangors-orm`) — this is that follow-through.

**Critical architectural constraint, verified directly against `Cargo.toml` files before writing
this doc — re-verify yourself, don't take this on faith:** `djangors-core`'s real `[dependencies]`
(not dev-dependencies) includes `djangors-orm = { path = "../djangors-orm" }`. `djangors-orm`'s own
`Cargo.toml` has **no** dependency on `djangors-core` anywhere. The dependency graph is
`djangors-core → djangors-orm → djangors-db`. **This means model-lifecycle signals cannot reuse
or import `djangors_core::signals::Signal<T>`** — `djangors-orm` (where the generated `save()`/
`update()`/`delete()` methods actually execute, and where any lifecycle-signal dispatch call must
therefore live) cannot depend on `djangors-core` without creating a dependency cycle. This project
has made this exact class of mistake three times already this session (rate limiting's
`ByAuthenticatedUser` needing to move from `djangors-core` to `djangors-rest`; two other design-doc
errors caught only by a dispatch's own workspace-wide grep) — do not repeat it. Confirm the
direction yourself with `grep -n djangors- crates/djangors-orm/Cargo.toml crates/djangors-core/Cargo.toml`
before writing a single line of signal code.

The fix: **duplicate the `Signal<T>` pattern (not the type itself) into `djangors-orm`**, as a new
`crates/djangors-orm/src/signals.rs` module. It's a small, self-contained ~100-line generic pub/sub
primitive (see `djangors-core/src/signals.rs` for the exact pattern to mirror: `RwLock<Vec<Arc<dyn
Fn(T) -> BoxedFuture>>>`, `connect()`, `send()` that spawns each callback via `tokio::spawn` and
isolates panics, logging via `eprintln!` rather than propagating). Copy the *shape*, not a
`pub use` re-export (that would still require the dependency).

Relevant generated code to wire into, in `crates/djangors-macros/src/model.rs` (read the real
current version yourself — line numbers below are where they were when this doc was written):
- `save()` (~line 654): `INSERT`-only, returns a new `Self` populated from the inserted row.
- `update()` (~line 666): full-row `UPDATE` by primary key, returns `Result<(), OrmError>`.
- `delete()` (~line 683): `DELETE` by primary key, returns `Result<(), OrmError>`.

All three are generated per-model inherent methods (not trait methods) inside the same `quote!`
block that also implements the `Model` trait for the struct. `field_values(&self)` (implementing
`Model::field_values`) already gives every field's current value in declaration order — reuse it
for the signal payload rather than inventing a second serialization path.

## Scope — what to build

1. **`crates/djangors-orm/src/signals.rs`**: a generic `ModelSignal<T>` type (same shape as
   `djangors-core`'s `Signal<T>`: `connect`, `send`, panic-isolated, concurrent dispatch via
   `tokio::spawn`). Export it from `djangors-orm`'s `lib.rs`.

2. **Per-model signal accessors, generated by the derive macro** (mirrors the existing
   `static META: OnceLock<ModelMeta>` pattern already used for `meta()` in the same file — follow
   that exact idiom, don't invent a new one): for every `#[derive(Model)]` struct, generate

   ```rust
   pub type ModelSignalPayload = Vec<(&'static str, djangors_orm::expr::Value)>;

   impl #struct_name_ident {
       pub fn pre_save_signal() -> &'static djangors_orm::signals::ModelSignal<ModelSignalPayload> { ... }
       pub fn post_save_signal() -> &'static djangors_orm::signals::ModelSignal<ModelSignalPayload> { ... }
       pub fn pre_delete_signal() -> &'static djangors_orm::signals::ModelSignal<ModelSignalPayload> { ... }
       pub fn post_delete_signal() -> &'static djangors_orm::signals::ModelSignal<ModelSignalPayload> { ... }
   }
   ```

   Each returns a `'static` per-(model-type) singleton (one `OnceLock` per signal per model,
   same as `meta()`'s own `static META: OnceLock<ModelMeta>` inside the function body).

   **Revised payload decision (supersedes an earlier draft of this doc that specified
   `Arc<Self>`): a first dispatch attempt at this correctly refused to fabricate completion and
   reported a real blocker instead — building `Arc<Self>` from `&self` still requires an owned
   `Self` (via `.clone()` or a signature change), so it doesn't actually avoid a `Clone`
   requirement; it just hides it. Checked directly: every real (non-test) `#[derive(Model)]`
   struct in this workspace already derives `Clone` today, so requiring it wouldn't currently
   break anything - but `#[derive(Model)]` is public API subject to this project's own API
   freeze/stability policy (see `docs/api-stability.md`), and silently adding a new implicit
   `Self: Clone` bound to every model going forward is a real compatibility change worth avoiding
   if there's a way to.** There is: `Model::field_values(&self) -> Vec<(&'static str, Value)>`
   already exists on every model (part of the `Model` trait, unconditionally generated, and
   already returns freshly-cloned owned `Value`s without needing `Self: Clone`). Use
   `Vec<(&'static str, Value)>` itself (aliased as `ModelSignalPayload` above for readability) as
   the signal payload type instead of `Self`/`Arc<Self>`. This gives receivers every field's
   current value (same data the admin changelist already renders through `field_values()`) with
   zero new trait bounds on any model.

3. **Wire dispatch into `save()`/`update()`/`delete()`**:
   - `save()`: fire `pre_save_signal()` with `self.field_values()` *before* the INSERT executes;
     fire `post_save_signal()` with `field_values()` called on the *newly returned* `Self` (the
     one built from `from_row` on the inserted row - it has the real generated primary key)
     *after* the INSERT succeeds. Do **not** fire `post_save` if the INSERT fails - propagate the
     error first.
   - `update()`: fire `pre_update`... **no** - Django only has `pre_save`/`post_save` (both insert
     and update go through `save()` in Django's model API). Djangors' `save()` is INSERT-only and
     `update()` is a separate method, which doesn't map 1:1 onto Django - **fire `pre_save`/
     `post_save` around `update()` too** (both `save()` and `update()` are "this row is being
     persisted" from a signal-receiver's point of view), not a separate signal pair. This keeps
     the receiver-facing API exactly Django's 4 signal names, matching the task's actual scope
     (`post_save/pre_save/post_delete/pre_delete`) rather than inventing a 5th/6th signal Django
     doesn't have.
   - `delete()`: fire `pre_delete_signal()` with `self.field_values()` before the DELETE executes;
     fire `post_delete_signal()` with the same (captured before the row is gone - there is no
     `Self` left to call `field_values()` on afterward) after the DELETE succeeds. Don't fire
     `post_delete` if the row didn't actually exist (`delete()` already returns
     `OrmError::NotFound` in that case - propagate that error before firing `post_delete`,
     matching the "don't fire post_* on failure" rule from `save()` above).

## Deliberately excluded (do not build these here)

- `m2m_changed`, `pre_init`/`post_init`, or any other Django signal beyond the 4 named in this
  task (`pre_save`/`post_save`/`pre_delete`/`post_delete`).
- Signals firing from `QuerySet::update()` (the bulk multi-row update) or a future `bulk_create`/
  `bulk_delete` - Django itself does **not** fire `pre_save`/`post_save` for bulk operations either
  (this is documented, intentional Django behavior, not an oversight to "fix") - only the
  per-instance `save()`/`update()`/`delete()` methods fire signals.
- Any change to `djangors-core`'s own `Signal<T>`/`REQUEST_STARTED`/`REQUEST_FINISHED` - leave that
  file untouched, this is a parallel, independent primitive in a different crate for architectural
  reasons explained above.
- A "disconnect" API - Django's own signal API barely uses this in practice; skip it unless
  trivial to add alongside `connect`.

## Required verification

Run yourself against the real Postgres database at
`DATABASE_URL=postgres://postgres:postgres@localhost/djangors_test` before finishing:

- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` all clean.
- Write and run new tests (in `djangors-orm`, following the existing test-file convention in
  `crates/djangors-orm/src/tests.rs` - a real `#[derive(Model)]` test struct, a real table,
  `DROP TABLE IF EXISTS`/`CREATE TABLE`/`DROP TABLE` around the test body) proving, against the
  real database:
  - Connecting a receiver to `pre_save_signal()` and calling `.save()` actually invokes it before
    the row exists in the database (e.g. assert the row is NOT yet queryable from inside the
    `pre_save` callback - this proves ordering, not just that the callback fired at all).
  - Connecting a receiver to `post_save_signal()` and calling `.save()` invokes it with the real
    generated primary key already populated, and the row IS queryable from inside the callback.
  - `update()` also fires `pre_save`/`post_save` (not a separate signal pair).
  - `pre_delete_signal()`/`post_delete_signal()` fire around `.delete()`, with the row still
    present during `pre_delete` and gone by the time `post_delete` fires.
  - A signal that is never connected to (no receivers) doesn't error or panic - `save()`/`update()`/
    `delete()` must behave identically whether or not anything is listening.
  - A panicking receiver does not prevent `save()`/`update()`/`delete()` from returning normally
    (mirrors the panic-isolation test already in `djangors-core/src/signals.rs` - write an
    equivalent for `ModelSignal<T>`).
- Do not claim a specific empirical result you have not actually observed in real committed test
  output.
