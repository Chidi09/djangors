# 15.1 — `select_for_update` and savepoints

Status: design, 2026-07-31. Implements the two missing primitives from `PLAN.md` Part 6 item 2.

## Why

Part 6 ("what banking grade concretely requires") item 2 names three concurrency primitives:
`select_for_update`, explicit isolation levels, and savepoints. Only isolation levels exist
(`Database::transaction_with_isolation`). The other two were never built:

- There is **no** `select_for_update` on `QuerySet`. The only `FOR UPDATE` SQL anywhere in the
  workspace is a hardcoded `FOR UPDATE SKIP LOCKED` inside `djangors-tasks`' claim query
  (`crates/djangors-tasks/src/lib.rs:239` and `:337`), which users cannot reach.
- There is **no** `SAVEPOINT` anywhere in the workspace, so partial rollback inside a transaction
  is impossible.

Without these, the documented double-entry-ledger example Part 6 asks for cannot be written
honestly, and the read-modify-write pattern at the centre of every ledger, inventory, and booking
system has no safe expression in this framework. This is the largest gap between the banking pitch
and the code.

## Scope

**In scope**

1. `QuerySet::select_for_update()` + modifiers, compiled into the generated `SELECT`.
2. Savepoint primitives on `Conn` (`savepoint`, `rollback_to_savepoint`, `release_savepoint`).
3. Dialect handling for both, tests for both, and a real guide section.

**Explicitly out of scope** (do not attempt):

- A closure-based `with_savepoint(|sp| ...)` helper. The `for<'c> FnOnce(&'c mut Conn<'c>)`
  signature on `transaction_conn` was hard-won; a nested closure over an already-borrowed `Conn`
  adds a second lifetime relationship that is not worth the risk in this slice. Explicit
  begin/rollback/release methods cover the same need. Revisit separately.
- `no_key` (Postgres `FOR NO KEY UPDATE`), `FOR SHARE`, `FOR KEY SHARE`.
- MySQL.

## Part 1 — `select_for_update`

### API

```rust,illustrative
impl<T: Model + FromRow> QuerySet<T> {
    /// Locks the selected rows for the remainder of the transaction.
    pub fn select_for_update(self) -> Self;

    /// Return immediately with an error instead of waiting for a lock.
    /// Mutually exclusive with `skip_locked`.
    pub fn nowait(self) -> Self;

    /// Skip rows that are already locked rather than waiting.
    /// Mutually exclusive with `nowait`.
    pub fn skip_locked(self) -> Self;

    /// Restrict locking to the named related tables (Postgres `FOR UPDATE OF`).
    pub fn lock_of(self, tables: &[&str]) -> Self;
}
```

Store this as one new field on `QuerySet<T>`, not four:

```rust,illustrative
#[derive(Debug, Clone, Default, PartialEq)]
pub struct ForUpdate {
    pub nowait: bool,
    pub skip_locked: bool,
    pub of: Vec<String>,
}
// on QuerySet:
for_update: Option<ForUpdate>,
```

`QuerySet` derives `Debug` and has hand-written `Clone` and `Default` impls
(`queryset.rs:38` and `:50`) — **both must be updated to carry the new field**, or `.clone()`
silently drops the lock and the resulting bug is invisible in tests that do not clone.

`nowait()`/`skip_locked()`/`lock_of()` called without `select_for_update()` first should imply it
rather than being silently ignored.

### SQL generation

The clause goes at the **very end** of the statement, after `ORDER BY`, `LIMIT`, and `OFFSET`:

```
SELECT ... FROM ... WHERE ... ORDER BY ... LIMIT ... OFFSET ... FOR UPDATE [OF a, b] [NOWAIT | SKIP LOCKED]
```

Emit it in `compile_select_with_order` (`queryset.rs:466`), which is the single funnel every read
path goes through. Table names in `OF` must be run through the same quoting the rest of that
function uses — `OF` takes **table** aliases, not columns.

### Dialect behaviour

| | Postgres | SQLite |
|---|---|---|
| `select_for_update()` alone | `FOR UPDATE` | **emit nothing**, succeed |
| `.nowait()` | `FOR UPDATE NOWAIT` | **`Err(OrmError::UnsupportedOnDialect)`** |
| `.skip_locked()` | `FOR UPDATE SKIP LOCKED` | **`Err(OrmError::UnsupportedOnDialect)`** |
| `.lock_of(...)` | `FOR UPDATE OF ...` | **`Err(OrmError::UnsupportedOnDialect)`** |

**This asymmetry is deliberate and is the most important decision in this document.** Plain
`select_for_update()` degrades to a no-op on SQLite because SQLite serialises writes at the
database level — an open write transaction already gives you something strictly stronger than row
locking, so emitting nothing is correct rather than merely convenient.

The modifiers are different in kind. `skip_locked` **changes which rows come back**. Silently
ignoring it on SQLite would hand the caller rows they explicitly asked to skip, and a worker loop
written against that would process the same row twice. That is a correctness bug, not a
performance difference, so it must fail loudly. `nowait` is the same argument: the caller asked to
not block, and silently blocking is a deadlock waiting to happen. Degrade the thing whose absence
is safe; refuse the thing whose absence changes results.

### Guards — reject these at query time

1. **Not inside a transaction.** `FOR UPDATE` against a pool checks out a connection, takes a
   lock, and returns it to the pool, releasing the lock immediately. The result is code that
   *looks* locked and is not — the worst possible failure mode for a ledger.

   The existing `Conn` enum makes this checkable for free: `Conn::PgPool`/`Conn::SqlitePool` are
   not in a transaction, `Conn::PgTx`/`Conn::SqliteTx` are. Return
   `OrmError::SelectForUpdateOutsideTransaction` for the pool variants. Django raises
   `TransactionManagementError` here for the same reason.

2. **Aggregates.** Postgres rejects `FOR UPDATE` with `GROUP BY`, `DISTINCT`, and set operations.
   `aggregate()` and `annotate()` must ignore or reject `for_update` rather than generate SQL the
   server will reject at runtime.

`debug_sql()`/`debug_params()` (`queryset.rs:77`, `:83`) hardcode `Dialect::Postgres`; they should
show the clause so it is testable without a live database.

## Part 2 — savepoints

`SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, and `RELEASE SAVEPOINT` are spelled identically in Postgres
and SQLite, so unlike almost everything else in Phase 13 this needs no dialect branching. Verify
that claim against the SQLite documentation before relying on it.

### API — on `Conn`, in `crates/djangors-db/src/executor.rs`

```rust,illustrative
impl Conn<'_> {
    pub async fn savepoint(&mut self, name: &str) -> Result<(), DbError>;
    pub async fn rollback_to_savepoint(&mut self, name: &str) -> Result<(), DbError>;
    pub async fn release_savepoint(&mut self, name: &str) -> Result<(), DbError>;
}
```

### Name validation is a security requirement, not a nicety

Savepoint names **cannot be bound as parameters** — they are identifiers and must be interpolated
into the SQL string. That makes this the one place in the ORM where a caller-supplied string
reaches the query text directly. The 2026-07-27 security review's positive finding was that no
raw user-value SQL interpolation exists anywhere in the ORM or REST layers; this must not become
the exception that falsifies it.

Validate before interpolating: reject anything that is not `[A-Za-z_][A-Za-z0-9_]*`, and cap the
length (63 chars, Postgres's identifier limit). Return a distinct error variant. Then **also**
pass the validated name through `Dialect::quote_ident`. Validation and quoting, not either alone.

Add a test that a name like `sp"; DROP TABLE users; --` is rejected by the validator, so the
guarantee is pinned by the suite rather than by a code comment.

### Calling a savepoint outside a transaction

`SAVEPOINT` outside a transaction is an error in Postgres and a silent no-op-ish oddity in SQLite
(where it opens a transaction). Match the `select_for_update` guard: return an error for the
`PgPool`/`SqlitePool` variants rather than letting the two backends diverge.

## Testing

Both backends, per the 14.1 harness. Postgres tests need `DATABASE_URL`; SQLite tests run with
`env -u DATABASE_URL TEST_BACKEND=sqlite`.

**Do not add tests that early-return when `DATABASE_URL` is unset.** The suite already has five
such tests and they report as *passing* on SQLite without executing — 14.1 flagged this as the one
thing in the suite that can be green while covering nothing. Do not add a sixth. Postgres-only
tests get `#[ignore]` or a `#[cfg]`, so a skip reads as a skip.

Required coverage:

1. SQL-shape tests via `debug_sql()` — no database needed. Assert the clause is last, after
   `LIMIT`/`OFFSET`, for each modifier combination.
2. `.clone()` preserves `for_update` — the hand-written `Clone` impl makes this a real risk.
3. Pool-not-transaction guard returns the error, on both backends.
4. `nowait`/`skip_locked`/`lock_of` return `UnsupportedOnDialect` on SQLite.
5. Savepoint round trip on **both** backends: insert, savepoint, insert, rollback to savepoint,
   commit → the first row is present and the second is not. This is the test that proves the
   feature actually works rather than merely emitting SQL.
6. Savepoint name validator rejects injection-shaped input.
7. A real two-transaction concurrency test on Postgres proving `skip_locked` skips a row locked by
   a concurrent transaction. Requires two connections; use `#[ignore]` if it proves flaky rather
   than weakening the assertion.
