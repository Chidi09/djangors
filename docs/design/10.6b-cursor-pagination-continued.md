# 10.6b — cursor pagination: continuation (ScopedViewSet wiring + required tests + a real bug fix)

## Context

`docs/design/10.6-cursor-pagination.md` was dispatched and mostly completed: `QuerySet::after`
(`crates/djangors-orm/src/queryset.rs`), `encode_cursor`/`decode_cursor`/`CursorPage`
(`crates/djangors-core/src/pagination.rs`), and opt-in `?cursor=` wiring into
`ViewSet::list_with_config` (`crates/djangors-rest/src/lib.rs:549`) all landed, compile, and pass
`fmt`/`clippy`/the full existing test suite. The dispatch **honestly reported two things left
incomplete**: `ScopedViewSet`'s cursor wiring, and every test the original design doc's "Required
verification" section demanded. Read `docs/design/10.6-cursor-pagination.md` in full first — this
doc only covers what's still missing, it doesn't repeat the original design.

**Also found during review, fix this too**: `crates/djangors-core/src/pagination.rs`'s
`decode_cursor` has a real bug. It does `raw.split_once('|')` (correctly splits into `pk` and
*everything after the first pipe*, which is already the unambiguous full ordering-value string),
but then adds `if value.contains('|') { return Err(CursorError::InvalidFormat); }` — this
incorrectly REJECTS any cursor whose ordering value itself legitimately contains a `|` character
(e.g. cursor pagination ordered by a text field like `title`, where a row's title happens to
contain a pipe). `split_once` already handles this correctly on its own; the extra `contains('|')`
check is wrong and must be deleted, not worked around.

## What to add

### 1. Wire `ScopedViewSet::list_with_config` the same way

Read `ViewSet::list_with_config` (`crates/djangors-rest/src/lib.rs:549`) in full to see exactly
what 10.6 added (the `cursor_ordering` tracking during `?ordering=` parsing, then the
`config.cursor_pagination && req.query("cursor").is_some()` branch before the existing
`Paginator::new(...)` line). Apply the **exact same block** to `ScopedViewSet::list_with_config`
(`crates/djangors-rest/src/lib.rs:772`) — the only difference should be that `ScopedViewSet`'s
queryset starts from `M::scope(&req, QuerySet::new())?` (per `docs/design/10.3-scoped-viewset.md`)
rather than a bare `QuerySet::new()`, exactly matching how every other method in `ScopedViewSet`
already differs from `ViewSet`. Do not touch `ViewSet::list_with_config` itself while doing this.

### 2. Fix the `decode_cursor` bug described above

Delete the `if value.contains('|') { return Err(...) }` check in
`crates/djangors-core/src/pagination.rs`'s `decode_cursor`. Add a test proving a cursor built from
an ordering value containing a literal `|` character round-trips correctly through
`encode_cursor`/`decode_cursor` (this is a real regression test for the bug just described, not
just a nice-to-have).

### 3. Write the required verification tests from the original design doc — none exist yet

All of the following, DB-backed, through `djangors-rest`'s actual HTTP layer (mirror
`test_viewset_filtering_and_ordering_end_to_end`'s fixture-setup style in
`crates/djangors-rest/src/lib.rs` for consistency — real Postgres tables, real inserted rows, real
`Router::handle`/`viewset_routes_with_config_and_permission` calls, not unit-level `QuerySet`
calls only):

- **Duplicate-ordering-value correctness**: seed rows where the chosen ordering field has ties
  (e.g. 3+ rows with identical `view_count`), page through with `?cursor=`, assert every row
  appears exactly once across all pages combined, in a stable order — this is the actual bug class
  unique to keyset pagination (missing the pk tiebreaker in `QuerySet::after` would either skip or
  repeat tied rows; offset pagination doesn't have this failure mode at all, so this test only
  makes sense for the new code path).
- **Concurrent insert during pagination**: fetch page 1 via `?cursor=`, insert a new row that would
  sort before the returned cursor position (per the current ordering), then fetch page 2 using the
  cursor from page 1's response, and assert no duplicate/skip occurs — this is cursor pagination's
  actual advantage over offset pagination; assert it directly, don't just assert the happy path.
- **Tampered/malformed cursor**: pass an invalid base64 string, a validly-encoded-but-wrong-format
  string (no `|` separator), and a non-numeric primary key portion as `?cursor=` — each must
  produce a clean `400`-class response, never a panic or 500.
- **Non-allowlisted ordering field**: attempt cursor pagination while `?ordering=` names a field
  NOT in `orderable_fields` (or with no `?ordering=` at all, if the config doesn't set a default) —
  must be rejected the same way plain `?ordering=` already is, not silently ignored.
- **`ScopedViewSet` isolation still holds under cursor pagination**: with the `ScopedViewSet`
  wiring from item 1 above, seed two "owners"/tenants worth of rows in one table (reuse or extend
  a fixture in the style of `test_scoped_viewset_enforces_owner_isolation_end_to_end`, from
  `docs/design/10.3-scoped-viewset.md`'s own dispatch), and prove cursor-paginating as owner A
  never returns owner B's rows, across multiple pages.
- Confirm every pre-existing test in `crates/djangors-rest/src/lib.rs` and
  `crates/djangors-core/src/pagination.rs` still passes unmodified.
