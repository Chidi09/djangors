# 5.8 part 5 — Convert `render_form` (add/change pages) to a template

**Status:** design, not yet dispatched. Follows 5.8.4 (save-changelist error page, commit
`8b7dce5`). See `docs/design/phase-5-roadmap.md`. Same discipline as every prior 5.8.x slice: one
page (well, one shared function used by four call sites), byte-identical output, no visual
changes, proven by the existing test passing unmodified.

## Scope: `render_form` and its four call sites

`render_form(meta, field_names, submitted_values, errors, is_add) -> String`
(`crates/djangors-admin/src/lib.rs`) is shared by:
- `admin_add_get` (empty `submitted_values`/`errors`, `is_add: true`)
- `admin_add_post`'s error branch (`is_add: true`)
- `admin_change_get` (`is_add: false`)
- `admin_change_post`'s error branch (`is_add: false`)

This is the first 5.8.x page with genuine **per-field-kind branching** (not just a list of
uniform rows): each field row is one of four shapes depending on the field's role and
`FieldKind`. Read `render_form`'s current body directly before implementing — do not work from
this summary alone, since the exact whitespace/attribute-ordering must be reproduced byte-for-
byte.

## The four row shapes (confirmed by reading the current source)

For each name in `field_names`, in order:

1. **Readonly** (`field.auto || field.primary_key`, and `is_add` is false — when `is_add` is
   true these fields are skipped entirely, not rendered as anything):
   `<div><label>{name} (readonly):</label> <span>{escaped_val}</span></div>` — no `for=`
   attribute, no error div (readonly fields never carry an error).
2. **Checkbox** (`FieldKind::Boolean`): the shared row wrapper (see below) with
   `<input type="checkbox" name="{name}" id="id_{name}"{checked}>` where `{checked}` is the
   literal string `" checked"` (leading space) when `val == "on" || val == "true"`, else `""` —
   no `value=` attribute on this input at all.
3. **Number** (`FieldKind::Integer | BigInt | Float`, **and every relation field** — the
   relation-field branch, `meta.relations.iter().find(...)`, builds the exact same
   `type="number"` input as this branch, just from a different code path):
   `<input type="number" name="{name}" id="id_{name}" value="{escaped_val}">`.
4. **Text** (every other `FieldKind` — the `_ =>` arm): `<input type="text" name="{name}"
   id="id_{name}" value="{escaped_val}">`.

Shared row wrapper for shapes 2–4: `<div><label for="id_{name}">{name}</label> {input_html}{err_html}</div>`
where `err_html` is `<div style="color: red;">{escaped_err}</div>` if `errors.get(name)` is
`Some`, else the empty string — note **no separator** between `input_html` and `err_html`, and
note the wrapper has exactly one space between `</label>` and `{input_html}`.

Whole form: `<form method="post">{all rows concatenated, no separator}<input type="submit" value="Submit"></form>`.

## Template-side design: pre-flatten to one row struct in Rust, template just switches on `kind`

Given the branching complexity, build a `Vec<FormFieldRow>` in Rust (same "flatten to plain
structs, template only loops/switches" pattern as every prior 5.8.x slice) rather than attempting
field-kind logic inside the template:

```rust
#[derive(serde::Serialize)]
struct FormFieldRow {
    kind: &'static str, // "readonly" | "checkbox" | "number" | "text"
    name: String,
    value: String,   // readonly span text, or the input's value="" attribute; unused for checkbox
    checked: bool,    // only meaningful when kind == "checkbox"
    error: Option<String>,
}

#[derive(serde::Serialize)]
struct RenderFormContext {
    rows: Vec<FormFieldRow>,
}
```

Build one `FormFieldRow` per iteration of the existing `for &name in field_names` loop, replacing
each `rows_html.push_str(&format!(...))` call with a `rows.push(FormFieldRow { ... })` of the
matching `kind`. Keep the exact same control flow (the `if field.auto || field.primary_key`
early-continue-when-`is_add` branch, the `match field.kind` for shape selection, the separate
`else if let Some(_rel) = meta.relations...` branch producing a `"number"`-kind row) — this is a
mechanical translation of each `format!()` call into a struct literal, not a rewrite of the
selection logic.

Note `value`/`checked` are plain `String`/`bool` fields, not `Safe`-wrapped — this page has no URL-
building at all, so 5.8.4's segment-substitution pattern doesn't even apply here; ordinary
autoescaping is exactly what's wanted for every one of these values (they're either static field
names or live form/database data).

## Template file: `crates/djangors-admin/templates/admin/render_form.html`

One continuous line, reproducing the shapes above exactly:

```html
<form method="post">{% for row in rows %}{% if row.kind == "readonly" %}<div><label>{{ row.name }} (readonly):</label> <span>{{ row.value }}</span></div>{% elif row.kind == "checkbox" %}<div><label for="id_{{ row.name }}">{{ row.name }}</label> <input type="checkbox" name="{{ row.name }}" id="id_{{ row.name }}"{% if row.checked %} checked{% endif %}>{% if row.error %}<div style="color: red;">{{ row.error }}</div>{% endif %}</div>{% elif row.kind == "number" %}<div><label for="id_{{ row.name }}">{{ row.name }}</label> <input type="number" name="{{ row.name }}" id="id_{{ row.name }}" value="{{ row.value }}">{% if row.error %}<div style="color: red;">{{ row.error }}</div>{% endif %}</div>{% else %}<div><label for="id_{{ row.name }}">{{ row.name }}</label> <input type="text" name="{{ row.name }}" id="id_{{ row.name }}" value="{{ row.value }}">{% if row.error %}<div style="color: red;">{{ row.error }}</div>{% endif %}</div>{% endif %}{% endfor %}<input type="submit" value="Submit"></form>
```

Double-check against the actual `render_form` source that: (a) the checkbox's `{% if row.checked %} checked{% endif %}` sits directly against the input's closing `>` with no other gap, matching the original's `"{}"` interpolation of `" checked"`/`""` immediately before `>`; (b) there is exactly one space between `</label>` and the `<input`; (c) `{% if row.error %}...{% endif %}` produces nothing (not even whitespace) when there is no error, matching the original's empty-string `err_html`.

## The `render_form` function's new signature and the 4 call sites

Change `render_form` to build `rows: Vec<FormFieldRow>` instead of `rows_html: String`, and return
`Result<Response, DjangorsError>` via `djangors_template::render(&ADMIN_TEMPLATES,
"admin/render_form.html", RenderFormContext { rows })` instead of returning `String`. Update all
four call sites (`admin_add_get`, `admin_add_post`'s error arm, `admin_change_get`,
`admin_change_post`'s error arm) to use `render_form(...)` directly as the tail
expression/return value (it now returns the same `Result<Response, DjangorsError>` type the
handler itself returns) instead of `let html = render_form(...); Ok(Response::html(StatusCode::OK, html))`.

## `ADMIN_TEMPLATES`: add the fifth entry

`("admin/render_form.html", include_str!("../templates/admin/render_form.html"))`.

## Known, accepted, non-blocking discrepancy (same as every prior 5.8.x slice)

`djangors_core::html_escape` renders `/` as `&#x2F;` (uppercase hex); minijinja's autoescape
renders it as `&#x2f;` (lowercase). Functionally identical in every browser, not byte-identical as
strings. Confirmed (by reading `test_admin_change_form_endpoints` directly) that none of its
values (`"New Added Row"`, `"Updated Row Name"`, the empty string, `"Field 'name' is required."`)
contain a literal `/`, so this does not affect this task's byte-identical-output requirement.
`'` is escaped identically by both (`&#x27;`) — confirmed by reading `djangors_core::html_escape`'s
source directly, not assumed.
