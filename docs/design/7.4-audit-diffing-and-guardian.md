## Part A — real field-level diffing for the audit log

**Read first**: `crates/djangors-admin/src/lib.rs`'s `LogEntry` struct (~line 747) and `log_action`
(~line 760), and grep the test module for every existing assertion against a literal
`change_message` string (e.g. `"Touch"`, `"Added."`, `"Changed."` — confirmed present at multiple
line numbers, search fresh since they may have shifted). **Those existing assertions must keep
passing unmodified** — do not change what `change_message` itself contains for any existing call
site. This is a deliberately **additive-only** change specifically to avoid the alternative
(rewriting `change_message` to be a real diff string) breaking a wide set of already-passing tests
for a benefit that can be had more safely.

Add a new **nullable** column/field to `LogEntry`: `field_diff: Option<String>` — a JSON-encoded
array of `{ "field": "...", "old": "...", "new": "..." }` entries, populated only for `CHANGE`
actions where the caller has both the pre-update and post-update field values available. Update
`log_action`'s signature to accept an optional diff (e.g. an added parameter
`field_diff: Option<Vec<(&str, String, String)>>` or similar — use your judgment on the cleanest
shape, but every **existing** call site that doesn't have diff data available should pass `None`
and see zero behavior change).

**Where real diff data is actually available**: `admin_change_post` (the handler that processes a
change-form submission) already has the submitted new values; check whether it already fetches the
pre-update row anywhere in its current flow (it likely needs to, to render error pages showing the
prior state, or it may only have the pk) — if it doesn't currently fetch the "before" row, add one
`SELECT`-by-pk immediately before applying the update (a small, real cost, but this is exactly the
point where diffing is meaningful) and compute which fields actually changed by comparing old vs.
new field values, building the `field_diff` from just the fields that differ (not every field —
Django's own admin diff only shows what changed).

Update the per-object History page (`admin_history`, ~line 2840-2900 per earlier grep — search
fresh) to render `field_diff` when present (a simple `<ul><li>field: old → new</li></ul>` block per
entry, gated on `{% if entry.field_diff %}` in `object_history.html` — read that template's current
structure first) — this is the "admin timeline view" showing real diffs, not just action labels.

**Required tests**: a new test proving a real change-form submission produces a `field_diff`
containing only the fields that actually changed (not unchanged ones), and that the History page
renders it. Every pre-existing audit-log test must still pass with **zero assertion changes** —
confirm this explicitly.

## Part B — `djangors-contrib-guardian` (new crate)

Django's `django-guardian`: per-OBJECT permission grants layered on top of the existing per-MODEL
permission system (`djangors_auth::has_perm`, already real — read
`crates/djangors-auth/src/lib.rs`'s `has_perm` function, ~line 385, for the exact existing
model-level check and its join-table pattern to mirror).

A new join table, following the *exact* same shape/convention as `UserPermission`/
`GroupPermission` in `djangors-auth` (plain FK ids, no real many-to-many ORM feature needed — this
project's established precedent):
```rust
#[derive(Model, Debug, Clone)]
#[djangors(app = "djangors_contrib_guardian", table_name = "djangors_object_permission")]
pub struct ObjectPermission {
    #[djangors(primary_key, auto)]
    pub id: i64,
    pub user: ForeignKey<djangors_auth::User>,
    pub permission: ForeignKey<djangors_auth::Permission>,
    #[djangors(max_length = 100)]
    pub app_label: String,
    #[djangors(max_length = 100)]
    pub model_name: String,
    pub object_id: i64,
}
```

```rust
/// Model-level OR object-level: true if `has_perm` already grants it, or if a specific
/// ObjectPermission row grants `codename` on this exact `(app_label, model_name, object_id)`.
pub async fn has_perm_for_object(
    db: &djangors_db::Database,
    user_id: i64,
    codename: &str,
    app_label: &str,
    model_name: &str,
    object_id: i64,
) -> Result<bool, djangors_auth::AuthError> {
    if djangors_auth::has_perm(db, user_id, codename).await? {
        return Ok(true);
    }
    // direct object-level grant check, joined against Permission by codename,
    // mirroring has_perm's own join-table query style/reserved-word quoting conventions
}
```

Also provide `grant_object_permission`/`revoke_object_permission` helpers (insert/delete an
`ObjectPermission` row) for a caller to manage grants programmatically.

**Deliberate v1 scope, document explicitly**: this crate does **not** wire itself into
`djangors-admin`'s existing `require_perm` automatically — that would mean changing a core,
heavily-tested admin permission-check path to be object-aware everywhere, a bigger, separate
change. Ship `has_perm_for_object` as a real, usable, tested function a project's own custom views
can call directly, and document (with a short example in the crate's module doc) how a project
would use it in a handler that needs per-object checks, the same "document the integration point,
don't auto-wire into every possible call site" pattern already used for
`djangors-contrib-messages` in 7.2.

**Required tests**: a real test proving `has_perm_for_object` returns `true` for a user with a
direct model-level grant (no object-level row needed), `true` for a user with only an
object-specific grant on the exact matching object, and `false` for a user with an object-specific
grant on a *different* object id (proving the object-scoping actually filters, not just checking
existence of any row).
