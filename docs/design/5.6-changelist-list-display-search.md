# 5.6 part 1 — Changelist customization: `list_display` + `search_fields`

**Status:** design, not yet dispatched. Follows 5.5 (delete confirmation, commit `aba0ff9`).
See `docs/design/phase-5-roadmap.md` for full Phase 5 context.

This is the first of several 5.6 parts. Per the roadmap's own sequencing, `list_display` and
`search_fields` are grouped together here because they share the one piece of new
infrastructure this slice actually needs: **a way to register a customized admin per model at
all** (today `AdminSite::register::<M>()` only ever produces the hardcoded, uncustomizable
`DefaultModelAdmin<M>` — every admin page for every model looks identical). `list_filter`,
`date_hierarchy`, `list_editable`, bulk actions, and saved views are explicitly OUT of scope
for this part and remain future 5.6 parts (2+).

**Computed-method columns are also explicitly out of scope for this part.** The roadmap doc's
phrasing groups "`list_display` (subset of fields + computed methods)" together, but a
computed-method column needs a closure stored per-admin (`fn(&M) -> String`), which is a
different, heavier mechanism than the `&'static [&'static str]` field-subset config this part
builds. `list_display` v1 here is **real field names only** (a subset and/or reorder of
`M::field_names()`), validated at registration time. Computed columns are a follow-up 5.6 part.

## The new registration API

```rust
// crates/djangors-admin/src/lib.rs
#[derive(Default, Clone)]
pub struct ModelAdminConfig {
    /// Subset/reorder of real field names to show as changelist columns.
    /// `None` = all fields, declaration order (today's only behavior).
    pub list_display: Option<&'static [&'static str]>,
    /// Real, text-like field names to ILIKE-match against `?q=`.
    /// `None` or empty = no search box rendered, `?q=` ignored if present.
    pub search_fields: Option<&'static [&'static str]>,
}

impl AdminSite {
    pub fn register<M: Model + djangors_orm::error::FromRow + Send + Sync + 'static>(&self) {
        self.register_with::<M>(ModelAdminConfig::default());
    }

    pub fn register_with<M: Model + djangors_orm::error::FromRow + Send + Sync + 'static>(
        &self,
        config: ModelAdminConfig,
    ) {
        let meta = M::meta();
        if let Some(list_display) = config.list_display {
            for name in list_display {
                assert!(
                    meta.fields.iter().any(|f| f.name == *name),
                    "list_display field '{}' does not exist on model '{}'",
                    name,
                    meta.struct_name
                );
            }
        }
        if let Some(search_fields) = config.search_fields {
            for name in search_fields {
                let field = meta.fields.iter().find(|f| f.name == *name).unwrap_or_else(|| {
                    panic!(
                        "search_fields field '{}' does not exist on model '{}'",
                        name, meta.struct_name
                    )
                });
                assert!(
                    matches!(
                        field.kind,
                        djangors_orm::meta::FieldKind::Char
                            | djangors_orm::meta::FieldKind::Text
                            | djangors_orm::meta::FieldKind::Email
                            | djangors_orm::meta::FieldKind::Url
                            | djangors_orm::meta::FieldKind::Slug
                            | djangors_orm::meta::FieldKind::Ip
                    ),
                    "search_fields field '{}' on model '{}' is not a text-like field",
                    name,
                    meta.struct_name
                );
            }
        }

        let mut reg = self.registry.lock().unwrap();
        reg.push(Arc::new(DefaultModelAdmin::<M> {
            config,
            _marker: PhantomData,
        }));
    }
}
```

Validation is a hard `assert!`/`panic!` at registration time (typically process startup, inside
an app's `admin.rs`/`admin_site()` function), not a `Result`. This mirrors Django's own
`admin.E108`-style system checks: a misconfigured `list_display`/`search_fields` referencing a
field that doesn't exist is a programmer error caught immediately at startup, not a runtime
condition any caller needs to handle gracefully. Do not make `register_with` fallible — every
existing call site (`examples/polls/src/admin.rs`, this crate's own tests) calls `register()`/
`register_with()` at setup time where a panic is exactly the right failure mode.

`DefaultModelAdmin<M>` changes from the current bare tuple struct `DefaultModelAdmin<M:
Model>(PhantomData<M>)` to a normal struct with a `config` field:

```rust
pub struct DefaultModelAdmin<M: Model> {
    config: ModelAdminConfig,
    _marker: PhantomData<M>,
}
```

There are exactly two existing construction sites to update (both already found by grep, no
others exist): `register()`'s internal `Arc::new(DefaultModelAdmin::<M>(PhantomData))` (becomes
the `register_with` body above) and one direct test construction, `DefaultModelAdmin::<ModelA>
(PhantomData)` around line 1443 of `crates/djangors-admin/src/lib.rs` in `#[cfg(test)] mod
tests` — update it to `DefaultModelAdmin::<ModelA> { config: ModelAdminConfig::default(),
_marker: PhantomData }`.

## `list_display`: changelist column projection

**Important scope boundary:** `list_display` affects the **changelist only**. It must NOT
affect the add/change form's field list (`ModelAdmin::field_names()`, used by `admin_add_get`/
`admin_change_get`/`admin_change_post`/`admin_add_post` via `render_form`) — Django's own
`list_display` doesn't touch the change form either, they're independent concerns. Do not
repurpose the existing `field_names()` trait method for this; leave it returning `M::
field_names()` (all fields) exactly as it does today.

The projection happens inside `DefaultModelAdmin::changelist()`, which currently hardcodes
`let columns = M::field_names();` and builds each row via `item.field_values().into_iter().map(|
(_, v)| v.to_string())`. Change it to:

```rust
async fn changelist(
    &self,
    db: &djangors_db::Database,
    order: Option<&str>,
    page: i64,
    per_page: i64,
    search: Option<&str>, // new parameter, see search_fields section below
) -> Result<ChangelistPage, DjangorsError> {
    let mut qs = M::objects();
    if let Some(o) = order { /* unchanged */ }
    if let (Some(term), Some(fields)) = (search, self.config.search_fields) {
        if !term.is_empty() {
            qs = qs
                .filter_or_icontains(fields, term)
                .map_err(|e| DjangorsError::Internal(e.to_string()))?;
        }
    }
    let total = /* unchanged, but must apply the same search filter — see note below */;
    // ... limit/offset/all() unchanged ...

    let columns: Vec<&'static str> = self
        .config
        .list_display
        .map(|cols| cols.to_vec())
        .unwrap_or_else(M::field_names);

    let mut rows = Vec::new();
    for item in &items {
        let field_values = item.field_values(); // Vec<(&'static str, Value)>
        let row_vals: Vec<String> = columns
            .iter()
            .map(|col| {
                field_values
                    .iter()
                    .find(|(name, _)| name == col)
                    .map(|(_, v)| v.to_string())
                    .unwrap_or_default()
            })
            .collect();
        rows.push(row_vals);
    }

    Ok(ChangelistPage { columns, rows, total, page, per_page })
}
```

**Note on `total`:** the existing `count(db)` call for `total` must go through the *same*
search filter as the row query, or the pagination total will overcount when a search term is
active (Django has this exact requirement — the count in "1-100 of 500" must reflect the
filtered set, not the whole table). Build the filtered `QuerySet` once, clone it before adding
`.limit()`/`.offset()`, and call `.count(db)` on the clone — check whether `QuerySet` already
derives `Clone` (grep for `impl<T: Model + FromRow> Clone for QuerySet<T>` in queryset.rs — it
does, confirmed at ~line 55) before writing new count logic. Do not compute `total` from
`M::objects().count(db)` unconditionally like today's code does — that line must also gain the
search filter.

## `search_fields`: a new generic `QuerySet` method

The existing `filter()` only accepts `UnresolvedExpr::And(Vec<UnresolvedCompare>)` — always
AND, always `Eq` (or a `__suffix` lookup on ONE field per compare). A search box needs "field1
ILIKE %term% OR field2 ILIKE %term% OR ...", which the underlying `Expr` enum (queryset.rs,
`use crate::expr::{..., Expr, ...}`) already fully supports (`Expr::Or`, `CompareOp::IContains`
— confirmed both are already compiled correctly by the existing `compile_expr_sql` function,
~line 806-880) but which `UnresolvedExpr`/`filter()` doesn't expose a way to construct. Add one
new method, right next to `filter()`:

```rust
/// ILIKE-matches `term` against every field in `fields`, OR'd together, ANDed
/// with any other filters already applied. Every name in `fields` must be a
/// real field on `T` (relations are not searchable this way — no `field_to_col`
/// mapping ambiguity to worry about since relation values aren't text).
pub fn filter_or_icontains(
    mut self,
    fields: &[&'static str],
    term: &str,
) -> Result<Self, OrmError> {
    let meta = T::meta();
    let mut compares = Vec::new();
    for field_name in fields {
        if !meta.fields.iter().any(|f| f.name == *field_name) {
            return Err(OrmError::FieldNotFound {
                field: field_name.to_string(),
                model: meta.struct_name,
            });
        }
        compares.push(Expr::Compare {
            field: field_name,
            op: CompareOp::IContains,
            value: Value::Text(term.to_string()),
        });
    }
    self.filters.push(Expr::Or(compares));
    Ok(self)
}
```

Pass the raw `term` as `Value::Text(term.to_string())` — do **not** wrap it in `%...%` yourself,
`compile_expr_sql`'s `CompareOp::IContains` arm already does that (see the existing match arm:
`Value::Text(t) => format!("%{}%", t)`). Wrapping it twice would search for literal `%` chars.

This method takes `fields: &[&'static str]` (a slice, not `Vec`) since the caller
(`DefaultModelAdmin::changelist`) already has `self.config.search_fields: Option<&'static
[&'static str]>` and shouldn't need to allocate a `Vec` just to call this. `filter()` next to it
takes an owned `UnresolvedExpr` for an unrelated historical reason (the `q!{}` macro builds one)
— don't change `filter()`'s signature to match, they're different call shapes for different
callers, that's fine.

**Field existence validation only** — this method does not re-validate "is this a text-like
field", because that's already guaranteed by `register_with`'s registration-time `assert!`
(above) for every real caller (`DefaultModelAdmin`). A generic ORM-level method shouldn't
duplicate a check its only real caller already performs; if `filter_or_icontains` ever gets a
second caller that skips that check, ILIKE against a non-text column will just produce a
Postgres type error at query time, which is an acceptable failure mode for a generic method
whose contract is "you called this on the right kind of field."

## `ModelAdmin` trait changes

Two changes: `changelist()` gains the `search: Option<&str>` parameter (shown above), and one
new required method:

```rust
fn search_fields(&self) -> &[&'static str]; // empty = no search box
```

`DefaultModelAdmin` implements it as `self.config.search_fields.unwrap_or(&[])`.

## Route handler + rendering changes

`admin_changelist` (`crates/djangors-admin/src/lib.rs`): read `let q = req.query("q");` next to
the existing `let o = req.query("o");`, pass it through to `admin.changelist(db, o, page,
per_page, q)`.

Rendering additions to the changelist HTML (same plain-`format!` style as the rest of the page,
no templating engine yet):
- If `admin.search_fields()` is non-empty, render a search box above the table:
  `<form method="get"><input type="text" name="q" value="{escaped current q}"> <input
  type="submit" value="Search"></form>`. Preserve the current sort order (`?o=`) across a
  search submission if practical, but do not treat that as a hard requirement — Django itself
  drops other query params on a plain GET form submit unless they're hidden inputs; adding
  `<input type="hidden" name="o" value="...">` when `o` is set is a reasonable nice-to-have, not
  required for this part to be considered done.
- Column headers (`<th>`) already iterate `page_data.columns` — no change needed there, they'll
  automatically reflect `list_display`'s projection since `columns` now comes from the admin's
  config instead of being hardcoded to `M::field_names()`.
- **The changelist row-link logic breaks once `list_display` can exclude the pk field — fix
  this as part of this task, it is not optional.** Today (`admin_changelist`, ~line 631-667)
  the first cell's edit link is built by finding the pk field's position within
  `page_data.columns` (`pk_col_idx = page_data.columns.iter().position(|&col| col ==
  pk_field_name)`) and reading that value back out of the row itself. That's only correct
  because `columns` is currently always *all* fields, so the pk is always present. Once
  `list_display` can produce a `columns` list that omits the pk, `pk_col_idx` becomes `None`
  and the existing fallback (`else { String::new() }`) silently produces a broken link
  (`<a href="/change/">`, empty pk prefix) instead of erroring — a real, easy-to-miss
  regression, not a hypothetical edge case, since "don't show the id column" is one of the
  most common real `list_display` configs. Fix it by not depending on the pk being a
  *displayed* column at all:
  - Add `pub pks: Vec<String>` to `ChangelistPage` (parallel array to `rows`, one entry per
    row, always the pk value regardless of whether the pk field is in `columns`).
  - In `DefaultModelAdmin::changelist()`, populate it alongside `rows` from the same
    `item.field_values()` call already being projected down to `columns` — look up the pk
    field's value from the *unprojected* `field_values` for each item, not from `columns`.
  - In `admin_changelist`, build each row's edit link from `page_data.pks[row_index]` instead
    of the current `pk_col_idx`/`row.get(idx)` dance. Delete the now-unnecessary
    `pk_field_name`/`pk_col_idx` lookup entirely — it's fully superseded by `pks`.
  - Add a test asserting this explicitly: `list_display` that excludes the pk field still
    produces a working, non-empty edit link in the response body (part of test #1 below, not
    a separate test).

## What NOT to touch in this task

- No `list_filter`, `date_hierarchy`, `list_editable`, bulk actions, CSV/XLSX export, or saved
  views — all separate, later 5.6 parts.
- No computed-method columns for `list_display` — real field names only, as explained above.
- No changes to `render_form`, the add/change routes, or the delete confirmation routes.
- No changes to `examples/polls/src/admin.rs` beyond what's needed to prove the feature works —
  a small, optional addition (e.g. giving `Question` a `list_display`/`search_fields` config)
  is welcome as a real usage example but is not required; do not go further and add
  configuration to every model just to exercise the feature everywhere.

## Required tests

Add to `crates/djangors-admin/src/lib.rs`'s existing `#[cfg(test)] mod tests` (same
Postgres-backed socket-level style as every other admin test — `DB_MUTEX` guard, real `CREATE
TABLE`/`DROP TABLE IF EXISTS` against `postgres://postgres:postgres@localhost/djangors_test`):

1. `register_with` with a `list_display` subset that **excludes the pk field** (e.g. 2 of a
   3-field model's non-pk fields, in a non-declaration order) → changelist response's `<th>`
   headers and row cells reflect only those columns, in the configured order; declaration-order
   fields NOT in `list_display` do NOT appear as column headers; AND the row's edit link
   (`<a href="{pk}/change/">`) still contains the correct, non-empty pk value even though the
   pk column itself isn't displayed. This last assertion is the one that catches the `pks`
   fix above if the dispatch skips it — don't drop it.
2. `register_with` with a `list_display` naming a field that doesn't exist on the model → the
   registration call itself panics (use `std::panic::catch_unwind` or `#[should_panic]` on a
   dedicated small test, following whatever pattern is idiomatic here — check if this crate or
   any sibling crate already has a `#[should_panic]` test to match style before picking one).
3. `register_with` with `search_fields` naming a non-text field (e.g. an `i64` field) → panics,
   same style as #2.
4. `search_fields` configured, `?q=` matching a substring of one row but not another (case-
   insensitive — assert a differently-cased query string still matches) → changelist response
   contains only the matching row, and the pagination/count reflects the filtered total, not
   the whole table (insert at least 3 rows, 1-2 matching, so an unfiltered-count bug would be
   observable — this is the test that catches the `total` note above if the dispatch gets it
   wrong).
5. `search_fields` configured but `?q=` omitted → all rows still show (unfiltered).
6. No `search_fields` configured (default `ModelAdminConfig`) but `?q=something` is passed
   anyway → no error, `q` is silently ignored, all rows show (confirms the "ignored if not
   configured" behavior explicitly, don't just assume it from #5).
