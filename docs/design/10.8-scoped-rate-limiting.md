# 10.8 — named, scoped rate limiting per endpoint

## Scope

Item #5 of the architecture-parity initiative (see `/root/.claude/plans/concurrent-inventing-glacier.md`
for the full roadmap; items 1, 2, 3, 4, 6, 8 are already done). Today the only rate limiter in the
codebase is `crates/djangors-auth/src/lib.rs`'s `RateLimitedBackend<B: AuthBackend>` — a decorator
around auth backends using an in-memory `Mutex<HashMap<String, Vec<Instant>>>`, per-username only,
not wired into any example app. There is no generic "rate limit any endpoint" mechanism.

**Deliberately excluded**: migrating `RateLimitedBackend` onto this new primitive — leave it
completely untouched, this is a separate, already-shipped code path; distributed/linearizable
exact-counting guarantees — a `RedisCache`-backed limiter is "best effort" under concurrency, not
provably exact, and that's an acceptable, explicitly-stated tradeoff, not a bug to chase; making
any route rate-limited by default — this must stay strictly opt-in, per every prior item's
purely-additive constraint; a generic per-route metadata table on `Router`/`Route` itself — bigger
than this item warrants, mirror the existing per-handler-wrapper pattern instead (see below).

**A real, confirmed gap you must design around, not paper over**: this codebase does NOT
currently expose the real socket peer address to request handlers anywhere — `crates/djangors-core/src/app.rs`'s
connection-accept loop captures `_peer_addr` and explicitly discards it (prefixed with `_`,
confirmed by direct inspection), and `Request` has no stored client-IP field. This means a `ByIp`
rate-limit key strategy can only be header-based (`X-Forwarded-For`/`X-Real-IP`), which is
spoofable by any client not sitting behind a trusted reverse proxy that actually sets those headers
itself. **Document this limitation plainly in the `ByIp` type's own doc comment** — don't silently
implement it as if it were a secure, unspoofable identifier; a project deploying without a trusted
proxy in front of it needs to know this before relying on `ByIp` for anything security-sensitive.

## The real design

Add a new module, e.g. `crates/djangors-core/src/ratelimit.rs`, exported from `lib.rs` — NOT a
`tower::Layer` wrapping the whole router (the same reasoning that already rejected this approach
for CSRF and login rate limiting in `docs/design/4.12-auth-rate-limit-signals.md`: a
router-wrapping layer can't cheaply see per-route/per-handler identity or a parsed request body).

```rust
/// A strategy for deriving the identity a rate limiter counts against from a request.
#[async_trait::async_trait]
pub trait RateLimitKey: Send + Sync {
    async fn key(&self, req: &Request) -> String;
}

/// Keys by the `X-Forwarded-For` (falling back to `X-Real-IP`) header. See the module-level
/// note: this is NOT a secure client-IP identifier unless the app is genuinely deployed behind a
/// trusted reverse proxy that sets this header itself and strips any client-supplied value —
/// document this exact caveat on this type's own doc comment.
pub struct ByIp;

/// Keys by the authenticated user's id (via the existing `djangors_auth::Auth`/`AuthUser`
/// extraction already used elsewhere in this codebase — check `djangors-rest`'s `IsAuthenticated`
/// for the exact extraction call to reuse). Requests with no authenticated user are rejected
/// (`DjangorsError::Unauthorized`) rather than silently falling back to an unscoped/global key.
pub struct ByAuthenticatedUser;

/// A named, scoped rate limiter. `name` scopes cache keys so two independently-configured
/// limiters never interfere with each other even if applied to requests with the same
/// `RateLimitKey` value.
pub struct RateLimiter<K: RateLimitKey> {
    name: &'static str,
    key_fn: K,
    max_attempts: u32,
    window: std::time::Duration,
    store: std::sync::Arc<dyn djangors_cache::Cache>,
}

impl<K: RateLimitKey> RateLimiter<K> {
    pub fn new(
        name: &'static str,
        key_fn: K,
        max_attempts: u32,
        window: std::time::Duration,
        store: std::sync::Arc<dyn djangors_cache::Cache>,
    ) -> Self { ... }

    /// Checks and records one attempt for `req`'s derived key. Returns
    /// `Err(DjangorsError::TooManyRequests(..))` if the limit is exceeded.
    pub async fn check(&self, req: &Request) -> Result<(), DjangorsError> { ... }
}
```

`djangors_cache::Cache`'s real methods (`crates/djangors-cache/src/lib.rs:27-35`, confirmed):
`async fn get(&self, key: &str) -> Result<Option<Vec<u8>>, CacheError>`, `async fn set(&self, key:
&str, value: Vec<u8>, ttl: Option<Duration>) -> Result<(), CacheError>`, `async fn delete(&self,
key: &str) -> Result<(), CacheError>` — **no atomic increment**. `RateLimiter::check`'s
implementation is necessarily a read-then-write over these primitives (deserialize a count +
window-start timestamp from the cached bytes, or start fresh if absent/expired, increment, write
back with `ttl: Some(window)`). This has a real, unavoidable race window under concurrent requests
from the same key within the same tick when the underlying `Cache` impl doesn't serialize
writes internally (`InMemoryCache`'s Moka backend can still interleave two concurrent
get-then-set sequences). **State this tolerance explicitly**: the guarantee is "never silently
allows unbounded requests through" (a broken implementation would always read a stale `0` and let
everything past), not "exactly `max_attempts`, never one more" under concurrent load — that's an
acceptable, deliberately-chosen tradeoff for a v1 in-process/best-effort limiter, not a bug.

**`DjangorsError` needs one new variant** — there is no 429-class variant today (confirmed: only
`NotFound`/`BadRequest`/`Internal`/`Panicked`/`Unauthorized`/`Forbidden` exist in
`crates/djangors-core/src/error.rs`). Add `TooManyRequests(String)`, mapping to
`StatusCode::TOO_MANY_REQUESTS` in `status_code()`. This is an exhaustive-match enum — the
compiler will point you at every match site that needs updating when you add the variant (at
minimum `error.rs`'s own `Display`/`status_code`/`into_response`/`code`/`message` methods and
`debug_page.rs`'s `render_debug_page` match); update all of them, don't leave any wildcard
`_ => ...` catch-all that would silently swallow the new variant with the wrong status/message.

Mount per-handler via a wrapper function mirroring `djangors-rest`'s existing `guarded()` pattern
exactly (`crates/djangors-rest/src/lib.rs:1661-1676` — read it in full, it's a short, direct
template: wraps a handler closure, checks a condition first, returns an error or delegates):

```rust
pub fn rate_limited<K, F, Fut>(
    limiter: std::sync::Arc<RateLimiter<K>>,
    handler: F,
) -> impl djangors_core::Handler
where
    K: RateLimitKey + 'static,
    F: Fn(Request, PathParams) -> Fut + Copy + Send + Sync + 'static,
    Fut: std::future::Future<Output = Result<Response, DjangorsError>> + Send + 'static,
{ ... }
```

Applied at route-registration time (e.g. `router.get("/login", rate_limited(limiter, login_handler))`),
not stored on `Router`/`Route` itself.

## Required verification

- **Concurrency race under load**: spawn N (e.g. 20) concurrent requests from the same
  `RateLimitKey` value against `max_attempts = 5` within one `InMemoryCache`-backed limiter —
  assert it never silently allows unbounded requests through (a real regression test for the exact
  failure mode described above: a naive get-then-set race always reading stale `0`), while
  explicitly NOT asserting an exact count under concurrency (document why in the test's own
  comment, per the stated tolerance above).
- **Scoping isolation**: two `RateLimiter`s with different `name`s but the SAME underlying
  `RateLimitKey` value must not interfere — exhausting one must not affect the other's remaining
  budget. This is the actual "named, scoped" guarantee the item is named for; test it directly.
- **Window expiry correctness against real elapsed time** (not a mocked clock): use a short real
  window (e.g. 200ms), exhaust the limit, wait past the window, confirm a new request succeeds.
- **`ByAuthenticatedUser` rejects unauthenticated requests** outright (`DjangorsError::Unauthorized`)
  rather than silently falling back to some shared/global key.
- A real end-to-end test through a mounted route (`Router::handle`, `rate_limited(...)` wrapping a
  simple handler) proving a request over the limit gets a real `429 Too Many Requests` response.
- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace` all clean — run these yourself and report
  the real results; if piped through anything, remember a bare `| tail` reports the pipe's own
  exit code, not cargo's.
