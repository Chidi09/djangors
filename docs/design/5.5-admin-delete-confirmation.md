# 5.5 — Admin delete confirmation

**Status:** design, not yet dispatched. Follows 5.4 (change form, commit `9f016fe`). See
`docs/design/phase-5-roadmap.md` for full Phase 5 context.

## What this builds

Two routes per registered model, mirroring the add/change route pair from 5.4:

- `GET /{app:slug}/{model:slug}/{pk:i64}/delete/` — confirmation page. Shows the object's
  display representation and a warning list of *other* registered models that have rows
  pointing at it via a foreign key, with counts.
- `POST /{app:slug}/{model:slug}/{pk:i64}/delete/` — performs the delete, redirects to the
  changelist on success.

Changelist rows (5.2/5.4) are not modified in this slice — no delete link/button is added
there. That's a `list_display`/actions-row concern that belongs with 5.6, not this slice; v1
of delete confirmation only needs its own two routes to exist and be reachable directly.

## The core problem this task solves, and why it does NOT touch the derive macro

Same shape as 5.4's `insert_raw()` reasoning: the derive-generated `delete(&self, db)`
(`crates/djangors-macros/src/model.rs`, ~line 668) requires a full typed `&self` instance.
The admin only has a `pk: i64` and a `&'static ModelMeta` (via `Arc<dyn ModelAdmin>`) — no
typed instance, and getting one would mean an extra `SELECT` purely to satisfy the macro's
signature. Add one new generic method instead of touching the macro:

```rust
// crates/djangors-orm/src/queryset.rs, impl block for QuerySet<T>
pub async fn delete_by_pk(
    db: &djangors_db::Database,
    pk: i64,
) -> Result<u64, OrmError> {
    let meta = T::meta();
    let pk_field = meta
        .fields
        .iter()
        .find(|f| f.primary_key)
        .expect("Primary key field not found");

    let sql = format!("DELETE FROM {} WHERE {} = $1", meta.table_name, pk_field.column_name);
    let res = sqlx::query(sqlx::AssertSqlSafe(sql))
        .bind(pk)
        .execute(db.pool())
        .await
        .map_err(OrmError::from)?;
    Ok(res.rows_affected())
}
```

This is a direct sibling of `insert_raw` (`queryset.rs` ~line 566): an associated function
(no `self`), built purely from `T::meta()`, following the exact same
`sqlx::query(sqlx::AssertSqlSafe(sql))` + `db.pool()` pattern already used throughout this
file (see `update()` ~line 452 and `filter().get()` for the surrounding conventions). No
`Value::Null` bind path is touched — `pk` is always a plain `i64` bind — so the
`null_bind_kind_for()` machinery from 5.3/5.4 is irrelevant here and must not be copied in
just for symmetry.

`rows_affected() == 0` means "no such pk"; the caller maps that to 404, exactly like
`get_by_pk` already does via `OrmError::NotFound`.

## Related-object collection: use the `inventory`-based global registry

Django's delete confirmation page walks *every model in the project* to find rows that
reference the object being deleted, not just models registered with this particular
`AdminSite`. This codebase already has the right mechanism for that, unrelated to the admin
registry entirely: `djangors_orm::meta::all_registered_models()` —

```rust
// crates/djangors-orm/src/meta.rs, already present, unmodified by this task
pub struct ModelRegistration {
    pub meta_fn: fn() -> &'static ModelMeta,
}
inventory::collect!(ModelRegistration);
pub fn all_registered_models() -> impl Iterator<Item = &'static ModelMeta> {
    inventory::iter::<ModelRegistration>().map(|r| (r.meta_fn)())
}
```

Every `#[derive(Model)]` struct anywhere in the final binary registers itself here at
compile/link time (see `crates/djangors-orm/src/tests.rs` ~line 115-162 for existing usage
and `test_inventory_registration` for proof this actually works). This is exactly what the
confirmation page needs and is *not* scoped to `AdminSite`'s own `Mutex<Vec<Arc<dyn
ModelAdmin>>>` registry — a model doesn't need to be admin-registered to show up as a
dependent, which matches Django's own behavior (it walks the whole app registry, not just
`admin.site`).

### The FK column-name convention already in this ORM

`RelationMeta { field_name, kind, target, on_delete, related_name }` (meta.rs ~line 137) has
**no separate SQL column name** — every other read site in `queryset.rs` (`update()`,
`filter()`, `insert_raw()`, etc., see the `r.field_name.to_string()` pattern used at ~line 129,
177, 360, 490, 586) uses `r.field_name` directly as the column name. Confirmed against real
models: `examples/polls/src/models.rs` has `pub question: ForeignKey<Question>` and the
column is literally named `question`, no `_id` suffix. The related-object query must follow
this exact same convention — do not invent a `{field_name}_id` column name.

### The collection function

New free function in `crates/djangors-admin/src/lib.rs` (not a `ModelAdmin` trait method — it
needs no typed `Self`, only a `&'static ModelMeta` and a `pk`, so it has no reason to go
through the trait):

```rust
pub struct RelatedObjectSummary {
    pub app_label: &'static str,
    pub struct_name: &'static str,
    pub field_name: &'static str,
    pub on_delete: djangors_orm::meta::OnDelete,
    pub count: i64,
}

async fn collect_related_objects(
    db: &djangors_db::Database,
    target_meta: &'static ModelMeta,
    pk: i64,
) -> Result<Vec<RelatedObjectSummary>, DjangorsError> {
    let mut summaries = Vec::new();
    for related_meta in djangors_orm::meta::all_registered_models() {
        for relation in related_meta.relations {
            if (relation.target)().table_name != target_meta.table_name {
                continue;
            }
            let sql = format!(
                "SELECT COUNT(*) FROM {} WHERE {} = $1",
                related_meta.table_name, relation.field_name
            );
            let count: i64 = sqlx::query_scalar(sqlx::AssertSqlSafe(sql))
                .bind(pk)
                .fetch_one(db.pool())
                .await
                .map_err(|e| DjangorsError::Internal(e.to_string()))?;
            if count > 0 {
                summaries.push(RelatedObjectSummary {
                    app_label: related_meta.app_label,
                    struct_name: related_meta.struct_name,
                    field_name: relation.field_name,
                    on_delete: relation.on_delete,
                    count,
                });
            }
        }
    }
    Ok(summaries)
}
```

Notes on scope, to keep this a v1:
- **Compare by `table_name`, not `struct_name`.** Two apps could plausibly have same-named
  structs; table names are the actual unique DB identity and `ModelMeta` already carries one.
- **Counts only, not object listings.** Django lists the actual related objects (with links).
  Doing that generically would need a "render this row's `__str__`-equivalent" call per
  related model, which is exactly `Model::field_values()` — but that requires a **typed**
  fetch of the related rows, and building a fully generic "fetch N rows of an unknown model
  type by FK value" path is real new surface area with its own edge cases (which columns to
  show, pagination if the count is huge, etc). Counts-only is the honest v1 scope and is
  explicitly what the roadmap doc already commits to ("v1 can list direct FK dependents
  only"). Upgrading counts to real object links is a natural 5.6/5.8 follow-up once the
  changelist customization work (5.6) already has to solve "render a row from
  `ModelMeta` + arbitrary filter" for `list_filter`/search anyway.
- **One hop only.** No transitive walk (X → Y → Z). Django does walk transitively; skipping
  it here is a deliberate, documented v1 cut, not an oversight.
- **`on_delete` is surfaced for display, still not enforced.** Per the roadmap ledger,
  `OnDelete` metadata exists but nothing in the ORM enforces it at delete time. This slice
  does not change that. The confirmation page shows the declared `on_delete` value next to
  each dependent count (e.g. "3 Choice rows reference this Question (on_delete: Cascade)")
  purely as information for the staff user — it is not a guarantee of what will actually
  happen. What actually happens on POST is whatever the real Postgres schema's FK constraint
  does (which, since there are no real migration files yet — `dj makemigrations` is still a
  stub — is whatever raw SQL happened to declare it, inconsistent across examples/tests
  already, and out of scope to fix here). If the DB itself rejects the delete (FK constraint
  violation because there's no `ON DELETE CASCADE`/`SET NULL` at the schema level), that
  surfaces as a normal `DjangorsError::Internal` from `delete_by_pk`'s `sqlx` call — no special
  "PROTECT" UI is built for that in v1; it just renders as an error page. Do not attempt to
  pre-check `on_delete == Protect` and block the POST in Rust — that would imply an
  enforcement guarantee this codebase doesn't actually have (the DB schema might not even
  match the declared `on_delete` value, since there's no migration system tying them
  together yet), which is worse than not pretending to enforce it at all.

## `ModelAdmin` trait: one new method

```rust
async fn delete_by_pk(
    &self,
    db: &djangors_db::Database,
    pk: i64,
) -> Result<bool, DjangorsError>; // false = no such pk (404), true = deleted
```

`DefaultModelAdmin<M>` implements it as a one-line call into the new generic:

```rust
async fn delete_by_pk(&self, db: &djangors_db::Database, pk: i64) -> Result<bool, DjangorsError> {
    let rows = djangors_orm::queryset::QuerySet::<M>::delete_by_pk(db, pk)
        .await
        .map_err(|e| DjangorsError::Internal(e.to_string()))?;
    Ok(rows > 0)
}
```

(Match whatever the existing `QuerySet` import path is in this file — check how `insert_raw`
or `M::objects()` is already referenced in `lib.rs` and follow that, don't introduce a new
import style.)

`get_by_pk` already exists (5.4) and is reused as-is for rendering the object's display
representation on the GET confirm page — same `Vec<(&'static str, Value)>` shape already used
by the change form, no new fetch method needed for that part.

## Routes and handlers

Two new routes registered in `AdminSite::urls()`, following the exact closure-capture pattern
already used for add/change (see `urls()` ~line 481-528 — every admin snapshot is cloned into
its own named `Vec<Arc<dyn ModelAdmin>>` per route to satisfy the closure capture, e.g.
`delete_get_admins`, `delete_post_admins`):

```rust
.get(
    "/{app:slug}/{model:slug}/{pk:i64}/delete/",
    move |req: Request, params: PathParams| {
        admin_delete_get(req, params, delete_get_admins.clone())
    },
)
.post(
    "/{app:slug}/{model:slug}/{pk:i64}/delete/",
    move |req: Request, params: PathParams| {
        admin_delete_post(req, params, delete_post_admins.clone())
    },
)
```

Handlers follow the established shape byte-for-byte (`require_staff`, look up the admin by
`app`+`model` slug from `params`, pull `Database` from `req.state::<djangors_db::Database>()`,
parse `pk` via `params.get_as::<i64>("pk")` — see `admin_change_get`/`admin_change_post` at
~line 740-835 for the reference pattern to copy):

- `admin_delete_get`: look up admin → `get_by_pk` (404 if `None`) → `collect_related_objects`
  → render a plain `format!` HTML page (matches every other admin page pre-5.8 theming):
  object's fields/values (reuse the same rendering approach as the change form's readonly
  display, or a simpler flat list — this is a confirmation page, not an edit form, so it does
  **not** need `render_form`'s input-widget machinery, just html-escaped label/value pairs),
  then a `<ul>` of related-object warnings if any, then a `<form method="post">` with a single
  submit button (no other inputs — there's nothing to validate, unlike add/change).
- `admin_delete_post`: look up admin → `delete_by_pk` → `false` maps to 404, `true` redirects
  to `/{app}/{model}/` (same redirect target the add/change POSTs already use on success).

All values in the GET page must go through `djangors_core::html_escape` before interpolation,
same as every other admin page (`lib.rs` ~line 360, 370, 414, 631) — this is a hard requirement
already established project-wide, not new to this slice.

## CSRF note (do not re-litigate, just inherit the existing gap)

The delete confirmation's `<form method="post">` has the exact same CSRF exposure already
documented for the add/change forms (5.4 ledger entry, `phase-5-roadmap.md`): header+cookie
double-submit only, no body-field token support, so a plain browser POST needs client-side JS
to supply `X-CSRFToken`. Do not add a hidden `csrfmiddlewaretoken` input here either — same
reasoning as 5.4 (would look like protection without being checked by the middleware). This is
already tracked centrally; this slice does not need its own ledger entry beyond noting the
delete route now also carries the same known gap.

## What NOT to touch in this task

- No changes to the derive macro (`djangors-macros`) — this task's whole point is proving the
  same "no macro needed" pattern insert_raw already proved for INSERT works for DELETE too.
- No changelist delete button/action — that's 5.6 scope (bulk actions).
- No `on_delete` enforcement logic anywhere in the ORM — display-only, per above.
- No transitive (multi-hop) related-object walk.
- No changes to `render_form` — the confirmation page is not a form with fields, don't force
  it through that function.

## Required tests

Following the pattern already established in `lib.rs`'s `#[cfg(test)] mod tests` (see the
existing `test_admin_change_form_endpoints` for the shape to copy — real Postgres-backed
socket-level tests against `postgres://postgres:postgres@localhost/djangors_test`):

1. GET delete confirm page for an existing pk as staff → 200, body contains the object's
   display value(s) (html-escaped).
2. GET delete confirm page for a nonexistent pk → 404.
3. Unauthenticated GET → 401. Non-staff GET → 403 (mirror the existing add/change auth tests).
4. POST delete for an existing pk with no dependents → 302 redirect to the changelist, row is
   actually gone from the DB afterward (verify via a direct query or via a subsequent
   changelist fetch).
5. POST delete for a nonexistent pk → 404.
6. **Related-object collection test.** `djangors-admin/src/lib.rs`'s own `#[cfg(test)] mod
   tests` (~line 838-863) already defines `ModelA`/`ModelB` (`admin_test` app, `test_model_a`/
   `test_model_b` tables) with no relation between them — add a third fixture model, e.g.
   `ModelC { id, parent: ForeignKey<ModelA> }` (`table_name = "test_model_c"`), in the same
   test module, register it too, `CREATE TABLE`/`DROP TABLE IF EXISTS test_model_c` alongside
   the existing `test_model_a`/`test_model_b` setup. Insert a `ModelA` row, insert a `ModelC`
   row with `parent` pointing at it, GET `ModelA`'s delete confirm page, assert the response
   body mentions `ModelC`/`test_model_c` and a count of `1`. This is the test the design
   itself is really about — don't skip it in favor of only testing the delete-with-no-
   dependents path, since the whole point of this slice beyond `insert_raw`'s already-proven
   DELETE-by-pk pattern is the related-object collection via the `inventory` registry.
