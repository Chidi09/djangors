# Design 5.3 — `dj createsuperuser` (real) + wire the admin into examples/polls (Phase 5 part 3)

**Status:** draft, pre-implementation. Two small, tightly-related slices that together make the
admin usable end-to-end for the first time: today there is no way to create a staff user except
raw SQL, and no example app actually mounts an `AdminSite`. After this task: `dj createsuperuser`
creates a real staff+superuser row, and `examples/polls` serves a real `/admin/` with `Question`
and `Choice` registered — index page plus the 5.2 changelist, staff-gated.

## Slice A — `dj createsuperuser` becomes real

`crates/djangors-cli/src/commands.rs` `createsuperuser()` is a println stub; `Commands::
Createsuperuser` (`cli.rs` line ~50) takes no args. The `migrate()` command in the same file is
the established real-command pattern to copy exactly: `DATABASE_URL` env var → `djangors_db::
Database::connect` → act → `eprintln!` + `std::process::exit(1)` on failure.

**v1 scope decision: non-interactive only.** Django's `createsuperuser --noinput` reads
`DJANGO_SUPERUSER_PASSWORD` from the environment; mirror that and *only* that. No interactive
prompting (a hidden-input password prompt needs a new dependency like `rpassword` and is
untestable in CI) — document interactive mode as deferred in the command's doc comment.

- `Commands::Createsuperuser` gains clap args: `--username <String>` (required),
  `--email <String>` (optional, default empty string).
- Password comes from the `DJANGORS_SUPERUSER_PASSWORD` environment variable. Unset or empty →
  clear error message naming the variable, exit 1.
- Implementation (`commands.rs`, async like `migrate`): connect via `DATABASE_URL`; refuse
  duplicate usernames (`User::objects().filter(q!(username = ...))` exists check → error message,
  exit 1); hash via `djangors_auth::hash_password` (lib.rs line ~327, argon2); insert via the real
  model: `djangors_auth::User { id: 0, username, email, password: hash, is_active: true,
  is_staff: true, is_superuser: true, date_joined: Utc::now(), last_login: None }.save(&db)`;
  print the created username on success.
- New deps for `djangors-cli`: `djangors-auth` (path), `djangors-orm` (path, for `q!`/QuerySet if
  not already present), `chrono` — check `Cargo.lock` for already-resolved versions before
  pinning (chrono 0.4.45); `djangors-db` and tokio are already there.
- `main.rs`: route the new args through; the match arm becomes async like `Migrate`'s.

**Tests** (in `djangors-cli`, real Postgres, same `postgres://postgres:postgres@localhost/
djangors_test` + raw-SQL `CREATE TABLE auth_user` pattern as `crates/djangors-admin/src/lib.rs`
tests — copy its exact auth_user DDL): factor the command's core into a testable
`pub async fn create_superuser_impl(db: &Database, username: &str, email: &str, password: &str)
-> Result<(), String>` (or similar) that the clap-facing wrapper calls after reading env —
tests call the impl directly, avoiding env-var/process-exit machinery. Cases: creates a user
with `is_staff && is_superuser` true and an argon2 hash that `djangors_auth::verify_password`
(check the real fn name in auth's lib.rs) accepts; duplicate username → Err. Plus one pure clap
parse test for the new args mirroring `cli.rs`'s existing `test_parse_*` tests. Use a `DB_MUTEX`
static if the crate gains more than one DB test touching `auth_user` (the admin crate's tests
also use `auth_user`, but test *processes* are per-crate, so only intra-crate serialization is
needed).

## Slice B — mount the admin in examples/polls

- `examples/polls/src/urls.rs` (or `main.rs` — pick `urls.rs` so the mounted router is covered by
  the existing integration-test route table too; check how `tests/voting.rs` builds its router —
  if it calls `urls::urls()`, putting the mount there gets test coverage for free):
  `AdminSite::new()`, `site.register::<Question>()`, `site.register::<Choice>()`,
  `.mount("/admin", site.urls())`. Both models already derive `Model` + `FromRow` (FK `Choice`
  works — `select_related` tests prove FK models roundtrip through QuerySet).
- `examples/polls/Cargo.toml`: add `djangors-admin` path dependency.
- Delete or update `examples/polls/src/admin.rs` if it exists as an aspirational placeholder —
  check first; if it's dead aspirational code, replace its contents with the real registration
  helper (e.g. `pub fn admin_site() -> AdminSite`) called from `urls.rs`, so the file matches
  Django's `admin.py` convention instead of lying.
- `examples/polls/README.md`: if it still marks admin as aspirational, update that line.

**Tests** (extend `examples/polls/tests/voting.rs`'s existing socket-level pattern — it already
creates users and a session cookie): unauthenticated GET `/admin/` → 401; make (or create) a
staff user, log in through the real login flow the test already exercises, GET `/admin/` → 200
containing `polls.Question` and `polls.Choice` links; GET `/admin/polls/question/` → 200
containing the seeded question's text (changelist end-to-end over a real socket). Non-staff 403
is already covered by djangors-admin's own tests — don't re-test it here, keep the polls test
focused on the wiring.

## What this task does NOT include

- Interactive password prompting for createsuperuser (deferred; documented in the command).
- `--noinput`-style flag plumbing beyond the env var (there is no interactive mode to opt out
  of yet).
- Change forms, delete confirmation, admin theming — later 5.x slices.
- Any change to `djangors-admin` itself (if wiring reveals a bug there, fix it as its own
  reviewed change, don't fold silent admin changes into this task).
