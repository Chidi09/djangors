# 7.2 — `djangors-contrib-messages`, shared pagination utility, humanize filters

## Scope

Continues Phase 7 after 7.1 (`djangors-cache`/`djangors-mail`, commit `c87a76d`). Bundles three
smaller, independent, low-risk pieces per the standing full-phase-batching instruction:
`djangors-contrib-messages` (flash messages), a shared pagination utility (extracted from
`djangors-admin`'s existing ad-hoc pagination math, not built from nothing), and Django-`humanize`-
style template filters added to `djangors-template`.

**Deliberately excluded from this dispatch, left for later 7.x slices**: `djangors-i18n`,
`djangors-contrib-audit`, `djangors-contrib-guardian`, `djangors-contrib-otp`, sitemaps/syndication/
flatpages/redirects. Each of those is either independently large (i18n, audit) or security-adjacent
enough (guardian, otp) to deserve its own focused dispatch rather than being folded in here.

## Part A — `djangors-contrib-messages` (new crate)

Create `crates/djangors-contrib-messages/` (picked up automatically by the workspace's `crates/*`
glob). Mirror an existing small crate's `Cargo.toml` `[package]` shape (e.g.
`crates/djangors-mail/Cargo.toml`).

## Part B — shared pagination utility

`crates/djangors-admin/src/lib.rs` already has ad-hoc pagination math inline (`PagerData` struct
around line 1758, `total_pages`/`page`/`total` computed inline around lines 1972-2009 — read the
real current line numbers and logic, don't assume they haven't shifted). This is the
"Pagination utility (shared by admin + user code)" bullet — extract the **math** (not the
href-building, which is legitimately admin-specific — `prev_href`/`next_href` are built from
admin's own query-string composition helpers) into a real, reusable, tested utility, and have
`djangors-admin` actually consume it (proving it's genuinely shared, not just duplicated
alongside).

**Where it lives**: a plain module in `djangors-core` (no new crate needed for something this
small) — e.g. `crates/djangors-core/src/pagination.rs`, exported from `lib.rs` alongside the
existing `pub mod`s.

Update `djangors-admin`'s `PagerData`-constructing code to build a `Paginator` and read
`total_pages()`/`offset()`/`has_previous()`/`has_next()` from it instead of the inline arithmetic,
keeping `prev_href`/`next_href`'s own href-building logic exactly as it is (only the numeric parts
move). **This must be verified behavior-preserving**: every existing changelist-pagination test in

pagination — grep for `PagerData`/`total_pages` usage in the test module to find them all) must

pure-extraction refactors.

**Required tests**: `Paginator`'s own unit tests (edge cases: 0 items, exactly one page, page
number past the end clamped correctly, page 0 or negative clamped to 1) live in
`djangors-core`, plus the admin-side regression check above.

## Part C — humanize template filters

Add Django-`humanize`-style filters to `djangors-template`'s existing filter set (read
`crates/djangors-template/src/filters.rs` and `src/engine.rs` for the exact real registration
pattern — `env.add_filter("name", function)`, currently called in **two** places, `new()` and
`from_embedded()` — register any new filter in both, this is a real, easy-to-miss duplication point
in this exact file, confirm you updated both call sites):

- `intcomma`: `1234567` → `"1,234,567"` (thousands-separator formatting for an integer or
  integer-like value).
- `filesizeformat`: a byte count → a human string (`"1.2 KB"`, `"3.4 MB"`, etc. — mirror Django's
  own binary-prefix-but-decimal-label convention, i.e. 1024-based steps labeled KB/MB/GB, or check
  Django's actual `filesizeformat` semantics directly rather than guessing, since this one has a
  specific well-known behavior worth matching exactly for anyone porting Django templates).
- `naturaltime`: a `DateTime<Utc>` → a relative-time string (`"3 minutes ago"`, `"2 days ago"`,
  `"just now"` for very recent times, `"in 5 minutes"` for future times) — check how the existing
  `date` filter (already in this file) accepts/parses its input value to match the same input
  convention (minijinja `Value` → `chrono::DateTime`), and compute the delta against the current
  time (`chrono::Utc::now()`) at render time, not a fixed reference — this means a real, working
  test needs to construct a known-offset timestamp relative to "now" at test-run time, not a
  hardcoded string comparison against a fixed date.

**Required tests**: one test per filter, covering at least: `intcomma` on a multi-thousand and a
sub-thousand value; `filesizeformat` across at least three magnitude steps (bytes, KB, MB);
`naturaltime` for a past offset, a very-recent ("just now"-range) offset, and a future offset.
