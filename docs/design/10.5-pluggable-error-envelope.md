# 10.5 — pluggable, project-customizable global error envelope

## Scope

Item #4 of the architecture-parity initiative ([[10.2]]/[[10.3]]/[[10.4]]'s design docs, `PLAN.md`'s
addendum): "`DjangorsError` is currently a fixed core enum" with no way for a project to customize
how errors render.

Direct investigation of this codebase found the gap is actually **two gaps**, not one:

1. `DjangorsError::into_response()` (`crates/djangors-core/src/error.rs:53`) renders **plain
   text** today (e.g. a `NotFound` body is literally `404 Not Found`, `Content-Type: text/plain`)
   — there is no JSON envelope at all for `DjangorsError`-originated failures, and no way to
   change the shape even if there were.
2. There are **three separate, hardcoded rendering paths** for `DjangorsError`, all in
   `crates/djangors-core/src/router.rs`, and no project can override any of them:
   - `Router::dispatch` (~line 410-464): plain text via `.into_response()`.
   - `Router::dispatch_debug` (~line 466-543): HTML via `debug_page::render_debug_page` (dev) or
     `debug_page::render_production_error_page` (prod) — used by `djangors-sessions`, tests, and
     some middleware paths.
   - `Router::dispatch_boxed` (~line 545-620): same HTML dev/prod pages, and **this is the path
     `crates/djangors-core/src/app.rs:270` actually uses for real running servers** — meaning any
     `djangors-rest` API error (e.g. `ViewSet::retrieve` returning `Err(DjangorsError::NotFound)`)
     in a real deployed app renders as an HTML debug/production error page today, not JSON. There
     is no content negotiation of any kind in `debug_page.rs` (checked directly — no `Accept`
     header handling exists).

**Deliberately excluded from this dispatch** (to keep this additive and zero-risk to existing
apps, matching the discipline of every prior architecture-parity slice): do NOT change any
*default* rendering behavior. No existing app should see a single byte of difference in its error
responses after this lands unless it explicitly opts in. Do NOT attempt real `Accept`-header content
negotiation (deciding HTML vs. JSON automatically) — that's a legitimately bigger, separate feature
with its own tradeoffs; this slice is about giving projects an explicit, opt-in override, not about
guessing what a client wants.

## The real design

Add a new trait to `crates/djangors-core/src/error.rs` (or a new small module if that fits the
crate's existing organization better — check how `Permission` is organized in `djangors-rest` for
precedent on trait placement, but this trait belongs in `djangors-core` since `DjangorsError`
itself lives there):

```rust
/// A project-supplied override for how [`DjangorsError`] values are rendered into an HTTP
/// [`Response`]. Register one via [`AppState::insert`] (as an `Arc<dyn ErrorRenderer>`) to
/// override ALL of `Router::dispatch`/`dispatch_debug`/`dispatch_boxed`'s error rendering in one
/// place. If none is registered, every dispatch path's existing default behavior is completely
/// unchanged (plain text / debug HTML / production HTML, exactly as today).
pub trait ErrorRenderer: Send + Sync {
    fn render(&self, err: &DjangorsError, req: &Request) -> Response;
}
```

Add a small helper on `DjangorsError` (or a free function) that each dispatch path calls first:

```rust
/// Looks up an `Arc<dyn ErrorRenderer>` registered in `req`'s `AppState` (via
/// `req.state::<Arc<dyn ErrorRenderer>>()`) and uses it if present; otherwise returns `None` so
/// the caller falls back to its own existing default behavior.
fn try_custom_render(err: &DjangorsError, req: &Request) -> Option<Response>
```

Wire this into all three dispatch paths in `router.rs`, at every point that currently constructs a
response directly from a `DjangorsError` (both the main handler-error path AND the inline
CSRF/body-read-failure shortcuts in each function — read each function in full first, there are
multiple such points per function, listed in the Scope section above). Pattern at each call site:
try the registered renderer first, fall back to the exact current behavior if `None`. This must be
a pure insertion, not a restructuring — do not otherwise touch these functions' control flow.

Also add a ready-to-use, batteries-included implementation projects can opt into for JSON API
error bodies (since `djangors-rest` is a JSON REST framework and today has no JSON envelope at all
for `DjangorsError`-originated failures reaching it):

```rust
/// A ready-made [`ErrorRenderer`] producing a JSON envelope of the shape
/// `{"error": {"status": 404, "code": "not_found", "message": "..."}}`.
/// `code` is a stable, machine-readable snake_case identifier per variant
/// (not_found, bad_request, internal, panicked, unauthorized, forbidden).
pub struct JsonErrorRenderer;

impl ErrorRenderer for JsonErrorRenderer {
    fn render(&self, err: &DjangorsError, _req: &Request) -> Response { ... }
}
```

Add a small `fn code(&self) -> &'static str` (or similar) on `DjangorsError` if useful for
`JsonErrorRenderer`'s implementation — check whether `status_code()`'s existing match arms can be
mirrored cleanly for this, reuse that structure rather than inventing a new one.

A project opts in like: `AppState::new().insert(Arc::new(JsonErrorRenderer) as Arc<dyn
ErrorRenderer>)` (or its own custom `impl ErrorRenderer`), the same way `Database`/other shared
values are already inserted into `AppState` today (see existing test/example call sites for the
exact idiom, e.g. `djangors-rest`'s own test suite's `.with_state(...)` usage).

## Required verification

- A real test proving the default (no renderer registered) path is **byte-for-byte unchanged**:
  compare a `NotFound`/`BadRequest` response through each of the three dispatch paths before and
  after this change (or just assert the current known plain-text/HTML behavior still holds when no
  `ErrorRenderer` is in `AppState`).
- A real test proving the opt-in override actually takes effect: register `JsonErrorRenderer` (or
  a small custom test `ErrorRenderer`) in `AppState`, dispatch a request that fails with each kind
  of error the framework can produce (at least `NotFound` and one error carrying a message, e.g.
  `BadRequest`/`Unauthorized`), and assert the actual JSON body shape and `Content-Type` header —
  through **all three** dispatch paths (`dispatch`, `dispatch_debug`, `dispatch_boxed`), not just
  one, since they're currently three independently-hardcoded call sites and it would be easy to
  wire only one and miss the others.
- Confirm every existing test in `router.rs`, `debug_page.rs`, and anywhere else touching
  `DjangorsError` rendering still passes unmodified (this must be additive — do not edit any
  existing test to make it pass).
- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace` all clean.

Print `DONE_MARKER_10_5_PLUGGABLE_ERROR_ENVELOPE` when finished (or when stopping early — say
exactly what works and what doesn't, do not fabricate a finished result).
