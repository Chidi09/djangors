# 5.8.12 — Every remaining Phase 5 item, bundled into one dispatch

**Status:** design doc, not yet dispatched. **This is a large, single dispatch per explicit user
instruction** ("do every remaining part of phase 5 in one dispatch") — bigger than any prior 5.8.x
slice. Read this whole doc before touching code; it covers 11 distinct features across
`djangors-admin` (and one `djangors-orm` touch-point). Implement them **in the order listed** so
that a partial/died dispatch leaves the most value landed — later items build on nothing earlier
items don't already have, so any prefix of this list is independently useful and independently
testable.

## §1 — `list_display` computed-method columns

`ModelAdminConfig` (line ~81) gains a new optional field:

```rust
pub struct ModelAdminConfig {
    pub list_display: Option<&'static [&'static str]>,
    pub search_fields: Option<&'static [&'static str]>,
    pub list_filter: Option<&'static [&'static str]>,
    pub date_hierarchy: Option<&'static str>,
    pub list_editable: Option<&'static [&'static str]>,
    pub computed_columns: Option<&'static [(&'static str, fn(&[(&'static str, djangors_orm::expr::Value)]) -> String)]>,
    // ... other fields added below by this same slice; keep Default deriving/impl accurate
}
```

A computed column is a `(name, function)` pair, where the function receives the full row's
`field_values()` (already available at every call site that needs it) and returns the display
string — no new data plumbing needed, just a new way to *produce* one column's text.

- `register_with`'s existing `list_display` validation (currently panics if a name isn't found in
  `meta.fields`/`meta.relations` — the exact gap 5.9 discovered for relation fields) must also
  accept a name found in `computed_columns`. Read the current validation code before editing it —
  extend the "is this name known" check to be `meta.fields.iter().any(...) ||
  meta.relations.iter().any(...) || computed_columns.iter().any(|(n, _)| *n == name)`.
- `DefaultModelAdmin::row_values` (line ~215) currently looks up each column name in
  `item.field_values()` only. Change it to check `self.config.computed_columns` first for a match,
  falling back to the existing `field_values()` lookup — i.e. a computed column's function runs
  once per row per render, called with that row's `field_values()`.
- No change needed to `effective_columns` itself, `ChangelistTemplateContext`, or the template —
  a computed column is just another string in the same `Vec<Vec<String>>` rows structure that
  already exists; the changelist template already renders whatever's in `row.cells` generically.

## §2 — Real bulk-actions dispatch mechanism (generalizes 5.6.3's hardcoded bulk-delete)

New types, placed near `ModelAdminConfig`:

```rust
pub struct AdminAction {
    pub name: &'static str,
    pub label: &'static str,
    pub requires_confirm: bool,
    pub handler: fn(&djangors_db::Database, &[i64])
        -> std::pin::Pin<Box<dyn std::future::Future<Output = Result<(), DjangorsError>> + Send + '_>>,
}
```

`ModelAdminConfig` gains `pub actions: Option<&'static [AdminAction]>`.

New route, mounted in `AdminSite::urls()` right alongside the existing `bulk-delete/` and
`save-changelist/` routes for the same model (read that section of `urls()` first and mirror its
exact closure-capturing style — `admins`/`branding` clones per closure, same as every other route
here): `POST /{app}/{model}/bulk-action/` → new handler `admin_bulk_action_post`.

```rust
async fn admin_bulk_action_post(
    req: Request,
    params: PathParams,
    admins: Vec<Arc<dyn ModelAdmin>>,
    branding: SiteBranding,
) -> Result<Response, DjangorsError> {
    // Same app/model lookup, db extraction, require_perm(..., "change") pattern as
    // admin_save_changelist_post (bulk actions need "change" permission at minimum;
    // an action that itself deletes is still gated by "change" here, matching Django's
    // own default admin action permission of requiring change_<model> unless the action
    // opts into something stricter - out of scope to make this per-action configurable).
    //
    // Parse `Form::<Vec<(String, String)>>` (mirrors admin_bulk_delete_post's own parsing,
    // NOT a HashMap - multiple "selected" checkboxes need every value, the same pitfall
    // 5.6.3's design doc already flagged and worked around).
    // - "action" key names the AdminAction by `name`.
    // - "selected" keys (repeated) are the pks, same parsing as admin_bulk_delete_post.
    // - "confirm" == "1" means this is step 2 of a requires_confirm action.
    //
    // Look up the action by name in admin's ModelAdminConfig (ModelAdmin trait needs a new
    // `fn actions(&self) -> &[AdminAction]` method, default-implemented as `&[]`, overridden
    // by DefaultModelAdmin<M> to return `self.config.actions.unwrap_or(&[])` - mirrors the
    // exact pattern `list_editable_fields()`/`list_filter_fields()` already use).
    // - Unknown action name -> DjangorsError::BadRequest.
    // - If action.requires_confirm && !is_confirm: render a new "bulk_action_confirm.html"
    //   template (same shape as bulk_delete_confirm.html - count, items via get_by_pk display
    //   join, pks, csrf_token, site_header/site_title/logo_url/accent_color - copy that
    //   template's exact structure, changing only the button label to action.label and the
    //   confirm form's target to reference the action name as a hidden field too).
    // - Otherwise: call `(action.handler)(db, &pks).await?`, then log ONE LogEntry per pk with
    //   action_flag ACTION_CHANGE and change_message set to the action's label (matches this
    //   slice's own established log_action() helper and per-object granularity from 5.8.11 -
    //   reuse log_action(), don't build a second logging path), then redirect to the changelist.
}
```

Reimplement `admin_bulk_delete_post`'s delete action as a *built-in* `AdminAction` that every
`DefaultModelAdmin<M>` exposes automatically (append it in `actions()`'s default implementation
after the config's own list) — but **do not remove or change `admin_bulk_delete_post` and its
existing route**; two working paths to bulk-delete (the pre-existing dedicated route, and the new
generic mechanism) is acceptable, deliberately zero risk to the many existing bulk-delete tests
(5.6.3, 5.8.10, 5.8.11) that already assert on that exact route/response shape.

`changelist.html` gains, inside the existing `<form method="post" action="bulk-delete/">` (right
before the existing `<button formaction="bulk-delete/">Delete selected</button>`), a new
`{% if actions %}` block:

```html
{% if actions %}<select name="action">{% for a in actions %}<option value="{{ a.name }}">{{ a.label }}</option>{% endfor %}</select><button type="submit" formaction="bulk-action/">Go</button>{% endif %}
```

`ChangelistTemplateContext` gains `actions: Vec<AdminActionRow>` (a small `{name, label}`
serializable struct — do not serialize `AdminAction` itself, it holds a raw `fn` pointer which
`serde::Serialize` cannot derive for; build the small display-only row struct the same way
`RecentActionRow` was built from `LogEntry` in 5.8.11), populated in `admin_changelist` from
`admin.actions()` (the "Delete selected" bulk-delete button and this new "Go" mechanism coexist —
if `actions` is empty, the new `<select>`/`Go` block simply doesn't render, zero visual change for
every model that doesn't configure any custom actions).

**Required tests**: one model configuring a real custom action (e.g. a trivial "mark active" flip
on a Boolean field, `requires_confirm: false`) proving it executes and logs; one action with
`requires_confirm: true` proving the two-step confirm/execute flow (mirror
`test_phase5_part6_3_bulk_delete`'s existing two-step shape exactly).

## §5 — `raw_id_fields` (plain lookup link, no client JS)

`ModelAdminConfig` gains:

```rust
pub raw_id_fields: Option<&'static [&'static str]>,
```

For a relation field named in `raw_id_fields`, `render_form` adds a plain `<a
href="/{target_app}/{target_model}/">Look up</a>` link immediately after that field's `<input>` —
`target_app`/`target_model` come from `RelationMeta::target()` (the same late-bound resolver
`collect_related_objects` already calls). This opens the target model's own changelist so the user
can find the pk they want and type it into the still-plain numeric input — genuinely useful without
any JS, and does not change how the value is submitted/parsed (still the existing raw-FK-id text
input, completely unchanged validation path). `FormFieldRow` gains
`lookup_href: Option<minijinja::value::Value>` (needs `from_safe_string` — mirrors the exact
`href`/`label` `Safe`-wrapping pattern and its safety comment from `IndexModelLink`, since this
value is also built purely from compile-time `ModelMeta` strings, never request-derived — copy that
existing comment's reasoning rather than writing new prose). Client-side autocomplete search (a
live JS-driven search dropdown) is explicitly **not** built here — this is the scoped-down v1 noted
in the accounting table above.

## §6 — Transitive related-object walk + `on_delete: Protect` enforcement

Both live in/near `collect_related_objects` (line ~2219) and the two delete handlers.

**Transitive walk**: add a `depth: u32` parameter (call site passes `2` — Django's own default admin
delete-confirm page also does a bounded, not unlimited, walk), and a `visited: &mut
std::collections::HashSet<&'static str>` (table names) to prevent infinite recursion on any cyclic
FK graph. At `depth > 0`, after finding a related row count > 0 for a given `related_meta`, if that
`related_meta`'s table hasn't been visited yet, recurse into `collect_related_objects` for
*that* model (mark it visited first) at `depth - 1`, and attach the results as a nested field on
`RelatedObjectSummary` (add `pub nested: Vec<RelatedObjectSummary>` to the existing struct, default
empty at depth 0 — the top-level call). `delete_confirm.html`'s existing `{% for r in related %}`
loop gains a nested `{% if r.nested %}<ul>{% for n in r.nested %}<li>...</li>{% endfor %}</ul>{%
endif %}` block, same field shape as the existing one level, indented visually.

**`Protect` enforcement**: new helper (or extend `collect_related_objects`'s traversal, reusing its
iteration rather than writing a second one) that, for each `RelationMeta` targeting the model being
deleted where `relation.on_delete == djangors_orm::meta::OnDelete::Protect`, checks whether any row
exists (same COUNT(*) query pattern already in `collect_related_objects`). If any protected relation
has `count > 0`, both `admin_delete_post` and `admin_bulk_delete_post`'s step-2 loop must reject
that pk's deletion with `DjangorsError::BadRequest` (a clear message naming which related model
blocked it) **before** calling `delete_by_pk` — write zero rows, this is purely a pre-check.
`admin_bulk_delete_post`'s loop deletes one pk at a time already (5.8.11 wired per-pk `LogEntry`
writes into that same loop) — a `Protect`-blocked pk in a bulk operation should be skipped (not
deleted, not logged, not a whole-request failure) while the rest of the batch still proceeds,
mirroring the existing "pk already gone is a per-pk no-op, not a whole-request error" reasoning
already established there; report which pks were blocked by including them in the final redirect's
generic behavior is out of scope for a first pass — a silent per-pk skip is acceptable v1 (Django's
own bulk-delete confirm page pre-checks and simply excludes protected objects from what gets
deleted, which is the same effective behavior).

**Required tests**: extend the existing delete-confirmation/related-object tests with one more
level of relation (three models chained A→B→C) proving the transitive walk surfaces C; a `Protect`
relation proving the single-object delete route now 400s instead of deleting, and a bulk-delete
batch with one protected and one unprotected pk proving only the unprotected one is removed.

## §7 — Admin UI for groups/permissions/user assignments

## §8 — UI-level hiding of unauthorized action buttons

Every template-rendering handler that already calls `require_perm`/`has_perm` per action
(`admin_changelist`, `render_form`'s 4 call sites, `admin_delete_get`) needs to also resolve the
*other* action permissions for display purposes and thread them into the template context as plain
booleans — **enforcement is already real and server-side (5.7.2); this is purely about not
rendering a button/link the click would 403 anyway.**

Concretely: `admin_changelist` already knows the current `user` (via `require_perm`'s return value)
and `db`; before rendering, resolve `can_add`/`can_change`/`can_delete` via `has_perm`
(superuser bypasses each check, mirroring `require_perm`'s own existing superuser short-circuit —
call the same pattern, don't reimplement it) and add all three as `bool` fields on
`ChangelistTemplateContext`. `changelist.html` gates: the row-level pk-link to the change page
around `{% if can_change %}`, the delete-selected button/action-`<select>` around `{% if
can_delete %}`, and (new) an "Add" link near the top of the page around `{% if can_add %}` — check
whether an "Add" link exists on `changelist.html` today; if not, this is a new, small, genuinely
useful addition, not just a permission gate. `admin_index.html`'s per-model list already only shows
models the user can view (5.7.2) — no change needed there beyond what already exists.

**Required test**: a non-superuser staff user granted only `view`/`change` (not `delete`, not
`add`) on a model sees no delete button/action-select and no add link in the rendered changelist
HTML, while a superuser sees all three — extend `test_admin_permissions_enforcement`'s existing
fixture setup rather than writing an entirely new one from scratch (read that test first).

## §10 — Extension points: custom admin views + scoped `get_queryset` override

**Custom admin views**: `AdminSite` gains a way to mount arbitrary extra routes alongside its
generated per-model routes. Read `Router`'s actual `.get`/`.post` method signatures in
`crates/djangors-core/src/router.rs` first to confirm the exact trait bound extra routes must
satisfy (every existing route in `urls()` is registered via a `move |req: Request, params:
PathParams| { ... }` closure returning a boxed/async future — mirror whatever bound already makes
that work, don't invent a new one). Add:

```rust
pub fn extra_route<F, Fut>(mut self, method: &'static str, path: &'static str, handler: F) -> Self
where
    F: Fn(Request, PathParams) -> Fut + Clone + Send + Sync + 'static,
    Fut: std::future::Future<Output = Result<Response, DjangorsError>> + Send + 'static,
{
    self.extra_routes.push((method, path, /* boxed/erased handler, matching whatever
        Router::get/post actually accept internally */));
    self
}
```

with a new `extra_routes` field on `AdminSite`, applied inside `urls()` right after the generated
per-model routes are mounted (extra routes take a literal path relative to wherever the whole
`AdminSite` is mounted, e.g. `"stats/"` for a custom dashboard page). This is intentionally generic
— no built-in example route needs to ship with it, just the mechanism and one test proving a
registered extra route is reachable through the mounted `AdminSite`.

**Scoped `get_queryset` override**: `ModelAdminConfig` gains:

```rust
pub base_filter: Option<fn() -> djangors_orm::expr::UnresolvedExpr>,
```

`DefaultModelAdmin::build_filtered_queryset` (line ~172, the single choke point already shared by
both `changelist` and `export_csv_rows`) ANDs this in when present — call `(self.config.base_filter)()`
and combine it with any existing `list_filter` compares via the same
`djangors_orm::expr::UnresolvedExpr::And(...)` pattern already used there for `filters`. This
covers changelist and CSV export; `get_by_pk`, `update_from_form`, `delete_by_pk` do **not** apply
`base_filter` in this slice (a known, explicitly-ledgered partial, matching the accounting table
above) — do not attempt to thread it further, that widens this already-large dispatch's blast
radius for marginal v1 value.

**Custom actions with intermediate pages**: already covered by §2's `AdminAction.requires_confirm`
— no separate work needed here, this bullet is satisfied by §2.
