# 14.1 — SQLite test harness (make the suite runnable without Postgres)

## Why

The original reason for adding SQLite was "tests would run faster too." That has not been
delivered. 13.1–13.3 made *application* code dual-backend; the framework's own test suite is still
Postgres-only, because every slice scoped test SQL out.

Concretely, what still requires a running Postgres server:

| Location | Postgres-bound test SQL sites |
| --- | --- |
| `crates/djangors-admin/src/lib.rs` | 251 |
| `crates/djangors-orm/src/tests.rs` | 57 |
| `crates/djangors-rest/src/lib.rs` | 41 |
| `crates/djangors-auth/src/tests.rs` | 39 |
| `crates/djangors-tasks/src/lib.rs` | 24 |
| `crates/djangors-migrations/src/lib.rs` | 13 |
| `crates/djangors-db/src/database.rs` | 13 |
| `crates/djangors-views/src/lib.rs` | 12 |
| `crates/djangors-contrib-guardian/src/lib.rs` | 10 |
| others | ~15 |

plus 11 Postgres-specific mechanisms in `djangors-test` itself (`pg_advisory_lock`,
`CREATE DATABASE` / `DROP DATABASE` per test, `pg_terminate_backend`).

The payoff is not only speed. Every environment failure in this project's recent history — Postgres
`53100` "no space left on device", `PoolExhausted` from two concurrent suites, the repeated
`target/` clearing — comes from the suite needing a real server plus a full debug build. In-memory
SQLite needs neither.

## Non-goal: replacing Postgres coverage

Postgres must keep working exactly as it does today. This is **dual-mode**, not a switch. The
dialect-specific paths (width-strict INT4/INT8 decoding, `ILIKE`, `EXTRACT`, advisory locks,
`SKIP LOCKED`) are only meaningfully covered against a real Postgres, and losing that would be a
worse regression than slow tests.

Selection is by environment variable:

- `TEST_BACKEND=sqlite` (or unset `DATABASE_URL`) → in-memory SQLite, no server needed.
- `TEST_BACKEND=postgres` (default when `DATABASE_URL` is set) → today's behaviour, unchanged.

CI runs both. Local development defaults to whichever is available.

## The harness

`djangors-test`'s isolation model is "one real database per test, arbitrated by a Postgres
session-level advisory lock." SQLite has neither advisory locks nor `CREATE DATABASE` — but it does
not need them: **a fresh `sqlite::memory:` handle is already a private database**, so isolation is
free and strictly stronger.

Add to `djangors-test`:

```rust
/// Which backend a test database is provisioned against.
pub enum TestBackend { Postgres, Sqlite }

impl TestDatabase {
    /// Provision a database for one test, honouring TEST_BACKEND.
    pub async fn new_for_backend(backend: TestBackend) -> Result<Self, ...>;
}
```

- SQLite arm: connect to `sqlite::memory:` with `max_connections(1)`. **The single connection is
  load-bearing** — with a plain `:memory:` URL every pooled connection is a *separate* database, so
  a pool of 10 would make setup DDL invisible to the next query. Pin it to 1 and document why.
- Postgres arm: exactly today's code, untouched.
- `Drop`/cleanup for SQLite is a no-op — the database dies with the handle.

Keep `pg_advisory_lock`, `CREATE DATABASE`, and `pg_terminate_backend` in the Postgres arm only.

## Porting test SQL

Mechanical, per the pattern `crates/djangors-orm/src/queryset.rs` already uses:

1. `$1`, `$2`, … → `dialect.placeholder(n)`.
2. `BIGSERIAL PRIMARY KEY` / `SERIAL PRIMARY KEY` → `dialect.auto_pk_type()`.
3. `TIMESTAMPTZ` → `dialect.timestamp_type()`; `now()` → `dialect.current_timestamp()`.
4. `BYTEA` → `dialect.bytea_type()`.
5. `ILIKE` → `dialect.ilike()`.
6. `.execute(db.pool())` → `db.conn().execute(&sql, &params)`.
7. `query_as`/`query_scalar` → `DbRow` accessors.
8. `ON CONFLICT` is fine — SQLite 3.24+ supports it.

Tests that assert genuinely Postgres-specific behaviour (isolation levels, advisory locks,
`SKIP LOCKED`, width-strict integer decoding) must be gated `#[cfg]`/skipped under SQLite rather
than weakened. **Skipping is only acceptable for behaviour SQLite genuinely cannot express** — not
as a way to make a failing test go away.

## Order of work

Harness first, then crates cheapest-to-hardest so a partial run is still useful:

1. `djangors-test` (the harness itself)
2. `djangors-db`
3. `djangors-migrations`
4. `djangors-contrib-guardian`
5. `djangors-views`
6. `djangors-tasks`
7. `djangors-auth`
8. `djangors-orm`
9. `djangors-rest`
10. `djangors-admin` (251 sites — largest, last)

Stop at a crate boundary if time runs short.

## Definition of done

1. `cargo build --workspace --all-targets` and `cargo clippy --workspace --all-targets -- -D warnings`
   clean.
2. With `DATABASE_URL` set, `cargo test --workspace` still passes all 405 tests — **no test
   weakened, ignored, or deleted** to achieve this.
3. With `TEST_BACKEND=sqlite`, every ported crate's tests pass with no Postgres server running.
4. Any test skipped under SQLite is skipped for a documented reason naming the specific Postgres
   feature it needs.
5. A note in `docs/src/guides/testing.md` describing how to run the suite against each backend.
