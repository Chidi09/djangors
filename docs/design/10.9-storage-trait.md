# 10.9 — pluggable storage trait + LocalDiskStorage (item 7a)

## Scope

Item #7 of the architecture-parity initiative, part a of two (see
`/root/.claude/plans/concurrent-inventing-glacier.md`; items 1-6, 8 are already done).
`crates/djangors-staticfiles` has zero storage abstraction today — confirmed by direct
inspection: `collect.rs`'s `StaticFiles::collect` reads every source directory and writes hashed
output files via raw `fs::read`/`fs::write`/`fs::create_dir_all`; `serve.rs`'s `StaticFiles::serve`
reads via raw `fs::read`, with path-traversal protection implemented inline in a private
`resolve_path` method (canonicalizes both the candidate target and each search directory, requires
`canonical_target.starts_with(&canonical_dir)`). This item adds a real `Storage` trait so a future
item (7b) can add an S3 backend without either crate's read/write call sites caring which backend
is actually in use.

**Deliberately excluded from this dispatch**: any S3 or non-local backend (that's 7b, a separate
design doc, `docs/design/10.10-s3-storage-filefield.md`); a `FileField` ORM type (also 7b).

**A real design decision, not a mechanical one — read this before touching `serve.rs`**:
`StaticFiles` currently searches **multiple** `source_dirs` in order (first match wins,
`collect.rs`'s `collected_files.entry(rel_str).or_insert_with(...)` and `serve.rs`'s `for dir in
&self.source_dirs` loop). A `Storage` trait, like Django's own `Storage` class, is naturally a
**single-root** abstraction — one backend, one place things live. Preserve the existing multi-dir
search behavior exactly (this must be zero-behavior-change, same constraint every prior
architecture-parity item has held to) by having `StaticFiles` hold a `Vec` of `LocalDiskStorage`
instances (one per configured source dir) internally, and trying each one in order via the trait's
own `open`/`exists` methods — the multi-root orchestration stays in `StaticFiles`, `LocalDiskStorage`
itself is single-rooted, matching the trait's natural shape.

**Similarly, split `collect()`'s read and write sides differently, deliberately**: the *read* side
(walking a project's own raw source asset directories on the developer's machine during
`collectstatic`) is inherently local disk — that's where a project's source files live before any
deployment, keep that as direct `fs::` scanning, don't force it through `Storage`. The *write* side
(writing the collected, content-hashed output files + `manifest.json` into `output_dir`) is exactly
what should become storage-pluggable, since that's the directory a project might reasonably want
to point at S3 instead of local disk in a future slice. Only refactor the write side.

## The real design

Add a new module, e.g. `crates/djangors-staticfiles/src/storage.rs`:

```rust
/// A pluggable backend for storing and retrieving files by a relative path/key.
#[async_trait::async_trait]
pub trait Storage: Send + Sync {
    /// Stores `content` at `path`, returning the actual path/key it was stored under (may
    /// differ from the requested `path` if the backend needs to disambiguate).
    async fn save(&self, path: &str, content: Vec<u8>) -> Result<String, StaticFilesError>;
    /// Reads the full contents stored at `path`.
    async fn open(&self, path: &str) -> Result<Vec<u8>, StaticFilesError>;
    /// Returns whether something is stored at `path`.
    async fn exists(&self, path: &str) -> Result<bool, StaticFilesError>;
    /// Deletes whatever is stored at `path`, if anything.
    async fn delete(&self, path: &str) -> Result<(), StaticFilesError>;
    /// Returns the public URL for `path`. Synchronous — constructing a URL string requires no
    /// I/O for either a local-disk or S3-style backend.
    fn url(&self, path: &str) -> String;
}

/// A [`Storage`] backend rooted at a single local directory.
pub struct LocalDiskStorage {
    root: std::path::PathBuf,
    base_url: String,
}

impl LocalDiskStorage {
    pub fn new(root: impl Into<std::path::PathBuf>, base_url: impl Into<String>) -> Self { ... }
}
```

`LocalDiskStorage::open`/`exists` must contain **exactly** the path-traversal-safety logic
currently in `serve.rs`'s private `resolve_path` (canonicalize both the joined target path and the
root, require the target's canonical path to start with the root's canonical path) — read
`resolve_path` in full first and move its logic verbatim, don't rewrite the safety check from
scratch (the risk here is silently weakening an existing security guarantee during the move, not
adding a new feature). `save`/`delete` are the straightforward `fs::write`/`fs::create_dir_all`/
`fs::remove_file` operations already present in `collect.rs`. `url` joins `base_url` with `path`.

### `serve.rs` changes

`StaticFiles` (currently `{ source_dirs: Vec<PathBuf> }`) becomes `{ backends: Vec<LocalDiskStorage> }`
(or keeps constructing them lazily per-call if that fits the existing `StaticFiles::new`/`handler()`
API better — check how `StaticFilesHandler` clones `source_dirs` today and preserve that same
cloning/construction shape). `serve()`'s loop over `source_dirs` becomes a loop over the backends,
calling `.exists(rel_path)` then `.open(rel_path)` (or just `.open()` and mapping a not-found error
to the next backend) — same "first match wins" semantics as today, same NotFound-when-nothing-
matches fallback.

### `collect.rs` changes

Read side (`walk_dir`, iterating `self.source_dirs`) is unchanged — still direct `fs::`. Add a new
method taking an injected storage backend for the write side:

```rust
impl StaticFiles {
    /// Collects static files from source directories, writing hashed output through `storage`
    /// instead of directly to disk.
    pub async fn collect_to(
        &self,
        storage: &dyn Storage,
    ) -> Result<Manifest, StaticFilesError> { ... }

    /// Convenience wrapper: collects into a local directory (existing behavior, unchanged from
    /// the caller's perspective).
    pub fn collect(&self, output_dir: &Path) -> Result<Manifest, StaticFilesError> {
        // constructs a LocalDiskStorage for output_dir and delegates to collect_to, blocking on
        // the async call (check how this crate's existing sync/async boundary is handled
        // elsewhere, e.g. via a small tokio current-thread runtime, to match established style)
    }
}
```

Keep `collect`'s existing signature and behavior (sync, same output on disk) for full backward
compatibility — it's the one every existing caller uses today (check `crates/djangors-cli/src/commands.rs`'s
`collectstatic` command for the real call site and confirm it still compiles unchanged).
