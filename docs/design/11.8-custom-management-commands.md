# 11.8 — Custom management commands plugin mechanism

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_8` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

`dj`'s CLI (`crates/djangors-cli/src/cli.rs`, `#[derive(Subcommand)] pub enum Commands`) is a
fixed, compile-time-closed set (`new`, `new-app`, `run`, `check`, `dbshell`, `runworker`,
`migrate`, `makemigrations`, `createsuperuser`, `createpermissions`, `shell`, `test`,
`collectstatic`) — there is no way for a user's own project to add `dj mycommand`, unlike
Django's `myapp/management/commands/foo.py` auto-discovery.

**The critical architectural fact that makes the naive approach (an `inventory`-based registry
checked directly inside the `dj` binary) impossible — verify this yourself before writing any
code:** `dj` is a separate, pre-compiled binary (built once as part of `djangors-cli`) invoked
inside a user's own project directory. The `inventory` crate's collection mechanism only sees
items registered via `inventory::submit!` **within the same compiled binary** — a user's project
crate registering a custom command via `inventory::submit!` produces an entry that only exists
inside *that project's own compiled binary*, never inside the separately-compiled `dj` tool's
process. This project has already solved the exact same problem once, for model introspection —
read `crates/djangors-core/src/lib.rs`'s `introspect_models_if_requested()` (~line 97) and its
caller `crates/djangors-cli/src/commands.rs`'s `introspect_models()` (~line 630) in full before
writing anything: `dj makemigrations` needs the user project's own compiled model registry, so it
shells out via `std::process::Command::new("cargo").args(["run", "--quiet"])` with a
`DJANGORS_INTROSPECT_MODELS=1` env var, and the user's own project's `main()` calls
`djangors_core::introspect_models_if_requested()` as its literal first line (confirmed already
present in both `examples/polls/src/main.rs` and `examples/school/src/main.rs`, and in whatever
template `crates/djangors-cli/src/commands.rs`'s `new()`/`new_app()` scaffolding functions
generate) — that function checks the env var, and if set, prints the registry as JSON and exits
before the real server ever starts. **Mirror this exact pattern for custom management commands -
don't invent a different mechanism.**

Also read `crates/djangors-macros/src/task.rs`'s `expand_task` in full — the `#[task]` attribute
macro (used for background tasks in `djangors-tasks`) is the exact pattern to mirror for a new
`#[management_command]` attribute macro: it generates a wrapper function and an
`inventory::submit! { SomeRegistration { name, handler } }` block.

## Scope — what to build

1. **A new registration type and `inventory::collect!` in `djangors-core`** (alongside
   `introspect_models_if_requested`, since that's the crate every project already depends on and
   already hosts this exact class of mechanism) — e.g.:
   ```rust
   pub struct ManagementCommandRegistration {
       pub name: &'static str,
       pub handler: fn(Vec<String>) -> std::pin::Pin<Box<dyn std::future::Future<Output = ()> + Send>>,
   }
   inventory::collect!(ManagementCommandRegistration);
   ```
   (adjust the handler signature to whatever's actually ergonomic - it needs to receive the raw
   extra CLI args the user passed after the command name, and it needs to be async since real
   commands will want to do DB work).

2. **`pub fn run_management_command_if_requested()`** in `djangors-core`, mirroring
   `introspect_models_if_requested()`'s shape: check a new env var (e.g.
   `DJANGORS_RUN_COMMAND`, containing the command name), and if set, look up the matching
   `ManagementCommandRegistration` by name via `inventory::iter`, call its handler with the extra
   args (forwarded via another mechanism - e.g. a second env var containing a JSON-encoded
   `Vec<String>`, or just `std::env::args()` itself since the extra args can be passed straight
   through on the `cargo run -- ...` invocation - pick whichever is simpler), then
   `std::process::exit(0)` (or a nonzero code if the command name doesn't match anything
   registered, with a clear error message). This function needs to be called from the same
   `main()` entry point as `introspect_models_if_requested()` - add the call right alongside the
   existing one in both example apps' `main.rs` **and** in the `dj new`/`new-app` scaffolding
   template inside `crates/djangors-cli/src/commands.rs`, so every newly-generated project gets it
   automatically.

3. **A `#[management_command]` attribute macro** in `djangors-macros` (new file, mirroring
   `task.rs`'s structure closely): `#[management_command] async fn seed_data(args: Vec<String>) {
   ... }` (or `#[management_command(name = "seed")]` to override the registered name, matching
   `#[task(name = "...")]`'s existing option) generates the wrapper + `inventory::submit!` block
   referencing the new `ManagementCommandRegistration` type in `djangors-core`.

4. **Wire `dj` itself to dispatch to unknown subcommands as custom commands.** In
   `crates/djangors-cli/src/main.rs`/`cli.rs`: before calling `Cli::parse()`, inspect the raw
   `std::env::args()` - if the first argument (after the binary name) is present and does **not**
   match any of the literal built-in subcommand strings, treat the whole invocation as `dj
   <custom-name> [...args]` and shell out via `std::process::Command::new("cargo").args(["run",
   "--quiet", "--"])` (mirroring `introspect_models()`'s exact `cargo run --quiet` pattern), setting
   `DJANGORS_RUN_COMMAND=<custom-name>` and forwarding the remaining args after the command name
   as the trailing args to `cargo run -- ...` so the user project's own process sees them via
   `std::env::args()`. If the subprocess exits with a nonzero code (meaning `dj` and the user's
   project both failed to recognize the name as anything), print a clear "unknown command" error
   listing the built-in commands.

## Deliberately excluded

- Auto-discovery/directory-scanning of a `management/commands/` folder (Django's literal
  mechanism) - Rust has no runtime dynamic-loading equivalent; the `inventory`-based
  compile-time registration above is the actual mechanism, not a stand-in for a future "real"
  version.
- Argument parsing/validation for custom commands beyond forwarding raw `Vec<String>` args - a
  custom command's own handler is responsible for parsing its own arguments (e.g. with `clap`
  itself, if the user wants that) - don't build a generic argument-schema system.
- Changing any existing built-in `dj` subcommand's behavior.
- A "list available custom commands" discovery command (`dj help` listing custom commands) -
  useful, but out of scope for this pass; the built-in `--help` output covers only the fixed
  subcommands.

- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`,

- A real end-to-end test proving this actually works, not just unit tests of the pieces in
  isolation: scaffold or use a real temp project (or reuse `examples/polls`/`examples/school` if
  that's simpler and doesn't require scaffolding machinery), register a real
  `#[management_command]` function that does something observable (e.g. writes a marker file, or
  prints a specific string to stdout), run the real `dj` binary against that project with the
  custom command name, and confirm the observable side effect actually happened. This must
  exercise the real `cargo run --quiet` subprocess path, not just call the Rust functions directly
  in-process (that would prove the registration mechanism works but not that `dj` itself correctly
  routes an unrecognized subcommand to it).
- Confirm `dj`'s built-in subcommands (e.g. `dj run --help`, `dj migrate`) still parse and behave
  identically to before - the new "unknown subcommand → shell out" path must not intercept any
  real built-in command name.
- Confirm an actually-unknown command name (one that isn't registered by the test project either)
  produces a clear error, not a silent success or a confusing panic.
- Do not claim a specific empirical result you have not actually observed in real committed test
  output.
