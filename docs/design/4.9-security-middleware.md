# Design 4.9 — Security middleware: HSTS, ALLOWED_HOSTS, Secure cookies (v1 scope)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 4's security-middleware bullet first.
This is part 3 of Phase 4, following [[4.7-sessions]] and [[4.8-csrf]] (both already built and
committed).

## v1 scope

`PLAN.md` lists: HSTS, X-Content-Type-Options, Referrer-Policy, a CSP helper, secure/httponly/
samesite cookie defaults, and `ALLOWED_HOSTS` host header validation. X-Content-Type-Options,
X-Frame-Options, and Referrer-Policy already ship (`SecurityHeadersLayer`, already committed).
**v1 adds the three highest-value, most mechanical pieces that don't require an app-specific
policy decision**: HSTS, `ALLOWED_HOSTS` validation, and a `Secure` cookie flag retrofitted onto
the two cookie-setting layers that already exist. **A CSP helper is deferred** — unlike the other
three, a Content-Security-Policy is inherently app-specific (it lists the exact script/style/
image sources an app actually uses); shipping a default policy risks either being so permissive
it's useless or breaking real apps that haven't configured it yet. Django's own core
`SecurityMiddleware` doesn't ship CSP either (it's the separate `django-csp` package) — matching
that precedent, defer it rather than guessing at a v1 shape.

## Part 1: `ALLOWED_HOSTS` validation (`HostValidationLayer`)

`djangors_core::settings::Settings::allowed_hosts: Vec<String>` already exists (default:
`["127.0.0.1", "localhost"]`, see `crates/djangors-core/src/settings.rs`). Nothing currently
checks the incoming request's `Host` header against it — add a layer that does, following the
exact `Layer<S>`/`Service<hyper::Request<Incoming>, ...>` shape `CsrfLayer`/`CsrfService`
already use in `crates/djangors-core/src/middleware.rs` (read that file, specifically the
`CsrfLayer`/`CsrfService` section, as the pattern to mirror — same crate, same file, add this
alongside it).

```rust
pub struct HostValidationLayer {
    allowed_hosts: Vec<String>, // lowercased at construction time
}

impl HostValidationLayer {
    pub fn new(allowed_hosts: Vec<String>) -> Self { ... } // lowercase + store
}
```

Behavior: read the `Host` header (fall back to checking the request URI's authority if `Host` is
absent — most requests will have `Host`, but be defensive). Strip a trailing `:<port>` if
present (host header comparison is host-only; `ALLOWED_HOSTS` entries don't include ports).
Lowercase and compare against `allowed_hosts` (already lowercased). If `allowed_hosts` is empty,
allow everything (matches this project's `Settings::default()` never actually producing an empty
list, but the layer itself shouldn't assume that — an empty list should mean "no restriction,"
not "reject everything," matching Django's own `ALLOWED_HOSTS = []` behavior of only enforcing in
non-DEBUG contexts; **v1 keeps it simpler than Django here: empty list always means unrestricted,
no DEBUG-flag special-casing** — that's a real behavioral simplification, note it in a doc
comment). If the host doesn't match, reject with a 400 Bad Request (matching Django's
`DisallowedHost` → 400 behavior) built directly as a `hyper::Response` (same pattern
`CsrfService` uses for its 403 — no `djangors_core::Response` available at this layer).

Required tests: allowed host passes through to the inner service; disallowed host is rejected
with 400 and the inner service is never called (prove with a counter, same pattern as the CSRF
tests); a host header with a port (`example.com:8080`) matches an `allowed_hosts` entry of
`example.com`; an empty `allowed_hosts` list allows any host.

## Part 2: HSTS layer

Django's `SecurityMiddleware` only sets `Strict-Transport-Security` when `SECURE_HSTS_SECONDS` is
non-zero — the header is a standing, cache-lasting promise ("only ever talk to me over HTTPS for
N seconds") that's actively harmful to set in plain-HTTP dev environments, since browsers that
receive it will refuse plain-HTTP connections to the host for the stated duration. **v1's
`HstsLayer` must be opt-in via an explicit constructor argument, never a bare default-on
`Layer::new()` with no args** — there's no safe default number of seconds here, unlike the
already-shipped `SecurityHeadersLayer` headers which are safe unconditionally.

```rust
pub struct HstsLayer {
    max_age_seconds: u64,
    include_subdomains: bool, // adds "; includeSubDomains" if true
}

impl HstsLayer {
    pub fn new(max_age_seconds: u64) -> Self { ... } // include_subdomains defaults false
    pub fn with_include_subdomains(mut self, yes: bool) -> Self { ... }
}
```

Sets `Strict-Transport-Security: max-age=<n>` (plus `; includeSubDomains` if enabled) on every
response — this can follow the exact `SetResponseHeaderLayer`-based pattern
`SecurityHeadersLayer` already uses (build the header value once at layer-construction time
since it's static per-layer-instance, then use `tower_http::set_header::SetResponseHeaderLayer::overriding`
exactly like the existing three headers do — no need for a hand-written `Service` impl for this
one, unlike `CsrfLayer`/`HostValidationLayer` which need to inspect/reject requests).

Required tests: header value format is correct for a given `max_age_seconds` with
`include_subdomains` both on and off; the header is present on the response regardless of
request path/method (it's unconditional once the layer is applied, matching
`SecurityHeadersLayer`'s own existing tests as the pattern).

## Part 3: `Secure` cookie flag on `SessionLayer` and `CsrfLayer`

Neither cookie-setting layer built so far (`djangors-sessions::SessionLayer`,
`djangors-core::CsrfLayer`) sets the `Secure` cookie attribute (browsers then send the cookie
over plain HTTP too, not just HTTPS). Both need a `secure: bool` knob, **defaulting to `false`**
(this project's own `Settings::default().debug = true`, i.e. dev-first — a default-`true` here
would break the plain-HTTP dev server every real user of this framework starts with) with an
explicit opt-in for production:

- `SignedCookieStore` (in `crates/djangors-sessions/src/lib.rs`) gains
  `pub fn with_secure(mut self, secure: bool) -> Self` (same builder pattern as its existing
  `with_cookie_name`/`with_max_age`), and `SessionService::call`'s `Set-Cookie` construction
  appends `; Secure` to the cookie string when the store's flag is set.
- `CsrfLayer` (in `crates/djangors-core/src/middleware.rs`) gains the same
  `pub fn with_secure(mut self, secure: bool) -> Self` builder method, threaded through to
  `CsrfService`, applied the same way in its `Set-Cookie` construction.

Required tests (one per layer, added to each crate's existing test module — do not create a new
test file, extend the existing ones): default (`secure` not called) produces a `Set-Cookie`
without `; Secure`; calling `.with_secure(true)` produces one that includes it. Reuse each
crate's existing end-to-end-style test setup rather than writing new scaffolding from scratch.

## What this task does NOT include

- Content-Security-Policy (helper or layer) — see the "v1 scope" section above for why.
- Wiring any of `HostValidationLayer`/`HstsLayer`/the `secure` cookie flag into any example app
  or a "production settings preset" — that's Phase 6 territory (`djangors check --deploy`,
  project scaffolding), not this task.
- Changing `Settings` itself (`allowed_hosts` already exists and is sufficient; no new settings
  fields are needed for this task — `HstsLayer`'s `max_age_seconds` and both layers' `secure`
  flag are constructor arguments, not settings-driven, matching how `SignedCookieStore::new`
  already takes its secret key as an explicit argument rather than reading global settings
  itself).
