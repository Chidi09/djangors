# 11.5 — A ModelForm-equivalent, generated from the model's own derive

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_5` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

`crates/djangors-forms` already has a real, working `Form`/`#[derive(Form)]` (see
`crates/djangors-macros/src/form.rs`): a hand-written struct with `#[djangors(max_length = ...,
required = ..., email, min = ..., max = ...)]` field attributes gets a generated
`{StructName}Cleaned` type and validation logic. The v1 scope doc for this
(`docs/design/*forms*.md` — search for it) explicitly deferred `ModelForm`. This task builds that
deferred piece: a form that's auto-derived from a **model's own fields** (Django's `ModelForm`),
not hand-written a second time.

**The key architectural decision, and why the obvious Django-mirroring approach doesn't
transplant directly into Rust — read this before writing any code:** Django's `ModelForm` is a
*separate* class (`class MyForm(ModelForm): class Meta: model = MyModel`) that introspects
`MyModel` at class-definition time. A naive Rust transplant would be a second
`#[derive(ModelForm)]` applied to a *different*, hand-written struct that somehow references
`MyModel` — but Rust proc macros only ever see the token stream of the item they're literally
attached to; a macro on struct `B` cannot introspect struct `A`'s field list even if `B` names `A`
in an attribute. This is a hard language limitation, not a design choice to work around cleverly.

**The fix used elsewhere in this codebase for exactly this class of problem: generate the
capability from the model's own `#[derive(Model)]` macro** (`crates/djangors-macros/src/model.rs`),
the same way `field_values()`, `save()`/`update()`/`delete()`, and the Phase 11 lifecycle-signal
accessors were all added *to that one macro* rather than invented as a second macro on a second
struct. `expand_derive_model` already has full, direct access to every field's name, type, and
`#[djangors(...)]` attributes (`max_length`, `nullable`, etc.) at macro-expansion time — reuse that,
don't re-derive field metadata from `ModelMeta` at runtime (that would work too, since `T::meta()`
is available at runtime, but generating real, statically-typed validation code directly in the
derive macro is more consistent with how this codebase already does things, and gives real compile
errors for field-type mismatches the way `#[derive(Form)]` already does).

Read `crates/djangors-macros/src/form.rs` in full first — it already solves "map a field's Rust
type + `#[djangors(...)]` attributes to a `FormField` impl and produce a cleaned value or errors."
Reuse its exact field-kind-to-validator mapping logic and its `{Name}Cleaned`-struct-generation
pattern; don't reinvent field validation from scratch.

## Scope — what to build

1. **Extend `#[derive(Model)]` (`crates/djangors-macros/src/model.rs`) to also generate a
   ModelForm**, gated so it doesn't force every model to pay for form-generation it doesn't need —
   either (a) always generate it (simplest, matches how `save()`/`update()`/signals are always
   generated unconditionally today), or (b) gate it behind a new `#[djangors(form)]`
   struct-level attribute if you find a concrete reason unconditional generation is a problem
   (e.g. a field type genuinely can't be form-validated) — prefer (a) unless you hit a real wall.
2. **Map each field's existing `#[djangors(...)]` model attributes to form validation
   semantics**: `max_length` → `CharField`'s `max_length`; `nullable` → the form field's
   `required` (a nullable model field is an optional form field); the field's Rust type (`String`,
   `i32`/`i64`, `bool`, `Option<...>`) → the appropriate existing `FormField` impl from
   `djangors-forms` (`CharField`/`IntegerField`/`BooleanField`/`EmailField`) using the same
   type-to-field-kind mapping `crates/djangors-macros/src/form.rs` already implements — don't
   invent a second mapping. Auto/primary-key fields are excluded from the generated form (they're
   never user-submitted), matching how `save()`'s own INSERT already skips `auto` fields.
3. **Validation entry point**: something like
   `pub fn validate_form(raw: &std::collections::HashMap<String, String>) -> Result<{StructName}FormCleaned, djangors_forms::FormErrors>`
   generated alongside the model's existing methods - validates every included field, collecting
   *all* field errors (not stopping at the first), matching `FormErrors`' existing multi-field
   design (`crates/djangors-forms/src/error.rs`).
4. **Construction from validated data**: a way to turn the cleaned/validated data into a real
   model instance ready to `.save()` - either the generated `{StructName}FormCleaned` struct
   itself IS constructible into `Self` (e.g. a generated `impl From<{StructName}FormCleaned> for
   Self` that fills in excluded fields - primary key, auto fields - with sensible defaults the
   database will overwrite on INSERT anyway), or a generated associated function like
   `Self::from_cleaned_form(cleaned: {StructName}FormCleaned) -> Self`. Pick whichever is more
   ergonomic; document the chosen shape clearly since it's new public API surface.
5. **Update, not just create**: the ModelForm needs to support editing an *existing* instance too
   (Django's `ModelForm(instance=existing_obj)`) - a way to apply validated form data onto an
   existing `Self` value (mutating only the form's included fields, leaving primary key and any
   excluded fields untouched) so the caller can then call `.update(db)` on it. A method like
   `pub fn apply_cleaned_form(&mut self, cleaned: {StructName}FormCleaned)` is a reasonable shape.

## Deliberately excluded

- Widget/HTML rendering (Django's `{{ form.as_p }}` / per-widget HTML) - `djangors-admin` already
  has its own bespoke form-rendering (`render_form` in `crates/djangors-admin/src/lib.rs`, ~line
  905) that maps `FieldKind` to an HTML input `kind` string; this task is the *validation and
  model-construction* layer only, not rendering. A future generic CBV task (tracked separately in
  `PLAN.md`) may build real HTML rendering on top of this - don't scope-creep into it here.
- Formsets (multiple forms of the same shape in one submission).
- File upload fields (`FieldKind::FileField`) - real multipart parsing is a separate, not-yet-done
  Phase 11 item; skip `FileField`-kind fields in the generated form for now (exclude them the same
  way auto/primary-key fields are excluded), don't attempt to handle them.
- Relation/foreign-key fields needing anything beyond a plain integer ID input - validate them as
  a plain integer (the related row's id), don't build a "choice field" / dropdown-population
  mechanism.
- Changing anything in `djangors-admin`'s existing `render_form` - leave it alone, it's a separate
  concern from this task.

## Required verification

Run yourself (`DATABASE_URL=postgres://postgres:postgres@localhost/djangors_test` is live and
reachable) before finishing:

- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` all clean.
- New tests (in `djangors-macros` and/or `djangors-orm`, wherever fits the existing test
  conventions - check both crates' existing test files for the pattern to follow) proving, with a
  real `#[derive(Model)]` struct:
  - Valid raw form data (a `HashMap<String, String>`) validates successfully and produces a
    cleaned value with the right types.
  - Invalid data (missing required field, a non-numeric string for an integer field, a string
    exceeding `max_length`) produces real, per-field errors - not just "some error," check the
    actual field name is present in the error map.
  - The validated/cleaned data can be turned into a real model instance and **actually saved to
    the real Postgres database** via the existing `.save(db)` method, then queried back and
    confirmed to have the right values.
  - Applying cleaned form data onto an *existing* instance (the update path) correctly changes
    only the form's fields and leaves the primary key intact, and the resulting `.update(db)`
    call genuinely updates the real row.
  - A model field genuinely excluded from the form (auto/primary-key, and any `FileField`) does
    not appear in the generated form's required inputs.
- Do not claim a specific empirical result you have not actually observed in real committed test
  output.
