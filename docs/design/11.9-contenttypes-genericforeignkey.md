# 11.9 — Contenttypes / GenericForeignKey framework

## IMPORTANT — process note, read first

**Do not run `git commit` or `git push` under any circumstances.** Leave all changes in the
working tree. Print the required `DONE_MARKER_11_9` string when finished — that is the sole signal
of completion this project uses. All review, verification, and committing is done by the
orchestrator after the dispatch finishes, never by the dispatch itself.

## Context

Django's `contenttypes` app gives every registered model a stable row in a `ContentType` table
(`app_label`, `model`), and `GenericForeignKey` lets any model reference *any other model's row* via
a `(content_type_id, object_id)` pair, resolved dynamically at runtime via
`content_type.model_class()`.

**This codebase already has two independent, bespoke, ungeneralized versions of exactly this
pattern — read both in full before writing anything:**
- `crates/djangors-contrib-guardian/src/lib.rs` (~line 51): object-level permissions store a raw
  `(app_label: String, model_name: String, object_id: i64)` triple directly as columns.
- `crates/djangors-admin/src/lib.rs` (~line 807, `struct LogEntry`): the audit log stores the same
  shape of triple, plus a human-readable `object_repr` string computed **at log-creation time**
  (when the concrete model type is still known, e.g. `format!("{} object ({})", meta.struct_name,
  object_id)`) — not resolved later from just the id. This is an important, honest design
  precedent: neither existing bespoke system tries to dynamically fetch-and-render an arbitrary
  row later purely from `(app_label, model_name, object_id)` - they capture what they need to
  display up front. Follow this same precedent rather than attempting true Python-style dynamic
  dispatch, which Rust's static type system doesn't support the way Python's does (there is no
  Rust equivalent of `ContentType.model_class()` returning an arbitrary, instantiable type at
  runtime without the caller already knowing the concrete type at compile time).

Also read `djangors-auth`'s `createpermissions` (the `dj createpermissions` command, real code in
`crates/djangors-cli/src/commands.rs` and `crates/djangors-auth/src/lib.rs`) - it already solves
"iterate every registered model via `all_registered_models()` and upsert a corresponding row per
model into a table, keyed by `(app_label, model_name)`" for permissions. **Mirror that exact
pattern for `ContentType` rows** - don't invent a different synchronization mechanism.

## Scope — what to build

1. **A new crate, `djangors-contrib-contenttypes`** (register it in the workspace - the root
   `Cargo.toml`'s `members = ["crates/*", ...]` glob already picks up any new `crates/*` directory
   automatically, confirm this yourself rather than assuming you need to edit the workspace
   `Cargo.toml`). A real `ContentType` model (`#[derive(Model)]`): `id` (auto pk), `app_label`,
   `model_name`, with a `unique_together` on `(app_label, model_name)` (mirror the exact
   `#[djangors(unique_together = [...])]` attribute syntax already used elsewhere in this
   codebase - grep for an existing example before guessing the syntax).

2. **A sync function/command** (`pub async fn sync_content_types(db: &Database) -> Result<(),
   ...>` or similar), iterating `djangors_orm::meta::all_registered_models()` and upserting one
   `ContentType` row per registered model (INSERT ... ON CONFLICT (app_label, model_name) DO
   NOTHING, or an equivalent idempotent upsert) - mirror `createpermissions`'s real upsert pattern.
   Wire it into `dj createpermissions` itself (extend that existing command to also sync content
   types in the same pass, since both are "iterate every registered model and upsert rows" - don't
   invent a second, separate `dj` subcommand for this unless you find a concrete reason a combined
   command doesn't work) or add a new one if genuinely cleaner - your call, but justify it.

3. **A `GenericForeignKey`-equivalent helper**: a plain struct any model can embed as two real
   columns -
   ```rust
   pub struct GenericForeignKey {
       pub content_type_id: i64,
       pub object_id: i64,
   }
   ```
   plus a helper to construct one from a concrete, compile-time-known model type and instance id -
   e.g. `pub async fn generic_key_for<T: djangors_orm::Model>(db: &Database, object_id: i64) ->
   Result<GenericForeignKey, ...>` that looks up (or lazily creates, via the same upsert as #2) the
   `ContentType` row matching `T::meta().app_label`/`T::meta().struct_name`-derived model name, and
   returns the pair. Also provide the reverse lookup: `pub async fn resolve_content_type(db:
   &Database, content_type_id: i64) -> Result<(String, String), ...>` returning the
   `(app_label, model_name)` strings for a given id - useful for generic display purposes
   (matching how `LogEntry`'s existing `object_repr` is used display-side), without pretending to
   fetch/deserialize the actual referenced row generically.

## Deliberately excluded

- **Do not migrate `djangors-contrib-guardian` or `djangors-admin`'s existing bespoke
  `(app_label, model_name, object_id)` fields to use the new `ContentType`/`GenericForeignKey`
  abstraction.** Both are already-shipped, stable, tested subsystems - this task ships the new,
  reusable primitive; adopting it elsewhere is separate, future work, matching how other Phase 11
  additions (e.g. multipart uploads, Phase 11 item 6) deliberately didn't wire into
  already-shipped call sites either.
- Any attempt at genuinely dynamic, type-erased fetching of an arbitrary referenced row purely
  from `(content_type_id, object_id)` (e.g. via `Box<dyn Any>` gymnastics or a giant match over
  every registered type) - the "Context" section explains why this isn't the right direction;
  don't build it.
- A Django-style `GenericRelation` (the reverse side - "all objects of type X referencing me")
  or Django's generic-relation queryset integration - just the forward key pair and the
  content-type sync/lookup helpers.

## Required verification

Run yourself (`DATABASE_URL=postgres://postgres:postgres@localhost/djangors_test` is live and
reachable) before finishing:

- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` all clean.
- New tests, against the real database, proving:
  - Syncing content types twice in a row is idempotent (no duplicate rows, no error on the
    second run) and produces a real row for at least one real registered test model.
  - `generic_key_for::<SomeTestModel>(db, 42)` returns a `GenericForeignKey` whose
    `content_type_id` genuinely corresponds to a `ContentType` row with the right
    `app_label`/`model_name` for `SomeTestModel`, and `object_id == 42`.
  - `resolve_content_type` correctly reverses that lookup, returning the same
    `(app_label, model_name)` pair.
  - Two different model types get two different, stable `ContentType` rows (not the same one,
    not regenerated with a different id on a second sync).
- Do not claim a specific empirical result you have not actually observed in real committed test
  output.
