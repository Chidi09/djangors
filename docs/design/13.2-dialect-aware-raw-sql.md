# 13.2 — Dialect-aware raw SQL (admin, auth, contrib, tasks, cache)

## Why

13.1 made the ORM query path dual-backend, but every crate that drops to raw SQL still
writes `$N` placeholders and calls `Database::pool()`, which **panics on a SQLite
handle**. So an app on SQLite gets an ORM that works and an admin that panics on the
first request. This closes that.

## Scope correction from 13.1

13.1's notes said "~555 raw `sqlx::query` sites". That count included test-setup SQL.
The **production** surface is 31:

| Crate | Production sites |
| --- | --- |
| djangors-admin | 4 |
| djangors-auth | 3 |
| djangors-tasks | 11 |
| djangors-contrib-guardian | 5 |
| djangors-contrib-contenttypes | 4 |
| djangors-cache | 4 |

Test-module SQL stays Postgres-only and is **out of scope** — those tests connect to a
real Postgres and may keep doing so.

## The two cases that are not mechanical

### 1. `admin` date_hierarchy uses `EXTRACT`

`crates/djangors-admin/src/lib.rs` (~line 2740) builds:

```sql
EXTRACT(YEAR FROM "col")::int = $1
```

SQLite has no `EXTRACT`. Equivalent:

```sql
CAST(strftime('%Y', "col") AS INTEGER) = ?
```

`%Y` year, `%m` month, `%d` day. Note `strftime` returns a zero-padded string, so the
`CAST(... AS INTEGER)` is required for the comparison to work against a bound integer.

Add to `Dialect`:

```rust
/// SQL extracting an integer date part (`"year"`, `"month"`, `"day"`) from `col`.
pub fn extract_date_part(&self, part: DatePart, col: &str) -> String;
```

with `DatePart { Year, Month, Day }`, so the branch lives in `djangors-db` next to the
other dialect differences rather than inline in the admin.

### 2. `tasks` uses `pg_advisory_xact_lock`

`crates/djangors-tasks/src/lib.rs` (~line 188) takes a Postgres advisory lock to
serialise the claim-and-advance sequence in `tick_recurring_tasks`.

SQLite has no advisory locks — **and does not need one here**. SQLite allows a single
writer at a time; a write transaction holds an exclusive lock on the database for its
duration, so the interleaving the advisory lock defends against (two ticks observing the
same due row under READ COMMITTED) cannot occur.

Therefore: issue the advisory lock **only** under `Dialect::Postgres`, and add a comment
stating why skipping it is correct on SQLite rather than a silent omission. Do not
attempt to emulate it.

## Everything else is mechanical

For each remaining site:

1. Replace hardcoded `$1`, `$2`, … with `dialect.placeholder(n)`.
2. Replace `db.pool()` with the `Conn` path so SQLite works — i.e. go through
   `DbExecutor`/`Conn::fetch_all`/`fetch_one`/`fetch_optional`/`execute` with
   `Vec<BindValue>`, exactly as `queryset.rs` now does.
3. `query_as`/`query_scalar` have no `Conn` equivalent — read via `DbRow`'s typed
   accessors instead (`try_i64`, `try_string`, …) and build the tuple/scalar by hand.
4. Type keywords: `BYTEA` → `BLOB` on SQLite (djangors-cache's `djangors_cache_entries`
   DDL). Use `Dialect` for this, do not hardcode.

`ON CONFLICT (key) DO UPDATE` in djangors-cache is supported by SQLite 3.24+ and needs
no change.

## Scope

**In scope:** production (non-test) SQL in djangors-admin, djangors-auth,
djangors-tasks, djangors-contrib-guardian, djangors-contrib-contenttypes, djangors-cache;
plus `Dialect::extract_date_part` in djangors-db.

**Out of scope:** any `#[cfg(test)]`/`mod tests` SQL; djangors-migrations' plan generation
(still Postgres-only, deferred); rewriting ORM code from 13.1.

## Definition of done

1. `cargo build --workspace --all-targets` clean.
2. `cargo clippy --workspace --all-targets -- -D warnings` clean.
3. `cargo test --workspace` — all 400 currently-passing tests still pass against
   Postgres. **No existing test may be weakened, ignored, or deleted.** (13.1's review
   found three transaction tests silently deleted; do not repeat that.)
4. No production code path outside `djangors-migrations` calls `Database::pool()`
   unconditionally any more. Verify with:
   `grep -rn "\.pool()" crates/*/src --include=*.rs` and confirm every remaining hit is
   inside a test module or in djangors-migrations.
5. A new test proving the admin's date-hierarchy drilldown SQL runs on **SQLite** —
   create a table with a datetime column, insert rows across two different years, and
   assert the year-extraction query returns the expected distinct years.
