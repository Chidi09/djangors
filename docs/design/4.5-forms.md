# Design 4.5 — Forms (v1 scope)

**Status:** draft, pre-implementation. Read `PLAN.md` Phase 3's forms bullet first — narrowed the same way 4.3/4.4 narrowed migrations/templates.

## v1 scope, and why it's narrower than the plan bullet

`PLAN.md` lists `Form` derive, `ModelForm` (generated from `ModelMeta`), a `clean_<field>`/`clean()` validation pipeline, typed `cleaned_data`, error rendering, the full Django widget set, `as_div`/`as_table` template-based rendering, formsets, and file-upload fields — all in one bullet. Formsets exist specifically to support the admin's inline editing (Phase 5, not started) and aren't independently useful yet; file-upload fields need multipart body handling that `djangors-core`'s `Request` doesn't fully support yet (body is eagerly buffered as `Bytes`, no streaming-to-disk path for large uploads). Both are real, valuable, and explicitly deferred.

**v1 delivers:** a `#[derive(Form)]` macro for plain (non-model) forms with the core field types or a well-typed subset (`CharField`, `IntegerField`, `BooleanField`, `EmailField` — matching the design's philosophy of "narrow but genuinely correct" over "broad but half-working"), the `clean_<field>`/`clean()` validation hook pipeline, typed `cleaned_data` access, and template-renderable field/error output consumable from `djangors-template`. `ModelForm` (deriving a form directly from a model's `ModelMeta`, matching Django's biggest form-related productivity win) is included since it's a direct, mechanical extension of the same field-collection logic once plain `Form` works, not a separate design problem.

**Deferred:** formsets (needs the admin's inline-editing use case to be real before designing formset ergonomics against it), file-upload fields (needs `djangors-core` multipart/streaming support first), the full Django widget catalog (v1 ships plain HTML input rendering per field type — `<input type="text">`, `<input type="checkbox">`, `<input type="email">` — not date-picker widgets, select-with-search, or other JS-enhanced widgets, which are a UI-layer concern layered on top of the correctly-typed-and-validated field underneath, not blocking for a working forms system).

## Field types and validation

```rust
pub trait FormField {
    type Value;
    /// Parse and validate a raw string form value (as it would arrive from
    /// an HTTP POST body) into a typed value, or a field-level error.
    fn clean(&self, raw: Option<&str>) -> Result<Self::Value, FieldError>;
}

pub struct CharField { pub max_length: Option<usize>, pub required: bool }
pub struct IntegerField { pub min: Option<i64>, pub max: Option<i64>, pub required: bool }
pub struct BooleanField { pub required: bool }  // required: bool here means "must be true", matching Django's BooleanField semantics for required checkboxes (e.g. "I agree to terms"), not "must be present"
pub struct EmailField { pub required: bool }    // validates a (deliberately simple, not fully RFC 5322 compliant) email shape — an allowlist-style regex/parse good enough to catch real mistakes, not a formal grammar
```

`#[derive(Form)]` on a struct generates field metadata (mirroring `#[derive(Model)]`'s `ModelMeta` pattern) plus a `clean(&self, data: &HashMap<String, String>) -> Result<CleanedData, FormErrors>` method, where `CleanedData` is a per-form generated struct holding the typed, validated values, and `FormErrors` maps field names to their validation errors (plus a `__all__`-style slot for cross-field errors from a form-level `clean()` hook, matching Django's non-field-error convention).

`clean_<field_name>()` hooks: if the derived struct's *implementation* (a hand-written `impl` block alongside the derive, not generated) provides a method named `clean_<field>`, the generated `clean()` calls it after the field's own basic type/required validation passes, letting it raise additional field-specific errors (Django's exact pattern — e.g. `clean_username` checking uniqueness against the database). Since v1's `Form` doesn't require a database connection for basic per-field cleaning, `clean_<field>` hooks that need one (uniqueness checks) take an optional `&Database` parameter — check the ergonomics of this against `ModelForm`'s actual use cases once building it, this is the one part of this design most likely to need adjustment once real code exercises it.

## `ModelForm`

`ModelForm<T: Model>` (or a `#[derive(ModelForm)]` proc macro parameterized on a model type — pick whichever is more ergonomic to implement, both achieve the same goal) generates form fields directly from `T::meta().fields`, mapping `FieldKind` to the closest `FormField` (`Char`/`Text` → `CharField` with `max_length` carried over, `Integer`/`BigInt` → `IntegerField`, `Boolean` → `BooleanField`, `Email` → `EmailField`; other `FieldKind`s not yet represented by a v1 `FormField` type produce a compile error naming the unsupported field, the same "honest error over silent wrong behavior" discipline used throughout this project's macro work) — Django's biggest form productivity win (define the model once, get a matching form for free) ported directly.

## Rendering

Django's `{{ form.as_div }}`/`{{ form.as_table }}` render a form as HTML from Python, not from a template file — v1 matches this: `Form::as_div(&self) -> String` (and `as_table`) produce ready-to-embed HTML directly (label + input + error list per field, wrapped in `<div>`s or table rows), usable inside a `djangors-template` template via `{{ form.as_div()|safe }}` (needing MiniJinja's `safe` filter/marker so the pre-escaped HTML isn't double-escaped — verify this integrates cleanly with the auto-escaping built in 4.4 before considering this piece done). This is a plain string-building function, not a template file itself, matching Django's actual implementation approach (Django's form rendering historically predates its own template-based form renderer, which is itself opt-in) — simplest correct choice for v1.
