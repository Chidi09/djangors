# 5.6 part 3 — Changelist bulk actions: bulk delete (v1)

**Status:** design, not yet dispatched. Follows 5.6.2 (`list_filter`, commit `cba2109`). See
`docs/design/phase-5-roadmap.md` for full Phase 5 context.

## Scope: delete only, one action, two-step confirm — and why

The roadmap's own sequencing groups "bulk actions (delete first, then CSV export...)" — this
part is delete only. With exactly one action, Django's `<select name="action">` action-picker
dropdown would be pure ceremony; this part is a single "Delete selected" submit button. When
CSV export (or any second action) is added later, that's the point to introduce a real action
dispatch mechanism (a `?action=` value or an actions registry) — do not build that scaffolding
now for a single action, it would be speculative.

**Bulk delete gets the same two-step confirm-then-act pattern as 5.5's single-object delete**,
not an immediate one-click delete. This is a deliberate consistency choice, not extra caution
for its own sake: 5.5 already established that any admin delete goes through a confirmation
step before anything is removed, and there's no reason bulk delete (strictly higher blast
radius than single delete) should be less careful than the thing it's built from. Concretely:
the SAME route handles both steps, distinguished by whether a `confirm` field is present in the
POST body — this mirrors Django's own bulk-action confirm flow (`request.POST.get('post') ==
'yes'`) and avoids inventing a second route just to tell "show confirm" apart from "actually
delete".

**The bulk confirm page does NOT run 5.5's cross-model related-object collection per selected
object.** For N selected objects, calling `collect_related_objects` (which itself walks every
registered model) N times is an unbounded amount of work for a single request as N grows — a
real cost the single-object page never had to consider. v1's bulk confirm page just lists which
objects (by pk + primary display field) are about to be deleted, nothing more. Upgrading this to
show related-object warnings per selected object is a reasonable future improvement, not part
of this task — note it in the roadmap ledger when this lands, don't build it now.

## Route: one new route, POST only

```rust
.post(
    "/{app:slug}/{model:slug}/bulk-delete/",
    move |req: Request, params: PathParams| {
        admin_bulk_delete_post(req, params, bulk_delete_admins.clone())
    },
)
```

Same closure-capture pattern as every other admin route (`urls()`, ~line 481-560 as of 5.6.2 —
clone the admins vec into its own named binding for this route same as the others). No `{pk}`
in the path — the set of pks to act on comes from the POST body, not the URL, since it's a
variable-length selection.

## Reading the selected pks: why `Form<HashMap<String, String>>` doesn't work here

Every existing admin POST handler (`admin_add_post`, `admin_change_post`, `admin_delete_post`)
uses `Form::<std::collections::HashMap<String, String>>::from_request(&req)`. **That extractor
is wrong for this route** — a changelist with multiple checked checkboxes, all named
`selected`, produces a form body like `selected=1&selected=3&selected=7&confirm=1`, and
deserializing that into a `HashMap<String, String>` silently keeps only the *last* `selected`
value, discarding the rest. This would silently bulk-delete only one of several checked rows —
a real, easy-to-miss bug if the existing extractor pattern is copied without noticing this
case.

Use `Form::<Vec<(String, String)>>::from_request(&req)` instead — `djangors_core::extract::Form<T>`
is generic over any `T: serde::de::DeserializeOwned` (`crates/djangors-core/src/extract.rs`
~line 92-102, backed by `serde_urlencoded::from_bytes`), and `serde_urlencoded` supports
deserializing a form body into a `Vec<(String, String)>` of *all* key-value pairs in order,
duplicates included — confirm this compiles and behaves as expected with a quick check before
relying on it if there's any doubt, but this is a standard, well-supported `serde_urlencoded`
target type, not something exotic.

```rust
let Form(pairs) = Form::<Vec<(String, String)>>::from_request(&req).await?;
let is_confirm = pairs.iter().any(|(k, v)| k == "confirm" && v == "1");
let mut pks: Vec<i64> = Vec::new();
for (k, v) in &pairs {
    if k == "selected" {
        let pk = v
            .parse::<i64>()
            .map_err(|_| DjangorsError::BadRequest("invalid selected pk".to_string()))?;
        pks.push(pk);
    }
}
```

Strict parsing (a malformed `selected` value is a `BadRequest`, not silently skipped) — this
matches the existing strictness convention everywhere else a pk is parsed in this codebase
(`params.get_as::<i64>("pk")` in every other admin route already fails hard on a bad value, not
skip-and-continue).

## Handler logic

```rust
async fn admin_bulk_delete_post(
    req: Request,
    params: PathParams,
    admins: Vec<Arc<dyn ModelAdmin>>,
) -> Result<Response, DjangorsError> {
    require_staff(&req).await?;

    let app = params.get("app").unwrap_or("");
    let model = params.get("model").unwrap_or("");
    let admin = admins
        .iter()
        .find(|a| { let meta = a.model_meta(); meta.app_label == app && meta.struct_name.to_lowercase() == model })
        .ok_or(DjangorsError::NotFound)?;

    let db = req
        .state::<djangors_db::Database>()
        .ok_or_else(|| DjangorsError::Internal("Database connection not found".to_string()))?;

    let Form(pairs) = Form::<Vec<(String, String)>>::from_request(&req).await?;
    // ... parse is_confirm / pks as shown above ...

    if pks.is_empty() {
        // Nothing selected - go back to the changelist, nothing to confirm or do.
        return Ok(Response::redirect(&format!("/{}/{}/", app, model)));
    }

    if !is_confirm {
        // Step 1: render the confirm page, listing each selected object.
        let mut items_html = String::new();
        for &pk in &pks {
            if let Some(row_vals) = admin.get_by_pk(db, pk).await? {
                let display = row_vals
                    .iter()
                    .map(|(_, v)| v.to_string())
                    .collect::<Vec<_>>()
                    .join(", ");
                items_html.push_str(&format!(
                    "<li>{}</li>",
                    djangors_core::html_escape(&display)
                ));
            }
            // A pk that no longer exists (already deleted concurrently) is just
            // skipped from the listing - it'll be a no-op in step 2 as well.
        }
        let hidden_inputs: String = pks
            .iter()
            .map(|pk| format!("<input type=\"hidden\" name=\"selected\" value=\"{}\">", pk))
            .collect();
        let html = format!(
            "<p>Delete {} selected object(s)?</p><ul>{}</ul>\
             <form method=\"post\">{}<input type=\"hidden\" name=\"confirm\" value=\"1\">\
             <input type=\"submit\" value=\"Confirm Delete\"></form>",
            pks.len(), items_html, hidden_inputs
        );
        return Ok(Response::html(StatusCode::OK, html));
    }

    // Step 2: actually delete. Best-effort per pk - a pk already gone (race, or
    // simply reselected after step 1 already removed it) is not an error, same
    // "false = already gone, not a failure" reasoning admin_delete_post already
    // uses for the single-object route.
    for &pk in &pks {
        admin.delete_by_pk(db, pk).await?;
    }
    Ok(Response::redirect(&format!("/{}/{}/", app, model)))
}
```

Note the confirm page's form action is omitted (defaults to the current URL, i.e. the same
`bulk-delete/` route) — same as 5.5's single-delete confirm form, which also omits `action`.

## Changelist page: add checkboxes + wrap the table in a form

In `admin_changelist` (`crates/djangors-admin/src/lib.rs`), the existing `<table>` is not
currently inside a `<form>`. Wrap it:

- Open `<form method="post" action="bulk-delete/">` before the table, close `</form>` after the
  pager (a bulk-delete submit only needs to reach the server, not preserve `o`/`q`/filter state
  across the submit — those are only relevant to *links*, not this one destructive POST — so
  this form does not need `build_query_string`/hidden `o`/`q`/filter inputs the way the search
  form does).
- Add one more `<th></th>` (empty header) at the start of `header_html`'s row, for the checkbox
  column — it's not one of `page_data.columns`, so build it separately, not via that loop.
- Add `<td><input type="checkbox" name="selected" value="{pk}"></td>` as the FIRST cell of each
  body row, using `page_data.pks[row_index]` (the same field 5.6.1 added for the edit-link fix —
  reuse it here too, don't re-derive the pk from `columns`).
- Add a submit button after the table (inside the form): `<input type="submit" value="Delete
  selected">`.

No "select all" checkbox in v1 — that needs client-side JS (this admin has none anywhere yet,
deliberately, until 5.8 theming) or a more complex "select all matching this filter across all
pages" server-side flow (Django itself needs JS for its own select-all checkbox). Individual
checkboxes only is the honest, working v1.

## What NOT to touch in this task

- No action-picker dropdown / generic bulk-actions registry — single hardcoded "delete
  selected" action and route, as explained above.
- No CSV/XLSX export.
- No related-object collection on the bulk confirm page (see scope section above).
- No changes to the single-object delete routes/handlers from 5.5.
- No changes to `render_form`, add/change routes, `list_display`/`search_fields`/`list_filter`
  logic from 5.6.1/5.6.2.
- No changes to `djangors-macros`.

## Required tests

Add to the existing `#[cfg(test)] mod tests` block in `crates/djangors-admin/src/lib.rs` (same
Postgres-backed socket-level style as every other test in this file):

1. Insert 3 rows. POST to `bulk-delete/` with `selected=<pk1>&selected=<pk2>` (no `confirm`) →
   200, response body lists both selected objects' display values, does NOT mention the third
   (unselected) row, and both rows still exist in the DB afterward (nothing deleted yet — this
   is the test that would catch the `HashMap` multi-value bug if the wrong extractor were used,
   since a `HashMap`-based implementation would only see one of the two `selected` values).
2. POST the same `selected=<pk1>&selected=<pk2>` again, this time WITH `confirm=1` → 302
   redirect to the changelist, both rows actually gone from the DB, the third (unselected) row
   still present.
3. POST with no `selected` values at all (empty selection) → redirects without error, nothing
   deleted.
4. POST with a `selected` value that isn't a valid integer → 400 Bad Request.
5. Unauthenticated / non-staff POST → 401 / 403 (mirror the existing pattern from every other
   admin route's auth tests).
