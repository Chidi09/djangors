# 10.3 — a compile-time-enforced "impossible to misuse" scoped viewset

## Scope

Item #2 of the architecture-parity initiative ([[10.2's]] design doc / `PLAN.md`'s new addendum).
The `school-management-saas-` codebase's single most-praised pattern was
`TenantScopedModelViewSet.get_queryset()` raising `NotImplementedError` by default — you cannot
accidentally inherit an unsafe, unscoped queryset; every subclass is *forced* to provide real
tenant-scoping logic. Rust has no class inheritance, so this can't be ported literally, but Rust
has something strictly **stronger** available: a trait with a required method and no default
implementation fails to *compile* if not implemented, rather than merely raising at the moment the
endpoint is actually hit. This slice builds that.

**Deliberately excluded from this dispatch**: this is NOT specifically about multi-tenancy (no
`School`/tenant model exists in djangors itself, and shouldn't — that's application-level, the same
way `school-management-saas-`'s own `School` model lives in ITS OWN code, not in Django itself).
This is a general **mandatory-queryset-scoping mechanism** any project can use for tenant isolation,
row-level ownership (a user only sees their own records), soft-delete filtering, or any other
"every query through this viewset must apply this filter, and forgetting to isn't an option" need.

## The real design

Read `crates/djangors-rest/src/lib.rs`'s existing `ViewSet<M>` in full first (lines ~519-800ish —
`list`/`list_with_config`/`retrieve`/`create`/`update`/`destroy`) to understand exactly where each
method currently builds its base `QuerySet::<M>::new()`. **Do not modify `ViewSet<M>` itself** —
it's existing, tested, working code used by real routes; this is purely additive.

Add a new trait, e.g.:

```rust
/// A model whose queries must always be scoped by some mandatory, caller-defined filter
/// (tenant isolation, row-level ownership, soft-delete exclusion, etc.).
///
/// Unlike Python/Django, where a base viewset can only enforce this at runtime (by raising
/// `NotImplementedError` the first time an unscoped subclass is actually called), this trait has
/// no default implementation for `scope` — a type that doesn't implement it simply won't compile
/// with `ScopedViewSet`, which is a *stronger* guarantee than the runtime check it's inspired by.
pub trait Scoped: Model + FromRow + Send + Sync + 'static {
    /// Applies mandatory scoping to a base queryset. Called before every read/write operation
    /// `ScopedViewSet` performs. Return an error if the request doesn't carry whatever context
    /// scoping requires (e.g. no authenticated user, no tenant in request state).
    fn scope(req: &Request, qs: QuerySet<Self>) -> Result<QuerySet<Self>, DjangorsError>;
}
```

Then a new `ScopedViewSet<M: Scoped>` type (parallel structure to `ViewSet<M>`, same
`list`/`list_with_config`/`retrieve`/`create`/`update`/`destroy` method set and behavior) whose
implementation is identical to `ViewSet<M>`'s **except** every place `ViewSet<M>` currently starts
from `QuerySet::<M>::new()`, `ScopedViewSet<M>` starts from `M::scope(&req, QuerySet::new())?`
instead — including in `create` (so a newly-created record can have scoping fields auto-populated
if you design `scope` to also be usable that way — investigate whether a single `scope` method
naturally covers both read-filtering and write-injection, or whether write paths need a distinct
hook; make the real design call and document it clearly either way, don't force a bad fit). Add
`scoped_viewset_routes::<M: Scoped>(router, base_path)` mirroring the existing `viewset_routes`
free function.

- A real, compiling example proving the "impossible to misuse" property is genuinely enforced:
  write a small test model implementing `Scoped` with real scoping logic (e.g. filtering by a
  `tenant_id` extracted from request state), and — as a **doc comment or code comment**, not a
  runnable test — show what happens if someone tries to use `ScopedViewSet::<SomeModel>` where
  `SomeModel` does NOT implement `Scoped`: it's a compile error, and you should show/describe the
  actual compiler error message you get when you try it (temporarily, to prove it, then remove the
  broken attempt).
- A real, working end-to-end test: two "tenants" (or two "owners," whatever the scoping key is)
  each with their own rows in the same table, a request scoped to tenant A only ever seeing tenant

  reasoning about the code.
- `cargo fmt --all -- --check`, `cargo build --workspace`, `cargo clippy --workspace --all-targets
  -- -D warnings`, `cargo test --workspace` all clean.

  untouched (diff should show zero changes to the existing type).
