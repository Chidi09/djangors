# 5.8 part 9 — CSRF: accept a `csrfmiddlewaretoken` form field, not just the header (core only)

**Status:** design, not yet dispatched. Follows 5.8.8 (per-site branding, commit `ad23e39`).
Revisits the CSRF header-only limitation documented since 5.4 and reconfirmed in
`crates/djangors-core/src/lib.rs`'s module doc comment and `middleware.rs`'s `CsrfLayer` doc
comment. See `docs/design/phase-5-roadmap.md`.

**This is Slice A of two.** This slice is **core-crate only** (`djangors-core`: `CsrfLayer`/
`CsrfService` in `middleware.rs`, `Router::dispatch`/`dispatch_debug` in `router.rs`) — it does
**not** touch `djangors-admin` or any template. Slice B (a separate design doc, dispatched only
after this one is verified and committed) wires a hidden `csrfmiddlewaretoken` input into the
admin's actual `<form>` elements using the mechanism this slice builds.

**Read this whole document before implementing anything.** This is a security-relevant,
architecturally non-trivial change to core request-handling middleware — unlike every prior 5.8.x
slice, several *existing tests are expected to require real, deliberate rewrites*, not just "stay
passing unmodified." That is called out explicitly in its own section below; do not treat a
failing pre-existing CSRF unit test as an error to fix by reverting behavior — check the "Tests
that MUST change" section first.

## The gap, confirmed directly from source

`crates/djangors-core/src/middleware.rs`'s `CsrfLayer` doc comment states plainly: "This
middleware only validates CSRF tokens via the custom HTTP header... It does **not** look at or
validate form body fields... Consequently, classic HTML `<form>` submissions without client-side
JavaScript headers are NOT protected in this version." Confirmed by reading `CsrfService::call`
directly: for an unsafe method (POST/PUT/PATCH/DELETE), if the `X-CSRFToken` header is missing or
doesn't match the cookie-derived token, the middleware returns a 403 **immediately**, before the
request ever reaches a handler — meaning a real browser rendering a plain `<form method="post">`
(no JS setting a custom header) literally cannot successfully submit to any CSRF-protected route
today. Confirmed via grep that neither `examples/polls/tests/voting.rs` nor
`examples/school/tests/admin_crud.rs` (the only two tests that exercise the *real* tower stack
including `CsrfLayer`) test this path either — both manually set `X-CSRFToken` on their raw HTTP
requests, faking the AJAX-style path a real unmodified `<form>` cannot take. **No existing test
anywhere in this repo proves a real HTML form, as actually rendered by the admin today, can be
submitted successfully by an unmodified browser.**

## Why this can't be fixed inside `CsrfLayer` alone

`CsrfService::call` is generic over the body type `B` (`Service<hyper::Request<B>>` for `B: Send +
'static`, no `Body` trait bound). In the real production stack (`crates/djangors-core/src/app.rs`,
`ServiceBuilder::new().layer(SecurityHeadersLayer).layer(CsrfLayer::new()).service(router_service)`
where `router_service: RouterService` implements `tower::Service<hyper::Request<hyper::body::
Incoming>>` — a *concrete*, non-generic body type), `B` gets monomorphized to
`hyper::body::Incoming`. To inspect a form field, `CsrfService` would need to buffer/collect that
body — but `hyper::body::Incoming` is an opaque, connection-bound streaming type that **cannot be
reconstructed from a `Bytes` buffer** once consumed. There is no way for `CsrfService` to collect
the body to check it and then hand a still-readable body of the *same required type* to the
downstream `RouterService`, without a much larger refactor making `RouterService` generic over any
`hyper::body::Body` (a legitimate but separate, larger undertaking — not what this slice does).

**The fix instead moves the fallback check to where the body is already being buffered**:
`Router::dispatch`/`dispatch_debug` (`crates/djangors-core/src/router.rs`) already call
`http_body_util::BodyExt::collect(body).await` to build `body_bytes: Bytes` for the framework's
own `Request` type — the exact same bytes `Form<T>`'s `FromRequest` impl later parses via
`serde_urlencoded::from_bytes` (`crates/djangors-core/src/extract.rs`). This slice adds the
CSRF-form-field fallback check *there*, reusing the bytes that are collected anyway — no new body
consumption, no reconstruction problem.

## The design: `CsrfLayer` defers instead of rejecting outright

Change `CsrfService::call`'s unsafe-method branch:

- **Header present and valid (unchanged, fast path):** proceed exactly as today — insert
  `CsrfToken(token_value)` into `req.extensions_mut()`, call the inner service. Zero behavior
  change for AJAX/JSON-style clients that already set the header; zero new body-buffering cost for
  this, the common API-client case.
- **Header missing or invalid (the changed branch):** instead of building and returning a 403
  response immediately, insert a **new** extension type carrying the expected token value, and let
  the request continue to the inner service (the router) — the actual accept/reject decision for
  this case moves downstream.

```rust
/// Inserted by `CsrfService` into a request's extensions when the header
/// check did not pass for an unsafe-method request, carrying the token
/// value a fallback form-field check must match. Only `Router::dispatch`/
/// `dispatch_debug` act on this — if a handler is reached without a
/// `Router` layer above it ever resolving this (e.g. a raw `service_fn`
/// test double), no fallback check ever runs and the request behaves as
/// if CSRF passed, so this type is deliberately not part of any public,
/// reusable "is this request CSRF-valid" API — it's an internal signal
/// between these two specific layers.
pub(crate) struct CsrfPendingFormCheck(pub String);
```

Insert `CsrfPendingFormCheck(token_value.clone())` (in addition to the existing, unconditional
`CsrfToken(token_value)` insertion — handlers that read `req.ext::<CsrfToken>()` today, e.g. to
embed the token into a re-rendered form after a validation error, should keep working exactly as
before regardless of which branch was taken) on the missing/invalid-header branch, then fall
through to `inner.call(req)` the same way the success branch already does — **do not** early-return
here anymore.

## `Router::dispatch`/`dispatch_debug`: the fallback check

After building `body_bytes: Bytes` and the framework `Request` (both functions, right after the
existing `let req = Request::new(...).with_state(...).with_extensions(parts.extensions);` line —
`with_extensions` is what makes `CsrfPendingFormCheck` visible via `req.ext::<CsrfPendingFormCheck>()`),
add:

```rust
if let Some(pending) = req.ext::<CsrfPendingFormCheck>() {
    let is_form_content_type = req
        .header("content-type")
        .and_then(|v| v.to_str().ok())
        .is_some_and(|ct| ct.starts_with("application/x-www-form-urlencoded"));

    let form_token = if is_form_content_type {
        serde_urlencoded::from_bytes::<std::collections::HashMap<String, String>>(
            req.body_bytes().await,
        )
        .ok()
        .and_then(|form| form.get("csrfmiddlewaretoken").cloned())
    } else {
        None
    };

    let valid = form_token
        .map(|t| crate::middleware::constant_time_eq(t.as_bytes(), pending.0.as_bytes()))
        .unwrap_or(false);

    if !valid {
        let err = DjangorsError::Forbidden("CSRF token missing or invalid".to_string());
        // adapt to dispatch's/dispatch_debug's own existing error-response shape — read how the
        // body-collect-error branch just above already builds its response (the `debug` branch in
        // `dispatch_debug` in particular renders a debug page, not a plain response) and mirror
        // that, don't introduce a third, different error-response pattern in the same function
    }
}
```

Confirmed the exact real `Request` API by reading `crates/djangors-core/src/request.rs` directly
(don't assume the above is 100% correct without re-checking it yourself too, this was verified
once but re-verify before use): `req.header(name: &str) -> Option<&HeaderValue>`,
`req.body_bytes().await -> &[u8]` (trivially async — the body is already fully buffered by this
point, this accessor just exists as a stable async-shaped API for callers, mirroring how `Form<T>`'s
own `FromRequest` impl in `extract.rs` already calls it). `body` is a **private** field on
`Request` — there is no direct field access, `body_bytes()` is the only way in, and it must be
`.await`ed even though it resolves immediately. `DjangorsError::Forbidden(String)` already exists
and is exactly the variant `CsrfLayer`'s own 403 path conceptually maps to (confirmed by reading
`crates/djangors-core/src/error.rs`) — reuse it, don't add a new variant. `constant_time_eq`
currently is a private `fn` in `middleware.rs` — change it to `pub(crate)` so `router.rs` can reuse
it rather than duplicating timing-safe comparison logic.

**Both `dispatch` and `dispatch_debug` need this same check** (mirrored, not shared via a helper
unless one already fits naturally — check whether factoring a shared private fn taking `(&Request)
-> Result<(), DjangorsError>` cleanly serves both call sites without fighting the two functions'
different error-response paths; if it doesn't fit cleanly, duplicating ~10 lines is fine and
matches this codebase's existing tolerance for two near-identical functions with different
debug-page-vs-production-page branching, already the case throughout `dispatch`/`dispatch_debug`).

## Tests that MUST change (read this before treating a red test as a bug)

Unlike every 5.8.x slice so far, this task **intentionally changes observable behavior** for one
specific case (missing/invalid CSRF header on an unsafe method), so tests that assert the *old*
behavior for that exact case need real rewrites, not preservation:

- `test_unsafe_method_no_header_or_mismatched_header_fails` (or whatever the actual test name is —
  read the real test, the name above is a guess) at the "Case 1: Cookie present, header missing"
  and "Case 2: Cookie present, header mismatched" scenarios in `middleware.rs`'s test module:
  these currently assert `resp.status() == 403` **and** `counter == 0` (inner service never
  called) directly against `CsrfLayer` wrapping a bare dummy `service_fn` with no CSRF-aware body
  checking. Under the new design, the inner service **is** now called (the decision moved
  downstream) — for a dummy inner service that just returns 200 unconditionally, these specific
  assertions (`counter == 0`, direct 403 from `CsrfService` itself) no longer describe reality and
  must be rewritten to assert what actually happens now: the request reaches the inner service
  (`counter == 1`), and separately, `CsrfPendingFormCheck` was inserted into the request's
  extensions with the expected token value (assert on that instead, since a bare dummy service
  can't perform the fallback check itself — that's the router's job, tested separately below).
- `test_end_to_end_router_csrf`: this one uses the **real** `router.dispatch(req)` inside its inner
  `service_fn`, so it exercises the actual fallback path end-to-end. Its case 3 ("POST carrying
  cookie but wrong/mismatched header value", asserting `403`) should **still produce 403** under
  the new design — a mismatched header now defers to the router's fallback, which finds no
  `csrfmiddlewaretoken` field in the (empty, `Full::new(Bytes::new())`) body and correctly still
  rejects — so this specific assertion's *outcome* doesn't need to change, but **read it and
  confirm this reasoning holds against the real test**, don't just assume. This test is also the
  natural place to **add a new case 4**: a POST with the valid cookie, **no** `X-CSRFToken`
  header, `Content-Type: application/x-www-form-urlencoded`, and a body of
  `csrfmiddlewaretoken=<the real token value>` — asserting `200` — this is the proof that the
  actual gap this slice targets is closed, a real form-body-only submission now succeeds.
- Any other `CsrfLayer`/`CsrfService`-focused test asserting the old "missing/invalid header always
  immediately 403s with the inner service never invoked" behavior needs the same treatment — read
  every test in `middleware.rs`'s CSRF section (not just the two named above; there may be more —
  search for `CsrfLayer::new()` in the test module and check each one's assertions against the new
  behavior) before assuming any one of them is unaffected.

**Everything else must stay passing unmodified**: `test_unsafe_method_cookie_present_matching_header_succeeds`
(the fast path, genuinely untouched), the cookie-generation/`Set-Cookie` tests, the `Secure` flag
test, `SecurityHeadersLayer`'s own tests, host-validation tests, and — critically —
`examples/polls/tests/voting.rs` and `examples/school/tests/admin_crud.rs`, which both always send
a valid `X-CSRFToken` header and so always take the unchanged fast path; they must pass exactly as
before with zero modification (this slice doesn't touch `djangors-admin` or its rendered forms at
all — that's Slice B).

## What NOT to touch

- `djangors-admin` — nothing in this crate changes in this slice. No template gets a hidden
  `csrfmiddlewaretoken` input yet; that's Slice B, dispatched separately after this slice is
  verified and committed.
- `SecurityHeadersLayer` — untouched.
- The cookie-generation/`Set-Cookie` logic, `generate_csrf_token()` — untouched.
- The GET/safe-method path — untouched (never enters the `is_unsafe` branch at all).
