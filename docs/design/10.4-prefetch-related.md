# 10.4 — batch eager-loading (`prefetch_related`-equivalent) + N+1 regression-test tooling

## Scope

Item #3 of the architecture-parity initiative ([[10.2]]/[[10.3]]'s design docs, `PLAN.md`'s
addendum). Djangors already has `QuerySet<T>::select_related` (see
`crates/djangors-orm/src/queryset.rs:745`) for the **forward** FK direction (row has a FK column,
you want the one related parent row, batched into 2 queries total regardless of row count). What's
missing, confirmed by direct investigation of this codebase:

1. **Reverse relation batch-loading** (Django's `prefetch_related`): given a `Vec<Parent>` you
   already fetched, load ALL children across ALL those parents in one extra query, grouped by
   parent id — instead of looping and issuing one child-query per parent (the classic N+1 trap).
   `related_name` metadata is already captured on every FK declaration (`RelationMeta.related_name`
   in `crates/djangors-orm/src/meta.rs:137`) but is **write-only today** — nothing reads it to
   build a reverse query path. Confirmed via grep: zero hits for `RelatedManager`/`ReverseRelation`
   anywhere in the workspace.
2. **Query-counting test infrastructure**: there is currently no way for a test to assert "exactly
   N real SQL queries ran." `Database` (`crates/djangors-db/src/database.rs:18`) is a thin
   `{ pool: PgPool }` wrapper with zero instrumentation; every `QuerySet` terminal operation in
   `queryset.rs` calls `db.pool()` directly (9 call sites: lines 324, 375, 393, 499, 637, 716, 736,
   790, 830). Without a counter, an N+1 regression can only be "proven" by manual reasoning about
   the code, not by an actual assertion a CI run enforces.

**Deliberately excluded from this dispatch**: many-to-many prefetching (no M2M support exists
anywhere in the ORM yet — this is FK/reverse-FK only, matching the existing `select_related`'s own
scope); a REST-level `?include=` query param or any `djangors-rest` integration (this item is
ORM-only, the same way 10.2 was migrations-only and 10.3 was `djangors-rest`-only — REST-level
"expand nested relations in list responses" can be a later slice once this primitive exists);
nested/recursive prefetching (prefetching a relation's own relations transitively) — one level
deep only, same as `select_related`.

## Part A — `prefetch_related`

Read `select_related` (`queryset.rs:745`) in full first to match its error-handling and validation
style (it validates the relation field exists and the target type matches, via `T::meta()`).

Add a new function (free function or associated fn on `QuerySet`, whichever fits the existing
module's style better — use your judgment, but keep it consistent with `select_related`'s shape):

```rust
/// Batch-loads the reverse side of a FK relation for a slice of already-fetched parent rows,
/// grouping results by parent primary key. Issues exactly one query regardless of how many
/// parents are passed (`WHERE <child_fk_column> = ANY($1)` over the parents' primary keys).
///
/// `related_name` must match a `RelationMeta.related_name` declared on `R` (the child model)
/// whose `target()` is `T` (the parent model) — i.e. the same string passed to
/// `#[djangors(foreign_key(related_name = "..."))]` when `R`'s FK field was declared.
pub async fn prefetch_related<T, R>(
    db: &djangors_db::Database,
    parents: &[T],
    related_name: &str,
) -> Result<std::collections::HashMap<i64, Vec<R>>, OrmError>
where
    T: Model,
    R: Model + FromRow + Clone,
```

Implementation sketch (adjust as the real APIs require — verify every type/method you use against
real source before assuming its shape, this codebase has a history of dispatches inventing plausible
but nonexistent APIs):

1. Find the `RelationMeta` in `R::meta().relations` whose `related_name == Some(related_name)` and
   whose `(relation.target)().struct_name == T::meta().struct_name`. If none found, return a
   descriptive `OrmError` (look at how `select_related` reports its own "relation not found"/"type
   mismatch" errors and mirror that).
2. Collect the parents' primary key values from the `parents` slice (use `T::meta()` to find the PK
   field, then read it via whatever mechanism `T`'s `Model`/`field_values()` trait already exposes
   — check how `serialize()` in `djangors-rest` or `select_related` itself extracts a field value
   by name to avoid inventing a new mechanism).
3. Issue ONE query: `SELECT * FROM <R's table> WHERE <relation.field_name column> = ANY($1)`
   against the collected parent pks (mirror `select_related`'s existing `= ANY($1)` pattern at
   queryset.rs — it already does exactly this for the other direction).
4. Group the resulting `R` rows into a `HashMap<i64, Vec<R>>` keyed by each row's own FK column
   value (the parent id it points back to). Parents with no matching children get no entry (caller
   should treat a missing key as an empty `Vec`, document this).

## Part B — query-counting infrastructure

In `crates/djangors-db/src/database.rs`:

- Add a field to `Database` holding an `Arc<std::sync::atomic::AtomicUsize>` (call it whatever
  fits, e.g. `query_count`). `Database` already derives `Clone`, and clones must share the SAME
  counter (it's cloned constantly across requests/tests via `.with_state(db.clone())`) — an `Arc`
  achieves that, a plain `usize` would not.
- `connect()` initializes it to `Arc::new(AtomicUsize::new(0))`.
- Add `pub fn record_query(&self)` — increments the counter (`Ordering::Relaxed` is fine, this is a
  test-observability counter, not a correctness-critical value).
- Add `pub fn query_count(&self) -> usize` — reads the current count.
- Add `pub fn reset_query_count(&self)` — resets to 0 (tests will typically reset right before the
  code path under test, then assert the exact count after).

In `crates/djangors-orm/src/queryset.rs`: call `db.record_query();` immediately before **every**
one of the 9 real query-execution call sites listed above (`fetch_all`/`fetch_optional`/
`fetch_one`/`execute` — anywhere `db.pool()` is actually handed to sqlx to run a real query against
Postgres). Do not add it anywhere that doesn't actually hit the database. Also add it to your new
`prefetch_related` function's own single query, and to `select_related`'s two queries
(`queryset.rs:745`) if they aren't already covered by shared code paths — check whether
`select_related` reuses the same private query-execution helper as `all()`/`get()` or has its own
inline `sqlx::query(...).fetch_all(db.pool())` (per the investigation, it appears to build its own
SQL directly — confirm and instrument it directly if so).

## Required verification

- A real, Postgres-backed regression test proving prefetch avoids N+1: create two tables (a parent
  and a child with a FK + `related_name` back to the parent — reuse or extend the existing
  `SelectRelatedParent`/`SelectRelatedChild` fixtures in `crates/djangors-orm/src/tests.rs:762-777`
  if that's a natural fit, or add a new pair), seed **at least 5 parents**, each with 2-3 children,
  then:
  - Reset the query counter, fetch all parents (`.all(db)` — 1 query), call `prefetch_related` for
    the children (1 more query), assert `db.query_count() == 2` **regardless of how many parents
    there are** (prove this isn't coincidentally true only for a tiny row count — 5+ parents is the
    point).
  - Assert the grouping is actually correct: each parent's `HashMap` entry contains exactly its own
    children, not another parent's.
  - As a contrasting negative-proof test (or a clearly-commented section of the same test): show
    that the NAIVE approach — looping over parents and issuing a separate filtered query per parent
    — really does cost `1 + N` queries by resetting the counter and measuring it, so the
    regression test actually demonstrates the problem `prefetch_related` solves, not just its own
    happy path.
- `cargo fmt --all -- --check`, `cargo build --workspace --all-targets`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace` all clean.
- Confirm `select_related` and every existing `QuerySet` method's public signature is unchanged
  (this should be purely additive to `queryset.rs` plus the new `Database` counter fields/methods,
  which are also purely additive).
