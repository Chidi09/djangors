# 5.7 part 2 — Wiring `has_perm` into every admin view

**Status:** design, not yet dispatched. Follows 5.7.1 (permissions data model, commit `bb284a4`).
See `docs/design/phase-5-roadmap.md` — this is the slice 5.7.1 explicitly deferred: "every admin
route currently checks only `is_staff`... wiring `has_perm` into actual view gates is 5.7.2."

## Read this first: this task has a real, unavoidable blast radius on existing tests

Every existing `djangors-admin` test that exercises real CRUD/changelist/bulk-delete/list_editable
behavior (not just the 401/403 auth-gate path) registers a "staff" fixture user with
`is_staff: true, is_superuser: false` and expects that user to freely use every admin feature.
Once this task lands, `is_superuser: false` staff users with **no explicit permission grants**
will correctly start getting `403 Forbidden` from every view they don't have the specific
permission for — because that is the entire point of this task. **This is not a regression to
work around; it's the intended new behavior, and every existing test's fixture must be updated to
match it.**

**The rule to apply uniformly:** in every existing test, the "staff" fixture user that's meant to
exercise real feature behavior (not specifically test the permission system) becomes
`is_superuser: true` instead of `false`. Superusers bypass `has_perm` entirely (per 5.7.1's own
`has_perm` doc comment — it was deliberately written to not special-case superusers itself, so
callers must check `is_superuser()` first), so this is the minimal, correct change to keep every
existing test asserting what it was actually meant to assert. **Do not grant individual
permissions to existing test fixtures instead of using `is_superuser: true`** — that would be
solving a problem those tests were never trying to solve, and would make 15+ existing tests
subtly about permissions when they aren't. The *new* tests this task adds (below) are where a
deliberately non-superuser staff user with specific/missing grants belongs.

Before writing any code, grep `crates/djangors-admin/src/lib.rs` for every
`is_superuser: false` occurrence (15 as of commit `bb284a4`) and classify each one:
- If it's the test's main "staff" user used to actually perform admin actions and assert `200`/
  `302` success → change to `is_superuser: true`.
- If it's a fixture specifically testing the *unauthenticated or non-staff* rejection path
  (asserting `401`/`403` before this task's changes) → leave it `is_superuser: false` (or however
  it's already set) since that test isn't about permissions at all, it's about the pre-existing
  `is_staff` gate, which is unchanged by this task.

Every existing test must still pass after this change, asserting the exact same outcomes it
already asserts — the fixture's `is_superuser` value is the only thing that should change in
those tests, not their assertions.

## Design decisions this slice resolves (flagged as open in the 5.7.1-era roadmap note)

1. **Per-view codename mapping**, using `sync_permissions`'s own codename format
   (`{app_label}.{action}_{model_name_lowercase}`, all lowercase — must match exactly or
   `has_perm` will never find a grant):

   | View | Action codename |
   |---|---|
   | `GET /{app}/{model}/` (changelist) | `view` |
   | `GET /{app}/{model}/export-csv/` | `view` |
   | `GET`/`POST /{app}/{model}/add/` | `add` |
   | `GET`/`POST /{app}/{model}/{pk}/change/` | `change` |
   | `POST /{app}/{model}/save-changelist/` (list_editable) | `change` |
   | `GET`/`POST /{app}/{model}/{pk}/delete/` | `delete` |
   | `POST /{app}/{model}/bulk-delete/` | `delete` |

2. **Missing permission → 403, same `DjangorsError::Forbidden` variant `require_staff` already
   uses** for "not staff" — Django itself doesn't differentiate the HTTP status between "not
   staff" and "staff but missing this permission," no reason to invent a distinction here.

3. **The admin index page filters to only models the user has `view` permission for** (or all
   models, for a superuser) — matching Django's own behavior, and the more coherent default:
   there's no reason to advertise a link to a model the user will just get 403'd on if they click
   it. This is the one place this task touches something other than a single `require_perm` call
   — see below.

4. **No UI-level hiding of action buttons based on permission** (e.g. the changelist's "Delete
   selected" button still renders even for a user without `delete` permission — they'd get a 403
   if they actually submit it). This is a deliberate v1 cut, not a security gap: the real
   enforcement point is the server-side check on the POST route, which this task adds
   unconditionally. Hiding buttons a user can't use is a UX nicety Django's admin also does, and
   is a reasonable future improvement once this lands — it needs per-request permission checks
   threaded into `admin_changelist`'s own rendering, which is more surface than this task's core
   goal of *actually enforcing* the permission.

## `require_staff` now returns the resolved user

```rust
async fn require_staff(req: &Request) -> Result<User, DjangorsError> {
    let auth = Auth::<User>::from_request(req).await?;
    if !auth.0.is_staff {
        return Err(DjangorsError::Forbidden(
            "staff status required".to_string(),
        ));
    }
    Ok(auth.0)
}
```

(Was `Result<(), DjangorsError>` — every existing call site (`require_staff(&req).await?;`, a bare
statement discarding the `Ok` value) still compiles unchanged with this new return type, since
Rust doesn't require a `Result`'s `Ok` payload to be used. This part of the change is safe on its
own; every call site listed below is being edited anyway to use the returned `User`.)

## New helper: `require_perm`

```rust
fn action_codename(meta: &'static ModelMeta, action: &str) -> String {
    format!(
        "{}.{}_{}",
        meta.app_label,
        action,
        meta.struct_name.to_lowercase()
    )
}

async fn require_perm(
    req: &Request,
    db: &djangors_db::Database,
    meta: &'static ModelMeta,
    action: &str,
) -> Result<User, DjangorsError> {
    let user = require_staff(req).await?;
    if user.is_superuser {
        return Ok(user);
    }
    let codename = action_codename(meta, action);
    let allowed = djangors_auth::has_perm(db, user.id, &codename)
        .await
        .map_err(|e| DjangorsError::Internal(e.to_string()))?;
    if !allowed {
        return Err(DjangorsError::Forbidden(format!(
            "permission '{}' required",
            codename
        )));
    }
    Ok(user)
}
```

## Handler-by-handler changes: reorder, then swap `require_staff` for `require_perm`

`require_perm` needs `db` (for `has_perm`) and `meta` (from the resolved `admin`, via
`admin.model_meta()`) — both of which every handler currently resolves *after* its
`require_staff(&req).await?;` call. **Every listed handler needs its top reordered**: resolve
`app`/`model` path params → look up `admin` in the registry → resolve `db` → call `require_perm`
with the right action string → *then* continue with the rest of the handler's existing logic
(which already needs `admin`/`db` anyway, so nothing downstream changes). Concretely, for
`admin_changelist` (and the same shape for every other handler in the table above):

```rust
async fn admin_changelist(
    req: Request,
    params: PathParams,
    admins: Vec<Arc<dyn ModelAdmin>>,
) -> Result<Response, DjangorsError> {
    let app = params.get("app").unwrap_or("");
    let model = params.get("model").unwrap_or("");

    let admin = admins
        .iter()
        .find(|a| {
            let meta = a.model_meta();
            meta.app_label == app && meta.struct_name.to_lowercase() == model
        })
        .ok_or(DjangorsError::NotFound)?;

    let db = req
        .state::<djangors_db::Database>()
        .ok_or_else(|| DjangorsError::Internal("Database connection not found".to_string()))?;

    require_perm(&req, db, admin.model_meta(), "view").await?;

    // ... rest of the function is completely unchanged from here on ...
}
```

Apply this exact reorder-then-swap to: `admin_changelist` (`"view"`), `admin_export_csv`
(`"view"`), `admin_add_get`/`admin_add_post` (`"add"`), `admin_change_get`/`admin_change_post`
(`"change"`), `admin_save_changelist_post` (`"change"`), `admin_delete_get`/`admin_delete_post`
(`"delete"`), `admin_bulk_delete_post` (`"delete"`). Every one of these already has the exact
`params.get("app")`/`params.get("model")`/registry-`.find()`/`db`-lookup block near its top in
the same shape — this is a mechanical, repeated change, not a structural rewrite. **Do not change
`NotFound` vs `Forbidden` precedence**: the `admin.ok_or(DjangorsError::NotFound)?` lookup must
still happen *before* `require_perm`, so a request for a genuinely nonexistent
`app`/`model` still 404s rather than 403ing (this is already the existing order in every handler
— just confirm the refactor doesn't accidentally reverse it).

## `admin_index`: filter by `view` permission instead of a single `require_perm` call

This is the one handler that doesn't map to a single codename — it lists every registered model,
so it needs a per-model check:

```rust
async fn admin_index(
    req: Request,
    _params: PathParams,
    registry: Vec<&'static ModelMeta>,
) -> Result<Response, DjangorsError> {
    let user = require_staff(&req).await?;

    let db = req
        .state::<djangors_db::Database>()
        .ok_or_else(|| DjangorsError::Internal("Database connection not found".to_string()))?;

    let mut body = String::new();
    for meta in &registry {
        if !user.is_superuser {
            let codename = action_codename(meta, "view");
            let allowed = djangors_auth::has_perm(db, user.id, &codename)
                .await
                .map_err(|e| DjangorsError::Internal(e.to_string()))?;
            if !allowed {
                continue;
            }
        }
        body.push_str(&format!(
            "<li><a href=\"{}/{}/\">{}.{}</a></li>",
            meta.app_label,
            meta.struct_name.to_lowercase(),
            meta.app_label,
            meta.struct_name
        ));
    }

    Ok(Response::html(StatusCode::OK, format!("<ul>{}</ul>", body)))
}
```

This is an N-query loop (one `has_perm` call per registered model for a non-superuser). For this
framework's current model counts (a handful in tests, a handful in `examples/polls`), this is
fine. Note it as a deferred optimization in the roadmap ledger when this lands (a single query
joining across all models' view codenames would be better at real scale) — not required for v1.

## What NOT to touch in this task

- No UI-level hiding of buttons/links based on permission state (see design decision 4 above).
- No admin UI for managing `Group`/`Permission`/assignments — still raw SQL or a script, per
  5.7.1's own scope note.
- No batching/optimizing `admin_index`'s N-query loop.
- No changes to `has_perm`, `sync_permissions`, or any of the 5.7.1 models themselves.
- No changes to `djangors-macros` or the ORM.

## Required tests

This task requires two kinds of test changes: (a) **updating existing tests' fixture users**
per the rule at the top of this doc (not new test scenarios — just `is_superuser: false` →
`true` on the "does real things" staff fixtures, confirmed to still pass with the exact same
assertions), and (b) **new tests actually exercising per-permission enforcement**, added to
`crates/djangors-admin/src/lib.rs`'s test module, following the same `DB_MUTEX`-guarded
Postgres-socket-level pattern as every other test in the file (this will need the
`auth_permission`/`auth_user_permissions`/`auth_user_groups`/`auth_group_permissions`/`auth_group`
tables created too, same `CREATE TABLE` shape as 5.7.1's own `test_permissions_and_groups` in
`crates/djangors-auth/src/tests.rs` — mirror those exact column definitions and quoting):

1. A staff, non-superuser user with **no** permissions at all → GET the changelist for a
   registered model → `403 Forbidden`.
2. The same user, after being granted the `view` permission for that specific model (insert a
   matching `auth_permission` row + a `auth_user_permissions` row linking them, using the exact
   `{app_label}.view_{model}` codename `action_codename` produces) → GET the changelist → `200`.
3. The same permissioned-for-`view`-only user → POST to that model's `add/` route → `403` (proves
   `view` doesn't imply `add` — the permissions are genuinely per-action, not all-or-nothing).
4. A staff, non-superuser user granted `view` via **group membership** (not a direct
   `UserPermission` row — `UserGroup` + `GroupPermission` instead) → GET the changelist → `200`
   (proves the admin's `require_perm` correctly goes through `has_perm`'s group path, not just
   its direct-permission path).
5. `admin_index` with a non-superuser staff user who has `view` permission for exactly one of
   two registered test models → the response body contains a link for that one model and does
   NOT contain a link for the other.
6. A superuser (regardless of any explicit grants, or lack thereof) → every action succeeds
   without needing any `auth_permission`/`auth_user_permissions` rows at all (proves the
   superuser bypass in `require_perm` actually skips `has_perm`, not just happens to pass it).

## Verification commands (unchanged standing process)

`cargo fmt --all` → `cargo build --workspace --all-targets` → `cargo clippy --workspace
--all-targets -- -D warnings` → `cargo test --workspace`. Postgres test DB as above. **Given this
task changes the observed behavior of every existing admin test's fixture user, running the FULL
existing test suite and confirming every single test still passes (not just the new ones) is the
single most important verification step in this task** — a failing pre-existing test here means
either a fixture wasn't updated per the rule above, or a handler's reorder introduced a real bug
(e.g. swapped `NotFound`/`Forbidden` precedence, or resolved `db` before the registry lookup that
can itself fail).
