# 8.3 — `djangors-rest` filtering/ordering + OpenAPI 3.1 generation

## Scope

Continues Phase 8 after 8.1/8.2 (`djangors-rest` core + auth, commits `a3f2257`, `e77c3cd`). Two
parts: query-param filtering/ordering for `ViewSet::list`, and real OpenAPI 3.1 schema generation
derived from `ModelMeta` — the "Rust's edge: schemas are actually correct" feature PLAN.md calls
out specifically, since the same compile-time metadata already drives serialization.

**Deliberately excluded from this dispatch, left for later 8.x slices**: throttling, the browsable
API HTML page, `djangors-channels`, background tasks.

## Part A — filtering/ordering for `ViewSet::list`

Read `crates/djangors-admin/src/lib.rs`'s `list_filter`/`search_fields` allowlist pattern (the
`ModelAdminConfig` fields, and how `admin_changelist` validates a requested filter/order field
against that allowlist before ever touching the database — grep for how `order_by` is validated,
since `djangors_orm`'s own `QuerySet::order_by` already returns a real `FieldNotFound` error for an
invalid field name, confirm whether that alone is a sufficient safety net or whether an explicit
allowlist is still warranted for a public API surface) — mirror the same allowlist discipline here,
since a REST API is a more exposed attack surface than the staff-gated admin.

```rust
pub struct ViewSetConfig {
    pub filterable_fields: &'static [&'static str], // exact-match ?field=value filters, empty = none allowed
    pub orderable_fields: &'static [&'static str],   // ?ordering=field / ?ordering=-field, empty = none allowed
}
```

Extend `ViewSet::list` (or however 8.2's `viewset_routes_with_permission` config shape ended up
structured — read the current real code first, don't assume the exact shape from this doc alone)
to accept a `ViewSetConfig`, parsing `?field=value` query params for any field in
`filterable_fields` (reject/ignore any query param not in the allowlist — don't silently accept an
arbitrary field name and let `QuerySet::filter`'s own `FieldNotFound` error become a confusing
500), and `?ordering=field`/`?ordering=-field` (leading `-` for descending, matching Django's own
convention) for any field in `orderable_fields`, using `QuerySet::order_by` directly.

**Required tests**: a real end-to-end test filtering `list` by an allowlisted field and confirming
only matching rows are returned; a non-allowlisted filter param being ignored (not erroring, not
silently matching everything — confirm the exact, deliberate behavior you chose and test it);
ordering ascending and descending by an allowlisted field with real, checkable row order.

## Part B — OpenAPI 3.1 generation

A real, generic schema generator walking any registered `Model`'s `ModelMeta` (the same struct
`djangors-admin`'s generic rendering and `djangors-rest`'s own `serialize`/`deserialize` already
walk — read `crates/djangors-orm/src/meta.rs`'s full `FieldKind` enum, confirmed to include Char/
Text/Integer/BigInt/Float/Decimal/Boolean/Date/DateTime/Time/Duration/Uuid/Email/Url/Slug/Ip/
Binary/Json variants — map each to its correct JSON Schema `type`/`format` combination, e.g.
`DateTime` → `{"type": "string", "format": "date-time"}`, `Uuid` → `{"type": "string", "format":
"uuid"}`, `Integer`/`BigInt` → `{"type": "integer"}`, `Decimal` → `{"type": "string"}` (a
fixed-precision decimal is not safely representable as a JSON number — confirm this is the
right call, Stripe's and most financial APIs' own OpenAPI schemas represent money/decimal fields as
strings for exactly this reason) or `{"type": "number"}` with a documented precision caveat — pick
one and justify it in a comment, don't leave the choice unexplained).

```rust
pub fn openapi_schema_for<M: djangors_orm::Model>() -> serde_json::Value;
    // a single component schema object for one model

pub struct OpenApiBuilder {
    // accumulates registered models + their mounted base paths
}
impl OpenApiBuilder {
    pub fn new(title: &str, version: &str) -> Self;
    pub fn register<M: djangors_orm::Model>(&mut self, base_path: &str) -> &mut Self;
        // records the model + generates standard list/retrieve/create/update/destroy path
        // entries for it, matching viewset_routes's own real URL convention exactly (read
        // viewset_routes/viewset_routes_with_permission's current code for the literal path
        // shapes: {base_path}, {base_path}/{pk})

```

A route to serve the generated document (e.g. `GET /openapi.json`) — a plain handler function
returning `Response::json` with the built document, not requiring any new router-mounting
abstraction beyond what already exists.

**Required tests**: `openapi_schema_for` producing the correct JSON Schema shape for a model
covering several different `FieldKind`s (at minimum one text-like, one numeric, one boolean, one
datetime, one relation field); `OpenApiBuilder::build` producing a document that is structurally
valid OpenAPI 3.1 (has `openapi`, `info`, `paths`, `components.schemas` top-level keys, and the
expected path entries for a registered model matching `viewset_routes`'s real URL shape) — if a
crate exists in this dependency tree already for validating OpenAPI document structure, use it for
a stronger test; otherwise assert the expected structure directly via `serde_json::Value` path
checks, which is an acceptable, real v1 test.
